# 如何通过写代码生成视频

> 做视频有三条路：自己剪、让 AI 生、写代码做。前两条已经讲滥了，今天讲第三条——**你写的不是视频，是一台能自动画出视频的机器。** 这篇文章回答三个问题：它好在哪、Agent 怎么替你写、Remotion 和 HyperFrames 该选哪个。

## 一、先分清：这不是「文生视频」

提到「AI 做视频」，大多数人想到的是可灵、即梦、Seedance、Veo——输入一句话，画面直接生成。

这和「用代码做视频」**不是同一种东西，甚至可以说是两个相反的方向**。

有人打过一个很准的比方：

> 即梦、可灵、Runway 是**摄影师**，镜头一按画面就有了；写代码做视频的 Agent 是一个**会写程序的导演**，先写剧本，再造一台会自己画画的机器，然后让机器画一整晚。

把两者摆在一起，差异立刻清楚了：

| 维度 | 文生视频（可灵 / 即梦 / Veo） | 代码生成视频（Remotion / HyperFrames） |
| --- | --- | --- |
| **输入** | 提示词、参考图 | 代码（React / HTML） |
| **产出方式** | 模型一次推理生成像素 | 代码逐帧渲染 → 截图 → 编码 |
| **确定性** | 抽卡，同提示词结果不同 | **完全确定**，同代码逐帧一致 |
| **修改成本** | 不满意只能重新生成碰运气 | **只改那一处** |
| **批量能力** | 一条一条来 | 换参数即可批量出片 |
| **擅长** | 真实质感、人物、镜头语言 | **精确信息**：文字、图表、时间轴 |
| **不擅长** | 精确数字、可读文字、严格时序 | 真实世界：一张有毛孔的人脸 |

一句话分工：

- **要精确传递信息的视频**（产品演示、数据报告、知识科普、教学）——代码路线天生合适。
- **要创意与镜头语言的视频**（Vlog、情绪短片、真人短剧）——文生视频更对路。

这不是谁取代谁。**代码画不了真实世界，模型不擅长精确信息**，两者最终会在同一条流水线里汇合——代码负责「发生什么」，模型负责「看起来怎样」。

## 二、它到底好在哪：五个别的路线给不了的东西

这不是「AI 更酷」，而是五个实打实的能力差。

**1. 稳定，不抽卡。**
同一段代码，每次渲染出来的视频**一模一样**，可以逐帧一致、用哈希校验。AI 生成则是抽卡——同样的提示词，这次好看，下次可能就崩了。做需要交付、需要过审、需要复现的内容，这一点是刚需。

**2. 改起来便宜。**
想改标题里的一个字，就改那个字，其他画面一点不动。品牌色要换？改一行。镜头想放慢？改一个数。「中秋快乐」要改成「国庆快乐」？改四个字，重新渲染，**不用重新抽卡**。AI 生成的视频不满意，你只能重新生成一遍碰运气。

**3. 能批量。**
同一套模板，换一组数据，就能一次生成 100 条不同内容的视频。做活动页、做年报、做个性化内容，这是刚需，而这恰恰是逐条生成的路线做不到的。

**4. 画面上的字和数字，永远清晰准确。**
这一条最实用。AI 生成的视频，画面里的文字经常是糊的、错的、看不懂的——因为它是在「画」字，不是在「写」字，更不是在「排版」。而代码渲染的文字，是真正的字体排版，多小的字号都清晰。

**5. 能做出一条生产线，而不只是几条片子。**
做过一个动效模板，下一条同风格视频直接复用、改参数；文案、字幕、素材、结尾各自独立成模块。人负责观点和判断，Agent 负责搭生产线，框架负责稳定出片。

**它适合做什么：** 知识科普、产品介绍、数据报告、教学演示、批量口播短视频。
**它不适合做什么：** 真人短片、需要真实质感和镜头语言的创意片——那种还得靠实拍或文生视频。

## 三、所有「代码生成视频」共用一个骨架

不管用哪个框架，底层原理是同一套三步：

```
写代码描述每一帧的画面
        ↓
无头浏览器（Chromium）逐帧截图
        ↓
FFmpeg 把图片序列编码成 MP4 → 成片
```

**工具可以换，骨架都一样：写代码画画面，截图存帧，拼成视频。**

区别只在中国那一步——**你用什么来描述「一帧画面长什么样」**：

- Remotion 用 **React 组件**（JSX / CSS）；
- HyperFrames 用**原生 HTML + CSS + GSAP**；
- Motion Canvas 用 **TypeScript 的 generator 函数**；
- Manim 用 **Python 对象**描述数学图形。

正因为底层是浏览器 + FFmpeg，代码生成视频天然继承了整个 Web 生态：CSS 动画、SVG、Canvas、Three.js（3D）、任何前端组件库——**浏览器能渲染的东西，它都能变成视频**。

## 四、Agent 怎么替你写：一条视频从零到成片

框架解决了「怎么渲染」，但还差一环：**谁来写这些代码？**

答案是 Coding Agent——Codex、Claude Code、WorkBuddy 等都能干。而 Skill 解决的是另一个问题：**Agent 会写代码，但它不知道你的规范、你的品牌色、你的内容节奏。** Skill 就是把这套「规范」固化下来，让 Agent 写出来的东西是你想要的样子。

所以整条链路分成三层：

```
框架层     Remotion / HyperFrames / Motion Canvas / Manim       ← 怎么渲染
              ↓  谁替你写代码
Skill 层   Remotion Skills / HyperFrames Skills / 场景化开源 Skill  ← 写什么规范
              ↓  用什么驱动
Agent 层   Codex / Claude Code / WorkBuddy                       ← 谁在敲键盘
              ↓
            成片
```

下面用两条真实路线，把「一句话到成片」拆开给你看。

### 4.1 通用流程：无论哪条路，都绕不开这六步

1. **先锁两份文档，再写代码。** `DESIGN.md` 锁视觉系统（色板、字体、动效、转场），`STORYBOARD` 锁分镜。**文档先定稿，Agent 严格照做、不许自由发挥**——跳过这一步，结果是每个镜头单看还行，放一起完全不统一。
2. **先写稿、再配音、后画面。** 先写逐字稿，按语音实测时长裁剪字数。
3. **配音。** 本地用 edge-tts（免费），或 MiniMax 等在线语音。
4. **字幕对齐。** 拿到配音的**词级时间戳**，用它去驱动所有动画——**字幕是整条视频唯一的时间基准**。
5. **场景编排 + 抽帧目检。** 先渲低画质、抽 6–8 帧逐场景看有没有溢出，确认没问题再出全片。
6. **交付。** 成片 + 封面 + 口播稿 + 发布文案。

## 五、Remotion vs HyperFrames：到底该选哪个

先把两个工具各自是什么说清楚。

### 5.1 Remotion：React 生态里的默认答案

Remotion 2021 年发布，是这条赛道的老玩家。官方定义很直接：给你一个帧号和一块空白画布，你可以用 React 在每一帧渲染任何内容——**一个视频本质上就是一组随时间变化的图像。**

- **强项**：组件化与复用最强；数据驱动批量出片最成熟；Web 生态（组件库、设计规范）可直接复用；**2026 年 1 月官方发布了 Agent Skills**，让 Claude Code / Codex 能写出规范的 Remotion 代码。
- **短板**：需要一点开发基础；**不是完全免费**——准确说它是 source-available（源码可见，但不是 OSI 意义上的开源），个人及 3 人以内公司可免费商用，超出需买商业许可（Creators 约 $25/人/月）；对真人实拍素材的混编不友好；本地渲染较重（要跑 Chromium）。

### 5.2 HyperFrames：为 AI 原生设计的新玩家

HyperFrames 是 **HeyGen 在 2026 年 4 月开源**的框架，Apache 2.0，完全免费，没有按人或按次数收费的门槛。它用原生 HTML + CSS + GSAP 写视频，每一页就是一个 HTML 文件。

为什么它对 Agent 特别友好：

- **AI 天生会写 HTML**。HTML/CSS 是大模型最熟悉的输出格式，让 Codex 写一页 HyperFrames，比写 AE 脚本靠谱得多，**大部分视频两三轮提示词就出来**。
- **改动成本极低**。改文案改文字，改样式改 CSS，改动画改 timeline。
- **和口播视频天然契合**。口播的本质就是「真人视频 + 透明图文层」，而 HTML 天生适合做叠加层：资料卡、截图、字幕、红框标注。
- **确定性渲染**。同一份代码逐帧一致，可用哈希校验。

- **短板**：**太新**。2026 年 4 月才开源，本机版本还停在 0.8.x、**没到 1.0**，生态、文档、社区远不如 Remotion，踩坑概率更高，**复杂动画撑不住**。

### 5.3 对比表

| 对比项 | **Remotion** | **HyperFrames** |
| --- | --- | --- |
| **描述画面的语言** | React / TSX | HTML + CSS + GSAP |
| **许可** | 个人及 ≤3 人免费，超出需商业许可 | Apache 2.0，完全免费 |
| **生态成熟度** | 五年沉淀，最成熟 | 很新（2026.04 开源） |
| **上手难度** | 要懂组件 / 帧模型 | 会基础 HTML 就行 |
| **更适合谁写** | 人写 + AI 辅助 | 直接交给 AI 写 |
| **改动一个镜头** | 改 TSX 组件 | 改 HTML 片段 |
| **复杂动画** | 撑得住 | 撑不住 |
| **口播图文层** | 要绕一下 | 天生契合 |
| **批量出片** | 最成熟 | 勉强 |
| **定位** | 长期的、可复用的视频生产线 | 快速的、单条的内容出片 |

补充一个真实数据点：我用**同一个主题、同一套规格**，让两个工具各做了一版竖屏短视频——两条成片都是 1080×1920 / 30 帧，时长一个 51.80 秒、一个 51.86 秒，**只差 0.06 秒**。

**这说明选哪个的关键从来不是「能不能做」，而是「哪个更顺手」。**

关于渲染速度也一样：第三方基准测试（1920×1080 / 60fps）显示，几个框架渲染同一条视频的耗时都在同一量级，**不存在数量级差距**。选型时真正该看的不是速度，而是生态、语言门槛和团队用不用得顺。

### 5.4 三个问题定选型

**问题一：团队熟 React，还是只想快点上手？**

- 熟 React、要复杂交互、要批量数据驱动 → **Remotion**
- 只想快速上手、内容以图文叠加为主 → **HyperFrames**
- 内容是数学/物理可视化 → **Manim**

**问题二：你要手搓动画，还是 Agent 代写？**

- 手搓（Motion Canvas / Revideo）精度最高，但要自己控时间轴，难以规模化。
- Agent 代写（两者 + Skill）效率高，但**你必须把规范讲清楚**，否则风格会乱。

**问题三：你要一次性出片，还是可复用的生产线？**

- **一次性**：直接让 Agent 写一版，导出，发。
- **生产线**：把视频拆成可复用模块，用框架稳定出片。

### 5.5 一条务实的路径

来自做了几十条视频的实践者：

> **试水、赶时间、做演示，用 HyperFrames；认真长期做，用 Remotion。**

更完整的做法是**分两步走**：

**第一条先用 HyperFrames 跑通 → 连续做几期、发现镜头结构稳定了 → 再让 Agent 把它整理成 Remotion 的固定栏目。**

轻量试水不浪费，成熟后又能沉淀成生产线——这是成本最低的走法。

## 六、几个必须记住的坑

代码生成视频最反直觉的一点是：**它做起来其实很工程，一点都不 vibe。**

- **不要跳过文档直接写代码**——每个镜头单看还行，放一起完全乱。
- **字幕是唯一时间基准**——先写稿 → 生成音频 → 拿字幕 → 用字幕驱动动画 → 最后配音效。**改时间轴要成套改**，只改一个，后半段会整体漂移。
- **先出低画质，最后出高画质**——直接渲 4K，十几分钟渲完发现中段空了一大段，全部重来。
- **自动检查全绿 ≠ 画面没问题**——机器能挡掉八成的错，剩下两成必须用眼睛抽帧看。
- **要验收的是渲染出来的文件，不是预览**——预览通过不代表成片没问题。
- **反馈要给到具体对象和位置**——「第 6 秒的标题太小」「字幕挡住了人物」才有用，「高级一点」对 Agent 无效。

## 七、写在最后

不管用哪个工具，底层都是同一件事：

> **写代码画画面 → 电脑逐帧截图 → 拼成视频。**

区别只是你写的是网页组件，还是网页本身；是用 Codex 现场做一条，还是用 WorkBuddy 攒一条生产线。

而这条路线真正的价值，是它给了文生视频给不了的两样东西——**确定性**和**可编辑性**：

> 你生成一段视频不满意，只能重新生成碰运气；代码渲染的视频，可以说「把第三段标题改掉」「音乐结尾延长两秒」「弹出动画快一点」，**它只精确改那个地方，其他不动。**

所以这条赛道的本质是：

> **视频不再只是一个导出的成品文件，它开始变成一个可以被修改、复用、扩展的内容系统。** 以前视频生产围绕时间线展开，现在开始围绕工作流展开。

最后留一句得说实话的提醒：

> **决定作品上限的，依然是创作者本身。工具降低的是制作门槛，不是内容门槛。观众不会因为你用了 AI 就多看一秒。**

把剪辑变成维护一条生产线，是把重复劳动还给了机器。**而真正值得你亲自做的，是选题判断、观点表达、案例选择、情绪分寸。**
