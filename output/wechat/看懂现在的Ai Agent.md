# AI Agent 到底有哪几类，一文理清楚

现在的 Agent 产品越来越像一团：会聊天、会调用工具、会连 MCP 的，似乎都能叫 Agent。

但真到要用时，差别很大。有的适合替你持续盯着一件事，有的适合坐在电脑前完成一次明确任务，有的只该碰代码，有的比通用工具更懂某个行业，还有一些根本不是给你“用”的，而是让你自己搭一套 Agent。

下面这五类不是严格的技术分类，而是一套选型方法：按它**主要交付什么结果**来分。很多产品会跨类，归类只是为了帮你更快做决定。各个产品的能力、许可和接入范围变化很快，实际选型仍应以官方文档为准。

---

## 一、先说结论：按交付物，Agent 可以分成五类

| 类别           | 它主要替你做什么        | 你最终拿到什么             |
| ------------ | --------------- | ------------------- |
| **个人 Agent** | 跨消息入口长期跟进事项     | 提醒、摘要、持续推进的结果       |
| **办公 Agent** | 在电脑和工作系统里完成明确任务 | 文档、表格、图表、已完成的操作     |
| **编程 Agent** | 在代码仓库里定位、修改和验证  | 代码改动、测试结果、PR        |
| **垂类 Agent** | 在一个具体行业里交付成品    | 设计稿、成片、可执行的方案       |
| **Agent 平台** | 把流程搭成可复用的应用     | 可发布的 Agent、工作流和运营能力 |

这五类没有高低之分。选错类，功能再强也会别扭；选对类，往往不需要最复杂的方案。

## 二、个人 Agent：住在消息里的长期助手

### 它适合什么

这类 Agent 的重点不是单次回答，而是**持续推进**。你把目标交代出去，它能在约定的时间继续收集信息、跟踪变化、提醒你处理。

例如：

> “帮我每天筛一遍 Hacker News 上和 AI Agent 有关的新帖，早上 9 点把值得看的内容发给我。”

它不只是推荐几个 RSS 工具，而是要自己去轮询、筛选，再把摘要送到你常用的入口。

这一类内部还有两种不同形态，值得先分清：**一种是“通道”，负责让 Agent 出现在你已经在用的 App 里；另一种是“大脑”，负责让 Agent 越用越懂你。** 前者解决“怎么联系上”，后者解决“是否越用越顺手”。真实部署里两者常常组合使用，而不是二选一。

### 常见产品

**OpenClaw** 代表“通道型”：自托管的 Gateway，把 Agent 接入 Telegram、Slack、WhatsApp、iMessage 等二十多个常用平台，并带定时任务和 webhook。渠道广、可控，代价是运行环境、账号和授权要自己负责。注意它的 Skill 是以 Agent 权限运行的代码，安装前必须审查。

**Hermes** 代表“大脑型”：Nous Research 出品，MIT 许可。特点是记忆和技能沉淀——多层记忆加语义检索，复杂任务做完后会自己写成可复用的技能，下次遇到同类问题直接调用。适合“越用越顺手”的场景。

**Muse、dots** 是另一条路线：厂商在云端为每位用户分配独立的 Agent 运行环境，让它跨应用持续工作。上手门槛更低，但数据在哪儿、它能访问什么、关键操作是否需要确认，必须用前问清楚。

需要注意的是，**“会自己学”不等于“可以不看”。** 自动生成的技能和默认权限仍要人工过一遍——技能沉淀解决的是重复劳动，不是质量担保。

### 应用场景

- **信息盯盘**：每天定时筛选 Hacker News、行业公众号和竞品动态，把值得看的几条摘要推到你常用的聊天窗口。
- **日程与待办跟进**：盯着邮件和日历，会前汇总背景资料，截止日前提醒未完成事项。
- **跨平台消息中转**：在 Telegram、Slack 等多个入口之间同步关键通知，不用来回切换 App。
- **个人知识沉淀**：把随手转发的链接、语音和想法整理进笔记，积累成可检索的资料库。

## 三、办公 Agent：坐在电脑前的执行者

### 它适合什么

办公 Agent 更像一个会操作电脑的同事：你在场，交代一项具体工作，它完成后停下来，必要时让你接管。

例如：

> “把这周销售数据按区域做成图，标出异常值，写一段给老板看的结论，再存到腾讯文档。”

理想状态下，它会拉取数据、生成图表、写结论、建立文档，并把链接交回来。你关心的是结果，也能随时检查过程。

这里有个容易含糊的地方：**“我让 AI 做了个 PPT” 不等于用了办公 Agent。** 真正的分界线是——产物是不是在一个真实的办公系统里、由真实的账号权限创建出来，并且别人能直接接手继续用。桌面上多了一个没人找得到的文件，不算交付。

### 常见产品

**WorkBuddy** 代表本地优先的路线：让 Agent 操作本机文件和应用，再通过连接器连到工作系统。文件在你机器上，中间环节更少，但也意味着你要自己确认它能读写哪些目录。

**千问办公、豆包工作** 更贴近各自办公生态：文档、表格、会议和分发渠道往往接得更顺。代价是深度绑定——模型选择、数据位置和第三方系统接入范围要逐项确认。

**goose** 是桌面 App、CLI 和 API 都能用的通用 Agent，不必被死板地看作“办公工具”或“编程工具”。当它替你处理本地文件、研究和工作流时，更接近这一类。

### 应用场景

- **数据报告**：拉取销售或运营数据，生成图表、标出异常值，写出结论并存入协作文档。
- **会议后续**：根据会议纪要整理待办，分派到飞书、钉钉等任务系统，并起草跟进邮件。
- **文件整理**：批量处理合同、简历、发票等本地文件，提取关键字段汇总成表格。
- **材料制作**：按模板把零散资料整合成周报、汇报 PPT 或方案文档。
- **跨系统搬运**：在多个系统之间对照、录入、核对数据，替代重复的手工操作。

## 四、编程 Agent：面向代码仓库的专家

### 它适合什么

编程 Agent 的优势不在于“懂很多技术名词”，而在于它能进入工程闭环：读代码、看日志、提出假设、修改文件、跑测试，再根据结果继续修。

例如：

> “这个导出功能在线上偶发崩溃，帮我定位原因、修复并跑完相关测试。”

好的交付不是一段建议，而是一组可审查的改动，以及它为什么这样改、测试是否通过。

### 常见产品

**Codex** 适合需要在本地、桌面端和云端任务之间切换的团队，Apache-2.0 许可。它的强项是**并行**：可以同时开多个 Agent 处理不同任务，各自提 PR，沙箱和审批策略可显式配置。

**Claude Code** 的强项是终端工作流和跨文件理解，适合在已有仓库中做排查、重构和验证。扩展面最完整：项目指令文件、按路径生效的规则、按需加载的技能、带独立上下文的子 Agent、钩子事件，以及细到 allow/ask/deny 的权限模式。

**Cursor** 走 IDE 路线：编辑器本身就是 Agent 的主场，上手摩擦最小。它的 **Bugbot** 先在本地审、再在 PR 上审、再把修复拉回同一套工具链，代表编程 Agent 的重心正从“帮你写代码”移向“帮你守住代码”。

**OpenCode** 提供更开放的模型选择，MIT 许可，可指向本地模型，是这几款里唯一能**完全离线运行**的选项。代价是打磨程度和生态更粗糙，质量取决于你给它挂的模型。

**pi Agent** 更像是搭建自定义 Agent 行为的 SDK，而不是一个开箱即用的成品。

### 应用场景

- **线上问题排查**：根据日志和报错定位原因、修复，并跑完相关测试。
- **存量代码改造**：跨文件改接口、升级依赖、迁移框架版本。
- **补测试与文档**：为覆盖不足的模块补单元测试，生成接口说明。
- **代码评审**：在 PR 上自动审查，提示潜在 bug、风格问题和安全隐患。
- **新功能原型**：从需求描述出发搭好骨架、跑通主流程，再由人接手打磨。
- **并行处理积压**：把一批小 issue 分给多个 Agent 同时处理，各自提 PR。

## 五、垂类 Agent：懂一个行业，交付成品

### 它适合什么

前四类 Agent 都是“通用”的：它们帮你处理信息、文档、代码和流程。但有一类问题它们天生做不好——**专业领域的正确判断**。

设计稿的排版是否符合品牌规范、视频里的镜头语言是否连贯、行程里的动线和预算是否合理，这些不是通用能力，而是行业经验。垂类 Agent 的定位是：把某个行业 know-how 和专用工作流封装成一个可以直接用的产品，让你只说行话、不必解释基础。

例如设计场景：

> “给一个新生代跑鞋品牌做商品详情页，主图要突出速度感，性能材质用特写，运动员上脚。”

通用 Agent 会给你几张好看的图。但专业交付物是一整套符合品牌规范的视觉资产——统一的光线、统一的角度、可编辑的图层、多尺寸适配。垂类 Agent 交付的是这个。

旅游场景同样如此：

> “10 天家庭京都—东京—首尔，两个十几岁的孩子，最便宜但不折腾的航班。”

这句话里的约束有几十条：多城市连线、避免红眼航班、靠近景点的家庭房、每日强度不能太高、跨国段的时间成本。通用 Agent 能列景点，但列出来的往往是一条来回折返的路线。

### 常见产品

**Lovart**（设计）主打品牌全案。差异化不在生成质量，而在于先“想”再“做”，加上 Brand Kit 保持跨物料的品牌一致、Touch Edit 做局部精修。导出覆盖 PSD、SVG 等源文件格式——交付物是**设计师能接着用的文件**，而不只是图片。

**LibTV**（视频）走“无限画布 + 节点式工作流”路线，把剧本、分镜、画面、视频、音频统一成可连线节点，比对话式工具更接近影视制作流程。角色三视图和主体库解决了 AI 视频最常见的角色崩坏问题。它还对外开放 Skill 接口，外部 Agent 可直接调用它的视频能力。

**iMean AI**（旅游）重点解决多城市、多人的复杂请求：实时扫描机票酒店数据、优化跨城路线，并用持久记忆记住你的偏好。方向是“旅行中的陪伴”——不只规划，还按实时位置和预约情况主动调整。

**设计、视频、旅游之外**，法律（合同审阅、尽调）、金融（研报、投研分析）、医疗（临床记录生成）、招聘（简历筛选）都是典型的垂类场景。这里的共同点是：这些领域的数据和流程高度专业化，通用模型能看懂但做不稳，而做错的代价又很高。

**各垂类的成熟度差异很大。** 客服是落地最成熟的；法律在合同审阅和尽调上已进企业规模；医疗受监管限制，最成功的形态是“环境记录”（医患对话自动转病历）而非自主决策；销售线索类融资最多、落地最少。**看一个垂类 Agent 在自己的核心里程碑上是否成立，比看它宣称覆盖多宽更有参考价值。**

### 应用场景

- **设计**：品牌全案、商品详情页、海报等成套视觉物料，要求风格统一、源文件可编辑。
- **视频**：从剧本、分镜到成片，适合短剧、广告片和角色保持一致的系列内容。
- **旅游**：多城市、多人出行的行程规划，比价机票酒店，行程中按实时情况调整。
- **法律与金融**：合同审阅、条款风险标注、尽调资料梳理，研报整理和财报对比。
- **医疗与招聘**：门诊对话生成病历草稿（需医生确认），简历筛选与岗位匹配。

## 六、Agent 平台：把业务流程变成产品的地方

### 它适合什么

前面四类大多是“你交代一件事，它帮你完成”——即使是垂类 Agent，边界也还停在“交付一份成品”。Agent 平台解决的则是：**怎样把一类重复工作做成可复用、可交接、可运营的应用。是构建Agent或AI应用的平台。**

例如客服场景：

> 用户提问 → 检索知识库 → 模型生成回答 → 判断置信度 → 低置信度转人工 → 高置信度直接回复。

搭完之后，得到的不是一次回答，而是一套可以发布、观测、修改和交给同事维护的服务。

需要提醒一句：**这一类也是变化最快的一类。** 过去两年不少可视化编排工具是被“编程 Agent 吸收掉的”——手工拖拽连线这件事本身，正在被按需生成胶水代码取代。更有不少明星项目在用户数还很漂亮的时候就归档停更。所以选型时不要只看功能列表，**这一类的风险不在功能，在项目寿命**：要看它是否还在维护、最近一次发布是什么时候、停止维护后你的流程能不能活下来。

### 常见产品

**Dify** 适合需要工作流、RAG、团队协作和私有化部署的团队。许可基于 Apache 2.0 并附加两个条件：**未经书面授权不能运营多租户服务**，且**不能移除前端 Logo 和版权信息**。单租户自用不受限，但要做对外托管服务须按商业许可评估。

**Coze Studio** 是可自行部署的开源版，Apache 2.0 许可；不要把它和云端商业版“扣子”的能力、可用渠道混为一谈。

**Langflow** 偏向希望看清组件逻辑、并愿意继续用 Python 扩展的开发者，采用 MIT 许可——**这是最宽松的一种**，可自托管、可修改、可对外提供服务。当前由 IBM 体系持有。

### 应用场景

- **智能客服**：用户提问 → 检索知识库 → 生成回答 → 低置信度转人工，沉淀成一套可观测、可调优的服务。
- **企业内部知识问答**：接入制度、产品文档和流程手册，员工随问随答，并保留答案来源。
- **业务流程自动化**：工单分派、报销单据核对、审批预审等规则明确、量大重复的流程。
- **内容生产流水线**：选题、初稿、审核、分发串成固定流程，不同角色各管一段。
- **对外产品化**：把一套流程封装成应用或 API，交给客户或业务系统反复调用。

---

## 写在最后

这五类 Agent 的分界线，说到底只有一条：**它替你交付什么。**想清楚交付物，再追问它的权限范围、能不能随时退出、出错之后要花多少代价收场，选择就不难做了。

工具的名字和功能会一直变，这套判断方法不会。先选对交付物，再选产品，很多热闹就不会把人带偏。
