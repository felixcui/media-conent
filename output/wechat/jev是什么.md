# AI新贵Jev 是什么

## 一、先说一件怪事

2026 年 9 月 15 日，一家叫 TypeSafe AI 的公司发布了一个新模型，名字叫 **Jev**。

它不能聊天，不能写代码，不能写文案，不能解释任何东西。你问它「今天天气怎么样」，它不会理你。

但就是这么个「废柴」，发布之后却引起了巨大的关注。原因是：**它不是不能回答，而是它只回答一种问题——你已经知道答案范围的那种。**

举个例子你就懂了。

你的客服系统收到一条用户消息，需要判断三件事：

- 这条消息紧急吗？
- 该转给哪个部门？
- 用户有多生气？

用传统大模型（比如 GPT、Claude、DeepSeek），流程是这样的：你把消息发过去，模型先写一段分析——「从用户表述来看，他连续三天无法连接账户，语气较为急切，因此我判断……」——最后才在结尾给出结论。然后你还得写代码，从这段文字里把答案「抠」出来。

用 Jev，流程是这样的：

```json
{
  "is_urgent": { "noul": 0.95 },
  "department": {
    "choice": "billing",
    "probabilities": { "billing": 0.87, "sales": 0, "technical": 0.13 }
  }
}
```

没有一句废话，直接给你可以塞进 `if` 语句里用的数字。

**这就是 Jev 的全部卖点：它不陪你聊天，它只做判断。**

---

## 二、Jev 到底是什么？

### 一句话定义

**Jev 是一个「语义决策引擎」——你给它一段状态信息，它给你一组符合预设格式的判断结果和概率。**

TypeSafe 官方给它起的学名是「**系统一模型**（System One Model）」。这个名字来自诺贝尔奖得主丹尼尔·卡尼曼的经典著作《思考，快与慢》：

- **系统一**：大脑的快速直觉。你一眼就能看出「这个人在生气」，不需要推理，几乎是瞬间完成。
- **系统二**：大脑的慢速推理。比如心算 17 × 24，你得停下来一步步算。

传统大模型（GPT、Claude、DeepSeek）更像**系统二**——它擅长深度推理、长文写作、代码生成，但代价是慢、贵、啰嗦。

Jev 是**系统一**——它不推理，它直接「看」出答案。

### 它的来历

Jev 的母公司 TypeSafe AI，由前 OpenAI 研究员 **Diogo Almeida** 创办。这位是 ChatGPT 的共同发明人之一。所以 Jev 不是又一个蹭热度的小作坊产品，它背后是有分量的人在做一件「反常识」的事：

> **在所有人都在追求「大模型更会说话」的时候，他们做了一个「故意不会说话」的模型。**

### 一个反直觉的洞察

为什么值得有一个「不会说话」的模型？因为——

> 当你的程序已经知道所有可能的答案时，**语言生成就是多余的**。

想想看：一张工单要么转给账务、要么转给技术、要么转给销售，答案只有三种。让一个大模型写一篇 200 字的分析报告，就为了从里面挑出「账务」这两个字，这笔买卖划算吗？

不划算。但过去几年，我们一直这么干，因为**没有别的选择**。

Jev 就是那个「别的选择」。

## 三、它凭什么承诺快 200 倍、便宜 400 倍？

先看官方给的对比数据（注意：这是 TypeSafe 自测数据，取的是对自己最有利的工作流，应视为上限而非普遍承诺）：

| 对比项 | 传统 LLM（如 GPT-5.6） | Jev |
| --- | --- | --- |
| **输出方式** | 生成文字，需要解析 | 直接返回结构化决策结果 |
| **响应速度** | 3 – 329 秒 | 70 – 500 毫秒 |
| **输入价格** | 约 $10 / 百万 token | $0.042 / 百万 token |
| **输出价格** | 约为输入价的 5 倍 | **免费** |
| **结构化输出错误率** | 0.58% – 45.5% | 0%（数学保证） |

这些数字看着夸张，但背后的原理非常朴素，三句话就能说清：

**① 为什么快？因为它不「写字」。**

传统 LLM 是逐 token 生成的——也就是一个字一个字往外蹦。哪怕答案只有一个词 `billing`，它也要一个字一个字地写出来。

Jev 用的是**并行采样**：它不去「写」答案，而是直接在预设好的选项上输出概率分布。所以它有另一个特性——**你一次问 1 个问题和一次问 10 个问题，响应时间几乎没差别。**因为所有问题是同时评估的。

**② 为什么便宜？因为它不产生输出。**

大模型的成本大头在输出 token，而且输出单价通常比输入贵好几倍。Jev 压根不生成文本，输出自然是**免费**的。

**③ 为什么格式化几乎不出错？因为它根本没机会出错。**

传统 LLM 是「先写出来，再校验格式」，写着写着就跑偏了。Jev 的输出结构在数学上就是被约束死的——**如果你定义了 `billing`、`technical`、`sales` 三个选项，它就不可能凭空给你返回一个 `legal`。** 它连违反格式的能力都没有。

## 四、它怎么「提问」？三种基本题型

用 Jev 的方式很简单，你只给它两样东西：

- **状态（State）**：描述当前情况的文本或 JSON，也就是「背景信息」。
- **问题（Questions）**：你想让它做的判断。

每个问题都要预先声明答案的形式。Jev 支持三种题型，官方叫「AI 原语」：

### 1. Noul：是非题

就是判断题，返回一个 0 到 1 之间的概率值。

```json
{
  "state": "我连续 3 天无法连接账户，正在丢失销售额，请尽快处理！",
  "questions": {
    "is_urgent": {
      "type": "noul",
      "instructions": "这条消息是否传达了紧急性"
    }
  }
}
```

返回 `0.95`，意思是有 95% 的把握认为它紧急。你在代码里写 `if noul > 0.8` 就能触发告警。

> 「Noul」这个名字是 TypeSafe 自创的，有点怪。但你不必纠结名字，只需要关注它吐出来的那个数字。

### 2. Choice：多选题

从你预设的选项里选一个，并给出每个选项的概率分布。

```json
{
  "department": {
    "type": "choice",
    "instructions": "这个工单应该分配给哪个团队",
    "criteria": {
      "billing": "付款、发票、退款相关问题",
      "technical": "Bug、系统故障、集成问题",
      "sales": "定价、账户咨询"
    }
  }
}
```

返回：

```json
{
  "choice": "billing",
  "confidence": 0.8,
  "probabilities": { "billing": 0.87, "sales": 0, "technical": 0.13 }
}
```

目前 Choice 最多支持 255 个选项。

### 3. Score：打分题

在你自定义的量表上打分，分数可以落在两个等级之间。

```json
{
  "frustration": {
    "type": "score",
    "instructions": "客户看起来有多沮丧",
    "criteria": ["冷静，只是在陈述事实", "不满但还算礼貌", "非常愤怒，言辞激烈"]
  }
}
```

返回 `score: 1.04`，表示介于第 1 级和第 2 级之间，偏向「不满」。等级可以自定义 2 到 10 个，越多越细。

## 五、被忽略的重点：概率比答案更重要

很多人第一次看 Jev，注意力都放在「它选了什么」。但真正让工程师兴奋的，是**它顺带给出的置信度**。

假设 Jev 把一张工单分给了账务团队，但概率是这样的：

```json
{
  "choice": "billing",
  "probabilities": { "billing": 0.52, "technical": 0.46, "sales": 0.02 },
  "confidence": 0.18
}
```

账务确实「胜出」了，但只赢了 6 个百分点——**这是个危险信号，直接自动分派就太冒进了。**

有了概率，你就可以设计一套分级处理策略：

| 置信度 | 处理方式 |
| --- | --- |
| **高** | 影响小的操作，直接自动执行 |
| **中** | 请求用户确认，或调用更强的模型再判一次 |
| **低** | 交给人工处理，或补充收集信息 |

Jev 是用 TypeSafe 自研的 **RLCD（面向校准决策的强化学习）** 训练的。所谓「校准」，意思是：**如果它对一组答案都说有 90% 把握，那么这组答案里真的应该有大约 90% 是对的。**

这和大模型的训练目标完全不同：

| 训练方式 | 优化目标 |
| --- | --- |
| RLHF（人类反馈，传统 LLM） | 让回答读起来通顺、让人类满意 |
| RLVR（可验证奖励，推理模型） | 让有标准答案的题做对（数学、代码） |
| **RLCD（校准决策，Jev）** | **让模型「说到做到」，概率即真实准确率** |

## 六、泼点冷水：「不会产生幻觉」是有前提的

TypeSafe 宣称 Jev「不会产生幻觉」。这句话**只在很窄的定义下成立**。

它成立的部分：Jev 无法返回结构定义之外的选项。你定义了三个部门，它就变不出第四个。当代码期待一个标签时，它不会返回一段格式不符的文字。

但它**做不到**的部分：**它仍然可能非常自信地选一个「合法但错误」的选项。**

类型安全能阻止不符合结构的输出，却**不能保证判断本身正确**。这个区别至关重要——

> 即使输出完全符合格式，一个错误判断依然可能导致：给错误的客户退款、把事故派给错误的团队、或者批准一条危险的命令。

所以更严谨的说法是：**「Jev 不会违反你声明的输出结构，但它仍然可能判断错误。」**

这一点在接入时尤其要记住：模型本身很便宜，可一旦出错，重试、人工复核、生产事故的代价，可能远超省下的那点 token 钱。

## 七、哪些场景适合用 Jev？

TypeSafe 官方给的最佳定位是——**一个「智能的 if 语句」**。

普通代码能判断「这个数字是否大于 100」，但判断不了「这条消息是不是在抱怨」。Jev 就是来补这个缺的：**它负责那些普通代码算不出来的、模糊的语义判断。**

适合的场景有三个共同点：**答案可以列举、认真读一遍的人能快速判断、这个判断发生得足够频繁（以至于延迟和成本已经值得优化）。**

具体来说，最典型的有几类：

**① 工单与消息分类**
一次请求同时判断：意图、紧急度、归属部门、是否垃圾信息、客户情绪。社区里有人用 Jev 给 1018 篇论文分类，分类部分只花了 0.08 美元。

**② AI Agent 的决策中间层**
Agent 每一步操作都要判断「该调哪个工具」「这个操作有没有风险」，这类判断交给 Jev，只有要生成代码或文字时才让传统 LLM 上。有人用这个思路做浏览器自动化 Agent，7.1 秒在 Google Flights 上跑完一次搜索，成本 0.0039 美元。

**③ 内容审核与风控**
一次性判断评论是否违规、属于哪种违规、风险多高，每条判断成本不到 0.001 美元。

**④ 给 LLM 输出做质检**
LLM 生成一段回答，用 Jev 快速检查有没有跑题、质量打几分——**用便宜的 AI 检查贵的 AI。**

**⑤ 模型路由**
简单查询和架构评审，对模型的要求天差地别。用 Jev 先评估请求，再把它分给「够用又最便宜」的模型，而不是无脑上最贵的。

**⑥ 大规模分类打标签**
给文档、论文、商品、用户消息批量打标签。过去因为太贵而无法覆盖每一行数据的判断，现在可以变成常规数据流水线的一部分。

**⑦ 实时决策场景**
有人用 Jev 玩数字华容道、连连看、超级马里奥，甚至打通了《星际争霸》第一关。这类对响应速度要求极高的场景，以前用传统 LLM 根本不可能做到。

## 八、哪些场景**不**适合用 Jev？

Jev 的边界同样清晰，一旦用错地方就是自找麻烦：

- **它不能生成任何文字**：写回复、写总结、写代码、解释推理过程，统统不行。
- **算术和精确处理不可靠**：计数、日期比较、字符串处理，交给普通代码。
- **需要多步隐式推理的判断题吃力**：要么把问题拆小，要么用推理模型。
- **无法提取未知的值**：它只能在「已知选项」里选，不能帮你从文本里挖出新的信息。
- **上下文给多了会掉准确率**：只发送当前判断真正需要的状态信息。
- **别不加验证地信任它**：模型权重未开放、产品还处早期、独立校准数据有限。

还有一条最重要的铁律：

> **如果确定性代码已经能正确解决，就继续用代码。**
> 一个普通的 `if` 语句，比任何模型都更快、更便宜、也更好测试。

## 九、想上手，有三条路

**① 官方 Playground（最简单）**
邮箱注册 TypeSafe 官网，打开在线 Playground，左边填状态和问题，点运行，右边直接看结果。

**② API / SDK（做产品）**
控制台创建 API Key，官方提供 Python 和 JavaScript SDK：

```python
# pip install typesafe-sdk
from typesafe_sdk import Choice, Noul, TypeSafeClient

client = TypeSafeClient()  # 自动读取环境变量 TYPESAFE_API_KEY

response = client.system_one(
    state="客户说：我被重复扣款了，订单号 A-104，请退款。",
    questions={
        "department": Choice(
            instructions="这个工单该分配给哪个团队",
            criteria={
                "billing": "付款、发票、退款相关",
                "technical": "Bug、系统故障、集成问题",
                "sales": "定价、账户咨询",
            },
        ),
        "is_urgent": Noul(instructions="这条消息是否传达了紧急性"),
    },
)

print(response.answers["department"].choice)  # "billing"
print(response.answers["is_urgent"].noul)     # 0.95
```

也可以走 Vercel AI Gateway、Cloudflare Workers AI 这类第三方平台。

**③ 装成 AI 工具的技能（最省事）**
TypeSafe 提供了通用 Skills 技能包，装到 Claude Code、Codex 等主流 AI 编程工具里，之后在对话中直接说「用 Jev 帮我判断」即可。

**接入时的稳妥姿势**：别一上来就让它接管线上决策。先找一个范围明确、风险低、答案可穷举的判断，让它以**影子模式**和现有流程并行跑，只记录结果、不改变行为；等你看清它的准确率和置信度关系、定好阈值，再逐步放权给最安全的分支。

## 写在最后

Jev 最值得记住的，不是那些夸张的倍数，而是它主动放弃了什么。

它放弃了「生成文字」这个能力。而正是这个放弃，让它变得又快又便宜又可靠——**因为它把自己变成了一个软件能安全调用的、纯粹的判断接口。**

如果只记一句话，那就是：

> **需要「说」的场景，交给传统大模型；需要「判」的场景，交给 Jev。**

它们不是竞争关系，而是互补的两种大脑：一个负责**生成**，一个负责**判断**。

过去几年，我们习惯让生成式模型用文字去解决一切智能任务。但许多真实的生产系统需要的，其实只是一个小、快、准，并且能被普通代码直接信任的判断。

即便未来 Jev 被别的模型取代，这个思路依然成立。

**别再让大模型写 200 字去回答一个「是或否」的问题了。**
