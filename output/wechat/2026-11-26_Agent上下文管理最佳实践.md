# Agent 上下文管理最佳实践：把注意力当成预算来经营

## 0. 一个被普遍误判的问题

上下文窗口正在变大。从 200k 到 1M，很多人的第一反应是"终于不用管上下文了"。

事实相反。Anthropic 在官方博客里点出了一个反直觉的现象：上下文腐烂（Context Rot）在 1M 时代反而更容易触发。原因不复杂——你能塞进去的东西变多了，模型判断"什么重要、什么不重要"的压力也跟着变大，早期那些已经无关的内容开始干扰当前判断。

更值得记的一句补充是：自动压缩（autocompact）往往在模型已经开始注意力涣散的时候才被触发。也就是说，系统做出"什么该留、什么该丢"这个关键决策的时刻，恰好是模型最不聪明的时刻。

所以上下文管理从来不是"省 token"的成本动作。它的目标只有一个：

> 在有限的注意力预算内，让模型在每一步只看到当前该看的东西。

这句话里有两个关键词。"有限"——注意力是稀缺资源，每一个进入窗口的 token 都在消耗预算；"每一步"——上下文不是一次性写好的静态文本，而是随工具调用、用户输入、环境变化持续演进的动态状态。

## 1. 全景：上下文管理到底在管什么

在进入具体做法之前，先把三件事建立起来：上下文是什么、它由什么构成、管理动作发生在哪些时间尺度上。

### 1.1 上下文是模型唯一的输入面

Karpathy 提出过一个被广泛引用的类比：现代 LLM 像一台新的操作系统（LLM OS），上下文窗口就是它的工作内存。

这个类比的价值在于它给出了一个硬约束：无论模型权重里存了多少知识，只要相关信息没有出现在上下文窗口里，对当次推理而言，那条信息就不存在。

于是"上下文管理"对应的就是操作系统的内存管理：优秀的做法不是把所有数据都塞进 RAM，而是在正确的时机把正确的数据调入，用完及时换出。

### 1.2 上下文由七类要素构成

把"上下文"等同于"我写的那句提示词"，是最常见的第一层误解。Philipp Schmid 的划分更容易落到工程上：

| 要素 | 内容 | 变化频率 |
| --- | --- | --- |
| Instructions / System Prompt | 角色、原则、行为边界 | 极低，跨会话复用 |
| User Prompt | 当下这一刻的具体请求 | 每轮变化 |
| State / History | 对话历史、任务状态 | 每轮增长，最快 |
| Long-Term Memory | 跨会话积累的偏好、决策、坑位 | 慢积累，需检索 |
| Retrieved Information | 外部文档、代码、实时数据 | 按问题动态检索 |
| Available Tools | 工具名称、描述、参数 | 低频，但常驻占位 |
| Structured Output | 输出格式约定 | 低频 |

这七类要素的性质完全不同：有的几乎不变（指令），有的每轮爆炸式增长（历史），有的只在需要时才该出现（检索信息）。把它们当成一坨文本统一处理，是后面所有问题的根源。

一个能说明差距的例子：收到一封"明天方便快速同步一下吗"的邮件，要 Agent 安排会议。

只给用户请求的 Demo Agent，输出是"感谢您的消息，明天可以，请问您希望几点"——代码跑得通，但没解决任何问题。而具备完整上下文的 Agent 会先取日历（明天排满）、取与该联系人的历史邮件（判断该用非正式语气）、取联系人列表（识别对方是重要合作伙伴）、调用发邀请工具，最后输出"明天我这边排满了，周四上午有空，邀请已发出"。

代码的职责在这里发生了根本转变：不再是"想办法回复"，而是"收集完成目标所需的信息"。

### 1.3 管理动作分四层时间尺度

这是本文的主干框架。上下文管理不是一组并列的技巧，而是按信息"存活时间"分层的四组动作：

```
L1 构建   单次调用前   该放什么进去        策展 / 分层注入 / 位置 / 工具定义
L2 演进   单会话内     只进不出怎么办      五动作 / 压缩 / 外置笔记 / 预算
L3 沉淀   跨会话       下次怎么不忘        长期记忆 / 知识库 / 索引与衰减
L4 共享   跨 Agent     协作怎么不折损      共享现场 / 隔离 / 制品 / 信箱
```

四层解决的是四个不同问题，混在一起谈就会出现"用更大窗口解决记忆问题"这类错配。

贯穿四层的原则只有一条：注入方式的生命周期，要匹配信息的半衰期。全程都需要的（构建命令、目录结构）就常驻；只在某类文件上生效的，就按路径加载；只在某个任务里用一次的，用完就该消失；只属于子任务的脏活，就别让它进主上下文。

## 2. L1 构建：决定什么进入窗口

### 2.1 三条物理约束：为什么"多给点"是负收益

"信息越多越安全"是最顽固的直觉，但它与三条经过实验验证的约束直接冲突。

**第一，位置决定可见度。** 斯坦福的 Lost in the Middle 研究给出了一条 U 型曲线：把唯一含答案的文档放在 10 到 20 篇文档的开头或结尾，正确率约 75%；夹在中间，正确率可能掉到 35% 左右。而完全不提供文档的闭卷基线是 56.1%——中间位置的准确率低于什么都不给。这不是某个模型的个例，在 Claude、GPT、MPT、LongChat 等多种架构上都稳定复现，文档数从 10 增到 30 后，中间区域的塌陷更明显。

由此得到四条可以直接执行的规则：

1. 最重要的系统级约束放在 System Prompt 开头（首因效应）；
2. 当前任务最关键的约束放在用户消息结尾（近因效应）；
3. 检索到的多份文档，最相关的一份放第一位或最后一位，不要放中间；
4. 不要把关键规则夹在大量工具调用记录的中间。

**第二，长上下文是慢性退化，不是突然崩溃。** 一个 Go 重构 Agent 的例子：第 1 轮设定"变量用 camelCase、错误变量统一叫 err、函数不超过 50 行"，前 10 轮严格遵守；到第 40 轮，上下文里累积了 39 轮对话、20 次完整文件读取、15 次编译错误日志、10 次测试输出，数万 token。最初的规范被推到"中间地带"，Agent 开始生成 snake_case。

它没有"忘记"指令，只是规范的信号被稀释到注意力权重难以起作用的程度。工程师常把这类现象归因为"模型不稳定"，实际是规则漂移。

**第三，注意力有 O(n²) 的成本。** n 个 token 要算 n×n 个注意力分数，长度增加带来三重代价：计算变慢、延迟变高、按 token 计费的钱变多。而训练数据中长序列远少于短序列，超过一定长度后质量还可能反向下降。

三条约束指向同一个公式：

> 最优上下文 = 最小 token 数量 × 最高信噪比

### 2.2 三层上下文栈：别只给任务层

Anthropic 建议把上下文理解为三层，每层职责不同、加载时机不同：

| 层级 | 内容 | 加载时机 |
| --- | --- | --- |
| 全局上下文 | 身份与角色、编码标准、安全约束、绝不可触碰的清单、处理不确定性的方式 | 始终存在 |
| 项目上下文 | 架构概览、带项目规则的 AGENTS.md、目录与命名约定、测试要求、关键依赖及选型理由 | 项目启动时 |
| 任务上下文 | 当前文件与相关文件、本次目标、近期变更、当前测试结果、本任务专属约束 | 每个任务 |

大多数开发者只给第三层。Agent 于是只能猜测它不了解的部分，而错误正是从这些猜测里长出来的。

判断自己是否只给了任务层，有个简单测试：把 Agent 的产出问题逐条追溯，如果失败原因里出现"它不知道我们约定过……"，缺的就是全局层或项目层。

### 2.3 粒度：Goldilocks Zone

系统指令的长度不是关键，粒度才是。三种典型状态：

- **太精细**：把规则写成枚举。"支付方式=信用卡且错误码=E001 则回复 A，E002 则回复 B……"写到 180 条。后果是维护成本极高、遇到未覆盖场景不会处理、大量规则永远用不到却常驻占位。
- **太宽泛**："你是一个有帮助的客服助手，请专业地处理用户问题。"没有任何实质约束，敏感场景可能做出不当决策。
- **适中**：给原则加边界。"先确认情绪再给方案；涉及资金安全立即升级人工，不自行决策；不承诺具体赔偿金额；必须查订单才回答，不凭猜测回答。"

原则式写法的优势是能泛化到未枚举的场景，同时把高风险行为的边界锁死。换来的代价是模型需要在原则之间做推理，因此原则数量也要克制——追加的指令越多，每条指令的遵循率越低，指令之间冲突时下降更快。

有一个 2026 年 7 月的官方工程观察值得放在这里：针对更先进的模型，Claude Code 移除了超过 80% 的 system prompt，内部编码评测未出现可测损失。被删掉的主要是三类——跨层重复的规则、已经过时的绝对化规则、可以移入 Skill 的专用流程。

但这条观察有明确边界：它不构成"所有提示词都该删 80%"的依据。业务事实、权限边界、验收条件必须保留。真正的做法是定期检查每条规则是否仍在解决一个真实问题。

### 2.4 工具定义与返回值，也是上下文

一个常被忽略的事实：工具的名称、描述、参数说明全部占据窗口，并直接影响模型"该调哪个工具"的准确率。

反面例子是五个功能高度重叠的搜索工具——`search_all_documents`、`search_recent_documents`、`search_documents_by_category`、`find_relevant_info`。面对"找最近一个月某类文档"，模型无法判断该用哪个，选择错误率显著上升。

Anthropic 用 ACI（Agent-Computer Interface）来类比：工具文档和参数描述对模型的作用，等同于 UI/UX 对人类用户的作用。人类工程师会反复打磨参数命名、错误提示、返回格式，让使用者少犯错；面向模型的接口需要同等的严谨度。四条原则：

1. 名称自描述（`read_file` 优于 `get_content`）；
2. 描述同时写明适用与不适用场景；
3. 工具之间职责不重叠，或边界极其清晰；
4. 参数描述具体，避免 `any`、`optional` 这类模糊项，给出示例值。

返回值同样是上下文。一次文件读取可能 3000+ token，如果原样透传，其中大部分是噪声。所以工具设计不只设计输入接口，也要设计输出格式——返回精简、结构化的结果，而不是把原始 API 响应直接塞回模型。

更进一步：工具结果被 Agent 消化、并据此做出决策后，原始结果就应该从历史中移除或折叠成摘要。这是最轻量的一级压缩，也是最常被漏掉的一级。

### 2.5 生命周期匹配：五种注入方式的成本结构

同一个诉求（"让 Agent 知道某件事"），不同注入方式的上下文成本差异极大。以 Claude Code 的机制为例：

| 方式 | 加载时机 | 上下文成本 | 适合放什么 |
| --- | --- | --- | --- |
| CLAUDE.md / AGENTS.md | 启动即加载，压缩后重新读取 | 全程占用，最贵 | 事实：构建命令、目录结构、团队共识 |
| Rules（带路径限定） | 碰到匹配路径的文件时 | 按需，不碰不占 | 跨目录但不全局的约束 |
| Skills | 启动只加载名称与描述，调用时载入正文 | 待机几十 token | 流程：部署清单、review checklist |
| Subagents | 独立窗口，主会话只收结论 | 主会话视角接近零 | 脏活累活、深度搜索、日志翻查 |
| Hooks | 完全绕过上下文窗口，由 harness 在外部执行 | 零 | 绝不允许发生的事、必须自动执行的事 |

这张表最有价值的一行是最后一行。凡是"绝对不能发生"的约束，写在提示词里是概率事件——长会话、压力大、被 prompt injection 干扰时都可能失效。只有落到 hook 或 permission 层做硬拦截，才是确定性的。

几个高频误区，几乎都能用这张表解释：

- 把"每次编辑后必须跑 formatter"写进 CLAUDE.md。模型"选择"做一件事和"自动执行"一件事是两码事，这该用 PostToolUse hook。
- 把"绝对不要执行某命令"写进 CLAUDE.md。该用 PreToolUse hook 直接以非零退出码阻断。
- 把 30 行的部署流程写进 CLAUDE.md。事实放常驻文件，流程放 Skill。
- 给 Rule 忘了加路径限定。没加 `paths:` 的 Rule 和写在 CLAUDE.md 里没有区别，全程白占 token。

压缩发生时的行为也值得记住：根目录 CLAUDE.md 压缩后会立即被重新读取，所以永远在；子目录 CLAUDE.md 会丢失，等再次碰到那个目录才重新加载；Skills 压缩后会被重新注入，但共享一个 token 预算上限，调用过多时最早的会被踢掉。

### 2.6 按需加载：先修入口，别急着加层级

即时检索（Just-in-Time）与预加载是两种哲学。关键差别不在"要不要检索"，而在"检索错了的代价"。

用户问"最新版本的 API 如何认证"，你检索了 5 篇文档，只有 1 篇相关。全部塞进去，正确答案就被夹在无关内容之间，Lost in the Middle 开始生效。此时检索到不相关内容，比没有检索更糟。

所以渐进式披露的正确姿势是：先看目录判断模块，再看函数签名确认方向，最后精读关键实现。Claude Code 用 head 只读文件前几行判断类型，用 grep 定位片段，而不是把整个文件读进来。

但渐进式披露有一个容易被忽视的上限。一项在长文问答基准上的研究比较了原文导航、Skill 式资料组织和检索器三种方案，结论是：单本书场景的收益依赖执行框架；多书场景中一层披露更稳，再增加第二层路由没有收益，有时反而损害准确率。

实践含义很清楚：先把入口做清楚（哪类问题看哪份资料），再评估是否真的需要更多层级。不要默认"拆得越细越好"。同时要区分"加载"和"缓存"——缓存命中能减少重复处理开销，但不代表无关内容已经移出上下文，输入长度、计费用量和任务质量需要分开观察。

## 3. L2 演进：破解"只进不出"

L1 决定了起点，但长任务真正的问题在过程中：ReAct 式的"思考—行动—观察"循环只进不出，每一轮都在往上下文里加内容，却没有任何机制决定"什么时候该移除或压缩什么"。

### 3.1 四个泄漏点

**Observation 无限膨胀。** 工具返回结果被永久追加。50 轮任务，仅 Observation 累计可超 80,000 token，其中大部分在做出决策后就没有价值了。

**规则漂移。** 系统指令从"开头"被推到"中间"，正好落入性能洼地。表现是前 10 轮严格遵守、第 20 轮偶尔出错、第 30 轮完全混用风格。

**错误轨迹污染。** 工具失败、超时、解析错误是常态。失败的 Thought 和错误的 Observation 被永久保留，一旦进入上下文就影响后续所有轮次——像谣言一样越传越偏。

**Thought 冗余积累。** 40 轮任务里，Thought 部分累计约 8,000 token，真正对当前决策有价值的可能不超过最近 3 到 5 轮。

四个泄漏点的共同本质是"没有出口"。因此 L2 的核心不是"怎么写得更好"，而是"什么时候、以什么方式丢掉什么"。

### 3.2 五个动作与它们的判据

Anthropic 官方把会话管理归结为五个动作。它们都能用，但用错场合代价都不小。这是本文最想让人记住的一张表：

| 动作 | 什么时候用 | 一句话判据 | 代价 |
| --- | --- | --- | --- |
| Continue | 当前上下文仍在起作用 | 下一步要用的信息，窗口里还在吗？在就继续 | 无 |
| Rewind | 刚走错方向、试错失败 | 需要擦掉错误记忆，而不是在错误上叠加纠正 | 丢弃该点之后的记录 |
| Clear | 开始一个全新任务 | 新任务用不上旧任务的实现细节 | 需自己写 brief，累 |
| Compact | 同一任务、上下文已长但仍有价值 | 必须保留脉络，但要压缩体量 | 有损，且压缩时机难判断 |
| Subagent | 只需要中间过程的结论 | 还会再用到中间输出吗？不会就开子代理 | 额外延迟与成本 |

几个动作值得展开。

**Rewind 被严重低估。** 典型场景：Agent 读了 5 个文件，试了一个方向，失败了。第一反应是追一句"这个方法不对，换 X 试试"。更好的做法是回退到读完文件那一刻，带着新信息重新提示："不要用 A，因为 foo 模块不暴露这个接口，直接走 B。"

差别在于：追加纠正消息，上下文里留下的是"失败尝试 + 纠正"两层信息，模型得从中推断你真正想要什么；回退之后，失败尝试直接消失，模型看到的是一份干净的、带最新理解的指令。Rewind 的本质是帮模型擦掉错误记忆。

配套用法是让模型先把踩坑学到的东西总结成一段 handoff，再回退、带上这段便条重跑——相当于让它给未来的自己留张纸条。

**Compact 的关键是时机和提示。** 自动压缩翻车的核心原因是：模型做压缩时并不知道你下一步要干什么。官方举的例子很具体——一段长调试会话后触发自动压缩，摘要围绕调试过程；下一句你说"现在去修 bar.ts 里另一个 warning"，而那个 warning 在调试会话里没怎么展开，很可能被当作无关信息丢掉。

再叠加"压缩触发时模型注意力已经涣散"这一点，等于让一个注意力涣散的人决定什么重要。所以更稳的做法是：在有腾挪空间时主动压缩，并带引导——"重点保留 auth 重构，丢掉测试调试部分"。

**Continue 的判据要克制。** 手头任务刚跑完一轮，上下文里都是有用的文件读取和工具输出，接着问下一步最省事。原则是：内容还在起作用就别动，换成压缩或清空都要付重建成本。但反过来，新任务就该开新会话——同一个终端开着，改完后端接着写文档，顺手让 Agent 继续跑，而写文档根本用不上后端接口细节，纯属白烧预算。

**Subagent 的判断只看一句话**：你还会再用到它的中间输出吗？只需结论就开，还要用中间过程就别开。让 Agent 在大型代码库里搜关键字并归纳，中间读取记录对你毫无价值，只需最后那份归纳——这是子代理的完美场景。一个子代理跑 50 轮搜索、读 200 个文件，主会话只多了一段摘要。

### 3.3 压缩怎么写：交接文档，而不是摘要

压缩质量取决于压缩提示词的设计。一个关键设计差异值得单独说：让压缩模型"做总结"，效果通常不如让它"写交接文档"。

Codex 的做法是，在提示词里告诉模型：你当前的工作要交给另一个模型了，你需要把交接文档写清楚、写重点。模型认为自己是在做交接，就会尽可能写得完整、结构化、清晰，而不是压出一段干瘪的摘要。

一个经过实践验证的模板结构大致是：

```markdown
保留以下内容：
1. 原始任务目标与后续澄清
2. 已完成的步骤及其结果
3. 关键决策及理由
4. 当前状态：正在改哪个文件、还剩什么问题
5. 未解决的错误与已知约束
6. 用户提到的重要偏好

压缩为 600 token 以内的结构化摘要。
不要包含：原始工具输出、重复的尝试、冗长的错误日志。

输出格式：
## 任务概览
## 进展
## 当前状态
## 关键决策
## 待解决问题
```

两条工程细节值得抄：

- 先优化召回率，再优化精确率。宁可留一点冗余，也不要丢掉关键信息——丢一条决策的代价远大于多占 200 token。
- 摘要之外单独保留最近访问的若干文件内容。Claude Code 在压缩时会额外保留"最近访问的 5 个文件"。原因是摘要负责"知道发生了什么"，最近文件负责"知道正在看什么"，后者常常在摘要里保不住。

还有一个与推理成本相关的设计：从最早的消息开始压缩。这样压缩后前缀 KV Cache 会丢，但只丢那一次；下一轮基于压缩后的稳定状态重新建立缓存，后面继续受益。如果反过来从中间切片，缓存前缀会反复失效。

### 3.4 外置：把信息搬出窗口，而不是压扁它

压缩是"把信息变短"，外置是"把信息搬走"。后者理论上支持无限长任务，关键在于**可恢复性**。

**结构化笔记**是最轻的形态。Agent 在执行过程中主动把关键信息写到外部存储，随时可重新加载。笔记分四类，各自解决一个问题：

- 进度笔记：已做什么、待做什么（`[✓] auth_service 已重构`）；
- 决策笔记：为什么这样做（选 JWT 而非 Session，理由是服务无状态、需水平扩展）；
- 发现笔记：过程中发现的重要事实（payment_service 每请求调用 auth_service 三次，冗余）；
- 策略笔记：下一步怎么做（先修冗余调用，再处理 panic，最后统一错误风格）。

Anthropic 记录过极限案例：Claude 玩《宝可梦》，需要在数千个游戏步骤中保持连续记忆。没有结构化笔记时，每次上下文重置就"忘记"进度；有笔记后，重置后读自己写的笔记就能无缝继续，在数小时的连续游戏中实现跨会话的连续记忆。

**上下文卸载**是更重的形态，腾讯云 Agent Memory 的方案值得完整拆解。核心思路是：完整信息卸载到外部文件系统，同时用结构化图把任务过程压成可导航的画布，让"完整信息在外部、关键状态在窗口内"。

一次工具调用结束后，信息拆成三种形态，对应四层折叠：

```
refs/*.md      完整原文（工具返回的全部内容）
JSONL          工具调用摘要（一行一次调用）
MMD            Mermaid Flowchart 任务节点（这些信息之间是什么关系）
metadata       任务入口（从哪进）
```

展开时按需逐层下钻，鸟瞰 → 聚焦 → 下钻。这样既有压缩率，又有可恢复性。

两个选型细节有实验依据：Mermaid 之所以适合做任务画布，是因为它满足符号化压缩的三条原则——通用知识（模型见过）、语法简单（生成不复杂）、表达自由（不局限于固定模板）；而在载体上，Flowchart 比 StateDiagram 效果好约 15%，因为 Agent 的执行过程更像自由探索，而不是状态机跳转。

效果数据：在超长 Session 评测中最高节省 61.38% token，任务通过率从 33% 提升到 50%（相对 +51.52%）。消融实验更能说明问题——只用上下文卸载，token 节省约 15%；加上图结构画布，达到 31% 到 33%。也就是说，**压缩只做一半没用，结构必须一起保留**。

这解释了一个常见失败：只做摘要的 Agent，信息变短了但关系丢了，模型知道"发生过 A、B、C"，不知道"B 是因为 A 失败才做的"。丢失结构比丢失细节更致命。

### 3.5 预算与触发：把阈值显式化

生产级实现普遍采用显式预算，而不是等到窗口满：

- 60% 左右发出警告，开始有意识地收敛；
- 70% 到 80% 触发压缩（Codex 的硬阈值是 80%，另设更低的软阈值用于"还要继续对话"的场景）；
- 触发点前先做一次"该外置什么"的判断。

除阈值外，Codex 还有两类触发条件值得注意：模型切换时（不同模型提示词不同，需要重建上下文），以及切换到上下文窗口更小的模型时（避免切完直接溢出）。这类边界在自建系统里经常被漏掉。

### 3.6 对缓存友好：只注入差异

一个容易被忽视的工程约束：上下文的重排会打破前缀 KV Cache，直接拖慢推理。

Codex 的 World State 设计是个好范例。环境信息（Shell 权限、AGENTS.md 模式等）每轮都可能变，但每次变化都把全部信息重读一遍极其浪费。它的做法是把"当前世界"拆成一组带类型的 Section，每个 Section 有稳定 ID、快照类型，以及与上次相比的 Diff。

初始加载全量；之后修改了 AGENTS.md，不再注入全文，只注入一条"AGENTS.md 的哪些部分变了"。模型结合补丁与前文就能理解变化。收益是双重的：不打破缓存前缀，同时降低窗口消耗。

对应的实践原则是：**稳定内容放前面且不重排，变化内容只追加差异。** 这一条在自研 harness 里经常被忽略，代价是推理延迟和成本双升。

## 4. L3 沉淀：跨会话的记忆

L2 解决"这一轮任务能不能跑完"，L3 解决"下次还要不要从零开始"。

### 4.1 三种记忆，三种管理方式

| 类型 | 定义 | 工程位置 |
| --- | --- | --- |
| 长期记忆 | 所有过去会话中学到的东西 | 外部文件 / 数据库，按需检索 |
| 短期记忆 | 当前对话中此前发生的事 | 上下文窗口内的历史 |
| 工作记忆 | 此刻位于窗口中的内容 | 就是窗口本身 |

CoALA 框架进一步把长期记忆分为情节（发生过什么）、语义（事实与概念）、程序（怎么做），三者都**不应全量注入**，而是按需检索、精准注入。

这里有一个与 L2 直接衔接的观察：长期记忆的载体，本质上就是 L2 里"外置"的那部分内容。区别只在于生命周期——L2 的笔记为当前任务服务，任务结束即失效；L3 的记忆要跨任务存活，因此需要索引、需要淘汰、需要治理。

### 4.2 跨窗口衔接：三层结构比一次压缩更可靠

Codex 8 月的 Token Budget 方案，是"把压缩做成记忆"的一个完整样本。

传统压缩的问题是：系统必须猜"哪些信息以后有用"。Token Budget 把这个决策权交回给主 Agent：达到阈值时不压缩，而是新开一个干净的 Context Window（带递增 ID），并用三个机制衔接：

**Thread Hint**——新窗口启动时，从后端注入约 4000 字节的提示，写在上一个窗口做到哪儿了。它只给背景，不给细节。

**Notes**——模型的私人笔记本，服务端托管的虚拟文件系统。上一个窗口在运行中持续记录：改了多少文件、改到什么地方、哪里卡住、哪些用例有问题。新窗口可以先列出笔记，再按需读取需要的部分；不需要就不读。

**History**——完整的 Agent Trace 全部留存，提供列表、读取、搜索等工具。模型读笔记时发现某个细节想深究，可以渐进式搜索历史，找到当时的准确信息。

三层的关系是"提示给轮廓、笔记给状态、历史给证据"。它没有做传统意义的压缩，形式更像记忆，但只是单 Session 内的任务状态衔接，而不是长期记忆。

这两者正交，不能互相替代：

| | 管什么 | 存哪里 | 生命周期 |
| --- | --- | --- | --- |
| Token Budget | 当前任务做到哪一步 | 窗口内提示 + 虚拟笔记 + Trace | 单 Session |
| Long-Term Memory | 跨会话不能忘的事 | 数据库 / 磁盘 | 跨 Session |

### 4.3 长期记忆的两阶段与遗忘机制

Codex 的长期记忆分两个阶段：

**逐会话提取**：从旧的会话 Rollout 中提取重要信息，让模型产出"需要记录的内容"，脱敏后入库。

**全局巩固**：对提取出的关键信息做 Top-N 筛选，选出最重要的 N 条落盘。判断重要性的依据是长期运行数据——某条信息被召回的次数（Citation 次数）越高，排名越靠前，下次被召回的概率越大。

结果就是一套可遗忘的衰减机制：常用的频繁浮现，不常用的慢慢沉底。这不是缺陷，而是让系统能自进化的必要条件——没有遗忘，记忆库会迅速膨胀到无法检索。

### 4.4 项目知识库：只记"代码里读不出来的东西"

如果说上面是产品级方案，那么团队自建知识库要回答一个更朴素的问题：到底该记什么？

一个经过实践的标准是：只记三类**连接性知识**。

1. **阴性知识**：代码里没写清、容易误判的事实。某字段的真实语义与字面意思不同。
2. **代码位置索引**：关键逻辑、配置、入口的具体文件路径。
3. **隐含关联关系**：不通过静态引用能看出来的跨系统连接。系统 A 的动作实际会触发系统 B 的什么行为。

代码里已经写明的业务逻辑、参数列表、目录结构，一律不记——这些 Agent 自己读代码就知道，记下来只是把上下文预算浪费在重复信息上。

判断一条知识值不值得写，用一句话：脱离"这次任务"的上下文单独拿出来看，是否依然成立、依然有用。按这个标准，过程性元信息（日期、执行者、变更记录）、范围声明（"本次改动范围内"）、给不出验证方法的猜测，都不该进库。

**结构用两级索引。** 一级只列模块；二级列该模块下的文档加一句话描述；三级才是正文。

AI 的固定动作是：读一级定位模块 → 读二级判断哪篇相关 → 读正文 → 都没覆盖才允许自己探索代码。这样即使库长到几百篇，也只读两三篇就能命中，不会一上来就全文检索。

每篇文档头部的 frontmatter 记录成熟度、引用次数、用过的场景、依赖路径。关键约束是：**frontmatter 不参与阅读**。读取时只取正文，避免把元数据一起拉进上下文；写入时一律定点修改、禁止整篇覆盖——覆盖会把看不见的 frontmatter 抹掉，成熟度和引用统计就静默丢失了。

**用硬约束保证"先查再动手"。** 把"先读知识库"写在提示词里，遵守是概率事件。做法是挂一个 PreToolUse hook 在所有探索类工具上（读文件、搜索、执行命令、MCP 调用）：当前会话没读过一级索引，一律阻断，并在阻断消息里告诉 Agent 该先读哪个文件。

这里有个性能细节：hook 是同步阻塞的，所以重量级同步放 SessionStart（每会话一次），PreToolUse 上只留轻量判定，否则每次工具调用都要付一遍启动开销。

同时保留一份软约束规则文本，形成"hook 硬拦截 + rule 软引导"双轨。工具链本身也从知识库同步——command、rule、hook 脚本的源放在知识库的 `toolchain/` 下，每会话开始自动同步到工作区。这样知识库不只是"被读的资料"，同时是工具链的发布源，改一条规则下次会话就生效。

**让库自己生长、自己淘汰。** 两个频率刻意不同的任务：

- 轻任务（会话结束自动跑）：只读新增的引用数据，做聚合信号、提升等级、累加计数、同步索引列、日志轮转。只提升，从不降级。
- 重任务（周期性跑）：读全库，去重、消歧、规范索引结构、执行衰减扫描。

分工原则是：便宜的机械动作高频跑，昂贵的判断性动作低频跑。把全库巡检塞进每天执行，成本会高到没人愿意跑。

成熟度分四级：`draft` → `verified`（被真实任务采用过）→ `proven`（跨会话、跨场景复用）→ `archived`。提升只看强信号：被采用 1 次升 verified；被采用 2 次以上且场景数 ≥2 升 proven。衰减按类型定周期——导航类 6 个月，决策类 9 个月，坑位与流程 12 个月，模型相关 18 个月。

信号分两条通道：弱信号（谁读了哪篇）由 hook 自动记录，只作诊断，不参与升降级；强信号（本次实际采用了哪几篇、用在什么场景、结论是否被验证）由任务结束时的复盘主动声明，只有这一路参与计算。这个区分很重要——"被读过"和"被用过"是两件事，混在一起算会让统计失真。

### 4.5 记忆的治理边界

最后一条容易被当作理念、其实很工程的要求：**记忆必须是白盒、可治理的**。

Agent 整理得对不对、沉淀了什么、有没有偷懒，人要能随时打开看、随时纠正。这和"黑盒记忆"是两回事。能被管理的记忆，才是能被托付的记忆——尤其当它开始影响生产决策时。

## 5. L4 共享：多 Agent 的上下文不靠转述

到这里，上下文都在单个 Agent 的窗口里。一旦进入多 Agent 或人机混合协作，问题换了一个性质：上下文要在主体之间流动。

### 5.1 折损是乘法，不是加法

协作的本质不是"发消息"，而是上下文在流动——你为什么做这个决定、考虑过哪些方案、排除了什么、卡在哪一步、手里有哪些材料、边界在哪。消息只是上下文被压缩、编码、说出口之后的产物。

单人时代，折损是加法：讲一遍，损一点。人-人-Agent 时代，折损变成乘法：

> 你的 Agent 写完竞品分析，你先读一遍，把结论转述给同事；同事按他的理解讲给他手上的 Agent；那个 Agent 产出结果，同事再读、再转述回来。一圈下来，最初分析里的细节——那些你的 Agent 明明分析到了、你转述时觉得"太细就没提"的部分——在第二个 Agent 眼里，从一开始就不存在。

一条任务链，上下文被编解码四次，每次都是一道有损压缩。更糟的是人被困在链路中间当中继器：Agent 算得再快，也要停下来等你把上下文翻译给下一个。

这才是多 Agent 协作真正的天花板。不是模型不够强，是上下文的流动方式还停留在"为人转述"设计的旧范式里。

### 5.2 两条路，只有一条通向根因

**第一条路：让 Agent 更像人。** 教它把成果打包成漂亮的总结，@ 给下一个。这条路顺，因为不改变任何人的习惯，但它没触碰根因：只要还靠"总结—转述—再理解"，折损就还在，只是把搬运的活从人手里挪到了 Agent 手里。本质仍是"用通信来共享上下文"。

**第二条路：不靠通信共享上下文，而靠共享上下文来通信。**

这句话值得拆开。人为什么必须"说出来"别人才懂？因为想法锁在自己脑子里，没有第二条通路。但 Agent 不一样——它做过什么、改了哪个文件、生成了什么产物、任务跑到第几步，本来就是可以被实时记录、也可以被另一个 Agent 直接读取的结构化状态。

把这些压成一段聊天记录，再让下一个 Agent 从消息里猜人类想表达什么，是一种倒退。能直接读的东西，不该被重新翻译成人类包装过的语言，再让机器逆向解码。

真正的解法不是优化转述，是消灭转述：让协作各方站在同一份实时上下文之上。协作不再是"我把我知道的告诉你"，而是"我们看着同一个现场一起干"。

### 5.3 三个构件与一个纵向维度

一个完整的落地形态（腾讯 Siboot 的实践）由四件事构成：

**群是场。** 群不是聊天窗口，是持续在场的上下文容器。人说的话、Agent 做的事、产生的文件、跑起来的任务，都沉淀在同一空间，对所有成员实时可见。新任务抛进来时，Agent 不需要你重新交代背景——上周的决策、刚才那份文档，它本来就看得见。

**Topic 是焦点。** 共享的天敌是噪音。二十人的群一个上午可能并行聊三件事：告警策略、BUG 复盘、下季度规划。糊在一条消息流里，跟进 BUG 的 Agent 窗口里塞满规划讨论，判断容易被带偏，token 也白烧。

拆成三条 Topic 后，跟进 BUG 的 Agent 只活在"BUG 复盘"这条线里。这件事的深层价值不是界面整洁，而是**让上下文变得可界定**：Topic 边界就是 Agent 的注意力边界，也是它的成本边界。

**@ 是接力，但不搬运。** 很多产品里接力等于"打包 + 转述"，又回到折损老路。在共享现场里，@ 只是喊下一棒进场——被 @ 的人和 Agent 本来就站在这条 Topic 的完整上下文里，看到的是从用户原话到代码改动的原始现场，不是被压缩两道的"结论"。

**文件是记性。** 这是纵向维度：一条 Topic 会沉底，会话会结束，热的上下文会变冷。三个月后还引不引得出来？答案如果是"忘了"，共享就只是一次性的。

解法不是更大的窗口——把所有历史都塞进去既烧钱也装不下。真解法和人一样：不是把所有东西都记在脑子里，而是分门别类写下来，需要时精准取回。一个产品 Agent 的云盘结构可以直接参考：收件区（inbox，新反馈先暂存）、事实与决策记录（notes，拍板过的事）、需求与 BUG 的独立档案（有编号、来源、状态）、分层报告目录。

关键不在"有这些文件夹"，而在**知道怎么维护**：定时任务醒来，拉新消息、判断哪些是有价值的信号、登记成需求或 BUG、更新决策记录、该写日报时落成文档。新登记一条需求前，先在已有档案里检索，命中相似的就补充而不是新建重复条目。

这套动作和尽职的人类同事整理工作台几乎一样，区别只在于不会累、不会忘、不会因为周五下午犯懒跳过归档。

于是完整的主线是：**热的上下文在场、聚焦、接力；冷的上下文在文件系统里结构化沉淀。** 横向共享，纵向沉淀，一个协作网络才算立起来。

### 5.4 隔离的档位与通信语义

多 Agent 的上下文管理，本质是在"继承多少"和"共享多少"之间调档。

**派生时的继承档位**（Codex 的 Fork Turns 给了三档，值得直接借用）：

| 模式 | 继承内容 | 适用 |
| --- | --- | --- |
| 全部继承 | 完整父对话 | 并行处理多个无串联关系的任务，加速 |
| 继承最近三轮 | 只带近期上下文 | 需要一定隔离、但保留近期信息的任务 |
| 无上下文 | 全新干净窗口 | 需要彻底隔离的子任务 |

**消息投递的语义**（Mailbox 两种）：

- Send Message：只入信箱，不触发目标新轮次。消息在目标下次有轮次时自动投递进上下文，不打断当前状态。代价是目标若长期不开新轮次，消息会滞留。
- Follow-up Task：入信箱的同时，若目标空闲则触发一轮把它唤醒；若正在运行，则在消息边界或当前工具调用完成后投递，而不是硬打断推理。

两种都保留是对的。前者适合"知会"，后者适合"催办"，混用会造成要么打断过多、要么消息烂在信箱里。

**团队编排时的上下文策略**（复杂任务版的实践）：成员被调用时都是全新上下文，只带"这一轮该干的事"；阶段之间靠制品文件传递（排查结论、改动说明、审查意见、验证报告），不靠对话历史。

由此推出一条硬要求：制品必须精确。审查和验证给出的问题要写到"文件:行"；回退时把上一轮的问题清单原文注入给编码成员，不能只说"上次有问题请修复"。制品写得越准，重载后的成本越接近"直接改代码"的下限。

另外两条值得抄的设计：审查和验证成员在工具层面被禁止改代码（直接去掉写文件的工具），而不是靠提示词约束；循环有上限（编码⇄审查、验证⇄编码各最多 3 轮），达到上限一律停下如实上报，不得静默继续。

### 5.5 边界：流程重量要匹配任务规模

多 Agent 上下文隔离的收益，建立在"任务可以拆成低耦合子任务"的前提上。

- 交付型任务（目标明确、有验收标准）适合严格约束与隔离；
- 探索型任务（还不知道要做成什么样）套重流程会直接掐死探索；
- 单点小改不需要团队版，改动面大才上。

这条边界不清，就会出现"用最贵的编排跑最简单的活"。

## 6. 反模式清单

把前面各层的错误做法收拢成一张表，便于自查：

| 反模式 | 表现 | 实际后果 | 正确做法 |
| --- | --- | --- | --- |
| 更多上下文更安全 | 所有相关文档、全部历史、全部工具记录都留着 | 稀释关键信号，早期指令遵从度下降 | 信噪比优先，无关即出 |
| 工具越多越好 | 注册十几个功能重叠的工具 | 工具定义占位，选择错误率上升 | 够用即可，职责边界清晰 |
| System Prompt 越详细越可靠 | 几千字覆盖每种边缘情况 | token 浪费 + 脆性，未枚举场景不会处理 | 给原则与边界，不给枚举 |
| 不清理工具输出 | 完整原始响应永久留在历史 | 加速 Context Rot | 消化后折叠为摘要 |
| 用大窗口当解决方案 | "200K/1M 肯定够，不用管" | 只是推迟问题，O(n²) 成本更高 | 任何窗口都要最大化信噪比 |
| 把硬约束写成提示词 | "绝对不要执行某命令"写在 CLAUDE.md | 长会话或注入攻击下失效 | PreToolUse hook 硬拦截 |
| 改上下文不看验收 | 凭感觉加规则、删规则 | 无法判断收益来源 | 先定验收标准，固定比较条件 |

最后一条值得单独强调，因为它决定了前面所有实践能不能持续改进。

## 7. 怎么验证一次上下文改动真的有用

上下文优化最容易变成"玄学调参"：加一段规则、删一段规则、换个压缩策略，感觉好像好了。要避免这一点，需要一点实验纪律。

**第一步，先分清要解决质量还是成本。** 遗漏条件、混淆规则、选错资料是质量问题；重复输入过多、响应慢、维护困难是成本问题。两种情况的最优解可能相反——输入更短但需要多轮纠错，整体成本未必更低；增加少量必要条件如果减少返工，可能更划算。

**第二步，先定验收标准。** 以日志分析为例：至少检查服务与时间范围、原始证据引用、不确定性标注，以及有没有把推断写成事实。没有可检查的标准，"效果变好了"就只是印象。

**第三步，固定比较条件。** 相同模型、相同设置、一组真实任务。不要同时换模型、重写规则、改工具，否则无法判断收益来自哪一项。

**第四步，留出未参与修改的任务。** 用已知失败定位问题，再用留出的任务检查是不是只修好了熟悉案例。

**第五步，同时记录质量与整体成本。** 首次合格率、关键遗漏、修复次数、用量、费用、耗时。小幅差异需要更多重复与任务支持。

这里有一个现成的负面证据：一次性的"重写优化"在不同任务上方向可能相反——在某个问答集上改善，在数学推理上退化，四组都没达到有反馈优化的成绩。说明"看起来更通顺、更完整"的重写稿，也需要用任务结果判断价值。

模型自称"已全面检查"、回答更长或更自信，都不能替代实际验收。

## 8. 落地顺序：从最便宜的开始

不必一次做全。按这个顺序，边际收益最高：

**第一步：建三层上下文栈。** 一份全局上下文文件（身份、核心规则、禁止清单）；一份项目级 AGENTS.md（架构、约定、不可触碰路径）；一份会话开始时读取、结束时更新的记忆文件。这一层的投入产出比最高，因为它消除的是"每次都要重新解释"的重复成本。

**第二步：给规则分生命周期。** 事实留在常驻文件，流程移入 Skill，路径相关约束加限定，绝不发生的事落到 hook。做完这一步，常驻常量的体积通常会显著下降。

**第三步：把五个动作用对。** 新任务先 clear 并自己写 brief；走错方向先 rewind 而不是追加纠正；长会话主动压缩并带提示；只需要结论的任务开子代理。这一步不改任何系统，只改使用习惯，收益立竿见影。

**第四步：建最小知识库。** 只记三类连接性知识，两级索引，一条 hook 强制先读。先不要做成熟度、衰减、自动整理——等库真的长到几百篇再上治理机制，否则维护成本会先压垮使用意愿。

**第五步：上外置与卸载。** 当任务开始稳定超过单窗口容量，再引入结构化笔记、分层折叠、差异注入。这一步的价值依赖前三步是否到位——没有干净的常驻层，外置只会让上下文结构更乱。

**第六步：最后再考虑多 Agent。** 只有当任务确实能拆成低耦合子任务、且单条探索路径会消耗数千到数万 token 时，隔离才划算。否则你付出的是编排复杂度，换回的是本来就不存在的污染。

## 9. 结语

回到开头那个误判。窗口变大不会让上下文管理失效，只会让每一次决策更值钱——因为你有了更多腾挪空间，也就有了更多犯错的余地。

把全文压缩成一句可执行的话：

> 上下文管理的目标不是让模型看到更多，而是让它在每一步只看到该看的；而"该看什么"由信息的生命周期决定。

再补三条可以贴在显示器上的判据：

1. 下一步要用的信息还在窗口里吗？在就继续，不在就先补再动。
2. 这段内容还会被再用到吗？不会就压掉或搬走，别留着占注意力。
3. 这件事是"希望模型记得"，还是"绝不允许发生"？前者写提示词，后者写 hook。

上下文是 AI 的操作系统。把内存管好，模型的能力才真正落到任务上；管不好，再强的模型也只能在一个被自己污染的环境里猜。
