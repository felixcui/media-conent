# 用代码做视频的工具怎么选？

> 不拍视频，写代码。同样是让 AI 做视频，一条路是「抽卡」——不满意就重新生成碰运气；另一条路是「写代码」——不满意就改那一行。前者像摄影师，后者像打印机。

## 一、先从一个刷屏说起

2026 年 9 月 22 日，Claude Opus 5.5 发布。接下来几天，X 上刷屏的全是视频。

有人做了 156 秒的水彩风 MV，有人做了 40 秒的「浏览器是怎么工作的」科普，有人让 AI 写了个 demoscene 风格的片头——画面和声音全部来自代码，最后打包成一个 280KB 的 HTML 文件，没用一张图、一段音频、一个库。

最容易被误读的一点是：**Opus 5.5 不能生成视频，连一张图都生成不了。**

那这些视频是哪来的？答案藏在四个字里：

> **它不拍视频，它写代码。代码画画面，电脑把画面一帧帧存下来，拼成视频。**

这就是「代码生成视频」（Programmatic Video / Video-as-Code）——本文要梳理的这条赛道。

过去半年，我把它下面几乎所有的框架和 Skill 都用了一遍，也用两条不同路线各产出了一条成片。这篇文章想把这条赛道讲清楚：**它和「文生视频」到底差在哪、底层骨架是什么、有哪些框架和 Skill、以及你到底该选哪一个。**

## 二、第一件事：分清两条完全不同的路

绝大多数人第一次听到「AI 做视频」，脑子里想的是可灵、即梦、Seedance、Veo——输入一句提示词，画面直接生成出来。

这和「代码生成视频」**不是同一个东西**，甚至可以说是两个相反的物种。

傅盛打过一个很准的比方：**即梦、可灵、Runway 是「摄影师」，镜头一按画面就有了；写代码做视频的 Agent 是一个「会写程序的导演」，先写剧本，再造一台会自己画画的机器，然后让机器画一整晚。**

把两者放在一起看，差异一目了然：

| 维度 | 文生视频模型（可灵 / 即梦 / Seedance / Veo） | 代码生成视频（Remotion / HyperFrames / Manim） |
| --- | --- | --- |
| **输入** | 提示词、参考图、参考视频 | 代码（React / HTML / Python） |
| **产出方式** | 模型一次推理生成像素 | 代码逐帧渲染 → 截图 → 编码 |
| **确定性** | 抽卡，同提示词结果不同 | **完全确定**，同代码产物逐帧一致，可用 SHA-256 校验 |
| **修改成本** | 不满意只能重新生成碰运气 | **只改那一处**，其余不动 |
| **批量能力** | 一条一条来 | 换参数即可**批量生成 100 条** |
| **擅长** | 真实质感、人物动作、镜头语言、氛围 | **精确信息**：文字、图表、数据、时间轴、品牌规范 |
| **不擅长** | 精确数字、可读文字、严格时序 | **真实世界**：一张有毛孔的人脸，代码画不出来 |
| **成本结构** | 按秒/按条计费，做得越多花得越多 | 算力成本，人力在前期搭模板 |

一句话总结分工：

- **要精确传递信息的视频**（产品演示、数据可视化、技术原理讲解、知识科普）——代码路线天生合适。
- **要创意感和镜头语言的视频**（Vlog、情绪短片、真人短剧）——文生视频模型更对路。

这不是谁取代谁。**代码画不了真实世界，模型不擅长精确信息**，两者最终会在一套流水线里汇合——代码负责「发生什么」，视频模型负责「看起来怎样」。

## 三、所有「代码生成视频」共用一个骨架

不管用哪个框架，底层原理是同一套：

```
写代码描述每一帧的画面
        ↓
无头浏览器（Chromium）逐帧截图
        ↓
FFmpeg 把图片序列编码成 MP4
        ↓
        成片
```

**工具可以换，骨架都一样——写代码画画面，截图存帧，拼成视频。**

差异只在中间那一步：**你用什么来描述「一帧画面长什么样」**。

- Remotion 用 **React 组件**（JSX / CSS）描述每一帧；
- HyperFrames 用**原生 HTML + CSS + GSAP** 描述每一页；
- Motion Canvas 用 **TypeScript 的 generator 函数**描述动画时间轴；
- Manim 用 **Python 对象**描述数学图形；
- 再底层一点，你可以**原生 Canvas + Playwright 逐帧截图 + ffmpeg**，连框架都不用。

正因为底层是浏览器 + FFmpeg，代码生成视频天然继承了 Web 生态的全部能力：CSS 动画、SVG、Canvas、Three.js（3D）、任何前端组件库——**浏览器能渲染的东西，它都能变成视频**。

## 四、渲染内核：五个框架怎么选

这是赛道的主体。我把主流框架按「技术栈」和「定位」列出来：

| 框架 | 描述画面的语言 | 许可 | 生态成熟度 | 一句话定位 |
| --- | --- | --- | --- | --- |
| **Remotion** | React / TSX | 个人及 ≤3 人公司免费，超出需商业许可 | ⭐⭐⭐⭐⭐ 最成熟 | 用 React 写视频，视频即组件 |
| **HyperFrames** | HTML + CSS + GSAP | Apache 2.0，完全免费 | ⭐⭐ 很新（2026.04 开源） | 用 HTML 写视频，对 AI 最友好 |
| **Motion Canvas** | TypeScript generator | MIT，免费 | ⭐⭐⭐ | 手搓动画精度最高，教学向 |
| **Revideo** | TypeScript generator | MIT，免费 | ⭐⭐ 社区小 | Motion Canvas 的生产级 fork |
| **Manim** | Python | MIT，免费 | ⭐⭐⭐⭐ | 数学 / 物理动画的行业标准 |

下面逐个说人话。

### 4.1 Remotion —— React 生态里的默认答案

Remotion 2021 年就发布了，是这条赛道的老玩家。官方文档的定义非常直接：

> 给你一个帧号和一块空白画布，你可以用 React 在每一帧渲染任何内容。**一个视频本质上就是一组随时间变化的图像。**

所以它**不是一个更复杂的剪映，而是一个视频生成引擎**。

它的强项是**组件化和复用**：你做过一个动效模板，下一条同风格视频直接 `import` 改参数；因为是 React，可以**数据驱动批量出片**——同一套模板配上 100 组数据，就是 100 条不同内容的视频。

它也有明确的短板：

- **对真人实拍素材的混编不友好**。把真人口播和代码画面揉在一起会很别扭，把实拍塞进 React 的帧驱动渲染管线，光让视频正常播放就要费很大力气。
- **有商业许可门槛**。个人和 3 人以下公司免费；更大的公司需要购买许可（Developer seat 约 $25/月，最低约 $100/月起）。
- **本地渲染较重**。因为要跑 Chromium，渲染是资源密集型任务。

**2026 年 1 月，Remotion 官方发布了 Agent Skills**（`github.com/remotion-dev/skills`），这是一件大事——见第六节。

### 4.2 HyperFrames —— 为 AI 原生设计的新玩家

HyperFrames 是 **HeyGen 在 2026 年 4 月开源**的框架，Apache 2.0，完全免费，没有按人头或渲染次数收费的门槛。

它的思路和 Remotion 不同：**用原生 HTML + CSS + GSAP 写视频**。每一页就是一个 HTML 文件，用 `data-*` 属性标记时间轴，框架负责渲染成 MP4。

为什么它对 Agent 特别友好，有四个理由：

1. **AI 天生会写 HTML**。HTML / CSS 是所有大模型最熟悉的输出格式，让 Codex 写一页 HyperFrames，比写 AE 脚本或剪映模板靠谱得多，**大部分视频两三轮提示词就出来**。
2. **改动成本极低**。改文案改 HTML 文字，改样式改 CSS，改动画改 GSAP timeline——不用重导工程、不用重对时间轴。
3. **和口播视频天然契合**。口播视频的本质就是「在一条真人视频上叠透明图文层」，而 HTML 天生适合做这件事：资料卡、截图、字幕、小窗、红框标注，用 HTML/CSS 写比 React 组件自然得多。
4. **确定性渲染**。同一份代码渲染逐帧一致，甚至可以用 SHA-256 校验成片有没有变。

短板也很清楚：**太新**。2026 年 4 月才开源，生态、文档、社区沉淀远不如 Remotion，踩坑概率更高，**复杂动画撑不住**。

有个必须知道的坑：**逐帧截图时视频 seek 机制会出问题，某些帧会被反复截到同一画面**——预览正常，成片里某个时间点却变成静帧。解法是**不让动态视频嵌在 HyperFrames 内部，HF 只负责透明图文叠加层，背景视频交给 FFmpeg 在最后合成阶段接进去**。

### 4.3 Motion Canvas / Revideo —— 手搓动画的两个极端

**Motion Canvas** 用 TypeScript 的 generator 函数描述动画，动画控制精度是这几个里最高的，社区氛围很好（约 8K 周下载），MIT 完全免费，**适合做教学类、解释类动画**。它的短板是工作流偏重 UI（编辑器和预览都在界面里），不太适合「自动化批量出片」。

**Revideo** 是 Motion Canvas 的 fork（约 3K 周下载），补上了 Motion Canvas 缺的东西：**音频支持、渲染 API、服务端渲染、模板系统**，定位是「面向自动化生产管线」。同样是 MIT 免费。代价是社区更小、文档更薄。

### 4.4 Manim —— 数理动画的行业标准

Manim 是 3Blue1Brown 的数学动画引擎（`github.com/3b1b/manim`），坐标、曲线、公式的动效非常丝滑，是数学和物理可视化的行业标准。

它不适合做通用视频，但如果你的内容涉及大量数学推导、几何动画，**Manim 的产出质量没有任何一个通用框架能替代**。

一个真实案例：有人用 **Manim + Remotion** 做了一条 5 分 26 秒、10 个镜头的论文解读视频——Manim 负责数学动画，Remotion 负责整体编排和包装。

### 4.5 渲染性能参考

如果你关心「渲染要多久」，有一份第三方基准测试（GitHub `takoyakisoft/remotion-motioncanvas-framescript-bench`，1920×1080 / 60fps，默认设置）：

| 工具 | 60 秒视频渲染耗时 | 120 秒视频渲染耗时 |
| --- | --- | --- |
| FrameScript | 91.4s | 162.8s |
| **Remotion** | **99.8s** | **158.0s** |
| Motion Canvas | 120s | 158s |
| Revideo | 110s | 174.3s |

结论是**几个框架的渲染性能在同一量级**，不存在数量级的差距。选型时真正该看的不是渲染速度，而是**生态、语言门槛和你团队用得顺不顺手**。

## 五、Skill 层：谁替你写代码

框架解决了「怎么渲染」，但还差一环：**谁来写这些代码？**

答案是 Coding Agent——Codex、Claude Code、WorkBuddy、豆包工作、纳米 Work 都能干。而 Skill 的价值在于：**Agent 会写代码，但它不知道你的规范、你的品牌色、你的内容节奏。**

于是这条赛道分化出了第二层：**Skill**。

按性质分成两类。

### 5.1 框架官方 Skill：让 Agent 写出正确的框架代码

| Skill | 来源 | 作用 |
| --- | --- | --- |
| **Remotion Agent Skills** | Remotion 官方 | 让 Claude Code / Codex / Cursor 写出符合 Remotion 规范的正确代码，2026 年 1 月发布 |
| **HyperFrames Skills** | HeyGen 官方 | 含 `faceless-explainer`（文章转不出镜讲解）、`hyperframes-creative`（口播节奏分镜）等子技能 |

Remotion 官方还提供了完整的四步流程，值得抄作业：

```bash
npx create-video@latest      # 建项目，模板选 Blank，同意安装 Skills
npm install && npm run dev   # 起 Studio 预览（这个终端占住）
claude                        # 另开一个终端跑 Agent
npx remotion render           # 描述完需求后渲染
```

注意第三步和第二步是**两个终端**——很多人把 Studio 停掉去跑 Agent，结果预览没了、调不动。

### 5.2 场景化 Skill：把一个具体工作流封装成一句话

这是 2026 年最热闹的一层。各式各样的开源 Skill 把「做某一类视频」的完整流程固化了：

| Skill | 作者 / 来源 | 做什么 | 亮点 |
| --- | --- | --- | --- |
| **guizang-product-video-skill** | 歸藏（`op7418`） | 产品宣传片 | **纯前端代码渲染，不依赖视频模型**；直接 import 你仓库的 React 组件渲染，音乐用 Python 波形合成；内置 11 种音效 + 自动 ducking |
| **video-skills-toolkit** | 泊舟（`bozhouDev`） | 口播 / 手绘故事 / 字幕 | 提出「**以字幕文件为唯一时间基准**」的方法论 |
| **srt-whiteboard-animation** | `geeklee` | 手绘白板动画 | 输入 SRT 字幕 → 拆分镜 → 线稿 → 渲染手绘过程 MP4，**七步确认，每步停下等你点头** |
| **chengfeng-videocut-skills** | 成峰 | 口播粗剪 + 动画叠加 | 2000+ Star；接 Codex 后加复杂动画，用 rough.js 画逻辑图效果最好 |
| **video-use** | browser-use | 真人口播素材处理 | 先转写、确认留哪段，再整理剪辑、字幕、补充画面 |
| **video-shotcraft** | Vincent（万星） | Remotion 镜头配方库 | 提供动态预览的镜头参考 |

### 5.3 Agent 入口：用什么驱动这些 Skill

同一个 Skill，挂在不同 Agent 上有不同的体感：

- **Codex**（OpenAI）：token 便宜、量大管饱、内置生图（GPT-Image-2）和 Computer Use（能打开页面看画面再改）。但注意一个坑——**它自带生图能力时会「自作主张」**，有人给了一张 Logo，它不光放了，还把图重画成 SVG，顺手把另一个不该换的 Logo 也换了。铁律：**用户给的素材优先直接引用原文件，未经确认不重绘、不换用途、不改格式。**
- **Claude Code**（Anthropic）：创作侧更强，但在「高度依赖精确时间码」的真人口播任务上对齐能力不够。
- **WorkBuddy**（腾讯云 CodeBuddy 团队）：桌面常驻，接入混元、DeepSeek、GLM、Kimi 等国产模型，**不用 API Key、不用翻墙**。有真实案例：一位用户用它做带货视频，单条 GMV 破 8000、盈利 4000 块，日产能从 3 条提到 10 条。
- **豆包工作**（字节）：最大特点是**「云电脑」**——任务跑在云端，手机、电脑、网页打开的是同一个对话，人在地铁上也能收推送给反馈。内置 TTS 免费，单次最长 120 秒。
- **纳米 Work**：全程可见（思考和执行并排展开），模型可选 K3 / GLM-5.2 / 豆包 seed-2.1 等，**一个 key 都不用配**。

## 六、我的实测：两条路线各跑了一遍

光看资料没有体感。过去一段时间，我把两条主要路线都完整跑了一遍。

### 6.1 Remotion 路线

项目 `codex-diagram-remotion`，用 Remotion 4.0.525 做的一条竖屏短视频：

- 规格：1080×1920，9:16，30 fps，53.63 秒，H.264 / AAC
- 配音：Edge TTS `zh-CN-YunxiNeural`，语速 +16%
- 字幕：基于语音服务返回的**词级时间戳**生成
- 交付物：MP4 + 封面 PNG + 独立 SRT + 发布文案

项目结构长这样：

```
src/Root.tsx         # 注册 Composition
src/scenes/          # 七段分镜
src/timing.json      # 时间轴
src/captions.json    # 字幕
script.json          # 口播稿
generate_voice.py    # 配音生成脚本
```

改一个分镜，只改 `src/scenes/` 下的一个文件；改口播，只改 `script.json` 然后重跑配音脚本。

### 6.2 HyperFrames 路线

项目 `video-agents-guide`，用 HyperFrames 做的一条竖屏短视频：

- 规格：1080×1920，30 fps，48.264 秒
- 配音：Edge TTS `zh-CN-YunjianNeural`，+5% 语速
- 编辑入口：`index.html` + `compositions/frames/`
- 导出：`npx hyperframes render --quality delivery`

### 6.3 两条路线的真实差异

| 对比项 | Remotion | HyperFrames |
| --- | --- | --- |
| **改一个镜头** | 改 TSX 组件 | 改 HTML 片段 |
| **心智负担** | 要懂 React 的帧 / 组件模型 | HTML + CSS 就能上手 |
| **口播图文层** | 需要绕一下（React 帧驱动 vs 实拍时间轴） | 天生契合 |
| **复杂动画** | 撑得住 | 撑不住 |
| **生态与文档** | 成熟，踩坑少 | 新，踩坑多 |
| **适合** | 长期沉淀模板、批量出片 | 快速试水、单条内容 |

一句话选型法则，来自做了几十条视频的实践者：

> **试水、赶时间、做个演示，用 HyperFrames；认真长期做，用 Remotion。**

更完整的做法是分两步走：**第一条先用 HyperFrames 跑通，连续做几期后发现镜头结构稳定了，再让 Agent 把它整理成 Remotion 的固定栏目。**

## 七、选型决策：其实只有三个真问题

工具那么多，但真正决定你选哪个的，只有三个问题。

**问题一：你要 React 生态，还是 HTML 的简单？**

- 团队熟 React、要复杂交互和批量数据驱动 → **Remotion**
- 只想快速上手、内容以图文叠加为主 → **HyperFrames**
- 内容是数学 / 物理可视化 → **Manim**

**问题二：你要手搓动画，还是 Agent 代写？**

- 手搓（Motion Canvas / Revideo）动画精度最高，但要自己控制时间轴，产出不可规模化。
- Agent 代写（Remotion / HyperFrames + Skill）效率高，但**你必须把规范讲清楚**——否则每个镜头单看还行，放一起风格全乱。

**问题三：你要一次性出片，还是可复用的生产线？**

这一条最容易被忽略，也最重要：

- **一次性**：直接让 Agent 写一版，导出，发。
- **生产线**：把视频拆成**可复用模块**——开场钩子、主体场景、字幕、素材、结尾，各自独立成组件。人负责观点和判断，Agent 负责搭生产线，框架负责稳定出片。

> **剪映适合手工剪一条视频，Remotion 适合批量生产同一类高一致性视频。**

## 八、一个反直觉的信号：模型够强时，Skill 可能是包袱

2026 年 9 月底，有一条推文在这条赛道里炸了锅。

`video-shotcraft` 的作者（GitHub 万星）公开说：**如果你在用 Opus 5.5，建议卸载所有用代码做视频的 Skill。**

他贴出的视频由 Opus 5.5 一句话生成，包括 BGM 和音效合成在内全部由代码完成。网友的反应更直接：

> 「完全没用任何 skill 直出，效果居然比用 skill 还好。」
> 「以前觉得特定领域的 skill 是护城河，现在发现都是历史包袱。」

这不是说 Skill 没用了，而是它揭示了一个规律：

> **工具每跨一代，手艺的价值就从「怎么做」挪到「做什么」。**

当模型的能力足够强，把「怎么用框架」封装成 Skill 的价值在下降；但把「做什么内容、什么风格、什么节奏」这份判断固化下来，价值反而更高。

**Skill 不应该是能力的束缚和封装，而更多是灵感和方向的指引**——这样才不会被下一代模型覆盖。

顺带一个更狠的旁证：有人只给 Opus 5.5 一句「做一个你自己最令人印象深刻的演示」，它跑了约 5 小时、烧掉约 6.97 亿 token，交出一个画面和声音全部由代码生成的片头，最后打包成 280KB 的 HTML。

> **code is all you need.**

## 九、踩坑清单：这些是拿血换的

代码生成视频最反直觉的一点是：**它做起来其实很工程，一点都不 vibe。** 下面是踩过的坑里最值得记住的几条。

**① 不要跳过文档直接写代码。**

跳过 `.md` 文档直接让 Agent 写代码，结果是每个镜头单看还行，**放到一起完全不统一**（蓝底黑底混用、字体不一、弹入淡入混杂）。

正确顺序是先锁两份文档：**`DESIGN.md` 锁视觉系统**（色板、字体、容器样式、动效规范、转场方式），**`STORYBOARD` 锁分镜**。文档先定稿，Agent 严格按文档来，不允许自由发挥。

**② 字幕是整条视频的唯一时间基准。**

有条被反复验证的心法：**先写逐字稿 → 生成音频 → 拿到字幕文件 → 用字幕文件驱动所有动画 → 最后配音效和 BGM。**

为什么？因为**视频本质上是一条以声音为轴的时间线**。没有这条轴，画面、动画、音效就是一堆各自为政的东西。

配套的两条经验：
- **音画同步的正确解法**是让 Agent 去字幕文件里查「这个词出现在第几秒」，而不是按句子顺序估时间。
- **改时间轴要成套改**——字幕、动画、音效、进度条、总时长一起动，只改其中一个，后半段就会整体漂移。

**③ 先出低画质，最后出高画质。**

有人直接渲 4K，十几分钟渲完，发现中段一整段是空白的，全部重来。**先用低画质调试，确认没问题再出高画质。**

**④ 检查全绿不等于画面没问题。**

遇到过所有自动检查项全绿、最后一帧帧看，成片里某个视频素材是个空窗口。**自动检查能挡掉 80% 的错，剩下 20% 必须用眼睛抽帧看。**

**⑤ 渲染一次只跑一个。**

有人横竖两版同时开渲，两个任务都去装渲染用的 Chrome，安装锁没有释放，白等了约 15 分钟、一帧没出。

**⑥ 最终渲染出来的 MP4 才是事实。**

预览通过不代表成片没问题。**要验收的对象永远是那个渲染出来的文件，不是 Studio 里的预览。**

**⑦ 反馈要给到具体对象和位置。**

「第 6 秒的标题太小」「这张截图至少停留 3 秒」「字幕挡住了人物」——这些才是有用的反馈。**不要只说「高级一点」「再好看一点」，那是人类对人类的说法，对 Agent 无效。**

## 十、写在最后

把这条赛道收束成一张图：

```
框架层     Remotion / HyperFrames / Motion Canvas / Revideo / Manim
              ↓  谁替你写代码
Skill 层   Remotion Skills / HyperFrames Skills / 各类场景化开源 Skill
              ↓  用什么驱动
Agent 层   Codex / Claude Code / WorkBuddy / 豆包工作 / 纳米 Work
              ↓
           成片
```

而支撑这一切的，始终是同一个骨架：**写代码画画面 → 逐帧截图 → 编码成视频。**

回到最开始那个问题——为什么一定要用代码？

因为在很多场景里，代码路线提供的是模型给不了的两样东西：**确定性**和**可编辑性**。

> 你生成一段视频不满意，只能重新生成碰运气；代码渲染的视频，可以说「把第三段标题改掉」「音乐结尾延长两秒」「通知弹出动画快一点」，**它只精确改那个地方，其他不动。**

品牌色要换？改一行。镜头想放慢？改一个数。「中秋快乐」要变成「国庆快乐」？改四个字，重新渲染，**不用重新抽卡**。

所以这条赛道的本质，和去年我们聊过的那件事是同一个：

> **视频不再只是一个导出的成品文件，它开始变成一个可以被修改、复用、扩展的内容系统。**

以前，视频生产围绕时间线展开；现在，视频生产开始围绕工作流展开。

最后留一句得说实话的提醒：

> **决定作品上限的，依然是创作者本身的能力。工具降低的是制作门槛，不是内容门槛。观众不会因为你用了 AI 就多看一秒。**

把剪辑变成维护一条生产线，是把重复劳动还给了机器。**而真正值得你亲自做的，是选题判断、观点表达、案例选择、情绪分寸。**
