# 微信公众号订阅方案调研

---

## 〇、先说结论

> 一句话：**不想折腾用 we-mp-rss；有自有公众号用 wechat-download-api；要最轻、只追新就用自建的微信读书服务**（第五章）。三者都属于「拉」，想要分钟级只能买商业推送。

### 硬约束：决定了所有方案长什么样

1. **公众号没有官方 RSS，也没有对第三方开放的「文章列表」接口。** 官方 `freepublish/batchget` 一类的发布能力接口只能拉**自己号**的文章，拉不了别人的。这是所有方案都要绕路的根因。
2. **只有两种物理形态：拉（轮询）和推（webhook）。** 这是结构差异，不是参数差异——拉想追上推，只能把轮询密度堆到成本不可承受。
3. **所以开源方案全部是「拉」。** 能做到分钟级的只有两类：第三方商业推送服务，或在本机挂一个微信客户端读本地数据库。前者要钱、且通常不给正文；后者要养机器、要小号、有封号风险。

### 选型：按自己的处境对号入座

4. **不想折腾 → we-mp-rss（WeRSS）**：4.4k star、2026-11 仍在活跃提交、MIT、Docker 一行、扫码授权，直接出 RSS + Markdown。延迟小时级，够「每天一批」的日报用。
5. **自己有公众号 → wechat-download-api**：完全免费开源，能拉任意号的**历史列表**与正文，自带 RSS 2.0 + Markdown + MCP 接入。代价是登录凭证约 4 天过期，要定期扫码。
6. **要最轻、且只追新不补旧 → 自建微信读书服务**（第五章）：只要一个微信读书账号，**不需要自有公众号**，纯标准库几百行，扫码登录 + 定时轮询。硬伤是微信读书已下线列表接口，**一次只能拿最新一篇、历史文章拿不到**，两轮之间发多篇会漏——适合「盯更新」，不适合「求完整」。

### 一条避坑

7. **wewe-rss 已经死了，不要再按老教程部署。** 仓库 2026 年 3 月归档，且核心逻辑跑在作者私有中转上，该中转已全端点 502。

## 一、底层约束：为什么没有「官方 RSS」

三条路都被堵死：

| 通道                  | 能力                | 卡点               |
| ------------------- | ----------------- | ---------------- |
| 公众平台发布接口            | 只能拉自己号已发布文章       | 拿不到别人的号          |
| mp.weixin.qq.com 网页 | 文章页可读             | 有滑块验证与频控；列表页需登录态 |
| 微信读书「关注公众号」         | 能拿到标题、封面、时间、文章 id | 需账号登录态，有配额与风控    |

实测数据（2026-11 掘金一位作者的 15 天对照实验）：直接用公众平台后台接口查**别人**的号，几分钟内 4 发 3 拒（错误码 200013），继续硬试导致会话作废（200003），等 24 小时仍全拒——**不是滚动窗口放行，是账号被打上长尾标记；限流记账号不记 IP，换网络出口无效。** 个人开发者打不起「代理池 + 账号池」这场军备赛。

结论：**别自己直连公众平台后台接口。** 要么用现成项目把风控这层包掉，要么换成微信读书那条路（第五章就是后者）。

## 二、五类技术路线

### 路线 A：微信读书侧（借登录态）

原理：微信读书里可以「关注」公众号，每个号在读书体系里对应一本书（bookId）。扫码登录读书账号 → 拿到 vid/token → 按「书的章节列表」拉文章列表。

> **⚠️ 2026-11-26 实测修正（重要）**：列表接口 `/web/mp/articles` **已被微信读书下线**，  
> 任何 Cookie（含浏览器完整 Cookie）调用都恒返 `errcode=-2041`。我在同一个有效登录态下  
> 交叉验证过：`/web/shelf/sync` 正常、`/mp/shelf/addToShelf` 正常、`/api/mp/cover` 正常，  
> 只有 `/web/mp/articles` 报 -2041；换成 `POST` 或其他候选路径全部 404。
>
> 现在能用的只剩两条：
>
> - `GET /api/mp/cover?bookId=` —— 一次只给**最新一篇**（reviewId / title / pic / name / avatar），  
>   对**未加入书架**的号同样有效，所以不再需要「先上架再拉」。
> - `GET /web/mp/content?reviewId=` —— 返回整页 HTML（单篇可达 4MB+），  
>   从 `#js_content` 切正文，顺带能挖 `var ct`（发布时间）与 `var author`。
>
> 结论：**公众号历史文章已经拿不到了**，只能靠轮询「最新一篇」往后累积。  
> 这也意味着 `-2041` 的语义变了：以前它约等于「列表接口已废弃」，现在只剩风控一种情况。

- **we-mp-rss（rachelos/WeRSS）** — 4.4k star，MIT，最后提交 2026-11-22。
  - 后端 Python/FastAPI + 前端 Vue3，SQLite/MySQL
  - Docker 一行起，Web 后台扫码授权
  - 输出：RSS（含全文）、Markdown、docx、pdf、json；Webhook 推钉钉/企微/飞书
  - 支持 HTML 过滤规则去广告、多账号配额、环境异常统计
  - 2026-10 已适配微信改版（二维码流程重写、`js_content` 移除后改从 JS 变量提正文）
  - 2026-11 官方文档已承认列表接口废弃，`weread_mp` 模式改为「cover 增量」采集
- **wewe-rss（cooderl）** — 9.4k star，**已归档（2026-03-20 归档 / 5-11 确认）**。半开源：开源的只是外壳，核心 API 调用与签名跑在作者私有中转 `weread.111965.xyz`，该服务现已 502。**新部署一步都走不通。**
- **wechat2rss（ttttmr）** — 1.6k star，**闭源付费**。免费版 300–400 个号（技术/安全/AI/财经为主），15 元/月可订任意号，150 元/年可私有部署。实测延迟中位 9–21 小时，但漏文最少、全文自带。

### 路线 B：公众平台后台接口（扫码登录 mp.weixin.qq.com）

- **wechat-download-api（tmwgsicp）** — 1.2k+ star，完全开源免费。
  - 前提：**自己有一个公众号**（订阅号/服务号均可），管理员微信扫码
  - 能力：搜号 → 拉任意号历史列表（分页 + 关键词）→ 单篇正文 HTML/纯文本/图片
  - 输出：RSS 2.0（支持聚合源、分类源）、Markdown（带 YAML frontmatter，可直接进 Obsidian）、Word/PDF/EPUB/Excel/JSON
  - 反风控：Chrome TLS 指纹模拟 + SOCKS5 代理池轮转 + 三层自动限频
  - 运维：凭证约 4 天过期，内置提前 24h/6h 预警 Webhook；有 MCP 服务，可让 Agent 直接搜号、订阅、读文
  - 本地跑即可，不一定需要公网服务器

### 路线 C：本地微信客户端数据库（chatlog 系）

原理：微信本地库是 SQLCipher 加密的 SQLite，取出密钥后解密，直接读「订阅号消息」表。

- **chatlog（sjzar）** — 读本机微信数据库，HTTP API + MCP
- **wechat-chatlog（lululu811 fork）** — 在其上做了公众号管理：动态流、LLM 每日简报、标签库、批量导出 Markdown、推 IMA 知识库、MCP
- 优点：全免费、正文自带、理论分钟级、纯本地不上传
- 代价：要一台常开的机器 + 微信小号；**macOS 需临时关闭 SIP** 才能取密钥；微信版本有上限；读进程内存有封号风险

### 路线 D：第三方商业 API

- **推送类**：服务端盯号，新文 webhook 推给你。实测发文到推送中位 **2 分钟**（1–3 分钟）。硬伤：推送只有标题 + 链接 + 时间，**没有正文**；只收群发文章。约 69 元/月 / 50 个号。
- **按次 API**：列表约 0.14 元/次、正文 0.04 元/篇（另一家 $0.02/次）。稳，但**结构性漏文**——列表窗口只认「昨日 0 点到今晨 2 点」的发文，窗口外永久错过（15 天对照漏 8–9 篇）。想快就加密度，30 个号半小时一轮约 6048 元/月。
- **微信读书 App 直接订阅**：免费，但更新比微信慢几小时到一天，且无法程序化取出。

### 路线 E：聚合 / 搜索（非订阅，可兜底）

- **腾讯元宝搜索 so.qq.com**（2026-11 上线）：覆盖公众号、视频号、腾讯新闻，腾讯云已开放检索 API。适合「按关键词找」，不适合「盯某个号」。
- **RSSHub 公众号路由**：依赖第三方网关，公共实例基本全挂（rsshub.app / rssforever / pseudoyu / injahow 实测全部超时或 403）。
- **搜狗微信**：早已失效。

## 四、「实时」到底能做到多快

把「实时」拆成三段，瓶颈各不相同：

1. **发现新文**：推送 1–3 分钟；自建轮询取决于 cron，10 分钟一轮也做得到，但会显著提高风控概率。
2. **拿到正文**：推送类不给正文，还得二次抓；自建类一次到位。
3. **落进你的库**：这一段完全可控，取决于本地脚本。

所以现实结论是：**「发现」可以做到分钟级，「正文入库」在免费方案里最快也是小时级。** 如果你的用途是每天早上一份 AI 资讯日报，小时级完全够；如果是追突发，只有买推送服务。

## 五、自建实现方案

### 5.1 为什么走微信读书这条路

四条路里只有它**没有额外前置条件**：不需要自有公众号（路线 B 的前提）、不需要常开机器和小号（路线 C）、不按量付费（路线 D）。代价是它给的能力最窄。

窄到什么程度，决定了整个架构：

- `/web/mp/articles` 列表接口**已下线**，任何 Cookie 调用恒返 `-2041`
- 只剩 `/api/mp/cover?bookId=`，**一次只给最新一篇**
- 所以：**没有历史回补，只能从添加监控那天起往后累积**

这不是「拉列表 + 翻页」，而是「反复问同一个问题：你最新一篇是哪篇」。

### 5.2 数据链路：四个接口各管一段

| 步骤          | 接口                                  | 拿到什么                                  | 量级        |
| ----------- | ----------------------------------- | ------------------------------------- | --------- |
| 链接 → bookId | 抓文章页，`var biz` 是十进制 fakeid 的 base64 | `MP_WXS_<fakeid>`                     | 一次 ~200KB |
| 查新文章        | `GET /api/mp/cover?bookId=`         | reviewId / 标题 / 封面 / 号名 / 头像          | 几十 KB     |
| 取正文（可选）     | `GET /web/mp/content?reviewId=`     | 整页 HTML；`var ct` 发布时间、`var author` 作者 | 单篇最大 4MB+ |
| 账号昵称        | `GET /api/userInfo`                 | name / avatar / userVid               | 极小        |

两个关键细节：

- **去重只靠 reviewId**。它形如 `MP_WXS_xxx_<token>`，末段就是 `mp.weixin.qq.com/s/<token>` 的 token，所以原文链接可以直接拼，不用二次请求。
- **`/api/mp/cover` 不需要先加书架**。实测未上架的号照样返回数据，所以「上架 → 再拉」那套绕行逻辑可以整个砍掉，少一个失败点。

### 5.3 轮询与写入

**节奏**：默认 30 分钟一轮。号与号之间 3–5 秒随机间隔（固定节奏本身就是特征），首个号不等待以便手动刷新能立刻响应。3 个号一轮实测约 9 秒；30 个号推算约 2 分钟。

**并发**：两道锁，职责不同——

- `REFRESH_LOCK`：同一时间只允许一轮抓取。手动刷新撞上定时轮询时返回 429。
- **单实例文件锁**：`data/service.lock` + `fcntl.flock`。两个进程各自「读整份 JSON → 改 → 写回」会互相覆盖，表现为**随机丢失刚写入的数据**（加完号过一会儿又不见了），极难排查。启动时抢不到锁直接报错退出。

**写入**：一律「锁内重新读盘再合并」。一轮轮询要跑几十秒，如果开头读一份快照、结尾整体写回，这期间用户新加的号必然被旧快照抹掉。所以每篇结果都走 `_merge_feed()`：`with DB_LOCK: db = load_db() → 就地合并 → save_db()`。附带好处是轮询途中被删的号不会被合并逻辑复活。

**正文默认关闭**。标题、封面、链接、号名都来自 `cover`，一篇只要几十 KB；正文只为拿发布时间和作者，却是 4MB+。关掉之后用「首次发现」时间代替发布时间，并在界面上明确标成灰色、不当成发布时间显示。

### 5.4 主要风险及应对

| 风险               | 具体后果                                                             | 应对策略                                                        |
| ---------------- | ---------------------------------------------------------------- | ----------------------------------------------------------- |
| **漏采**（最实质）      | 两轮之间发多篇，只留最新一篇；停机一晚 = 那晚全空。**没有回补手段**                            | 缩短间隔到 10–15 分钟；接受「不保证完整」的定性；要完整只能回到浏览器自动化                   |
| **Cookie 即账号凭证** | 拿到 `wr_vid + wr_skey + wr_rt` 就能以你的身份读书架、笔记、阅读记录                 | 只监听 `127.0.0.1`；**把 `data/` 移出同步目录**（`.gitignore` 管不了同步客户端） |
| **接口随时失效**       | `/web/mp/articles` 说下线就下线，无公告无过渡期；现在押在三个逆向接口上                    | 接口调用集中封装、失败可诊断；不接受就换方案                                      |
| **风控 `-2041`**   | 限频；持续高频可能升级为限制账号功能                                               | 随机间隔、单实例、低频长周期；连续失败置该号冷却                                    |
| **「环境异常」验证墙**    | `mp.weixin.qq.com` 间歇性返回 17KB 验证页，且微信 UA 被拦、桌面 UA 能过 → **加新号失败** | 用带 `__biz=` 的长链而非 `/s/<token>` 短链；稍后重试或换网络                  |
| **合规**           | 自用归档风险低；一旦对外提供订阅（做 RSS 给别人、做站点）即涉「信息网络传播权」                       | 严格限定个人阅读与归档，不做二次分发                                          |
| **规模与存储**        | 单文件 JSON 全量读写，文章上万后变慢                                            | 到量后迁移 SQLite，并按 reviewId 建索引                                |

**定性**：这条路线只能支撑**半自动的个人阅读工具**，不是能保证完整性的采集系统。它能替代「手工 WebFetch 单篇」，但替代不了「订阅源必须不漏」这种要求。放在这个位置上，多数风险可控；往上加期待，最先崩的是数据完整性。
