## 一、《构建 AI 时代的知识底座：直播数据 LLM Wiki 实践》

> 原文链接：https://mp.weixin.qq.com/s/1J3EEmjmisxUejV7fpZF5g
>
> 大淘宝技术，2026-11-16

**一句话概括**：用"LLM 编译"替代人工写 Wiki，把散落、矛盾、易腐化的领域知识编译成结构化、可验证的知识资产，作为 AI 时代的底座。

**业务场景描述**
- 团队与领域：大淘宝技术—直播数据团队，负责直播业务的数据资产建设与维护。
- 典型日常工作：① 口径答疑——业务方问"某指标怎么算的""数据为何对不上"，需人工翻代码和文档；② 问题排查——数据异常时追溯链路，定位是哪张表、哪个任务出错；③ 代码/SQL 生成——开发新需求时，需理解现有表结构和血缘，写出正确 SQL；④ 数据模型迭代（高频且高风险）——改一张表，要沿血缘影响可达数十张下游表，字段还参与 WHERE 条件、CASE WHEN 分档，改错会导致业务判定失效；新旧口径差异需双跑验证。传统流程为：需求理解→查表结构→查血缘→判影响→估风险→写SQL→验数据，全程人工 grep+逐表排查，耗时易错。
- 核心痛点：这些场景本可被 AI 极大提效，但卡在"知识喂不进去"——知识散落、矛盾、易腐化，AI 拿了原始文档也答不准。

**面临什么问题**
1. 知识本身质量差：散落在代码/注释、配置、钉钉文档、沟通记录中，无统一载体；口口相传，人走知识断；同一指标口径矛盾无人仲裁；文档长期不维护，三个月后与线上不符。
2. 工程熵增：没有全局视图，重复建表、重复造链路，累积数据负债。
3. RAG 治标不治本：传统 RAG 查询时现找现拼原始碎片，不改变原材料状态——散落的还散落、过期的还过期，变成"AI 找到了但答不准"。

**核心解决思路**
- 在检索前加"编译"：把 DDL、任务代码、文档等源材料，通过 提取→生成→归类→聚合→链接→验证 六步（类比编译器），预先编译成结构化页面。
- 产出是"知识资产"：每页 frontmatter(YAML)+正文，遵循 Schema 契约；域按树形组织渐进披露；血缘/归属/消费/引用关系显式存为图，可遍历、可计算影响面。
- 保证"准"的工程纪律：代码即真相（多源冲突以生产任务代码为准）；生成与判断分离（推断字段生成时留空，后续独立判断并过机械门禁+人工门禁）；证据链可追溯（每页 sources 指向原始材料）；正确性可度量（结构、语义、人工三层校验）。
- Agent 编排：wiki-orchestrator 只做路由/确认/调度/汇报，6 个 skill（材料预处理、基础生成、高阶生成、图构建、健康检查、检索）高内聚低耦合，通过文件系统交互，可并行、可独立调试。
- 效果：血缘查询提速 15 倍，遗漏率降为 0%，在指标召回、SQL 生成、模型迭代中显著提效，人力从机械劳动转向决策确认。

**结论**：领域知识只能内部积累，是 AI 系统最值得长期投入的部分；LLM Wiki 用"编译思维 + 结构化约束 + 显式关系 + 可验证"给出了系统化沉淀方法。

## 二、《基于 LLM Wiki、OKF 与 Git 的 Agent 知识库：淘宝直播互动团队的 AI Coding 实践》

> 原文链接：https://mp.weixin.qq.com/s/N_D1fo-S8KomtfaLQG68Gg
>
> 大淘宝技术，2026-11-20

**一句话概括**：为 Coding Agent 构建 LiveX Wiki——用 LLM Wiki 编纂业务理解、OKF 轻量表达知识、Git 治理版本迭代，把跨仓跨端业务经验沉淀为机器可解析、可核验、可维护的上下文，弥合通用 Agent 与真实业务需求间的认知鸿沟。

**业务场景与背景**
- 团队：淘天集团—直播互动团队，负责淘宝直播/点淘的互动体验、用户增长与运营研发，探索 AI Native 研发。
- 场景：复杂业务编码需求往往跨仓跨端、涉及业务黑话、复杂配置与实验设计；通用 Coding Agent 拿到原始 PRD 无背景补充时，产出方案/代码不可用，表现为代码采纳率低、对话轮次和返工高、交付提效不明显。
- 早期尝试：用过 RAG 向量知识库补材料，统计 2026 年 7–9 月数据：知识相关率 25.45%→42.20%，知识库支撑占比 44.23%→55.87%，但采纳率仅在 20.54%–28.05% 波动——问题从"能不能搜到"变成"能不能按业务结构理解"。

**面临什么问题**
1. 上下文完备度：隐性规则、历史兼容、跨仓依赖分散在代码/配置/人脑里，Agent 写的代码满足表面需求却漏掉业务约束（认知 gap）。
2. 上下文准确性：Agent 缺少判断歧义、查证时机的依据；猜着写返工，频繁问人抵消提效。
3. RAG 四点局限：知识点状缺整体视角；业务视角需临时拼装；影响分析要额外调查；知识新鲜度无版本/证据约束。
4. Agent 知识库四条设计约束：按需供给（不全量堆）、按业务结构组织（不条目堆积）、给可核验路径（不只给结论）、有生命周期（随变更演进）。

**核心解决思路**
- 技术选型四维：
  - 建模：业务场景为核心单元，按"域—场景—共享知识"三层组织；借鉴 OKF，用 Markdown+YAML frontmatter 表达身份、来源、依赖，人可审阅、程序可检查、Agent 可按结构读取。
  - 生产：人工定场景边界与责任，Agent 跨源调查与回源核验（固定版本→两轮搜索→正反向追查→LLM 编纂），未闭合证据单列。
  - 消费：层次索引（程序给紧凑入口）+ Agentic Search（Agent 按需展开、回代码/平台核验当前事实），证据齐备即停、未命中报缺口。
  - 迭代：LLM 增量更新与全量审查 + Git 候选分支/评审/门禁/回退，知识像代码一样版本化。
- 知识图谱：树给确定入口、图保留跨边界关系，渐进披露控制展开范围；归属回答"谁维护"，依赖回答"变化后查哪里"。
- 生命周期治理：规则由仓库级 AGENTS.md（入口/读取顺序/行为边界）和 MAINTENANCE.md（生产/维护/发布流程）统一承接，封装为 Skill 供 Agent 调用。

**关键成果**
- 端到端生码：综合得分较无知识库平均相对提升 39.15%（两批分别 +54.5%、+23.8%），较 RAG 向量库平均提升 30.1%（两批 +44.3%、+15.9%）；功能正确性、实现契合度、兼容安全性、工程质量均正向。
- 需求路由：已覆盖场景上定位准确率/召回率显著提升，链路 F1 达 1.38 : 0.10；线上仓库定位准确率从 60% 升至 90%。

**适用边界与局限**：适合跨仓、跨端、持续变化且反复开发的业务；场景边界需人参与、覆盖需持续投入；依赖图可能遗漏未建模关系；Git/CI 能保证可追溯和确定性检查，但不能保证业务判断正确，必须有人兜底。

## 三、《滴滴开源 HelixHarness：让团队 AI Coding 稳定交付》

> 原文链接：https://mp.weixin.qq.com/s/N2AXnzXKYtaNy3rO9dFnKw
>
> 滴滴技术—金融技术团队，2026-10-29
>
> 项目地址：https://github.com/didi/helixharness

**一句话概括**：在现有 Coding Agent 之上构建一套团队级 AI Coding 工程化基础设施（Harness），把项目知识、团队规范、研发工作流和评测机制统一组织起来，让 AI 在真实工程环境中稳定、可控、可衡量地交付，并支持各团队持续演进自己的专属 Harness。

**业务场景与背景**
- 来源：源于滴滴金融技术团队内部 OpenHarness 项目，"Helix（螺旋）"寓意持续演进、循环迭代。
- 落地规模：已推广至滴滴内部 10 余个部门和团队，累计应用于上百个业务模块。
- 出发点：从个人用 AI Coding 提效，走向支撑团队规模化研发交付——解决的不只是"AI 写出更好的代码"，而是"AI 在真实工程中稳定完成任务"。

**面临什么问题**
1. 工程化支撑不足：AI 缺乏对项目知识、业务逻辑、工程规范的完整理解，缺少贯穿需求/开发/验证的统一工作流，开发者仍需大量引导。
2. 过程数据不可观测：工具调用、代码修改、返工路径缺乏记录，难分析效率与问题根因。
3. 框架迭代缺少评测：知识、规则、Skills、工作流持续改，但无统一评测体系，改进效果无法客观衡量。
4. 框架与团队不适配：各团队技术栈、规范、流程不同，通用 Harness 难直接适配，重复定制成本高。

**核心解决思路**
- 标准化命令驱动端到端工作流：把研发拆解为初始化 → 方案设计 → 开发执行 → 结果归档阶段，用统一命令组织 Coding Agent 在约束下有序完成任务。
- 四层工程上下文，让知识成为可复用资产：在项目目录里用标准化结构（docs/ 下的 harness/、knowledge/、specs/、hooks/，加根级 AGENTS.md）统一组织工程约束、项目知识、需求契约与检查规则，与业务代码共同维护；再把 Knowledge/Harness/Specs/Hooks 融入需求分析→方案设计→开发验证全流程。
- 可观测 → 评测 → 自进化闭环：整体思路为 可观测 → 形成假设 → 候选修改 → 统一评测 → 受控采纳 → 持续迭代，让每次框架调整（改 Rule、加 Skill 等）都有数据依据、效果验证和风险控制，而非凭经验。
- 差异化定位：不重复造代码理解/规划/工具执行能力，而是在现有 Coding Agent 生态（Skills、MCP 等）之上，重点解决工程能力如何在团队中统一组织、复用、持续改进，支持各团队构建专属 Harness。

**关键结论与规划**：文章未给出量化提升数据，强调机制与定位——核心是把 AI Coding 从"个人提效工具"升级为"团队稳定交付的工程化体系"。未来规划：① 扩展 Agent 支持，覆盖主流 Agent；② 支持工作流程自定义，适配不同团队研发流程。

## 四、《我们放弃了"全自动生成代码"——网盘 Coding Agent 落地与迭代实录》

> 原文链接：https://mp.weixin.qq.com/s/ax_eh5s3Z7ROgqj6n_Rvkg
>
> 百度Geek说（作者：三石），2026-10-13

**一句话概括**：网盘团队把一次性全自动流水线改为人机多轮的 Agentic Engineering Loop——执行前做证据化需求调研、不确定项挂账，执行中分轮验证、过程可观测，目标从"生成代码"转向"可验证的交付"。

**业务场景与背景**
- 原流程：需求规格→技术设计→任务拆分→代码生成→质量检查五阶段串联，产物自动传递，无确认关键假设的节点。接入真实迭代后出现两类失败：被未就绪的接口卡住；走完全程却建立在没人确认的需求理解上，验收才发现偏差、回头返工，且过程记录不全难定位跑偏环节。
- 核心认知：难点不是生成代码，而是在真实、复杂、持续变化的环境中靠可靠上下文把活干对；需求、历史知识与外部依赖常带未确认部分。

**面临什么问题**
1. 执行过程：上下文堆叠致字段引用错、接口判断失准、推断被当成事实；记录只留阶段结果，难还原当时用了哪些输入、做了哪些判断；任务进度、卡点、质检结果、资源消耗无统一视图。
2. 任务输入：需求歧义（缺口径、异常分支、验收标准，Agent 自行补全后出现"实现与测试自洽、整体偏离业务目标"）；存量经验未显式化；知识图谱覆盖不全（"没检索到"不等于约束不存在）；接口未就绪或状态不稳致验证无法进行，原流程缺暂停、恢复与替代验证。
3. 根因：全自动把"不确定"当"确定"往下传，错误在最贵、最靠后、最难定位处才暴露。

**核心解决思路**
- 重新分工：脚本与门禁负责路径、分支、编译、校验、日志；人定需求口径、方案取舍、历史兼容、体验；Agent 理清证据、摆候选方案，仅在关键决策点找人拍板。门禁结果不等于业务验收。
- 多轮反馈：保留 SDD"先定目标、约束、验收标准"内核，按"观察—决策—修改—验证—复盘"循环，满足验收后交研发确认才算交付。作者澄清：循环不天生优于流水线，主 Agent 协调也不自动解决长上下文问题。
- 循环前需求调研：把业务描述整理为目标、工程约束、改动范围、验收标准，对齐真实实现（文件、调用关系、提交历史），拆成可独立验收单元并分别编号；暂不能确认的挂为待确认项，不写成实现前提。
- 过程可观测：每轮事件、指标、迭代记录汇到远端，形成运行/任务/事件/产物结构化记录；"SDD 运行记录"看板展示阶段、耗时、token 成本、门禁结果、上下文占用。复盘须区分"执行完成/检查通过/业务验收通过"，不可混同。

**关键结论与规划**：已跑起来的是证据化需求打磨、人机多轮可纠偏循环、过程上报与复盘；未解决问题包括知识图谱覆盖不全、接口后置、存量经验转 Skills 仍在积累、自动化与可控性的平衡点持续调整。作者强调这些是能力建设进展，尚无量化收益验证；后续按任务类型跟踪人工介入、端到端耗时、返工和验收结果。分工共识：Agent 组织分析与执行，工程工具落实可检查规则，研发与业务责任人确认取舍和验收。
