## 〇、先给结论

把这些资料读成一条脉络，Data Agent 在 2026 年的变化可以压缩成一句话：

**它不是 Text-to-SQL 换了个名字，而是数据系统从「人写查询、机器执行」转向「机器理解业务语义、自主编排并自我校验」的一次结构性迁移——但行业的真实水位仍在 L2 到 L3 之间。**

七条关键判断：

1. **定义尚未统一，但学术分级已经收敛。** 业界把「智能问数插件」「云上数据分析师」「Agentic BI」「自主数据研发」都叫 Data Agent；学术侧则已有较通行的 L0–L5 分级（arXiv 2510.23587，借鉴 SAE J3016），把「人在环路中的角色」作为分级标尺。厂商自定义分级（高德 BI L0–L4、快手 L1–L3 + M1–M4、火山自称 L3）互不兼容，不能横向等同。（arXiv 2025-10-27；火山引擎 2025-06；高德 2026-10-01）
2. **瓶颈已经从「SQL 写不对」转到「口径找不到、用错了」。** Anthropic 内部实测：直接把 Claude 接数仓准确率约 21%，补齐语义层与 Skills 后稳定在 95% 以上；得物 Text2SQL 系统测评准确率随语义标注密度从 85%+ 升至 95%+；高德用 NL2Metric2SQL、淘宝用 NL2MDL2SQL 在自然语言与 SQL 之间插入指标/语义层。四方独立指向同一结论：这是上下文与验证问题，不是代码生成问题。（Anthropic 2026-06；得物技术 2026-09-16；高德 2026-11-05；天猫技术 2026-09-05）
3. **工程的核心是「把确定性约束从模型里剥离出来」。** Agent = Model + Harness 成为共识：高德 CFHL（Context/Function/Harness/Loop）、1688 的五角色 Small Team + 三道安全网、得物 Hermes 的「单 Agent + 多 Skill + 人工确认点」、HarnessSQL 的只读沙盒与二值奖励，本质都是给不确定性模型套上可检查、可回放、可回滚的工程骨架。（数据研发 Harness 2026-07-16；高德 2026-11-05；得物技术 2026-06-17；港科大/微软 2026-11-03）
4. **市场已由验证期进入规模化增长，但只有一个主要口径。** 赛迪顾问给出：2025 年中国 Data Agent 市场 16.8 亿元，2026 上半年 18.3 亿元，2026 全年预计 40.2 亿元；其中数据分析智能体占 35%、数据治理智能体占 24%。这是单一机构的测算口径，尚缺第二家可比数据，引用时应标注来源与口径。（赛迪顾问 2026-11-19）
5. **产品格局分成四个阵营，且正在向平台内置收敛。** 云厂商平台型（阿里云 DataWorks Data Agent、火山引擎 Data Agent）、BI 增强型（瓴羊 Quick BI、Smartbi、观远、衡石、帆软）、开源/湖仓原生型（WrenAI、PandasAI、Databricks Genie、Snowflake Cortex、Fabric Data Agent）、企业自建 Skill 型（高德、淘宝、1688、得物）。海外大厂已把 Data Agent 做成数据平台的默认能力，国内则更强调私有化与信创适配。（阿里云 2026-11；火山引擎 2025-06；衡石 2026；得物技术 2026-09-16）
6. **效果数字普遍是团队自述，需统一打折。** 高德 L2 准确率 85%+ 与 WAU 450、Anthropic 95% 自动化/95% 准确率、1688「24 小时交付」、淘宝「30–120 秒降至 3–10 秒」均无第三方复现；同一篇高德文章中「12% 差异」（小标题）与「约 10%」（正文）并存，verify-data 的「2–4 小时降至 30 分钟」与「15–30 分钟」统计对象不同。相对可信的是公开基准 + 开源的 HarnessSQL：Spider 2.0-SQLite 45.2%，基线 15.5%。（高德 2026-11-05；Anthropic 2026-06；天猫 2026-09-05；新智元 2026-11-03）
7. **落地顺序应是「场景 → 语义 → 评测 → 单 Agent → 编排」，不是反过来。** 多篇实践共同给出的起步顺序：挑一个真实高频窄场景，先把 10 个核心指标的口径结构化，建一个小评测集，再引入 Skill/Harness 与人工确认点，最后才谈多 Agent 和 L3 自主编排。高德特别提醒「L4 不等于无人化」——即使在较高自主级别，人仍参与关键取舍并带回执行反馈。（曹犟 2026-09-03；高德 2026-10-01；得物技术 2026-06-17）

## 一、全景：Data Agent 是什么

### 1.1 四种主流含义辨析

「Data Agent」这个词在 2025–2026 年被四种语境同时使用，混用是造成预期错配和选型失误的首要原因。

| 语境 | 一句话定义 | 代表来源/产品 | 典型说法 |
|---|---|---|---|
| **通用概念 / 学术对象** | 以 LLM 为核心、能编排 Data+AI 生态完成复杂数据任务的自主系统，覆盖数据管理、准备、分析全链路 | arXiv 2510.23587《A Survey of Data Agents》、Awesome Data Agents 仓库 | 「数据智能体」「自主数据分析系统」 |
| **云厂商品牌产品** | 云厂把数据开发、治理、问数能力封装成可售卖的「AI 数据分析师」 | 阿里云 DataWorks Data Agent、火山引擎 Data Agent、Microsoft Fabric Data Agent | 「企业的第一位 AI 数据专家」 |
| **ChatBI / Agent BI** | 以自然语言问数为入口，向归因、报告、执行闭环演进的对话式 BI | 瓴羊 Quick BI、Smartbi 白泽、观远、衡石、帆软 FineChatBI | 「智能问数」「Agentic BI」 |
| **开源框架 / SaaS 工具** | 面向开发者与分析师的 NL→SQL/Python 执行工具，常配语义层 | WrenAI、PandasAI、Julius AI、Databricks Genie、Snowflake Cortex Analyst | 「对话式数据分析」「Text-to-SQL 工具」 |

（arXiv 2025-10-27；阿里云 2026-11；火山引擎 2025-06；衡石科技 2026；WrenAI/Julius 官网 2026）

**本文所指**：以企业数据资产和业务语义为上下文，能自主完成「理解问题 → 找数取数 → 校验 → 解读归因 → 交付判断 → 反馈回流」多步链路的 AI 系统；单纯的 NL→SQL 生成器和固定看板不在其列。

学术综述对术语混乱有直接批评：Data Agent 一词把「简单查询响应器」与「复杂自主架构」混为一谈，导致用户预期错配、责任界定困难与产业沟通屏障；为此该综述提出首个系统性的六层分级（arXiv 2510.23587）。

### 1.2 一个工作定义与一个能力公式

把多篇一手实践并行对照，可以给出一个工程可用的定义：

> **Data Agent = 语义层（知道真相在哪）× 工具执行（能取数、能算、能调度）× 验证闭环（知道自己什么时候错）× 记忆与反馈（下次不再犯同样的错）。**

四项中任一项接近零，整体价值明显下降——这解释了四种常见失败：

- 有工具执行没语义层：**SQL 能跑，数据不对**（淘宝、Ontology 落地篇反复出现的失败模式）；
- 有语义层没验证闭环：**口径对了但结果陈旧、检索失败无人察觉**（Anthropic 三大错误模式）；
- 有执行没记忆：**每次接新任务都像新人第一天入职**（得物 Hermes、腾讯 Ontology 文章的共同痛点）；
- 有答案没业务翻译：**会念数字的是复读机**（高德下篇）。

```
业务问题（A）
   ↓ 降维：意图澄清 → 指标/语义消歧 → 计划
数据需求（C） → 取数执行（D） → 校验门禁
   ↑ 升维：做减法配参照 → 归因 → 判断 → 业务结论（A）
                    ↓
              证据/反馈回流到语义层与规则包
```

### 1.3 分级：学术 L0–L5 与厂商口径的对照

arXiv 2510.23587（2025-10 首发，2026-11 更新 v3）借鉴自动驾驶 SAE J3016，按「主导权与责任从人转移到 Agent 的程度」划分六层：

| 级别 | 自主程度 | 人的角色 | Agent 的角色 | 典型能力 |
|---|---|---|---|---|
| **L0** | 无自主 | 主导者（亲自动手） | 不存在 | 人写 SQL、清洗、可视化、解读 |
| **L1** | 辅助 | 主导者（整合结果） | 响应者 | 无状态问答、生成代码片段、给建议 |
| **L2** | 部分自主 | 主导者（编排流程） | 流程执行者 | 感知环境、调工具、有记忆，在既定流程内执行 |
| **L3** | 条件自主 | 监督者 | 主导者 | 自主编排端到端数据流水线，处理多样任务 |
| **L4** | 高度自主 | 旁观者（委托） | 主动主导者 | 自主发现值得查的问题，无需监督与显式指令 |
| **L5** | 完全自主 | 无 | 生成式主导者 | 发明新方法、新范式，推动数据科学边界 |

（arXiv 2510.23587；Awesome Data Agents 配套仓库）

该综述判断：**当前最关键的技术跃迁是 L2→L3**——从「在人类定义的工作流内执行」变为「自主编排跨域流程」，需要战略推理、动态工具演进与全生命周期覆盖的突破。L4/L5 仍属愿景。

厂商口径则是另一套坐标系，不可直接换算：

| 来源 | 分级定义 | 自述当前位置 | 注意事项 |
|---|---|---|---|
| 高德商业智能中心（2026-11-05 / 10-01） | L2=SQL 取数跑准；L3=回答业务问题；L4=给靠谱判断、接决策行动 | 商业智能中心处于 L2 向 L3/L4 迈进；本地生活大部分任务达 L3、部分 L4 | 明确「L4 不等于无人化，人仍参与关键取舍」 |
| 快手（2026-09-08） | 需求成熟度 L1 辅助/L2 协同/L3 自主；能力成熟度 M1 Demo/M2 试用/M3 规模应用（准确率>85%）/M4 成熟无需人工 | 未明确宣布当前 M 级 | >85% 是 M3 的定义阈值，不是实测准确率 |
| 火山引擎（2025-06） | 自称 L3 级智能体 | L3 | 强调「从发生了什么到如何行动」，未给细分级别定义 |
| 衡石等 BI 厂商（2026） | 用 L1 告警洞察/L2 增强分析/L3 任务执行等标签做榜单 | 厂商自评 | 榜单由厂方发布，评分与排序需打折 |

**结论**：做能力与采购沟通时，建议以学术 L0–L5 为共同语言，把厂商自称级别作为「营销定位」而非技术事实。

### 1.4 概念谱系：从报表 BI 到 Data×AI

```
报表 BI（人定义看板）
   → 自助 BI / 大数据平台（人拖拽、人写 SQL）
   → ChatBI（NL→SQL→图表，一问一答）
   → Agent BI（多步分析、归因、报告、执行闭环）
   → Data Agent（语义底座 + 工具执行 + 验证 + 记忆）
   → Autonomous Data Team（前瞻：主动发现问题、自组织分工）
```

赛迪顾问用「Data+AI → Data×AI」描述这一变化：数据不再只是被模型读取的素材，模型反过来重塑数据的治理与消费方式，价值路径从「人找数、人看数」转向「智能体用数、智能体行动」。（赛迪顾问 2026-11-10）

### 1.5 为什么是 2026 年

三组可核查的背景信号：

1. **数据规模与调用量**：赛迪援引数据显示，中国数据生成总量 2023–2025 年同比增速分别为 22.4%、25.0%、27.3%；日均 Token 调用量从 2024 年初至 2026 年 3 月末增长超过 1400 倍。（赛迪顾问 2026-11-10）
2. **模型能力外溢**：长上下文、多模态、复杂推理、工具调用与多智能体协同成熟，使「模型调用 SQL/Python/API 并根据反馈调整」成为可用工程手段。（赛迪顾问 2026-11-10；arXiv 2026）
3. **企业侧压力**：BI 范式自 2003 年前后确立后二十年变化有限；数据堆积成成本账单，业务方要求「人人可用数据」，数据团队则被临时取数淹没。（高德 2026-11-05；Anthropic 2026-06）
4. **厂商推动**：火山引擎 2025 年 4 月推出 Data Agent 并开放体验中心，阿里云 DataWorks Data Agent 2026 年 5 月 28 日起正式商业化收费，Gartner 把 Agentic AI 列入 2025 年十大技术趋势。（火山引擎 2025-06；阿里云 2026-11；Gartner 转引 2025-06）

### 1.6 与相邻概念的边界

| 概念 | 上下文 | 工具 | 交付物 | 与 Data Agent 的区别 |
|---|---|---|---|---|
| 通用 Agent / Coding Agent | 代码库、文件系统 | Shell、编辑器、测试 | 代码变更 | Data Agent 的上下文是业务语义与数据资产，错误代价体现在「数字错但格式对」 |
| Chatbot | 会话 | 检索、生成 | 文本 | 无环境感知、无执行、无验证 |
| BI 平台 | 看板与报表 | 拖拽、SQL | 图表 | 由人定义口径与视图；Data Agent 负责把问题翻译到口径 |
| 数据分析师 | 业务背景 + 数据工具 | SQL、Python、PPT | 判断与建议 | Data Agent 的目标不是替代判断，而是把判断前的准备做完（得物 Hermes 边界定义） |
| 数据治理平台 | 元数据、质量规则 | 规则引擎、调度 | 治理动作 | Data Agent 消费治理成果，并把消费反馈回灌治理优先级（得物指标平台 4.0） |

## 二、结构拆解：一个 Data Agent 系统的四个坐标

理解任何一款 Data Agent 产品，都可以从四个坐标切入：**做什么任务、自主到什么程度、相信什么真相、如何验证**。这四个坐标也是后文产品与案例章节的通用坐标系。

### 2.1 坐标一：任务对象

| 任务类型 | 典型问题 | 代表实践 | 赛迪场景成熟度 |
|---|---|---|---|
| 智能问数 | 「昨天 GMV 多少？」 | 高德 L2、淘宝 NL2SQL、得物 Text2SQL | 客户服务、智能营销、风控合规为高成熟场景 |
| 归因诊断 | 「GMV 为什么跌了？」 | 淘宝波动归因、高德假设-验证循环、高德本地生活经营诊断 | 政企决策、运维、生产、供应链为中等成熟 |
| 预测与策略 | 「下季度库存怎么配？」 | 火山智能营销 Agent、观远销量预测 | 同上 |
| 数据研发交付 | 「把这个埋点需求落成表」 | 1688 Multi-Agent、Copilot 24h、得物 Hermes | 创新和研发管理成熟度偏低 |
| 数据质量验数 | 「新表与基准表口径一致吗？」 | verify-data Skill、Data Harness Checklist | 数据治理智能体占 2026H1 市场 24% |
| 训练数据工程 | 「自动找数、清洗、组数据」 | DataMaster 数据树/数据池 | 学术前沿 |

（赛迪顾问 2026-11-10；各案例原文）

赛迪把渗透率结构概括为「前端较强、后端偏弱、生产和研发待突破」：客户服务、智能营销、风险合规已形成商业化闭环；自动化运维、政企决策、智能化生产、供应链管控受数据孤岛与系统改造成本制约；创新研发以头部试点为主。（赛迪顾问 2026-11-10）

### 2.2 坐标二：自主性与责任转移

学术分级真正刻画的不是功能清单，而是**责任归属**：L1 人对结果负全责；L2 人编排流程、Agent 执行步骤；L3 Agent 主导编排、人监督；L4 人委托并旁观；L5 人退场。这一坐标直接决定三项设计：

- **确认点放在哪里**：L2 的确认点在流程节点，L3 的确认点在异常与高风险动作，L4 的确认点退化为事后审计；
- **出错时的回滚粒度**：越接近自主，越需要 run log、handoff、artifact、open questions 四类恢复资产（Harness-Engineering-Booklet 第 23 章）；
- **评测口径怎么定**：L2 评测 SQL 准确率，L3 评测任务完成率与归因质量，L4 评测主动发现问题的命中率。

高德的提醒值得放在这里：**「L4 不等于无人化」**——系统自主完成分析与建议，人仍参与关键取舍并把执行结果带回系统。（高德 2026-10-01）

### 2.3 坐标三：真相源与语义层

所有一线案例都在解决同一件事：**把散落在人脑、文档、SQL、血缘里的业务知识，变成 AI 能检索、能核对、能追溯到源头的资产。**

Anthropic 给出的真相源优先级是一个可直接复用的排序：

```
语义层（强制首选）
  → 血缘与转换图 / 表排名
  → 查询语料库（供人精选，不直接喂给 Agent）
  → 业务上下文 / 公司知识图谱
```

（Anthropic 2026-06）

三家中国团队的落地形态各有侧重：

| 团队 | 语义资产形态 | 核心机制 | 关键结论 |
|---|---|---|---|
| 高德（2026-11） | 官方指标词典 + 行业知识文件 + 固定版本知识快照 | NL2Metric2SQL：先召回指标，再对应表字段 | 「收入」躺着应付 GMV、实付 GMV、核销 GMV 三个口径 |
| 淘宝（2026-09） | 六层知识体系 + WrenAI MDL + Hologres | NL2MDL2SQL，SQL 生成后经语义层校验字段/口径/可复用性 | 直接 Text-to-SQL 有幻觉字段、口径错误、不可复用三宗罪 |
| 得物（2026-09-16） | 指标字典 + OneData 资产 + 结构化知识库 | 业务侧「沉淀→观察→转正」；数仓侧四步收敛到域内精品宽表；产品侧 YAML 批量生成 + 二义性拦截 | 语义标注密度决定 Text2SQL 准确率上限；覆盖率分母必须锁定认证资产目录 |
| Ontology 团队（2026-11-07/13） | 五类本体知识（表、字段语义、指标口径、业务规则、生产证据） | 本体资产 + 七路按需召回 + 三条反馈链路飞轮；规则可追溯到线上代码 | 「数据库管数据在哪，语义层管口径统一，本体管让 AI 具备写对 SQL 的完整业务理解」 |

一个高价值细节：得物明确反对「一次性全量收编指标」——早期尝试把梳理出的全部指标推入数仓开发，资源撑不住且多为离散定制口径；改为长尾指标先登记、复用次数上升后再「转正」。（得物技术 2026-09-16）

### 2.4 坐标四：验证与可信闭环

Data Agent 与 ChatBI 最大的工程差异在验证层。四类验证机制反复出现：

1. **口径对账（reconciliation）**：Data Harness 要求每个 count 有口径、每个输出能回到输入；示例口径卡片为 Input 10,000 → valid phone 9,820 → unique phones 9,100 → duplicate 720 → Output 9,100 → Rejected 180。（Harness-Engineering-Booklet 第 22 章）
2. **七项数据验证**：schema 检查、空值检查、唯一键检查、count 对齐、抽样复核、输出文件打开检查、业务口径复述；同一 booklet 列出 Data Agent 七类常见失败（count 不一致、去重口径错误、字段类型误判、时间窗口错、混用业务口径、空值处理不清、输出表无法复查）。
3. **在线对抗式审查**：Anthropic 的对抗式审查使评测集准确率提升 6 个百分点，代价是多消耗 32% token、延迟增加 72%；其「溯源页脚 + 被动监控 + 主动收割纠正并开 PR 回流」构成在线闭环。（Anthropic 2026-06）
4. **证据化判断**：高德下篇要求 check list + 留推断证据，作者实测在上下文不爆炸时 90%+ 会执行；并强调「敢说证据不足，先不下结论」。（高德 2026-11-05）

一个反直觉发现：Anthropic 的消融实验显示，把成千上万条历史查询的原始检索权限交给 Agent，准确率提升不到 1 个百分点；让 LLM 自动生成指标定义给语义层冷启动是净负向。结论是——**查询历史是供人精选的原材料，不是 Agent 的真相源；定义由人掌管，Claude 负责生成文档。**（Anthropic 2026-06）

## 三、技术架构

### 3.1 总体分层

把各案例的架构图叠在一起，可以得到一个六层参考栈：

```
① 接入与意图层   自然语言 / IM / 定时任务 → 意图识别 → 澄清与参数包
② 语义与知识层   指标字典 / MDL / Ontology / 血缘 / 规则包 / 会话记忆
③ 规划编排层     Supervisor 路由 / ReAct 循环 / 任务分解 / 人工确认点
④ 工具执行层     SQL / Python / 调度 API / 元数据 / 外部检索（MCP）
⑤ 验证门禁层     语法与权限校验 / count 对齐 / 对抗审查 / 预演 / 三档结论
⑥ 交付与反馈层   数字 / 图表 / 报告 / 判断与置信度 → 反馈池 → 语义层与规则包
```

（综合：高德 2026-11；淘宝 2026-09；得物 2026-06/09；数据研发 Harness 2026-07）

### 3.2 两段翻译：高德 CFHL 与六步往返

高德把一次分析定义为「降维 + 升维」两段往返翻译，这是目前最完整的业务侧心智模型：

**降维（A 业务需求 → B 分析需求 → C 数据需求 → D 数字结果）**

1. **A→B**：厘清目标与方法，补齐记忆系统、知识库/知识图谱、意图识别与澄清、任务规划四项能力，产出《详细分析需求》；
2. **B→C**：主线 NL2Metric2SQL（列查数目标 → 官方指标词典召回候选 → 对应表字段 → SQL 构建 → 门禁校验）；支线 NL2SQL（无指标定义 → 寻找可解数据表 → 理解元数据 → SQL 构建 → 门禁校验）；
3. **C→D**：执行 + 强制体检门禁（常识边界：比率 0–100%、点击率不可能 40%、分母不为零）。

**升维（D 数字结果 → C 数据解读 → B 分析判断 → A 业务结论）**

4. **D→C**：先做减法（几十个数只留三五个），再配参照（高低、离目标差多少）；异动识别方法包成「武器库」，每件标作用、射程、实战，由 AI 读业务背景后自选；
5. **C→B**：异步场景走假设-验证循环（提假设 → 取数验证 → 排除混淆 → 留证据 → 再迭代）；
6. **B→A**：翻成可拍板的判断与动作建议，依靠业务 sense（盘子多大、本季目标、可动用资源、落到谁头上、现实约束），并标置信度。

总框架 **CFHL** = 补知识 Context + 补能力 Function + 卡校验 Harness + 留兜底 Loop；团队自述口诀是「脑子里有货、手上有活、心里有尺、事后有账」。（高德 2026-11-05）

高德给出的可靠性算账值得单独记住：每步 99% 准确时，10 步后仅剩 90.44%，50 步后约 60%，100 步后仅三成多——这是数学连乘推算而非实测，但解释了为什么长链路必须设门禁和兜底。同时团队承认线上仍有 1%–3% 任务中 LLM 会幻想出不存在的表和字段。（高德 2026-11-05，团队自述）

### 3.3 语义层技术路线：NL2SQL → NL2Metric/MDL2SQL → Ontology

三条路线在资料中构成明显的演进关系：

| 路线 | 做法 | 优点 | 局限 | 代表 |
|---|---|---|---|---|
| Text-to-SQL / NL2SQL | 自然语言直接生成 SQL | 起步快、Demo 效果好 | 幻觉字段、口径错误、不可复用 | 早期 ChatBI |
| NL2Metric2SQL / NL2MDL2SQL | 先映射到官方指标或语义模型（MDL），再生成并校验 SQL | 口径统一、字段存在性可校验 | 依赖指标/语义资产建设 | 高德、淘宝、得物、Snowflake Cortex |
| Ontology 驱动 | 把表、字段语义、指标口径、业务规则、生产证据建成可追溯本体，按需召回 | 能处理「SQL 能跑但数据不对」的隐性规则 | 建设成本高，需从生产代码抽取与持续校准 | OntSQL Agent、EvoOntology |

淘宝的 NL2MDL2SQL 实现细节最有工程参考价值：WrenAI MDL 语义层包含 `mdl.json` / `dry_plan` / `recall` / `fetch_context`；生成 SQL 后经语义层校验字段存在、口径正确、可复用；Hologres 外部表直读 ODPS，把单次 SQL 从 30–120 秒降到 3–10 秒，切库自愈最多增加 3 秒（团队自报）。六层知识体系为 L1 能力清单、L2 SQL 模板、L3 编写规则、L4 血缘关系、L5 指标注册表、L6 会话记忆。（天猫技术 2026-09-05）

Ontology 路线强调「按需召回 + 渐进式披露」：一次召回为七路并行，给材料而不给硬规则；本体含五类知识，四成表靠血缘分析找出；三道抽取校验为对指纹、回溯 SQL、查格式；规则可追溯到线上代码具体位置。同团队落地篇的提醒是：一个经营分析需求常串起数十甚至上百张表，同一数据域有十余张相似表且粒度各异，典型错误是选错表、用错字段、口径对不上——「SQL 能正常执行、能返回结果、不报任何错，但数据就是不对」。（Ontology 原理 2026-11-07；淘宝落地 2026-11-13）

### 3.4 编排：多 Agent、ReAct，以及「单 Agent + 多 Skill」的反例

**多 Agent 路线**：淘宝用 Supervisor 统一调度，避免巨大 system prompt 与几十个工具的上下文膨胀，子 Agent 在 ReAct 循环（Thought → Action → Result）中自主决定工具与参数；1688 设五个角色——老架（调度验收）、小需（需求澄清）、小研（建模研发）、CR Agent（独立审查）、小验（测试发布），并通过「一个需求 = 一个 issue、reassign 驱动流转、@mention 触发」把协作落进平台。（天猫技术 2026-09-05；1688 2026-07-15）

**单 Agent + 多 Skill 路线**：得物 Hermes 明确比较了三种方案后，选择「单 Agent 编排 + 多能力模块 + 看板确认点」，理由是这类数据研发链路更需要统一上下文与统一状态机；多 Agent 拆分会带来上下文同步、责任归属和状态恢复成本，「容易把流程问题拆成协作问题」。（得物技术 2026-06-17）

这是一个重要的取舍点：**是否拆成多 Agent，取决于任务是否需要并行与角色隔离，而不是为了显得先进。** 高德 CFHL 用「补能力 Function」而非多角色；Copilot 需求交付 Skill 用 P1–P4 四阶段 Spec 链把有状态服务降为无状态服务，同样没有引入多 Agent。（高德 2026-11-05；直播技术数据 2026-07-21）

### 3.5 Harness 工程：从「能跑」到「可信」

「Agent = Model + Harness，模型决定上限，Harness 决定下限」是本轮资料中出现频率最高的工程命题之一。（数据研发 Harness 2026-07-16）

数据研发 Harness 实践把系统拆成三层与六大支柱：

```
身份层（Identity）        执行前：角色、边界、红线
执行层（Orchestration / Context / Gate / Recovery）
                         执行时：路径规划、上下文加载、门禁、状态追踪、故障恢复
进化层（Evolution）       执行后：经验沉淀、规则回写、身份增强
```

其递进逻辑为「身份定形 → 可靠执行 → 进化增强 → 身份增强（螺旋上升）」；行为约束采用三层金字塔，顶层是「超级红线」，规则被违背记为错误、同类错误反复出现升级为红线，红线过严可降级。子 Agent 采用独立会话隔离、信息分舱、物理文件隔离；据团队自述，3 张 ADS 表由 3 个代码专家并行出代码比串行快 3 倍（无样本量与基线说明，需打折）。（数据研发 Harness 2026-07-16）

Data Harness 则给出更「接地气」的可操作清单：三条铁律（原始数据不可变、口径先于计算、每个输出都能追溯）+ Count Reconciliation + 七项验证 + Data Task Checklist；其原则句是「数据任务最怕『口径错但格式对』」「Agent 最后应该报告数字，而不是只说『已生成』」。（Harness-Engineering-Booklet 第 22 章）

### 3.6 训练侧前沿：把交互环境纳入训练闭环

HarnessSQL（港科大与微软等团队）是本轮资料中可复现性最高的工作：论文、公开基准与代码齐备（GitHub: YangHaolin0526/HarnessSQL）。它解决「训练与部署脱节 Train–Deploy Mismatch」，三大基石为：

1. **密闭 SQL 执行沙盒 + 蓝图合成**：基于 Spider 2.0-Lite（30 个 SQLite）与 DBT（49 个 DuckDB）构建 79 个复杂数据库沙盒；只读绑定、单语句约束、60 秒超时；先用 SQL-First 提取 Schema/样本值/外键路径，采样可执行 SQL，再反向生成自然语言问题与验证 Oracle；
2. **极简 SQL Harness 契约**：改造 DeepSeek-Harness 为四元动作契约，避免繁杂 Bash 工具导致注意力涣散；协议校验只读权限、语法合规、无死循环、T 步内显式提交；
3. **两阶段长程后训练**：全轨迹长程 SFT 冷启动（教师探索、Oracle 验证筛选）+ 执行奖励 RL（DAPO，二值奖励：结果等价且合规得 1，报错/超时/不符得 0，无人工 Reward Shaping）。

论文数据（团队自报、媒体转述，但可回溯）：HarnessSQL-8B 在 Spider 2.0-SQLite 执行准确率 45.2%，为同底座基线 15.5% 的近 3 倍，超过 OmniSQL-32B（14.8%）、Arctic-Text2SQL-32B（16.3%）；14B 达 54.8%；LiveSQLBench 上 8B 24.8%、14B 28.5%，为全部 32B 基线（7.0%–8.9%）的 3–4 倍。消融显示：直接 RL 15.5%→20.0%，仅 SFT 8B 30.4%，非交互式 SFT + DSH 推理仅 9.6%（低于未微调基座），上下文 8K→32K 时 27.4%→45.2%。（新智元 2026-11-03）

这结论对工程选型的含义是：**不要只在部署侧套 Harness；如果做自有模型微调，训练环境必须与部署环境同构。**

DataMaster 则从数据侧给出另一条自迭代路径：固定模型与训练算法，让 AI 用「数据树（每次数据工程尝试为节点）+ 数据池（可复用数据源）+ 全局记忆（尝试、分数、失败原因、可复用策略）」自主找数与清洗。论文数据为奖牌率 35.91%→68.18%、平均分 8.47%→31.17%、GPQA 18.75%→31.02%（超过专家指令模型参考 30.35%），但 PostTrainBench 整体均分专家指令模型仍更高；7479 条训练样本经泄漏检查无精确/模糊匹配。（DataMaster 2026-06-03）

| HarnessSQL | 公开基准 + 变异测试 + Oracle | 8K→32K 上下文带来 17.8pp 提升 |

（天猫技术 2026-09-05；Anthropic 2026-06；1688 2026-07-15；得物技术 2026-09-16；新智元 2026-11-03）

一个常见误区是只看「静态快照准确率」。得物给出纵向证据：随着语义标注密度与二义性检测能力上线，系统测评准确率从 85%+ → 90%+ → 95%+，提升节奏与语义层治理动作逐一对应，不是自然波动。（得物技术 2026-09-16）

为避免不同厂商的「准确率」各说各话，建议把评测拆成五个可分别验收的指标：

| 指标 | 定义 | 计算口径建议 | 对应自主级别 |
|---|---|---|---|
| 意图识别准确率 | 用户问题被正确归类到任务类型与参数包的比例 | 人工标注问题集上的分类准确率 | L1–L2 |
| 取数/SQL 执行准确率 | 生成查询可执行且结果集等价的比例 | 公开基准（如 Spider 2.0）或 Golden Dataset 执行比对 | L2 |
| 口径一致性 | 结果与官方指标定义、时间窗口、过滤条件一致的比例 | 由业务口径 Owner 抽查，不能由数仓侧自评 | L2–L3 |
| 任务完成率 | 端到端问题无需人工返工即交付的比例 | 「一次通过」而非「最终修对」作分子 | L3 |
| 归因/判断可采信率 | 归因链有证据支撑、结论被业务采纳的比例 | 人工评审 + 采纳记录 + 置信度校准 | L3–L4 |

（综合：淘宝 6D 评测、Anthropic 验证层、得物双口径抽查、1688 四维度冒烟）

### 3.8 上下文工程：渐进式披露与无状态化

- **渐进式披露（Progressive Disclosure）**：Ontology 路线强调「召回给的是材料，不是硬规则」；得物 Hermes 把会议纪要按「路径结论、研发反馈、待澄清问题、风险信号」四类结构化后写入工作区，不把聊天全文塞进长期记忆；Copilot 需求交付 Skill 用 P1–P4 Spec 链把上下文固化。（Ontology 原理 2026-11-07；得物技术 2026-06-17；直播技术数据 2026-07-21）
- **无状态化**：Copilot 的 P4 交付物是自包含结构化 Prompt，把 Copilot 从「有状态」降为「无状态」服务，使多需求可并行推进、人只在 P1 确认与 P3 CR 介入；团队自述简单取数约十分钟可得主体框架正确的代码，复杂需求仅写 Prompt 准备就半小时起步。（直播技术数据 2026-07-21）
- **上下文不是越多越好**：Anthropic 的历史查询原始检索 <1pp 增益、高德「上下文不爆炸时 checklist 90%+ 执行」的前提，都指向同一取舍——上下文质量比数量重要。（Anthropic 2026-06；高德 2026-11-05）

## 五、典型落地案例

本章是全篇的证据主体。每个案例按「场景 → 架构 → 数字 → 证据强度」展开；所有效果数字均按原文口径标注，团队自报者不再重复提醒，统一见第十章边界说明。

### 5.1 高德 DataAgent：从业务问题到可信数据，再到业务决策

**场景**：商业智能中心日常经营问数与归因，系统已日常运行。（高德 2026-11-05 上/下篇）

**架构**：见 3.2 的 A→B→C→D→C→B→A 六步往返与 CFHL 框架。降维段用 NL2Metric2SQL 主线 + NL2SQL 支线；升维段用「先做减法再配参照 → 武器库归因 → 假设-验证循环 → 置信度标注」。

**关键数字（团队自报）**：WAU 约 450 人；L2 智能问数准确率稳定在 85% 以上；线上 1%–3% 任务出现幻想表/字段；check list + 留证据机制在上下文不爆炸时 90%+ 会执行；「收入」有三个口径（应付 GMV、实付 GMV、核销 GMV）。

**最值得记住的三句话**：

> 「能跑通 SQL 取数的很多，能跑准的也不少（L2 阶段），但能真正回答业务问题、给出靠谱判断的很少。」

> 「会念数字的是复读机，会挑重点、给基准才是分析师。」

> 「能查数的工具很多，敢说『证据不足，我先不下结论』的很少。」

**证据强度**：一手长文、架构描述详细，但所有效果数字为其团队自报，无公开评测集与第三方复现；连乘衰减为数学推算。

### 5.2 高德本地生活：BI 能力 L0–L4 与经营判断层

**场景**：FY27 S1 全业务单元例行经营诊断与行业简报。（高德 2026-10-01）

**架构**：三层框架——基础底座（知识/语义、固定版本知识快照）→ 分析能力层（Skills 写方法、Pipeline 连步骤：经营状态识别 → 归因诊断 → 策略研判 → 跟踪复盘）→ 经营判断层（经营环 + 战略环，命题中枢路由；Agentic loop 按发现补证据、查反证、调路径）。知识被拆为「稳定行业文件 + 时效主题文件」，指标口径更新 Pipeline 以业务顶层看板口径为权威源反向追踪。

**L0–L4 定义（正文明确给出的部分）**：L2 智能问数（解决 30%+ 需求）；L3 回答「为什么下降」（沿业务链路排查并拿证据，绝大部分任务已具备）；L4 接决策与行动（部分场景已达，不等于无人化）。L0/L1 的文字定义仅在原图 2 中，本文不复述。

**关键数字（团队自报，且存在口径冲突）**：L2 解决 30%+ 需求；全行业一轮报告 ≤1 小时；过去每业务单元人工约 1 小时、一轮约 22 人时，按 1 小时折算批量效率约 22 倍；某次交付批次为「11 份报告」；同一指标差异小标题写 12%、正文举例约 10%——因分子分母来自两套数据源、统计范围未对齐，两个数字并列保留。

**判断**：这是目前把「分析执行 → 知识复用 → 经营判断」三层讲得最完整的公开案例，但其效率倍数是折算而非实测，不宜当作 ROI 基准。

### 5.3 淘宝百亿补贴：NL2MDL2SQL + 多 Agent + ReAct

**场景**：bybt-data-analysis-assistant 提供 NL2SQL 取数、波动归因、血缘溯源、Python 分析。（天猫技术 2026-09-05）

**架构**：意图识别（一次 LLM 输出标准化参数包，失败降级关键词+规则）→ Supervisor 多 Agent 调度 → ReAct 推理循环 → 四阶段知识检索 → NL2MDL2SQL（WrenAI MDL + 语义校验）→ Hologres 加速。知识体系三层：应用层 6 类检索工具、采集层（AST 血缘 6-Phase、指标注册、Onboard 5 步）、存储层六层 L1–L6。评测为 6D 维度 + Golden Dataset + 意图感知权重 + 节点级归因。

**关键数字（团队自报）**：ODPS 单次 SQL 30–120 秒，一次诊断 5–10 次 SQL、总耗时可超 10 分钟；Hologres 外部表直读加速到 3–10 秒；切库自愈最多 +3 秒；意图识别示例 confidence 0.95（示例参数，非系统准确率）。指标注册表含漏斗/加法/比率三种公式，例如 GMV = IPVUV × CVR × AOV；血缘走 KG 优先、AST 降级链。

**证据强度**：架构细节与失败案例写得具体，但耗时与置信度均为团队自报；0.95 不可当作问数准确率。

### 5.4 Anthropic：95% 分析自动化的四层栈

**场景**：Anthropic 内部业务分析查询自动化。（Anthropic 2026-06，公众号译述）

**架构**：数据基座（维度建模、测试左移、新鲜度与完整性检查）→ 真相源（语义层 → 血缘/表排名 → 查询语料库 → 业务上下文/知识图谱）→ Skills（markdown 文件夹按需读取，为被 LLM 检索而写）→ 验证（离线看板+长尾评测；在线对抗审查、溯源页脚、被动监控、主动收割纠正并开 PR 回流）。

**关键数字（均为 Anthropic 内部评测、无样本量与时点披露）**：95% 业务分析查询由 Claude 自动完成、整体准确率约 95%（两个不同指标）；无 Skills 时准确率不超过 21%，加 Skills 后稳定 95%+，特定域约 99%；对抗式审查 +6pp、token +32%、延迟 +72%；开放历史查询原始检索 <1pp；数据模型有数百选项、潜在字段数百万。

**三大错误模式**：概念与实体歧义、数据陈旧、检索失败。作者明确承认静默失败「还没有一套足够稳健的解法」。

**证据强度**：方法论影响力大，但数字全部来自厂商内部且经二手转述；曹犟在 2026-09-03 文章中转述同一组 21%/95%/<1% 数据，属二手引用而非独立验证。（曹犟 2026-09-03）

### 5.5 得物双案例：指标语义底座与 Hermes 工作流

这两个案例来自 ima 知识库检索，正文关键词复核后纳入，是本次调研相对本地语料的新增素材。

**案例 A：指标平台从语义底座到智能消费**（得物技术 2026-09-16）

- 三条线并行：业务侧「沉淀→观察→转正」攻克隐性指标；数仓侧四步收敛到域内精品宽表（摸清现状 → 血缘核查 → 分批推进 → 域边界协议）；产品侧结构化表单 + AI 识别 + YAML 批量生成 + 二义性拦截。
- 二义性拦截在提报环节做语义相似度检测与口径冲突预警，被作者称为语义底座的「免疫系统」；覆盖率分母锁定精品数据资产目录中经认证/推荐的字段，而非数仓侧自评。
- 关键数字（团队自报）：系统测评 SQL 准确率 85%+ → 90%+ → 95%+，与语义层治理动作同步；分析师人工抽查 90%+；错误归因中条件拼接近五成、口径边界近四分之一、时间解析小于 5%；AI Coding 在某域 OneData 全流程提效 40%+、核心模型开发提效 70%+。

**案例 B：Hermes Agent 重构数仓工作流**（得物技术 2026-06-17）

- 明确边界：Agent 负责把问题整理到足够可判断，人负责业务语义、指标口径、敏感字段、下游影响与生产放行。
- 架构选择：单 Agent 编排 + 多能力模块（素材采集、历史检索、变更预演、发布确认、经验沉淀五类 Skill）+ 看板确认点；工作区留证、看板推状态、规则包沉经验、结构化工具接口验证生产状态。
- 三道门：事实源门、预演门、责任门；缺任何证据只能停在候选方案或待确认状态。
- 效率测算（团队保守测算，非实测）：常规埋点需求数据承接投入从约 0.5–1.0 人日降到 0.1–0.3 人日；复杂需求从 1–2 人日降到 0.3–0.6 人日。作者自己指出下一步要用连续样本证明准备时间、交付周期、评审通过率与返工原因的变化。

**判断**：得物两篇合起来给出一条比「堆 Agent」更现实的路线——先把语义与流程工程做实，再谈自主性；其自评式的克制表述反而提高了可信度。

### 5.6 1688 与 Copilot 24h：组织级 Multi-Agent 与需求交付

**1688 数研飞轮**（1688 2026-07-15）：KST 三支柱——K 知识（元数据知识库、Multi-Agent 配置、经验沉淀库）、S 行为规范（节点输入/输出/验收契约，指令 v1→v5）、T 任务（顺序协作 + 反馈循环 + 人工审批卡点）。Harness 被编码进 CLAUDE.md，形成「知识是变量，Harness 是常量；换场景不换 Harness，只换知识包」。五角色小队、四层 Loop、三道安全网（知识校验、SQL CR 独立审查、置信度评估+降级兜底）。

团队自报数字：200+ 指标手工录入需数周、Agent 扫描+审核数小时；分销域冷启动产出 13 个规则文件、40+ 表描述、1 本 SQL 规范，Agent 扫描约 2 小时出初稿；80% 通用知识可自动提取，20% 潜规则需使用中发现沉淀；平台上线约 6 周、18 支小队跑多轮冒烟，最近一轮 7 支一次性通过；24 条 SQL CR 记录自动沉淀为 Bad Case。注意 18 支与 7 支统计范围不同，不可合并为一个通过率。

**Copilot 需求交付 Skill**（直播技术数据 2026-07-21）：P1 需求澄清 → P2 资源管理 → P3 模型设计（人工 CR）→ P4 自包含结构化 Prompt 交付；P1/P3 为强制确认节点。团队自报「文档清晰、口径准确的临时取数需求」24 小时内交付；Agent 可自动完成 90% 设计工作，但数仓规范再完善也难 100% 遵循，仍需人工 CR。

**关键限定**：24h 只适用于「文档清晰、口径定义准确」的临时取数需求；不可泛化为所有数据需求。原文金句「所有口头共识都是薛定谔的共识」恰好说明了 P1 澄清节点的价值。

### 5.7 数据研发与验数：Ontology、Harness、verify-data

- **Ontology 原理篇**（2026-11-07）：OntSQL Agent = 本体资产 + 按需召回 + 飞轮迭代；五类知识、七路召回、三道校验、三条反馈链路、五层递进检测；标准化为 Turtle/JSON/Markdown + 索引文件，生成日志/采纳统计/反馈/回归测试为独立 Python 模块，不绑定 AI 平台。团队自报效率数字：需求处理量「提升数倍」、AI 代码行占比「个位数→八成以上」、单需求耗时「数人日→约一人日」——无绝对量与基线时点。
- **Ontology 落地篇**（2026-11-13）：淘宝行业经营分析实战，从生产代码自动抽取隐性规则，三元组抽取 + 三道校验，人工仅两处介入（核心表首次进本体复核、线上不对时判断是否为本体问题）；明确「全文未给量化指标」。与原理篇的效率数字形成口径反差，引用时须分别标注。
- **verify-data**（2026-05-28）：端到端验数 Skill，一句话触发自动发现基准表 → 研发表代码逻辑 → 维度指标映射 → 降级验数 → 三批次执行 → 报告发布。两阶段基准表发现（Top-1≥0.7 直接选用，Top-5<0.3 进降级，共 4 种降级策略）；工具含 5 类场景、10 类 SQL 模板、14 个参考文档、19 条踩坑记录；结论分 PASS/WARNING/FAIL 三档。效率口径不一：一处称 2–4 小时压缩到 30 分钟以内，另一处称完整 9 步流程耗时 15–30 分钟——统计对象不同，并列保留。原文金句「标准化比智能化更重要」「踩坑记录是核心资产」。
- **数据研发 Harness**（2026-07-16）：见 3.5；其价值在于把 Multi-Agent 的组织分层与红线机制讲清楚，而非给出可复现的收益数据。

### 5.8 开源学术前沿与平台化旁证

- **HarnessSQL**（2026-11-03）：见 3.6，公开基准 + 开源代码使其在全部案例中可复现性最高；局限是基线由论文方选取，且新智元为第三方转述而非独立复现。
- **DataMaster**（2026-06-03）：见 3.6；论文 + GitHub（sjtu-sai-agents/DataMaster）+ 泄漏检查，证据强度较高，但"GPQA 单项超越"不等于"整体超越"。
- **EvoOntology**（arXiv:2609.15779，腾讯文章 2026-11-14 转述）：面向 Data Agents 的自进化本体层，分 Content/Schema/Tool 三部分，提供 browse/resolve 两类访问，会话初始只给简要说明、按需查询，最终测试前冻结本体。腾讯内部 Bug 定位试验加入图谱后成功率 58%→65%（+7pp），但作者主动打折：样本、任务集、时点未披露，不能换算成完整研发效率提升，也不能单独证明本体语义层贡献全部增益。
- **快手内部 Data Agent**（2026-09-08）：负责人演讲称内部「最有名」的 Data Agent 覆盖报表配置、数据分析、OLAP 洞察，位于统一 AI 基建上层；研发过程数据实时回流「研发大脑」，Agent OS 资产层沉淀 CRI/Skill/知识库。80%+ AI 代码渗透率、30%+ AI 生成代码占比、需求周期下降约 60% 为全公司研发效能口径，**不是 Data Agent 专属指标**；M3 的 >85% 是定义阈值而非实测准确率。
- **「专有的是系统不是模型」**（曹犟 2026-09-03）：以茶饮品牌「公众号线下扫码支付转化漏斗」为例，说明两处歧义（漏斗首步口径、线下扫码场景 ID 定义）模型猜错不会告知，反而给出单位一致、量级也对的数字；落地三步为挑一个真实工作流 → 把口径规则结构化（哪怕先只做 10 个指标）→ 建一个小评测集，之后再谈模型与部署。

**判断（业内判断）**：效率提升真实存在，但现有公开数字大多缺少统一基线、样本范围与失败率分母；更可靠的 ROI 表达应同时给出「覆盖多少任务 × 准确率 × 单次节省时间 × 人工复核成本」。

一个可操作的 ROI 核算框架如下（本文自行归纳，供 POC 阶段填数）：

```
年化净收益 = 任务覆盖率 × 任务量 × 一次通过率 × 单次节省工时 × 工时成本
           - 语义资产建设一次性投入摊销
           - 评测/复核/门禁的人工成本
           - 平台与 Token/算力年成本
```

其中「一次通过率」必须用「无需人工返工即交付」作分子；若用「最终修对」作分子，会把人工隐性投入从成本侧抹掉，这是厂商效率数字普遍偏乐观的主要原因。

## 七、风险、边界与争议

### 7.1 技术风险：静默失败是最大风险

Data Agent 的危险不在于报错，而在于**给出格式正确、量级合理、口径错误的结果**：

- 幻觉表与字段：高德线上仍有 1%–3% 任务出现（团队自报）；
- 概念与实体歧义、数据陈旧、检索失败：Anthropic 总结的三大错误模式；
- 「SQL 能跑、数据不对」：选错表、用错字段、口径对不上，常规测试拦不住（Ontology 落地篇）；
- 长链路可靠性连乘衰减：每步 99%，100 步后仅三成多（数学推算）；
- 上下文爆炸：高德 checklist 执行率 90%+ 的前提是「上下文不爆炸」；
- 评测集污染与静态快照误判：得物强调需纵向观察准确率随语义治理提升的趋势。

把失败模式与可落地的检测/缓解手段对应起来，可以作为架构评审的检查表：

| 失败模式 | 典型表现 | 检测手段 | 缓解机制 |
|---|---|---|---|
| 幻觉表/字段 | 引用不存在的表或列 | Schema 校验、元数据白名单 | 语义层强召回 + 门禁拒绝 |
| 口径边界歧义 | 「新客」「线下扫码」定义猜错 | 二义性检测、口径冲突预警 | 提报阶段拦截 + 执行前二次确认 |
| 数据陈旧 | 数字对但用的是过期快照 | 新鲜度检查、时间戳回显 | Pipeline 保鲜、固定版本知识快照 |
| 检索失败 | 该召回的指标没召回 | 召回命中审计、Top-1/Top-5 阈值 | 降级策略、人工兜底 |
| 条件拼接错误 | 字符串字段用 LIKE/等值而非 FIND_IN_SET | 错误归因分类、字段取值规则 | 元数据显式声明「该怎么被查询」 |
| 时间窗口错 | 用户未带年份，默认年份用错 | 时间解析规则校验 | 语义层固化默认解析规则 |
| 长链路衰减 | 多步后整体正确率骤降 | 逐步校验与中间断言 | 拆短链路、Sprint Contract、Resume 机制 |
| 静默失败 | 无报错但结果错 | 对抗式审查、count 对账、抽样复核 | 溯源页脚、证据化判断、人工确认线 |

（综合：Anthropic 2026-06；得物技术 2026-09-16；Harness-Engineering-Booklet 第 22 章；高德 2026-11-05）

### 7.2 数据安全与权限风险

- **权限继承**：Fabric、Databricks Unity Catalog、Snowflake RBAC、BigQuery「只可见用户已有权限数据」都把权限作为 Agent 的硬边界；自建系统必须显式实现同样的继承，而不是用服务账号通配。
- **工具暴露面**：在 MCP Server 上同时暴露语义工具与原始 `SYSTEM_EXECUTE_SQL` 会让客户端绕过语义视图，应拆分 Server 并用最小权限角色。
- **写入生产**：得物 Hermes 的三道门（事实源、预演、责任）与 1688 的 SQL CR 独立审查，都是针对「Agent 直接写入生产」的防线。
- **审计留痕**：工作区、看板、确认记录、交付快照构成可回放链路；没有留痕的自动化无法追责，也无法把失败转成规则资产。

### 7.3 证据风险：数字口径与自述折扣

| 冲突/易混点 | 具体表现 | 处理方式 |
|---|---|---|
| 同名不同义 | 85% 在高德是 L2 问数准确率，在快手是 M3 定义阈值；95% 在 Anthropic 同时指自动化占比与准确率；得物 95%+ 是 Text2SQL 系统测评 | 保留来源与指标定义，禁止横向平均 |
| 同篇口径冲突 | 高德本地生活 12%（小标题）vs 约 10%（正文）；verify-data 2–4h→30min vs 15–30min | 并列并注明统计范围不同 |
| 折算当实测 | 高德 22 倍是按 1 小时折算；火山「超百倍」是厂商披露 | 标「折算/厂商披露」，不作 ROI 承诺 |
| 厂商自评榜单 | Agentic BI 排行榜由参评厂商发布 | 只取产品清单线索，结论靠 POC |
| 阈值当实测 | 快手 M3 的 >85% 是级别定义 | 明确标注为定义阈值 |

### 7.4 组织与争议

1. **知识沉淀成本被低估**：1688 的经验是 80% 通用知识可扫描提取，剩余 20% 潜规则必须在使用中才发现；得物强调长尾指标「先登记、后转正」。这意味着 Data Agent 不是一次性上线项目，而是持续运营的知识工程。
2. **平台维护成本**：ima 知识库中《智能体工程的隐形技术债》（InfoQ 2026-04）标题本身即提示——10 分钟造一个 Agent 容易，公司要为它养一个平台团队；自建路线必须评估长期维护。
3. **「无人化」叙事的边界**：高德明确 L4 不等于无人化；得物 Hermes 把「不替人拍板」写进架构原则；Anthropic 也承认静默失败无稳健解法。所谓「95% 自动化」指的是任务类型覆盖率，不是无人值守率。
4. **分级营销化**：厂商自称 L3/L4 缺乏统一定义，容易抬高采购预期；应以可验收的任务集和准确率口径替代级别标签。

## 八、选型与落地建议

### 8.1 选型决策树

```
是否已有一套可信的指标字典/语义层？
├─ 否 → 先做语义底座（10 个高频指标 + 血缘核查 + 二义性拦截），暂不采购重型 Agent
└─ 是
   ├─ 已深度绑定某云（阿里云/火山/AWS/Azure/GCP）？
   │    └─ 优先评估云厂商内置 Data Agent，验证权限继承与跨源能力
   ├─ 已有 BI 体系且以报表为主？
   │    └─ 评估 BI 增强型（问数/归因/报告），用自有口径做 POC
   ├─ 强合规/私有化/信创？
   │    └─ 评估国产 BI 私有化方案或开源 WrenAI + 自建语义层
   └─ 有强数据工程团队、场景独特？
        └─ 自建 Skill + Harness，参照得物/1688 的单 Agent+多模块路线
```

### 8.2 分级落地路线

| 阶段 | 目标 | 关键动作 | 退出条件（可验收） |
|---|---|---|---|
| 0 选场景 | 找到高频、口径清晰、可容忍少量错误的窄场景 | 统计近三个月取数/验数请求分布，选 Top 1 | 有明确的问题清单与人工基线耗时 |
| 1 语义底座 | 把高频指标口径结构化 | 核心指标上架、血缘核查、宽表收敛、二义性拦截 | 10 个指标口径唯一、可查、可追溯 |
| 2 评测集 | 建立可复现的验收标准 | Golden Dataset + 多口径准确率（系统测评/人工抽查）+ 错误归因分类 | 评测集覆盖主要问题类型，可重复跑 |
| 3 单 Agent + Skill | 跑通取数→校验→交付闭环 | 流程契约、只读沙盒、门禁、人工确认点、留痕 | 在限定场景达到约定准确率，且错误可回放 |
| 4 编排与记忆 | 从执行流程走向自主编排 | 多 Agent 或 Spec 链、规则包/本体飞轮、对抗式审查 | 任务完成率提升且人工介入点稳定 |
| 5 持续治理 | 消费反哺治理 | 消费热度榜、口径纠正回流、过时检测、回归测试 | 形成「消费越多→治理越准」的闭环 |

（综合：曹犟 2026-09-03；得物 2026-09-16/06-17；1688 2026-07-15；Anthropic 2026-06）

每进入下一阶段前，建议显式检查以下「阶段门」，未通过则退回上一阶段补齐基础设施，而不是靠换更强模型硬推：

| 阶段门 | 必须通过的条件 | 常见不通过原因 |
|---|---|---|
| 场景门 → 语义门 | 场景问题集与人工基线耗时已记录 | 需求太泛，无法定义「答对」 |
| 语义门 → 评测门 | 核心指标口径唯一、可查、可追溯到源头 | 指标字典由数仓侧自评，业务未认证 |
| 评测门 → 执行门 | Golden Dataset 可重复跑，错误可归因到具体环节 | 只有静态快照准确率，无法定位失败点 |
| 执行门 → 编排门 | 限定场景一次通过率达标且错误可回放 | 靠人工在后台反复修正，链路无留痕 |
| 编排门 → 治理门 | 人工介入点稳定、反馈能写回语义层与规则包 | 经验只留在会话里，下次仍从头解释 |

### 8.3 组织与角色

| 角色 | 职责 | 来源依据 |
|---|---|---|
| 业务口径 Owner | 拍板指标定义、边界条件与歧义裁决 | 得物「口径冲突预警」、高德「证据不足不下结论」 |
| 语义/指标工程师 | 维护指标字典、本体、血缘与宽表契约 | 得物三条线、Ontology 五类知识 |
| Agent/Harness 工程师 | 编排、工具契约、门禁、恢复与可观测 | 数据研发 Harness 六大支柱 |
| 评测与审计 | Golden Dataset、评测口径、错误归因、上线门禁 | 淘宝 6D、Anthropic 验证层 |
| 平台/运维 | 权限、成本、缓存、版本与知识保鲜 | 火山/Agent OS、高德知识快照 |

1688 的经验表明，角色分离不必等于多 Agent 拆分；关键是每个角色有明确的输入/输出/验收契约，以及人工审批卡点。

### 8.4 避坑清单

1. 不要从「把数仓接上大模型」开始，先从口径开始。
2. 不要用纯 Text-to-SQL 作为生产方案；至少加一层指标/MDL 语义层。
3. 不要让 LLM 自动生成指标定义做语义层冷启动——Anthropic 评测为净负向。
4. 不要一次性全量收编指标；长尾先登记、按复用度转正。
5. 不要用历史 SQL 原始检索当真相源——增益 <1pp，应由人精选。
6. 不要一上来就拆多 Agent；先判断是否需要并行与角色隔离。
7. 不要只看 Demo 准确率；用自有口径做 POC，并同时看系统测评与人工抽查。
8. 不要把折算倍率、厂商披露当实测 ROI。
9. 不要让 Agent 在无预演、无确认的情况下写入生产。
10. 不要宣称「无人化」；把人工确认点写进架构，并保留可回放证据链。

## 九、趋势判断

> 以下均为【前瞻推演，非既成事实】，依据现有资料的方向性信号归纳，不作为确定性预测。

1. **语义层将成为数据平台的内置能力，而非项目交付物。** Snowflake 语义视图、Databricks 指标视图、WrenAI MCP、得物指标平台都在把「口径」变成平台一等公民；未来采购 Data Agent 可能默认附带语义建模工具。
2. **训练与部署同构会成为自有模型路线的门槛。** HarnessSQL 证明非交互式训练会退化到低于基座水平；做自有 SQL Agent 的团队必须把执行环境纳入训练闭环。
3. **本体与自进化从论文走向工程。** EvoOntology、OntSQL、腾讯三层图谱都在探索「本体按使用反馈修订」，但当前证据仍以内部试验为主，58%→65% 一类数字需打折。
4. **Agent BI 的竞争点从「答得准」转向「闭环完整度」。** 监控发现 → 归因 → 建议 → 对接业务系统执行 → 组织记忆，五个环节中「执行 + 记忆」是当前最薄弱环节。
5. **评测与治理将成为第一采购指标。** 当各家都能演示问数时，差异会转向评测集、口径一致性、可解释性与审计能力；厂商自评榜单的可信度会下降。
6. **市场高速增长但口径分化。** 赛迪的 40.2 亿元预测可能被不同机构用不同口径重复解读，引用时应始终绑定来源与统计范围。
