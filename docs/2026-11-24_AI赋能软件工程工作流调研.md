## 〇、先给结论

把这半年中外材料读成一条脉络，可以压缩成一句话：

**2026 年下半年，行业的关注点已经从「让 AI 写代码」整体迁移到「让 AI 写的代码可信、可维护、可核算」；方法论收敛为「意图/规格前馈 + Harness 控制 + 多轮验证回路 + 度量与成本治理」四层结构，而组织能否吸收这些产出，取代模型能力，成为新的胜负手。**

十条关键判断：

1. **四层框架已基本定型。** 上层用 Spec / 需求契约把意图钉死（前馈）；中层用 Harness（AGENTS.md、Skills、工具、权限、沙箱）约束 Agent 的工作环境；下层用 Loop + 确定性门禁把验证左移并闭环；最外层用 DORA + 返工率 + 评审负荷 + FinOps 核算价值。信通院在 2026 年 9 月把这套思路正式命名为「驾驭工程」，提出连接、编排、循环、效能、安全、评估优化六大能力与 L1–L5 成熟度模型。【A｜信通院 2026-09】

2. **AI 是放大器，不是变压器。** DORA 的核心判断在 2026 年被反复引用：工程基础好的团队更快也更安全，基础差的团队只是更快地制造混乱。多项研究给出同向结论——绿地/边界清晰任务收益约 30%–40%，存量复杂代码低于 10%；组织级 DORA 指标并未随个人体感同步改善。【C/D｜DORA 2026 ROI 报告，页面最后更新 2026-04-22；C｜Faros AI 2026 转述】

3. **瓶颈从「写」转移到了「审、测、发」。** Faros AI 数据显示评审等待时间增长 91%、PR 体积增长 154%、人均 bug 增长 9%（C，厂商遥测）；GitClear 对 6.23 亿次改动的分析显示块级重复从每百万行 40.3 升至 73.0、重构占比从 21% 降至 3.8%（C，相关性证据）。生成越快，人类评审带宽越成为硬约束——小 PR、证据包、风险分级评审因此从「好习惯」变成「必需品」。

4. **上下文工程从技巧变成架构。** 共识是「渐进式披露」而非全量塞入：OpenAI 把 `AGENTS.md` 压到约 100 行做目录，结构化 `docs/` 才是真正的 system of record；得物 Akashic 用 L1 入口 / L2 文档与 Skill / L3 源码注释三层按需加载（B）。反面证据同样明确：一项覆盖 138 个真实仓库的研究发现，LLM 自动生成的上下文文件反而降低任务成功率并推高 20% 以上推理成本，开发者手写精简版本带来约 +4% 提升（A/预印本）。**`/init` 生成的规则文件是草稿，不是成品。**

5. **验证必须「确定性优先、语义兜底」。** Thoughtworks 的 2×2 模型把控制手段分为 Guides（行动前）/Sensors（行动后）× Computational（确定性、毫秒级）/Inferential（语义判断、模型驱动）；能推到计算格的工作绝不留给人或模型猜（D｜martinfowler.com 2026-04）。窗口内的中国团队实践与之高度一致：独立 subagent 即时 CR、CDP 真实浏览器验证、Figma 视觉走查量化、变异测试识别「永远绿的测试」。【B｜百度质量团队 2026-07】

6. **从「一次性全自动」退回到「多轮反馈回路」是一次理性修正。** 网盘团队明确放弃五阶段一键流水线，改为「观察—决策—修改—验证—复盘」的 Agentic Engineering Loop：先做需求调研与不确定项挂账，执行中分轮验证、全程可观测，人只在关键决策点介入（B｜2026-10）。关键不是「循环比流水线好」，而是**把不确定项显式化，不让它在链路里被当成确定事实一路传递**。

7. **团队级能力的核心是「把个人经验变成可审查的资产」。** Prompt 要有 Review、经验要进 Skill、过程要可观测、结果要回写知识库。得物 EP-Harness 用 Issue 管任务、Workflow 管规则、Skills 管经验（B｜2026-08）；得物 Akashic 把代码变更检查与会话提炼接入 Git Hook，候选知识经 Session Agent 提炼、Audit Agent 复核、Owner 审核后以 MR 回写（B｜2026-11）；Uber 自报已有 3600+ Skills、日均 3 万+ 次技能执行（C）。

8. **度量要盯「结果」不要盯「活动」。** LOC、PR 数、prompt 次数、acceptance rate 在 Agent 时代必然上涨，与价值无关。建议记分卡覆盖交付（DORA 四项）、评审负荷、质量（缺陷逃逸率、返工率）、结构健康、成本、体验六类；一个关键陷阱是「评审轮次下降」往往不是质量提升，而是评审者开始盖章。【A/C｜Thoughtworks Radar 2026-04；C｜多家工程分析厂商】

9. **收益曲线是 J 形，不是线性。** DORA 用「验证税」解释初期的生产力下滑，并用 500 人组织示例给出首年 ROI 约 39%、回本约 8 个月的模型——但报告明确声明这是高不确定性估算、用于引发讨论而非公式，示例假设「15% 下滑持续三个月」是占位输入（D*，官方原文核验）。更值得记住的是 DORA 的结论：ROI 主要来自内部平台、流程清晰度与协作一致性，而不是工具本身；报告明确反对把裁员当 AI 策略。

10. **国内已出现标准与官方框架，但产业整体仍在 L1–L2。** 信通院 2026 年 7 月可信云大会发布《AI重塑软件工程产业洞察报告》与《智能原生软件工程》首批评估结果；9 月发布《驾驭工程：赋能智能原生软件工程研究报告（2026年）》及 L1–L5 成熟度模型。报告称超 50% 企业 AI 应用成熟度处于 L1–L2，截至 2026 年 5 月 67.3% 软件企业已将 AI 投入生产、31.2% 完成智能体与核心流程内嵌（A，报告存在性；数字为报告自述口径）。另据多家媒体报道，DORA 于 2026 年 9 月宣布暂停年度调查，行业失去过去十几年唯一中立的横向基准（C，未取得官方公告原文）——这意味着**自建基线比以往更重要**。

## 一、全景：这套方法论由什么组成

### 1.1 术语地图：别被新词淹没

半年里最容易被误读的，是把一层的方法当成另一层的替代品。实际它们是**嵌套关系**：

| 层次 | 解决的问题 | 典型产物 | 代表术语 |
|---|---|---|---|
| Prompt Engineering | 一句话怎么说清楚 | System Prompt | 结构化提示词 |
| Context Engineering | 模型每次看到什么 | 检索规则、压缩、文档分层、AGENTS.md | 渐进式披露、Context Graph |
| Spec / Intent Engineering | 要做什么、做到什么算完 | `spec.md`、验收标准、EARS 语句、需求契约 | SDD、Spec Kit、OpenSpec |
| Loop Engineering | 多步任务怎么收敛 | 计划—执行—验证—复盘的状态机 | Agentic Loop、Planner/Generator/Evaluator |
| Harness Engineering | 模型外面那一整套环境怎么建 | Skills、工具、沙箱、权限、CI、日志 | 驾驭工程、Guides/Sensors |
| Organization / Platform | 团队怎么复用与治理 | 技能库、平台、政策、指标看板、审计 | Managed Agents、FinOps、AI 治理 |

一句话记忆：**Prompt 管一句话，Context 管一屏，Spec 管一件事，Loop 管一段过程，Harness 管一整套环境，平台管一个组织。**

### 1.2 全景结构图

```

                          │  目标与取舍 · 风险拍板 · 关键验收 · 对结果负责      │
                          └───────┬──────────────────────────────▲───────────────┘

  ② 上下文层 ── L1 入口 ── L2 文档/Skill ── L3 源码注释 ── 渐进加载 ──┤

  ③ 执行层 ── Agent + Harness（工具/权限/沙箱/状态落盘/模型路由）────┤
```

## 二、方法论主线：六个流派如何组合

### 2.1 Spec-Driven Development：事实上的默认流程

**核心主张**：在生成代码之前，先产出可被人和 Agent 共同评审的规格产物；Spec 是事实来源，代码只是它的一种展开。

**收敛后的循环**：

```
intent.md → spec.md → plan.md → tasks.md → 实现（一次一个任务）→ verify
      ↑            ↑            ↑
   人确认       人/评审 Agent   验收标准锁定为断言
```

**七条被反复验证的规则**：

1. **先写 spec 再写 prompt**——「spec is the prompt」。「加个登录」不是需求；模型会用「合理默认值」填空，而合理默认值几乎不是你想要的。
2. **验收标准用 EARS 记法**：`WHEN <触发> THE system SHALL <响应>`、`IF <条件> THEN THE system SHALL <响应>`。目的是让 Agent 无法自行发挥。
3. **仓库根部放「宪法」**（`AGENTS.md` / `constitution.md`）：类型严格、禁止未评审新增依赖、覆盖率不得下降、认证/支付改动必须人类签核。
4. **Spec 与代码同仓、同 PR、同版本**：一个特性一个目录。评审对象从「千行 AI 代码堆」变成「针对已批准 Spec 的聚焦 diff」。
5. **每个阶段边界都评审**，不要只在最后评审。错误在计划阶段只是一段话，在 800 行代码之后就是重写。
6. **构建教会你新东西时改 spec，不要在 chat 里打补丁**。只在对话里打的补丁，下次从 spec 重建时必然丢失。
7. **知道何时不用**：单行配置、依赖升级、有显然测试的 bug 修复不需要完整 spec。经验阈值是——跨多个模块、需要作者以外的人评审、或多个 Agent 参与时才写。

**两阶段节奏**：先 vibe-code 一个 spike 探明问题 → 把学到的东西沉淀成 spec → 再 spec-drive 生产版本。spike 用于发现需求，spec 用于钉死需求；直接对未知问题写完整 spec 是自欺。

**一个必须补上的缺口**：对 335 个架构文档完备的开源仓库调研发现，63% 已把文档交给 Agent 使用，但只有 8% 会检查「代码是否仍符合文档」。因此 **CI spec-drift check**（解析验收标准与已合并 PR，偏离即失败）是这个流派当前最值得补的一环。【A/预印本，经近期综述引用】

**窗口内实证**：作业帮公开口径为「需求契约 + SDD/TDD 双驱动」，SDD 约束做什么、TDD 证明做对了，歧义回写 SDD；自报人均月需求吞吐 +31%、AI Coding 覆盖率 >92%、月均 Bug 数持平（C，会议自报，未独立验证）。

### 2.2 Harness Engineering（驾驭工程）：2026 年最重要的新增概念

**定义**：`Agent = Model + Harness`。Harness 是模型之外的一切——上下文组装、工具暴露、循环、审批、验证、可观测性。模型改不了，Harness 能改，因此工程杠杆主要落在这里。

**Thoughtworks 的 2×2 控制模型**（D｜2026-04，虽在窗口外，仍是权威参考）：

|  | **Guides 前馈（行动前引导）** | **Sensors 反馈（行动后观测）** |
|---|---|---|
| **Computational 确定性** | 项目模板、代码生成器、清晰的 Makefile 命令、类型定义 | 编译器、类型检查、单测/E2E、linter、模块边界检查、**1 分钟内可完成的构建** |
| **Inferential 语义判断** | AGENTS.md、设计文档、Spec、Skills、优质代码示例 | AI code review、Evaluator Agent 亲自点击运行中的应用、带 rubric 的 LLM Judge |

两条诊断规则：
- 只有 Sensors 没有 Guides → Agent 反复犯同一个错；
- 只有 Guides 没有 Sensors → Agent 编码了规则，却永远不知道规则是否奏效。

**「棘轮」实践**：Agent 每犯一次错，就改它的环境使它不可能再犯——`AGENTS.md` 里每一行都对应一次真实错误；每次修好再紧一格，不松回去。修复落在仓库里，所有后续会话和所有 Agent 自动继承。

**窗口内的官方升级**：信通院《驾驭工程》报告提出六大能力——连接、编排、循环、效能、安全、评估优化；并构建 L1–L5 成熟度模型。报告把驾驭工程定位为「为智能体构建运行环境、约束规则与反馈机制」的核心管控框架，承载统筹协同、规范治理、效率提升、安全保障四大职能（A｜2026-09）。报告同时提醒实施误区：标准跑在实践前面，不要为了「上平台」而上平台。

**未解的最大敞口**：Thoughtworks 作者自己指出，现有 Harness 措施主要覆盖内部质量与可维护性，**「软件是否真的做了用户需要的事」这一行为/功能验证仍是空白**；依赖 Agent 自己写的测试，等于对 AI 生成的测试寄予极大信任。这是当前最值得投入的方向。

### 2.3 Context Engineering：从「塞满」到「按需披露」

**核心变化**：不再把整个仓库塞进大窗口，而是先给轻量索引，按任务拉取相关内容。三个进展最快的方向：静态指令的 prompt caching、MCP server 的动态按需加载、把组织推理建模为可查询的 Context Graph。

**`AGENTS.md` 的实证要点**：

- 2025 年 12 月由 OpenAI Codex、Amp、Google Jules、Cursor、Factory 共同推动，移交 Linux Foundation 下的 Agentic AI Foundation 托管；2026 年已被主流 Coding Agent 广泛原生支持。OpenAI 主仓自身有 88 个 `AGENTS.md`，monorepo 采用嵌套、就近优先。（D）
- 行业实践共识是**控制在 150 行以内**：一是 lost in the middle，二是它每轮都加载，每一行都是经常性成本。
- 466 个 `AGENTS.md` 的 MSR 2026 研究给出五类语句：descriptive / prescriptive / prohibitive / explanatory / conditional。多数失败不是「模型不听话」，而是**语句放错类别**——把规定写成描述会被忽略，把条件规则写成普遍规定会在条件不成立时出错；约一半文件从未更新过。（A/预印本）
- 写作规则：同一件事被纠正两次就加一行；具体到文件路径（「用 `components/ui/button.tsx` 的 Button」胜过「用我们的组件」）；重要规则写清 *why*；不要粘整篇文档，用链接。
- **该删掉的**：linter 已强制的风格规则、tsconfig/ESLint 已强制的库限制、README 副本、`/init` 生成段。工具链能管的，别写进上下文。

**分层知识库范例（得物 Akashic，B｜2026-11）**：

```
L1  AGENTS.md            → 入口与全局路由，短
L2  docs/ + skills/      → 模块知识、链路架构、术语、专题、面向任务的操作流程 + 脚本
L3  源码注释             → 贴近代码演进的局部约束
```

执行时按任务类型渐进深入：先由 L1 找到模块入口 → 读模块文档 → 调用对应 Skill → 必要时读专题 → 定位到源码注释确认局部约束。**「正确上下文在正确时机进入 Agent」，而不是一次性全给。**

**成本侧提醒（C｜Uber 自报）**：MCP 工具 schema 是隐性 token 税——100+ MCP server 在用户还没输入前就吃掉 5 万–7 万 token；改用惰性加载与按需解析后明显下降。即使模型支持 1M 上下文，Uber 仍在约 400K 就自动压缩：大窗口是容量，不是目标。

### 2.4 Loop Engineering / Agentic Engineering Loop：让多步任务收敛

**为什么需要**：LLM 是概率性的、工作记忆有限且易失。长任务里错误会指数累积；全自主「一口气跑完」可靠度不足。Loop 的价值是把任务切成可验证的小步，每步都有明确目标与退出条件。

**网盘团队的循环定义（B｜2026-10）**：

```
观察（当前代码/反馈）→ 决策（本轮目标）→ 修改（边界内）→ 验证（跑检查）→ 复盘（决定下一轮）
                                                              ↓
                                     满足验收 → 研发人员确认 → 交付
```

**执行前的必要一步**：需求调研。把业务描述整理成目标、工程约束、改动范围、验收标准；对照真实实现（文件、调用关系、提交历史），划清哪些必须保持不变；需求、验收标准、改动计划各自编号，便于一一对应。暂时确认不了的信息挂成**待确认项**，而不是当成实现前提。

**三种编排形态的选择**（B｜得物/Claude 生态实践综合）：

| 形态 | 适用 | 注意 |
|---|---|---|
| Subagent | 跑腿：隔离上下文、专项检查 | 独立上下文是关键优势，避免自审偏差 |
| Skills | 背书：把工作流、工具序列、失败模式打包 | 按需加载，不占常驻上下文 |
| Agent Team / Workflow | 打团战/建工厂：并行、分阶段、代码化调度 | 成功案例都依赖详细 Spec + 完整测试；产品开发中不宜盲目上 swarm |

**状态落盘**是长期任务的关键：把任务状态、决策、产物写到文件（issues / context.yaml / task.log），中断、换人、换工具都能续跑。Thoughtworks Radar Vol.34（D｜2026-04）把「编码 Agent 蜂群」列入 Caution，理由是成功案例的前提条件在普通产品团队里通常不具备。

### 2.5 Skills / Knowledge as Code：经验的载体

**Skill 是什么**：一个 `SKILL.md` 加可选脚本，把某个可复用工作流（提示词、规则、脚本、MCP 配置、已知失败模式）打包成可寻址单元，按需加载。它比一段聊天提示词更有价值，因为它编码了工具序列、仓库知识、约束、预期输出和已知坑。

**团队化后的四个变化**（B｜得物 EP-Harness 2026-08）：
- Prompt 从个人技巧变成**可 Review 的团队规程**；
- Context 从复制粘贴变成结构化工作现场（Issue、需求、项目、Workflow、Skills、Runtime、运行记录）；
- Agent 从「能说话的模型」变成**可管理的执行单元**（身份、权限、日志、成本可见）；
- Loop 从「一直跑」变成**有发现、派发、执行、验证、记录、下一步决策的闭环**。自报累计自动修复 100+ 个异常日志问题，典型高频问题从每 4 小时 2400+ 条降到个位数（C，团队自报）。

**知识回写闭环（得物 Akashic，B｜2026-11）**：

```
代码变更 → 脚本按映射定位受影响文档 → Agent 结合源码判断是否需更新 → 与业务代码一起提交
研发会话 → 归档 OSS → Session Agent 提炼候选知识 → Audit Agent 复核证据/冲突
        → 以 MR 提交 → Owner 审核 → 回写知识库
```

分工原则很清楚：**模型负责提炼与复核，程序负责外部系统交互与流程编排，Owner 负责最终审核**。提炼和复核使用同一份会话快照与固定版本源码，避免前后依据不一致；没有可靠、可复用结论时就不改知识库。

**反向信号也很有价值**：得物用对话洞察统计会话轮次、Token、时间跨度，并标注「补充知识 / 调整方向 / 要求重做 / 确认有效」等信号——轮次增加且「补充知识」增多，说明知识库覆盖不足；轮次增加且「要求重做」增多，说明任务理解或验证路径有问题。这把「体感不好用」转成了可定位的工程问题。

### 2.6 Eval 驱动：让改进可证伪

**离线私有评测集**：从自己仓库近 20–50 个已关闭 bug 中取样（不在公开基准里、模型训练后产生），这是对抗 benchmark 泄漏和 reward hacking 最有效的办法。评测要看三件事：通过率、轨迹是否合理（是否「碰巧过测试」）、下游结果（30 天内是否被 revert）。【C｜多家工程咨询机构 2026】

**A/B 式 Skill 评测**：同一模型、同一任务，分别跑「有 Skill / 无 Skill」，记录通过率差值（Lift，百分点），并把安全与缺陷数一起统计。只有可测量的 Lift 才配称为「最佳实践」。

**独立 Evaluator**：Anthropic 的方案是 Planner / Generator / Evaluator 三 Agent，Evaluator 是独立实例并挂 Playwright MCP，在给分前真的把应用点一遍（D｜2026-03）。窗口内的百度团队用了同一思路：即时 CR 必须由**独立 subagent** 执行，因为 Agent 倾向给自己的代码打高分。

**变异测试**：AI 很会生成「永远绿」的测试。cargo-mutants / Stryker / PIT 通过注入小 bug 检验测试是否真的能抓回归；Thoughtworks Radar Vol.34 将其列入 Trial（D）。

## 三、按工作流环节拆解的最佳实践

### 3.1 需求：把歧义挡在链路之外

- **产出「需求契约」**：经业务确认、研发可执行、可版本追溯；包含目标、业务口径、边界、异常分支、验收标准（B｜作业帮）。
- **歧义回写而非猜测**：Agent 可以把候选理解摆出来，但「业务口径、历史兼容、方案取舍」由责任人拍板，不确定的先挂账。
- **AI 的正确角色是引导者**：用结构化追问帮人把隐性意图显式化，而不是替人决定意图。
- **门禁**：没有已确认 Spec 不进入 Plan 阶段；PR 上要能追溯到 Spec 的提交号。

### 3.2 设计：把架构约束写成可检查的东西

- **分层架构用结构测试强制**，而不是写进规范里「请大家遵守」。能机械检查的约束（模块边界、依赖方向、禁用包）绝不交给提示词。
- **ADR（架构决策记录）与 Spec 同仓**，作为上下文资产被 Agent 按需读取；决策变更时同步更新。
- **大范围改动先做影响面分析**：跨服务、跨事件、跨特性开关时，靠知识图谱/调用图做正向与反向依赖查询，而不是靠 grep 猜测。

### 3.3 编码：小步、短会话、强隔离

- **短对话优先**：一个任务一个新会话，从 `plan.md` 冷启动，避免早期约束掉出上下文；长会话及时压缩并落盘。
- **Plan mode 先行**：先产出计划再执行；人工审查计划比审查千行 diff 便宜几个数量级。
- **每个任务独立 worktree / 沙箱**，避免并行 Agent 互相污染；凭据放在沙箱外，权限按会话和工具粒度授予。
- **确定性脚本优先于多轮工具调用**（code-mode）：重复工作流写成一段脚本，token 可降一半以上（C｜Uber 自报）。
- **模型路由**：架构决策与模糊调试用前沿模型；仓库检索、机械改动、边界清晰实现用便宜模型。

### 3.4 评审：把人的注意力用在意图和风险上

- **AI 做第一遍，人做第二遍**：人不再读语法，改读意图、架构、安全、风险——这次改动是否符合 Spec、是否契合系统、是否引入新失败模式。
- **升级类必须人审**：认证、支付、schema、数据迁移、测试/CI 变更，以及任何没有自动化覆盖的行为。
- **PR 体积上限 + 证据包**：PR 里带测试说明、验收记录、截图/预览地址；大 diff 让人失去审查能力（<100 行 PR 能抓约 87% bug，>1000 行只能抓 28%，C）。
- **大 diff 并发审查范式（百度，B｜2026-07）**：逐行解析 unified diff → 按目录前 3 级分组 + 模块内按行数 bin-packing（每 chunk ≤500 行）→ CLI 子进程并发派发（10+）→ 每个 chunk 输出结构化 JSON → 聚合为 `review.json` → 按文件分 worktree 自动修复 → 按变更行数从小到大 merge，每次 merge 后跑构建，失败即 revert。
- **警惕评审剧场**：评审轮次下降、approve 变快，配合缺陷逃逸率上升，就是盖章的信号。

### 3.5 测试：稳定、可信、可量化

- **断言 stability 优先于数量**：只对业务相关、可重复验证、结果稳定的字段生成断言；依赖运行时状态的断言宁可移除。回归测试首先要稳定可信（A/B｜字节 NL2Test，ISSTA 2026）。
- **LLM 只做语义部分**：字段查找、schema 校验、值匹配、参数替换交给确定性程序；模型输出用 schema 与允许集合约束，越界输出除非有唯一确定性修复否则直接丢弃。
- **任务拆小**：请求匹配、依赖提取、断言意图识别、受约束代码生成各自独立，每步校验后再进下一步；端到端一次生成虽简单但无法定位错误。
- **上下文治理**：原始流量里的静态资源、轮询、trace id、临时字段都是噪声；先过滤、摘要、突出候选字段，再喂给模型。**「必要且干净的证据」胜过「完整流量」。**
- **浏览器/CDP 验证**：DOM 断言 + 标注截图 + console 检查 + memory 跨任务积累。DOM 断言能说「元素存在」，标注截图才能发现「元素被裁掉一半」。
- **视觉走查量化**：用 VET（Visual Expression Tree）把动态内容替换为色块，只保留位置、大小、层级；先在设计页建立颜色方案，再在开发环境按语义对应注入同色，消除 DOM 深度差异噪声；每个候选问题用独立 subagent 复核、`getComputedStyle()` 量化到 px、SVG 标注截图（B｜百度 2026-07）。
- **变异测试**作为「测试质量」的诚实信号，尤其针对 AI 生成的测试。

### 3.6 发布与运维：让 Agent 能自己验证

- **CI 必须快**：把构建压到 1 分钟内。慢 CI 会卡住背景 Agent 的高频验证回路，速度问题会直接变成 AI 采用问题（B｜Notion Afterburner 项目目标是把 CI 压到 1/4）。
- **每个 worktree 一个可启动实例 + 可查询的可观测性**：日志、指标、链路让 Agent 自己读；能启动应用、驱动 UI、读日志，才谈得上「自证」。
- **状态分离**：把「执行完成」「检查通过」「业务验收通过」三件事分开记录，不能用其中一个当交付结论（B｜网盘）。
- **运维闭环示例（得物，C）**：定时拉取异常 → 聚合 fingerprint 与影响面 → Agent 分析根因 → 生成修复/验证建议 → 必要时建 Issue，每轮都有记录、判断、产出和后续动作。

### 3.7 知识沉淀：从「文档维护」到「工程闭环」

- 一次检查只是工具，**能持续复用与迭代的检查机制才是团队资产**：规范 → Rules，CR 经验 → rules.md，页面验证 → memory，视觉走查 → Skill 组合，QA 高频问题 → 反向写入 Rules/Skill。
- 知识统一在 Git 仓库维护，以源码为依据；按适用范围与读取时机分层，避免把全局约定、模块规则、局部细节全塞进一个文件。
- 错误的价值：每次人工纠偏都是一条潜在的规则候选，但要经过「证据充分 + 无冲突 + Owner 审核」才入库，避免错误经验被固化。

## 四、度量与经济学

### 4.1 记分卡：看什么、别看什么

**不要看**：LOC、commit 数、PR 数、velocity、prompt 次数、acceptance rate。这些在 Agent 时代只要生成就必然上涨，与质量无关。

| 维度 | 指标 | 健康信号 / 说明 |
|---|---|---|
| 交付（DORA） | 变更前置时间、部署频率、变更失败率、恢复时间 | 目标是**吞吐上升 + 稳定性持平或更好**；吞吐升、失败率也升＝借来的速度 |
| 评审容量 | 首次评审时间（小时级而非天级）、PR 体积、changes-requested 率、评审者负载 | 「生成快过人类能负责评审的速度」是人为制造的瓶颈 |
| 质量 | 缺陷逃逸率（按捕获位置分桶：本地/发布前/生产）、返工率（合并后 30 天内被 revert/hotfix）、结构健康趋势 | 返工率是低信任 diff 的税；逃逸率要按人写/AI 生成分桶 |
| 验证有效性 | 变异测试存活率、Spec 覆盖率、spec-drift 检查通过率 | 防止「永远绿的测试」和「文档与代码两张皮」 |
| 成本 | 每合并 PR 的 AI credits、每任务 token、top 10% 用户支出占比 | credits 比美元更适合工程侧，能映射到模型选择与上下文行为 |
| 体验 | 信任度、认知负荷、是否愿继续用 | 信任下行 + 使用上行＝评审瓶颈的先行指标 |
| 组织/知识 | 同类任务会话轮次与纠偏标签趋势、Skill 复用次数、知识库 MR 回写数 | 用于判断知识工程是否真的减少了重复解释 |

**一个反直觉陷阱**：评审轮次下降常被读成质量提升，更常见的解释是评审者开始盖章；必须与缺陷逃逸率一起看。另一条：**如果唯一改善的指标是工具自身的使用量，那就什么都没改善。**

### 4.2 J 曲线与验证税

DORA 2026 ROI 报告（D*，官方页面核验：最后更新 2026-04-22）把初期下滑拆成三项：
1. **学习曲线**：从「我写代码」切换到「我指挥 Agent」；
2. **验证税**：Someone reviews the AI-generated code, and that someone is a senior engineer whose time is the most expensive input you have；
3. **管道适配**：测试与变更审批要能承接更高的变更量。

报告称之为「转型的学费」，并明确警告：把低谷误判为失败而撤资，会丢掉后面的回报。其示例模型（500 人组织、人均全口径年薪 17.6 万美元、人均节省 12.5% 时间）给出首年 ROI 约 39%、回收期约 8 个月，其中变更失败率 5%→6% 折算约 −34.4 万美元停机损失。**报告自己声明这是高不确定性估算，用于引发讨论，不是公式。**

### 4.3 成本治理：按 FinOps 做

Token 是可变的经常性成本，Agent 化后增长最快。可操作的杠杆（主要来自 C 级自报，供参考）：
- 上下文纪律：精简常驻指令、压缩、按需披露；
- 技能库：把重复工作流固化为 Skill，减少反复解释；
- 模型路由：按任务难度分层，别把便宜任务交给前沿模型；
- 工具选择：MCP 惰性加载，避免 schema 常驻；
- code-mode：确定性脚本替代几十次 LLM 往返；
- 预算可见化：按团队额度与告警，追踪「消耗是否换来了保留下来的合并代码」。

### 4.4 ROI 的正确问法

DORA 的立场值得原样记住：ROI 不再是「能替代多少开发者」，而是「把系统性苦工卸载给自主 Agent 后能释放多少人类创造力」。报告明确反对以裁员为 AI 策略。落地顺序应是——**先修平台与流程 → 再扩大 AI 使用 → 把回收的产能投入减少返工，而不是直接削减人力**。

## 五、风险清单与证据分歧

| 风险 | 关键数据 | 证据口径 |

**关于 GitClear 的口径提醒**：它是代码分析厂商，数据来自自有引擎的逐行分类，是相关性而非因果证据；反证方同样存在（GitHub 的 202 名开发者试验、151 仓库学术研究发现采纳后 churn 未普遍上升）。正确用法是**抄方法，不抄标题**：在自己的仓库上用两周 churn、块重复密度、move 占比、错误掩蔽计数、老代码触达率、变更失败率建基线。

**一处需要并列呈现的分歧**：Liu 等发现大量 AI 引入问题长期未修；另一项覆盖 201 个开源项目、20 万+ 代码单元的研究发现 AI 代码的行级修改风险比人写低 15.8%（即更长寿）。两者并不矛盾——AI 代码倾向**留存**，而**当它带病时，病也一起留存**。这正是结构性闸门比事后清理更重要的原因。

**当前公认未解**：行为/功能正确性验证仍是空白；「用 Agent 自己写的测试来验证 Agent」循环论证；跨 Agent、长任务的失败归因与恢复仍不成熟；多 Agent swarm 的收益条件尚不普适。

## 六、落地路线：30 / 60 / 90 天

### 前 30 天：立规矩、建基线

1. 写一页 AI 使用政策：批准工具与层级、允许的数据分类、secrets 规则、Agent 权限与审批、审计日志用途、事件上报路径。
2. 在推广前**先建基线**：评审负载、交付、质量、体验四类；从版本控制与部署日志取数，不用问卷。
3. 把前 10 个任务分类：哪些「边界清晰且可验证」，从这里开始；哪些不适合。
4. 在评审量上来之前改评审流程：PR 体积上限、证据包要求、风险分级、AI review 只作第一遍。
5. 把 `AGENTS.md` 砍到 150 行以内，细节外链；删掉工具链已强制的内容。
6. 选一个窄场景做 spike（如依赖升级、测试补齐、日志归类），先验证闭环再谈平台。

### 31–60 天：搭最小 Harness 与上 SDD

7. 最小 Harness = 短入口文档 + 一条测试命令 + 一条 lint/type-check + 一个 pre-commit hook + 一个结构测试；**构建压到 1 分钟内**。
8. 上轻量 SDD：`spec.md` + plan mode + 已锁定验收标准；Spec 与代码同仓，同名目录。
9. 加 CI spec-drift check，补上「92% 团队缺位」的漂移检测。
10. Agent 沙箱化：独立 worktree / Dev Container、最小权限身份、分支保护强制人类批准。
11. 上独立 subagent 做即时 CR；把规则写成可复用的 `code-validation` Skill，开发期与流水线共用一套规则。

### 61–90 天：闭环、评测、成本

12. 上变异测试；针对 UI 增加 CDP 浏览器验证与截图证据。
13. 建技能库：把重复工作流写成 `SKILL.md`，纳入 Review 与版本管理；建立 Skill 的 A/B Lift 评测。
14. 建知识回写闭环：代码变更同步文档、会话归档与经验提炼、Owner 审核后 MR 入库。
15. 成本可见化：按团队 token 预算与告警、自动压缩、MCP 惰性加载、模型路由。
16. 每季度复盘政策与规则，把「Agent 做错的事」沉淀为新规则（棘轮）。

### 按团队规模取舍

| 场景 | 重点 | 不要做 |
|---|---|---|
| 个人 / 小团队（<10 人，绿地为主） | 短 AGENTS.md、Plan mode、测试先行、小 PR、1 分钟构建 | 不要自建平台、不要多 Agent 编排 |
| 中型团队（10–100 人，存量 + 增量） | SDD + 质量关卡左移 + 技能库 + 度量基线；先一个服务试点 | 不要一次性全员铺开，会失去对照组 |
| 大型 / 受监管组织 | 攻防与零信任、Agent 专有身份与审计、平台化 Harness、L1–L5 成熟度评估、行业刚性校验 | 不要把 AI 治理并入现有流程后就算完成；合规要原生嵌入契约层 |

### 对本团队的适配建议（4 人技术保障团队，安全合规优先）

考虑到事业单位信息化与安全保障的约束，建议把投入排序为：**规则与文档可审查化 > CI/测试提速 > 质量门禁左移 > 知识回写 > 平台化**。第一阶段只做三件事：`AGENTS.md` 精简与版本化、关键路径测试覆盖率与秒级 lint/test 打通、PR 证据包（测试输出 + 变更说明 + 风险标记）。等这三个跑稳，再考虑 Skill 与独立评审 Agent。**先把「路」修好，再换引擎。**

## 八、一句话收束

**模型能力决定 Agent 能做什么，Harness 决定它在这支团队里能做成什么；2026 下半年真正拉开差距的，不是谁用了更强的模型，而是谁先把规格、验证、知识、评审与成本做成了可复用、可审查、可迭代的工程资产。**
