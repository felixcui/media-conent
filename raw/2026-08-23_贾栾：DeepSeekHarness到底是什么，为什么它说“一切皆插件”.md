# 贾栾：DeepSeek Harness 到底是什么，为什么它说“一切皆插件”

## 前言

DeepSeek 刚刚开源了 DeepSeek Harness（DSH），很多人会以为 DeepSeek 又做了一个 AI 模型，或者 Claude Code、Codex 之外又多了一个同类工具。

今天我实操了一遍，我尽可能的用通俗的语言来给讲明白 DSH 到底是什么。



要理解 DSH，关键是先把它放到正确的一层。



模型负责理解和生成。

Claude Code、Codex 这样的 Agent 接收任务，调用工具，读写文件，再把事情做完。



DeepSeek Harness 管理 Agent 外面的那套运行机制，包括给它接什么模型、开放什么工具、遵守什么规则、在哪个工作区行动，也包括要不要把一部分任务交给另一个 Agent。

这就是 Harness。中文里很难找到一个完全对应的词，可以把它理解为 Agent 的运行和组织框架。

DSH 提供一套开放框架，让不同模型、工具、界面、插件和其他 Agent 能够在同一个环境里组合起来。



## 先分清模型、Agent 和 Harness



这三层经常被混在一起，其实各自解决的问题不同。

| 所在层 | 主要解决什么 | 常见例子 |
|-|-|-|
| 模型 | 理解信息，推理并生成内容 | DeepSeek、Claude、GPT |
| Agent | 接收任务，调用工具并执行 | Claude Code、Codex |
| Harness | 配置 Agent 的模型、工具、规则、工作环境和协作方式 | DeepSeek Harness |

如果你只是问一个问题，模型可能就够了。想让 AI 读文件、改代码、运行命令，需要 Agent。想继续决定这个 Agent 能用什么工具、怎样扩展界面、什么时候把任务交给另一个 Agent，就进入了 Harness 这一层。



DSH 就工作在最后这一层。实际用起来，你仍然是在本机 Web 页面里给 Agent 下达任务。它可以查看工作区、调用工具，也可以在需要时把一部分任务交给其他 Agent。DSH 向用户开放了这些能力的配置和组合方式。

![这张图展示了你、AI Agent与DSH的关系：你通过DSH的Web界面发起任务，DSH承载AI Agent会话，该会话可调用AI模型，AI Agent会话能向DSH的工作区读写文件、使用工具执行命令。图中还标注了DSH的相关特性：若DSH停止，当前会话会中断，但历史记录仍会保留，这也呼应了文档中关于DSH停止后会话中断、历史记录留存的说明。](https://feishu.cn/file/LPRSbWk1bosLYdxLRY1cVzeRn8b)

*Agent 会话由 DSH 承载，模型可以来自外部服务。DSH 停止后，当前会话会中断，历史记录仍会保留。*

补充：
**DeepSeek的DSH和Harness Engineering、Hermes Agent 有什么本质区别吗？**
Harness Engineering 是一种工程方法论：继提示词工程、上下文工程之后的第三次范式转移。它研究的是“怎么给大模型这匹烈马配驾驭装置”——验证循环、重试策略、状态管理、评估反馈，目标是让 Agent 输出稳定、可控、可复用。
后来出了一个产品叫 **Hermes Agent**，给 harness 装上学习闭环，让 Agent 自己长本事**——赌进化路线**。
DSH 是 DeepSeek 开源的一个具体框架：把 harness 这一层做成“一切皆插件”的可组合产品，用户可以自己决定接什么模型、装什么插件、把任务派给哪个 Agent。——赌**组合路线**

## 它已经可以指挥 Claude Code 和 Codex



这次实际使用改变了我对 DSH 的判断。它已经能够把任务交给 Claude Code 和 Codex。



在 DSH 里，一个 Agent 可以把独立任务派给本机已经安装并登录的 Claude Code 或 Codex。对方完成后把结果交回来，DSH 再继续推进主任务。



这并不意味着 DSH 内置了 Claude Code 或 Codex。用户仍要在电脑上安装并完成登录，模型选择和权限也由各自的工具管理。DSH 负责调用和组织它们。

![图片展示了DSH调用Claude Code与Codex的真实链路。左侧是用户贾栾发起任务，中间是DSH Web GUI，右侧是Claude Code CLI和Codex CLI的配置信息，包括完整可执行文件路径、headless命令等。下方有工作空间共享和可验证证据的标识。该图与上下文紧密相关，直观呈现了DSH调用两个模型时的配置与执行流程，帮助理解DSH如何调用和组织Claude Code和Codex。](https://feishu.cn/file/So8JbwY9aokFSoxom6GcsOPvnKf)

*这张图记录的是本机实测环境。*

*图中的模型、版本、路径和工作区只代表这次配置，DSH 不会替用户安装、登录或配置两个 CLI。*



这个特点很重要。一个刚起步的框架，不需要等自己的所有能力都长齐，才开始解决真实问题。它可以先调用已经成熟的 Agent，把擅长编码、分析或执行的任务交给它们，同时继续发展自己的插件和工作方式。

因此，理解 DSH 时，不能只问它能不能替代 Claude Code。更值得问的是，它能不能把 Claude Code、Codex、不同模型和本地工具组织成一套适合自己的工作系统。



## “一切皆插件”到底是什么意思



DeepSeek 在官方仓库里用一句话描述 DSH 的架构，**Everything is a Plugin。**



很多软件也有插件，但插件通常只负责补充少量功能，产品主体仍由开发团队固定。DSH 把更多组成部分放进同一套组合机制里。底座、Web 界面、工具和后来添加的能力，都可以按统一规则进入系统。

在我当前使用的 DSH 的 网页端配置里，官方基础组件、官方 Web 应用，以及后来安装和制作的三个插件，都出现在同一份插件列表中。它们的功能大小不同，进入 DSH 的方式却是统一的。



“一切皆插件”说的是系统如何组织能力。判断这句话有没有兑现，不要先数插件商店里有多少东西。先看这套系统开放了多少位置，能力能否增加、替换和重新组合。

![图片以毛坯房为喻，展示DeepSeek Harness（DSH）的可组合结构。左侧是成熟CLI（如Claude Code CLI、Codex CLI）和用户自建插件，可接入DSH。中间是DSH极简内核，右侧是用户DIY组装成的工作台，包含聊天、文件窗口、终端等界面。底部流程图显示选择插件、插入内核、装成工作台，强调一切皆插件，极简内核+用户接入插件可慢慢装成自己的AI工作台，与上下文介绍DSH开放位置、能力可组合相呼应。](https://feishu.cn/file/KK2rbadkloIPOMxuXRPcHyvrn6b)

*这张图用毛坯房表现 DSH 的可组合结构。左侧的成熟 CLI 和用户创建的插件都能接入，图中表达的是扩展方式，不代表插件生态已经成熟。*



今天我验证的三个案例，刚好落在三个不同位置。

| 插件 | 改变的位置 | 用户能感受到的变化 |
|-|-|-|
| `@` 文件引用 | 输入方式 | 输入 `@` 就能选中工作区里的文件或目录，让 Agent 知道该从哪里开始处理 |
| 可视化文件窗口 | 工作界面 | 聊天旁边可以查看目录、预览和编辑文件，也可以使用终端等工作面板 |
| 重启插件（我 DIY 的） | 运行管理 | 设置页多出重启入口，改完配置后可以直接重启 DSH |



`@` 文件插件并不会把整份文件自动塞进对话。它先插入工作区路径，Agent 需要时再打开。

可视化窗口改变了人与 Agent 一起处理文件的方式。

重启插件则把扩展范围推进到了本机服务的运行管理。



三个功能本身都不复杂，合在一起却验证了一个关键点。DSH 的插件边界横跨输入、界面和运行端。插件在这里承担着系统增加能力的主要工作。



## 用早期鸿蒙理解 DSH 的发展路径



我更愿意用早期鸿蒙来理解 DSH。

鸿蒙原生生态还不完整时，需要先兼容安卓应用，让用户能够使用已经存在的成熟生态。随着原生应用越来越多，它才逐渐长出自己的能力和体验。



DSH 目前也处在一个相似阶段。自己的插件生态还在早期，它可以先把任务交给 Claude Code、Codex 这些成熟 Agent，解决眼前的真实工作。与此同时，开发者和用户继续为它增加原生插件，让输入方式、工作界面、工具和业务流程逐步完善。

这个类比讲的是生态的发展路线，两者的技术实现并不相同。

以后即使 DSH 的原生插件越来越丰富，Claude Code 和 Codex 也未必需要退出。它们仍然可以作为专业 Agent，继续承担自己擅长的任务。DSH 更可能负责选择谁来做、给谁什么工具，以及怎样把结果接回整个流程。



所以，DSH 今天有多少功能，只能说明当前状态。它未来能走多远，要看插件能不能持续生长，组合规则能不能保持稳定，权限和维护能力能不能跟上。



## 一天实操同时验证了方向和边界



这次实际使用给出了四个比较明确的结果。

- DSH 调用 Claude Code 和 Codex 执行任务，已经在真实环境中跑通。
- 社区插件已经能够解决具体问题，生态很早，但并非一片空白。
- 用户可以根据自己的需求制作插件，AI Agent 也能参与开发和排错。
- 插件会把自己的兼容性和维护成本带进系统。我自己做的重启插件曾因为模块格式声明和实际代码不一致，直接导致 DSH 启动失败，修正后才恢复运行。



这四件事放在一起，结论会更准确。DSH 提出的架构已经可以工作，外部 Agent 和社区插件也已经能被实际使用。它离稳定、省心的成熟产品还有距离，当前不少问题仍要由使用者自己查看日志、判断原因并完成修复。



官方目前把 DSH 标为 Developer Preview，并明确提醒后续会出现破坏兼容性的改动。现在参与进去，更接近测试和共同建设，还不是把关键工作全部迁过去的时机。[DeepSeek Harness 官方仓库](https://github.com/deepseek-ai/deepseek-harness)



## 为什么有私有化需求的企业值得关注



个人尝鲜时，在自己的电脑上启动 DSH 就能开始。企业谈私有化部署，关注的问题要大得多。

他们需要考虑，框架能否运行在企业可控的环境里，能接哪些模型和内部工具，员工能访问哪些资料，操作能否审计，业务流程能否通过插件长期保留下来。



比如，一家公司希望 Agent 在权限范围内读取内部知识库，调用合同、客服或内容生产系统，再把一部分专业任务交给 Claude Code、Codex 或其他 Agent。固定功能的通用聊天工具很难完全满足这样的需求，公司需要一套能够自行控制和继续扩展的 Agent 框架。

DSH 采用开源的 MIT 许可证，又把能力组织成可组合的插件，这让它成为一个值得持续观察的候选框架。对于有私有化部署需求的企业，当前更应该关注它能否逐步长成一个可控、可扩展的内部 Agent 平台，无需急着把它装进生产环境。

边界也要说清楚。私有化部署不自动等于所有数据都留在本地。只要接入云端模型、外部 Agent 或第三方服务，数据仍可能离开企业环境。身份权限、密钥管理、审计、升级和故障恢复，也都需要企业自己补齐。

![图片展示了小企业私有化部署的控制边界。左侧为企业可控环境，有员工、内部知识库、业务系统等，中间是DHS，右侧是可选外部服务，包括云端模型、Claude Code / Codex、第三方服务。箭头表示数据流方向，如按配置可能出域。底部文字强调私有部署≠数据全部留在本地，部署、插件和接入方式可控，数据流仍需单独治理。该图与上下文紧密相关，直观呈现了私有化部署中数据流动及控制情况。](https://feishu.cn/file/OwuNbiDuXou5hwxCd7wcxu2XnMd)

*企业可以控制 DSH 的部署、插件和接入方式。接入外部模型、Agent 或第三方服务后，跨边界的数据流仍需单独治理。*



因此，**DSH 现在还不是一套拿来就用的企业解决方案。它提供了一个有潜力的技术方向，距离可靠落地仍要经过生态、兼容性和治理能力的持续验证。**



## 现在适不适合用

如果你已经在使用多个 Agent，有反复出现的真实工作流程，也能处理终端、日志和配置问题，现在可以拿一个小任务试用 DSH。先验证它能否减少真实工作中的切换和重复，无需一开始就安装很多插件。



如果你主要需要聊天、写作、问答或稳定的编码体验，成熟工具仍然更省心。了解 DSH 的方向已经足够，没有必要因为它代表未来就立刻迁移。



如果你经营一家有私有化需求的企业，可以把 DSH 放进长期观察或小范围验证名单。下一步可以挑一个可回退、风险较小的内部流程做验证。等它经历升级仍能稳定运行，权限、数据和日志也能管住，再考虑把更重要的工作交给它。
