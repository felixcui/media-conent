## 摘要

业务 Skill 的一次修复通常从失败 Case 开始：看执行过程、找漏掉的规则、改 SKILL.md、再跑评测。场景一多就暴露两个问题：**修好一个场景会弄坏另一个**；连续改多次后**说不清哪版更好、收益来自哪条规则**。作者把这套流程改造成**可追溯的搜索闭环**：用**黄金评测集 + Ground Truth + 执行轨迹**生成反馈，模型只负责**提出候选修改**，**确定性程序**负责边界校验、版本比较和状态维护，**人**管业务边界与最终交付。方法上对比 **GEPA、SkillOpt、EvoSkill、Trace2Skill** 后选了 **GEPA 的反思搜索**，并展开候选池、Module 划分和归因变异提示词。**注意：文中没有量化结果，作者也明说当前实现与完整设计之间还有边界。**

业务 Skill 的一次修复，往往从一个失败 Case 开始：看执行过程、找到遗漏的规则、修改 SKILL.md，再跑一遍评测。随着业务场景增加，这种方式会遇到两个问题：修好一个场景时可能破坏另一个场景；连续多次修改后，很难判断哪个版本更好，以及收益来自哪条规则。

▐ **2.1 全局流程**

整体流程沿用 GEPA 的核心思想：以黄金评测集上的评测结果和执行轨迹为原始信号，先生成逐 Case 反思反馈，再由反思、归因并产生变异，通过多轮“选择—反馈生成—反思变异—全量评测—择优保留”持续搜索更优的 Skill 版本。进化期间冻结黄金集、Ground Truth、rubric 身份、模型和执行配置，让各版本尽可能在同一口径下比较。服务端动态数据与模型随机性仍需通过运行证据和复测披露，不能仅凭配置冻结就认为所有波动已经消失。

![](https://mmbiz.qpic.cn/mmbiz_png/DthwRd8vvp0BK1U59hcyMicUE3KZZZSicKj3icIvH8P4DJDS8fONEianKdzQoa0c5gvJt65WMhG5ZFpGG9oXwt68bv5m8tGgMZxaw5M1V4aJaib4/640?wx_fmt=png&from=appmsg)

整体流程分为以下步骤：

1. 进化准备：确定本轮要优化的 Skill，冻结黄金评测集、评测标准、执行模型、工具与运行环境，并设置最大生成轮次与子候选评测预算，完成 Module 人工审核。基线评测与模型反思成本应另行记录。
2. 初始版本全量评测：使用当前 Skill 并发运行全部黄金 case，记录每个 case 的执行轨迹和结构化评测结果，包括总分、逐维度得分、原子问题答案及判分证据，形成版本比较的基线。评测阶段本身不生成面向 Skill 优化的反思反馈。
3. 选择父版本：从当前已经保留的版本中选择一个父版本，作为本轮继续探索的起点。父版本已有的全量评测产物直接复用，无需重复运行。
4. 生成反思反馈：读取父版本的逐 case 执行轨迹和结构化评测结果，并结合黄金评测期望，生成供反思 LM 使用的逐 case 反思反馈。该反馈是自进化流程根据评测产物生成的派生数据，不是现有评测系统直接保存的字段。
5. 反思与生成子版本：基于逐 case 反思反馈进行归因，生成一个新的子 Skill 版本。本步骤只负责提出一次定向变异。
6. 有效性校验与隔离部署：确认子版本结构完整、能够被正确加载和执行，然后部署到隔离的评测环境，避免影响当前正式版本。
7. 子版本全量评测：对新子版本并发运行全部黄金 case，得到与父版本口径完全一致的逐 case 分数、执行轨迹和结构化判分结果。评测完成后不立即额外生成反馈；该版本后续被选为父版本时，再进入反馈生成步骤。
8. 父子入池判定：比较子版本与直接父版本的逐 Case 分数，不比较全量平均分。若父版本在所有 Case 上均不差于子版本，并且至少在一个 Case 上严格优于子版本，则父版本严格支配子版本，子版本不进入候选池；若子版本支配父版本，或二者互不支配，则子版本进入候选池。父子逐 Case 分数完全相同时，视为无有效提升，子版本不入池。无论是否入池，都记录本轮变异、父子关系、评测结果和判定原因，保证过程可追溯。
9. 更新并继续迭代：子版本通过父子入池判定后，加入全局候选池。若预算尚未耗尽，则在下一轮开始时基于全局候选池重新计算逐 Case 领先候选的活动前沿，并从活跃前沿中选择新的父版本；否则结束搜索。候选即使已经入池，后续被其他候选严格支配时，也不会进入活跃前沿和父版本采样范围，但其版本及评测记录仍保留在候选池中。
10. 最终版本确认与发布：搜索结束后，从全部已保留版本中选出黄金评测集平均得分最高的版本，完成规范检查并输出版本差异和进化报告。搜索结束先恢复评测空间种子版本，报告进入最终评审。经人工确认与规范检查后写回目标 SKILL.md，发布、提交和代码评审按独立流程执行。

▐ **2.2 候选池设计**

候选池采用“全局保存、动态选优”的设计：

| 数据集合 | 含义 | 是否参与父代采样 |
| --- | --- | --- |
| 全局候选池 | 种子版本及所有通过入池判定的子版本 | 只有进入活动前沿后才参与 |
| 活动前沿 | 当前在不同 case 上具有领先能力的候选 | 参与 |
| 失败尝试集 | 校验失败、评测失败或未通过入池判定的子版本 | 不参与 |
| 当前冠军 | 全局候选池中全量平均分最高的候选 | 仅用于最终选优 |

![](https://mmbiz.qpic.cn/sz_mmbiz_png/DthwRd8vvp3zFicIQpBZtJ6nmko8JI0TNWcPQwlnEA4qEsvhPwUxLEVkfWMlXibJvIFJlD8q6pGOPcobE0ribYblh2pEJ811gu0qw71hkJYacA/640?wx_fmt=png&from=appmsg)

其中，t 表示当前迭代轮次。活动前沿是从全局候选池计算得到的临时结果，用于探索而不直接代表上线资格。候选即使没有进入本轮活动前沿，也不会从全局候选池中删除。

每个入池候选至少记录以下信息：

| 字段 | 含义 |

- 入池规则

子版本完成全量评测后，只与它的直接父版本比较，不与全局候选池中的其他版本做入池判定。这样既能解释一次变异的效果，也能保留互补能力；后续父代采样再由全局候选池的活动前沿决定。

：子版本；

：父版本在第 个 case 上的分数；

：子版本在第 个 case 上的分数。

实际连续分数比较使用 `epsilon=1e-6` ：不差于允许 epsilon 容差，严格更优需超过 epsilon；全部差异在容差内视为同分。下表给出入池结果：

| 父子关系 | 处理结果 |
| --- | --- |
| 父版本严格支配子版本 | 子版本不入池 |
| 子版本严格支配父版本 | 子版本入池 |
| 父子互不支配，各自有更优 case | 子版本入池 |
| 父子所有 case 分数完全相同 | 视为无有效提升，子版本不入池 |
| 子版本内容与已有候选完全相同 | 根据 `content_hash` 去重，不重复评测和入池 |

因此，入池规则保留两类版本：整体优于父代的版本，以及虽然没有整体提升、但在部分 Case 上产生新优势的版本。后者可能包含局部回退，最终交付必须披露这些回退，不能把入池当成无回归保证。

![](https://mmbiz.qpic.cn/mmbiz_jpg/DthwRd8vvp1T5J0I1rmeRpRbL8rm19RkIn1uxm3HdqwrpQ0u5icqUdtUCnrkG9MVpKbTannniaMmsxBUP130MuGDLQfE9JVzjW6344pbzstl0/640?wx_fmt=jpeg)

候选没有领先任何 Case 时，不进入活动前沿。对于存在重叠覆盖的候选，需要定义确定性处理顺序，避免同样的分数矩阵产生不同结果：

1. 初始化未覆盖集合为全部 Case。
2. 选择覆盖最多未覆盖 Case 的候选。
3. 覆盖数并列时，依次优先均分更高、最差 Case 分更高、创建更早和 ID 字典序更小的候选。
4. 从未覆盖集合中移除已覆盖 Case，重复直到全部 Case 都被覆盖。

这个过程保留了逐 Case 领先能力，避免冗余候选都参与采样。它是贪心覆盖，不保证候选数最少，也不等于完整 Pareto 非支配集。

▐ **2.3 Skill Module的设计**

借鉴 GEPA 的模块化优化思想，我们将候选 `SKILL.md` 拆分为多个可独立优化的业务 Module，每轮只选择其中一个 Module 进行反思和变异，其余内容保持不变。

- Module 划分方法对比

|  | 整体作为单一 Module | 按文档固定章节划分 | 按 Skill 内部业务能力划分✅ |
| --- | --- | --- | --- |
| 划分方式 | 整份 SKILL.md 作为一个 Module | 按输入、流程、约束、输出等章节划分 | 每个可由一类用户意图独立触发、具有独立执行流程和输出规则的业务能力作为 Module，公共规则单独划分 |
| 优点 | 实现简单，不需要额外配置 | 边界清晰，适合结构统一的 Skill | 与评测 case 和失败归因更容易对应，变异范围较完整 |
| 缺点 | 每次改动范围过大，容易修复一个场景却破坏其他场景 | 依赖统一的章节结构；Skill 的章节组织并不完全一致，而且同一业务能力可能分散在多个章节中，通常仍需逐个 Skill 配置。 | 需要为每个 Skill 建立一次 Module 配置 |

- Module 结构

一份 `SKILL.md` 按实际内容划分成下列 Module，不要求包含全部类型：

| Module 类型 | 默认是否允许自动进化 | 使用说明 |
| --- | --- | --- |
| routing | 是 | 路由遗漏或错误分流时修改 |
| `capability.<name>` | 是 | 主要进化对象；评测 case 应尽量映射到一个具体 capability（具体业务能力） |
| shared.response | 是 | 输出时共用的规则/模板 |
| shared.boundaries | 是 | 失败归因指向边界判断时修改 |
| shared.guardrails | 否 | 权限、安全、合规和不可逆操作确认等硬性保护规则 |

以 `query-object-ranking` 为例，它包含 TOP 排名和指定对象查询两个可以独立归因、独立修改的业务能力：

```nginx
routingcapability.object_rankingcapability.object_detailshared.responseshared.boundaries
```

| Module | 对应 SKILL.md 内容 | 职责 | 典型失败 |
| --- | --- | --- | --- |
| routing | frontmatter 的 description、触发条件和 Step 0 | 识别排名查询或指定对象查询，并选择对应模式 | 排名请求未触发，或对象查询被分到排名模式 |
| `capability.object_ranking` | Step 1.2，以及 Step 2～Step 4 中 TOP 排名模式的规则和输出 | 选择分析任务，查询并输出对象 TOP 排名 | 多任务时未让用户选择，或排名结果输出错误 |
| `capability.object_detail` | Step 1.1，以及 Step 2～Step 4 中单对象模式的规则和输出 | 按名称或编号查询指定对象，并合并多个数据分组的数据 | 单对象查询被输出成 TOP 榜单，或多个数据分组未合并 |
| shared.response | 两种模式共同遵守的 Markdown、表格和数值展示规则 | 保证公共输出格式一致 | 表格格式错误或公共字段遗漏 |
| shared.boundaries | 不适用场景、对象名称与类别混淆处理及共用异常规则 | 区分对象查询与类别、分组、目标、归因等其他维度 | 类别或分组查询错误进入本 Skill |

从能力划分看，“哪些对象的待处理记录最多”对应 `capability.object_ranking` ；“查一下示例对象 A 的示例指标”对应 `capability.object_detail` 。该 Skill 不包含权限、安全或不可逆操作，因此不需要强行增加 `shared.guardrails` 。该示例用于说明业务边界；是否能启动自动进化，还需单独检查 Case 真值和评测就绪条件。

- 不同类型 Skill 的划分建议

| Skill 类型 | 建议划分方式 |
| --- | --- |
| 单一处理路径 | 一个 `capability.runtime` ，必要时增加 `shared.boundaries` 和 `shared.guardrails` |
| 多处理路径 | 每个可独立归因和修改的处理路径建立一个 `capability.<name>` |
| 包含公共输出规范 | 能力 Module 之外增加 `shared.response` |
| 包含公共业务边界 | 将适用条件、业务阈值、异常输入和降级规则划入可进化的 `shared.boundaries` |
| 包含权限或高风险操作 | 将权限、安全、合规和不可逆操作确认划入只读的 `shared.guardrails` |
| 以能力识别和分流为主 | 单独建立可进化的 `routing` ；修改 Skill 触发范围时须有路由评测 case 覆盖 |

Module 数量不宜过多。只有当两部分内容对应不同能力或处理路径、能够独立归因，并且可以独立修改时，才应拆分为不同 Module。

- Module 边界定义方式对比

|  | 在 `SKILL.md` 中加 分隔符 | 外部 `module_spec` ✅ | **每** **轮** **由** **模型** **动态识** **别** |
| --- | --- | --- | --- |
| **实现⽅式** | 直接 在 正⽂中 标 记Module 起⽌位 置 | 在 独⽴ 配置 中记录 Module 与 `SKILL.md` 内 容范 围 的 映 射 | **反思** 时由模型临时判断 Module 边界 |
| **优** **点** | **定位准 确** | 不修改现有 Skill ，可进⾏⼈⼯审核和版本管理 | **⽆须预先** 配置 |
| **缺** **点** | 需要修改全部现有 Skill ，并在业务⽂档中引⼊进化标记 | **Skill** 结构 变化后需要 同步 更 新 配置 | 边界不稳定，不同轮次可能识别出不同结果 |

- Module 配置与使⽤约束

`module_spec` 在 Skill ⾸次进⼊进化流程时⽣成，配置⽣成和使⽤规则如下：

| 阶段 | 处理规则 |
| --- | --- |
| ⾸次配置 | 当前⼯具按标题和关键词⽣成草稿；⼈⼯按业务能⼒合并或拆分 span，并确认只读规则 |
| 进 **化** **启** **动** | 重新计算 `SKILL.md` 的内容摘要；若与 `source_hash` 不⼀ 致 ， 则 暂 停 进 化并重新确认 Module 边 界 |
| Module **选择** | 根据失败 case 的归因结果，选择最相关的可修改 Module ，不按固定顺序轮询 |
| 单轮变 **异** | 反思模型读取完整⽗版本作为上下⽂，但默认每轮只修改⼀个⽬标 Module ，其他内容保持不变 |
| **变** **异** **校** **验** | 检查实际差异是否全部位于⽬标 Module ，并确认只读 Module 未发⽣变化 |
| 复杂 **归** **因** | 单 Case 涉 及多 个 Module 、 指向只读规则 或⽆ 法 可靠定位 时 ， 交由⼈⼯确认 ，不 ⾃动 执⾏跨 Module 修改 |

Module 变异完成后的⼦版本全量评测、⽗⼦⼊池判定及候选池更新，统⼀按照 2.1 全局流程执⾏，本节不再重复说明。

▐ **2.4 归因变异提示词设计**

归因与变异使用两个独立提示词：归因提示词按 Case 执行，变异提示词在选定目标 Module 后执行。

- **归因提示词输入**

| 输入项 | 内容 |
| --- | --- |
| 当前 Skill | 父候选对应的完整 `SKILL.md` 内容 |
| 用户问题与 Ground Truth | 当前 Case 输入和按维度组织的可信标准答案，用于判断期望行为 |
| Module 配置 | `module_spec` ，包括 Module ID、对应内容范围及是否允许修改 |
| 执行轨迹 | Zelda `执行轨迹接口` 返回的结构化 `messages` ，包括用户输入、助手回复、工具调用和工具结果 |
| 评测结果 | Zelda 统一评测链路产出的最终结构化结果，语义上对应 `评分接口` 的判分数据：总分、各维度分数、原子问题判定、评分依据和原因；不传无关 ID 与 debugInfo 等调试字段 |

全部黄金 Case 都执行归因。失败 Case 用于定位问题，成功 Case 用于识别变异时需要保留的正确行为。统一评测系统负责产生 Trace 和评分，自进化流程负责把这些产物编译成反思反馈。

归因输出需要表达分类、责任 Module、证据引用、失败原子问题、期望行为、需要保持的行为和置信度。只有可信 SKILL\_ISSUE 驱动变异；RUBRIC\_ISSUE、CASE\_ISSUE、ENVIRONMENT\_ISSUE 和 UNCERTAIN 分别进入指标、Case、环境处理或人工澄清。证据非空不等于证据真实，引用应能在对应执行记录中校验。

选择目标 Module 时，当前实现聚合 `(1 - case_score) × confidence` 。最高信号并列或责任范围无法收敛时暂停；零信号和低置信度的确定性门禁仍需补齐。

- 变异提示词输入

| 输入项 | 内容 |
| --- | --- |
| 当前 Skill | 父候选对应的完整 `SKILL.md` 内容 |
| 用户问题与 Ground Truth | 当前 Case 输入和按维度组织的可信标准答案，用于判断期望行为 |
| Module 配置 | `module_spec` ，用于确定各 Module 的内容范围和修改权限 |
| 目标 Module | 根据归因结果选出的本轮唯一可修改 Module，以及该 Module 的当前内容 |
| 执行轨迹 | 全部黄金 Case 的 `执行轨迹接口` 结果，供模型核对实际执行行为 |
| 评测结果 | 全部黄金 Case 的 `评分接口` 最终结果，供模型同时识别失败问题和需要保留的成功行为 |
| 归因反馈 | 归因提示词生成的 Case 级问题原因、责任 Module、证据和期望行为 |
| 历史变异 | 目标 Module 最近被淘汰的修改内容及淘汰原因；没有历史记录时不传 |
| 修改约束 | 仅允许修改目标 Module，不得修改只读 Module、硬编码评测 Case 或虚构不存在的工具能力 |

变异提示词只生成目标 Module 的替换内容，再由系统与父候选中的其他内容合并，形成完整子候选。模型不能修改只读 Module、写死评测答案或虚构工具能力；Trace、用户文本和工具输出作为不可信证据输入，不能变成新的执行指令。

上表描述完整设计输入。当前实现传入父 Skill、Module、分数、归因摘要和简略失败记录，尚未完整传入全部原始 Trace、判分及历史 diff。已有评测引用、diff.patch 和 mutation.json 可以复用，后续主要补齐证据消费链路，避免新增第二套存储或评分流程。

![](https://mmbiz.qpic.cn/mmbiz_png/33P2FdAnju8PWonAvnSfAGMpeE3YoiaMh4VoKj8BNXvBKD7gmWMIVHVCTFwpicOzsEO86cHYQfhz705RmljnolKA/640?wx_fmt=png&from=appmsg)

实践中的关键取舍

这套设计保留了三组取舍：通过全量评测换取候选可比性，通过单 Module 修改换取边界可解释性，通过全局候选池保留局部优势而不立即只追逐均分。

更完整的搜索系统也意味着额外成本：需要可信真值、首次 Module 审核、候选评测预算，以及对版本、异常和人工决策的状态管理。它适合业务边界较清楚、评测资产较完整、需要持续优化的 Skill；缺少可信真值或环境不稳定时，应先建设这些基础条件。

Skill 自进化最终要让每次修改都能回答三个问题：依据是什么，范围在哪里，收益如何验证。黄金集与 Trace 提供依据，Module 收住范围，全量评测和独立保留集检验效果，状态与报告保留可追溯过程。人工在首次边界和最终交付中作出业务判断，模型在这个范围内探索更好的版本。
