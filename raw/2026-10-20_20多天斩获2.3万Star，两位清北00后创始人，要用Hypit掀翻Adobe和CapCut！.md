**🚥 十字路口**

比起用 Opus 剪视频，Hypit 有什么不同？

**👨🏻💻 Kashorin**

Opus 5.5 想创意的能力已经很强了，但要把创意变成一条完整的视频，中间还有一大堆制作工作。

人物和声音要生成，产品界面要用真实录屏，有些动效适合用 JS 代码而非 diffusion model，甚至还要涉及 2d、3d 场景和 blender 建模，最后还要把这些东西放到同一条时间线上，口播说到哪个词、音乐卡在哪个点、画面对应怎么变化，都得视听联动、紧密配合。

当然，直接放手交给 Agent 做，它也会想办法调工具、写脚本，把视频做出来。但这是它给自己临时搭的一套视频制作系统，下一条可能又换一套、或者换另一个会话可能完全看不懂，所以前面搭的脚手架很难复用。

**Hypit 在做的就是，把这个制作层提前做明白、做彻底。把这些需要反复折腾的制作工作彻底工程化，让 Agent 的创意能够更顺利地变成视频结果。**

比如，素材编排、AI 生成、代码动效，以及它们之间的时间关系，这些都可以用同一门语言来表达，而 Agent 可以像维护一个代码项目一样，持续修改视频。

另外，做好的组件、字幕、特效样式，也可以一行代码 import 到下条视频里。

接下来，介绍一下你们专门为视频 Agent 设计的那套语言吧？

**👨🏻💻 Kashorin**

这门语言叫 SVML，Semantic Video Markup Language。

**你可以把它理解成视频的源代码：口播谁来说、稿子怎么写、需要哪些素材、画面层级怎么组织，以及说到哪里发生什么，都可以在同一个项目工程里统一表达。**

**Agent 负责在 svml 源文件里把创意写明白，Hypit 的编译器和运行系统负责把它执行出来。**

**🚥 十字路口**

视频领域为什么需要一套新的语言范式？

**👨🏻💻 Kashorin**

现在制作一条视频，已经有几种很不一样的范式被混在一起了。

大家自己做内容的时候，一部分是对已有素材的剪辑，一部分要调 AIGC 模型生成，还有一部分是让 Agent 写 js 代码做动效。它们经常出现在同一条视频里，但各自的工具理解和表达的是不同的。

如果生成素材在一个脚本、动效在另一个脚本、音画对齐又换了一个脚本，那对这条视频来说，一开始原本应该存在的完整的、自包含的创意，就被拆散到各个地方了。

但最后总要有地方记录这些东西为什么放在一起，以及改了其中一部分之后，其他地方该怎么跟着联动更改。

**传统剪辑的起点是：我已经有这些素材了，接下来应该怎么剪辑、怎么编排。但 AIGC 是反过来的，先有意图、再组织素材。**

而且，视频创作的具体执行者也从人类变成 Agent 了。

过去的 NLE 软件界面可以让人用手眼直接调整画面，确实很直观；但 GUI 或者 computer use 并不是 Agent 原生拥有的能力，代码读写才是。

**我们希望给 Agent 一个能直接表达这些关系的源代码入口。**

让它能用一行代码表达“这段话期间这样展示这张卡片”，再由系统把关系落实到时间线上，从而让创作意图能跟着工程一起精准地保存。

这也是为什么我们从做内容、做画布、交付客户，一路更新到了做语言、做系统。

我们反复遇到的其实是同一个问题：一条视频要生成、要剪辑、要写动效，还要不停地修改。 **必须要有一层统一的表达范式，让这些工作能在同一个工程里彼此承接，值得复用的模块也能积累到生态。**

**🚥 十字路口**

做这样一个产品最大的难点是什么？

**👨🏻💻 Kashorin**

**架构上最难的其实是把它做小。我们花了很多精力把语言内核做到最简。**

一开始很容易把自己熟悉的制作流程写死进去：这里先生成口播，那里再加字幕，最后必须有一步导出视频。这样搭一条流水线很快，但是做几种不同的视频就会发现，有的根本用不到 AIGC，有的是纯动效，有的全程是用户提供的实拍，比如 VLOG 混剪。

如果每多一种情况，都要去改一次底层，那这个系统很快就会达到指数级的复杂度。

**我们把内核收敛到了一个很简单的职责上：推进一张依赖图。**

**具体架构设计上很像 DSH 的“一切皆插件”的思想：通过模块化、解耦合来消除不必要的复杂度。**

只需要知道一个节点需要什么、产出什么，哪些结果已经有了，接下来可以做什么。至于这个节点是在生成视频、对齐语音还是渲染字幕，由内核之外的组件和能力实现。甚至于说，源码怎么被解析成依赖图，也可以和内核本身分开。

**🚥 十字路口**

展开聊聊在这个架构中，用户能感知到的一些设计点？

**👨🏻💻 Kashorin**

我举三个我们自己做视频时反复遇到的问题，它们后来都变成了 Hypit 里的设计。

**第一个是语义时间线——把视听关系直接写进口播稿。**

比如我们之前给客户做了一百条口播，每条都要在说到 Google 时弹出图标。我们让作者在稿子上标记：这段话期间展示配图，这个词说完时触发音效，系统把实际声音与台词逐词对齐，再显化到成片时间线上。有上百条视听素材的积累。

这样保存下来的视听关系，就能随新的口播重新对齐，音效、配图和字幕不用每次重新找位置。

![](https://mmbiz.qpic.cn/sz_mmbiz_gif/a16Y4PLxPql1C7AT1u5sYEl2fiaBUGon7yFJ51YcYzyGYjBd8H2Niarice3EQF9HKw8RvlHDPo0vUAWVds8fjOtSfHXOnuNTXAzmfKwzgNuk0w/640?wx_fmt=gif&from=appmsg)

左边是口播稿，右边是视频，时间点都用「@」语法直接标记在口播稿里

**第二个是 Dual 语法——让字幕和朗读各自表达准确。**

比如字幕写“9:30”，但口播要读成“nine thirty”，就在口播稿里直接写 <9:30 | nine thirty>。左边给字幕，右边给朗读和语音对齐，创作者不用去维护两份口播稿。

还有更有意思的玩法：这支队伍<实力一般 | 路边一条>，如果不开声音还以为无事发生。这样既能照顾发音，也能让字幕显示<更简洁 | 不被审核抬走>，不用把所有口语都原样显示在画面上。

**第三个是双图解耦——让创作意图和运行意图彻底分开。**

创作图只用写制作安排：台词、素材、动效，以及它们之间的依赖关系；运行图写这次执行要得到什么、明确复用哪些已有结果。

现在，市面上大多数画布产品显然没有做到解耦，所以每次想单跑一个素材，必须得把所有接线都删掉，生成完之后再重连。我们之前用 ComfyUI 的时候也浪费了大量时间做这种事，而 Hypit 天然避免了这个问题。

**🚥 十字路口**

AI 视频的 token 调用量居高不下，Hypit 能降低到什么程度？

**👨🏻💻 Kashorin**

我们主要优化两件事：Agent 的效率，以及 AIGC 的可用率。

**AIGC，关键就是把已经满意的结果留住。**

Hypit 可以做到，人物口播做好了，如果只想改字幕和排行榜布局，就明确复用原来的口播及对齐结果，只重新做后面的合成；如果某个镜头不满意，就把重新生成的范围限定在那个镜头，以及确实受它影响的后续步骤。

**Hypit 做的还有一层，制作方式的分工。**

人物和场景可以交给生成模型，字幕、Logo、数据图表和很多动效，则用代码渲染。比如字幕颜色不对，直接改参数重新渲染就可以，不需要让视频模型重新生成整段画面。我们通过把这些部分拆开、再统一编排，把修改控制在真正需要变化的地方。

节省幅度会随视频类型和修改次数变化。

**我们希望做到的是：下一次修改能根据已有成果往下接续制作；下一条同类型视频生成能沿用验证过的制作方法，让创作积累真正转化为更低的制作成本。**
