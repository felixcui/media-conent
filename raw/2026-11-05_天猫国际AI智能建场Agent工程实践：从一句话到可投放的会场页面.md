**作者**: 天猫技术团队

## 摘要

天猫国际把运营一句自然语言需求变成可投放的会场页面，做法不是让模型直接生成 JSON，而是「**ReAct 决策 + 确定性系统托底**」的 Agent Harness：**ReAct 决定下一步做什么，状态机决定当前阶段允许做什么**（不同任务状态对应不同工具白名单）。模型只负责理解目标、选工具、解释 Observation；代码负责模板缺口审计、状态迁移、字段坐标与 Schema 校验、确认值落盘、生产账本、并发锁/CAS/fence 与异步恢复。生产型工具按业务意图封装，统一携带 moduleName / moduleUuid / slot / key 四级业务坐标；圈品等分钟级任务走 MetaQ 异步回调续跑，迟到的回调要做有效性判断；前端用 SSE/AG-UI 同时消费文本、工具事件与业务卡片（900 秒超时、15 秒心跳）。项目沉淀的流式执行、Session/Task 模型、工具治理、异步续跑与 Trace 不绑定“会场”，可复用到 AI 设计、视频生成等长任务场景。

## 正文

本文介绍了天猫国际 AI 智能建场 Agent 的工程实践，旨在将运营人员的一句自然语言需求转化为可投放的会场页面。系统并非简单让大模型生成 JSON ，而是构建了以 ReAct 驱动决策、确定性机制约束边界的 Agent Harness 架构。通过状态机管控执行权限，利用字段级生产计划与业务坐标精准定位操作，并借助 MetaQ 异步回调处理耗时任务，确保长流程可控、可恢复。同时，项目沉淀了流式执行、AG-UI 事件协议及工具治理等通用基建，不仅支撑智能建场落地，也为 AI 设计等其他复杂 Agent 场景提供了可复用的底层能力。
摘要
“帮我搭一个七夕轻奢箱包会场。”
对于运营，这是一个自然、完整的业务目标；对于系统，它却远不是一份可以直接执行的指令。主题和品类之外，商品数量、选品条件、模块结构、素材尺寸、文案要求都可能缺失。系统还要跨越 U+ 圈品、图片生成、文案生成、页面装配与人工修改等多个环节，其中既有秒级同步能力，也有通过 MetaQ 回调完成的分钟级异步任务。
我们最终将智能建场设计为一个由 ReAct 驱动、由确定性机制约束的生产 Agent：模型负责理解目标、选择工具和根据 Observation 继续决策；状态机、生产计划、字段坐标和任务账本负责限制模型可以做什么、结果写到哪里以及失败后如何恢复；前端通过 SSE/AG-UI 同时消费文本、工具事件和业务卡片；异步圈品则在原对话结束后通过回调继续更新任务事实。
在落地智能建场的同时，项目沉淀了流式执行、AG-UI 事件、会话任务模型、工具执行与日志、异步任务续跑、Trace 和场景扩展点等基础设施。这些能力并不绑定“会场”语义，可继续承接 AI 设计、视频生成以及其他需要多轮交互和长任务编排的新场景。
业务背景：一句需求背后
是一条生产流水线
传统会场生产需要依次完成营销目标理解、模板与模块选择、商品圈选、图片与文案制作、页面配置、预览修改和投放发布。它并不是一条只能向前的固定流水线：商品不符合预期时要调整条件，图片风格不匹配时要重新生成，页面预览不协调时要局部修改模块。
运营目标  → 模板与模块  → 商品圈选  → 图片 / 文案生产  → 页面装配  → 预览与修改  → 投放
AI 能够降低理解和生产成本，但也引入三类新的工程问题。
第一，自然语言不等于生产参数。“七夕轻奢箱包”没有说明价格、品牌、商品分层和坑位数量。模型如果自动补齐，会替用户做不可见的业务决策；如果系统逐项追问，AI 又会退化成效率更低的表单。
第二，模型决策不等于业务事实。模型可以说“圈品已完成”，工具也可以返回 success=true，但 U+ 可能只是接受了任务。真正的 datasetId 需要等待异步回调；商品数不会在生产回调中额外查询，投放结果则要等用户点击“我要投放”后才能产生。
第三，一次连接覆盖不了完整生命周期。圈品可能持续数分钟，期间用户可能刷新页面、关闭 SSE 或修改同一字段。系统必须脱离聊天上下文保存任务状态，并能判断迟到的回调是否仍然有效。
因此，智能建场的目标不是“让模型输出页面”，而是：
把不完整的用户目标转化为可确认的生产计划，让每次工具调用都有明确边界，让跨请求结果能够恢复，并让最终页面的每个字段都可解释。
整体设计：ReAct 决策，
确定性系统托底
▐  3.1 一次建场任务如何流动
完整链路可以概括为：
用户输入自然语言  → 恢复 Session / Task  → 模板缺口审计与澄清  → 用户确认终值或 AI 生成指令  → 形成字段级 ProductionPlan  → ReAct 选择圈品 / 生图 / 生文工具  → 同步结果写入页面，异步结果登记账本  → 前端预览并提出局部修改  → 重新生产受影响字段  → 用户确认完成
这里有两条并行但不能混淆的链路：
推理链路：模型根据用户目标、任务状态和工具 Observation 决定下一步；
事实链路：Task 保存页面终值、待生成字段和异步终态，决定系统实际上完成了什么。
对话是入口，Task 才是业务事实。
▐  3.2 为什么采用 ReAct
固定 Workflow 适合输入完整、路径稳定的任务，但会场生产的执行顺序取决于模板和用户选择：有的模板只需要生图，有的同时需要生图、生文和圈品；用户还可能在预览后只修改其中一个字段。如果预先为所有组合编排固定节点，流程会随着模板和场景快速膨胀。
ReAct 适合处理这种动态决策：
Reason：理解当前缺口与任务状态Action：选择并调用一个或多个工具Observation：读取工具结果或受理状态Reason：判断继续生产、请求确认还是结束本轮
但我们没有让 ReAct 自由控制业务。模型只负责“下一步想做什么”，确定性系统负责“当前是否允许做”“参数是否合法”“结果写到哪里”。
▐  3.3 ReAct 与状态机如何分工
两者职责可以用一句话区分：
ReAct 决定下一步做什么；状态机决定当前阶段允许做什么。
任务状态与工具白名单对应：
核心状态转移为：
INIT + CLARIFY_COMPLETE → RUNNINGRUNNING+ MATERIAL_GENERATED → WAITING_CONFIRMWAITING_CONFIRM + MODIFICATION_CONFIRMED → RUNNINGWAITING_CONFIRM + PUBLISH_CONFIRMED → COMPLETED
状态门控是运行时权限，不是写在 Prompt 里的建议。即使模型判断发生漂移，也无法在需求未确认时提前圈品，或者在任务完成后继续写入。
▐  3.4 模型与确定性机制的边界
模型适合承担：
理解自然语言目标；
生成摘要和预填建议；
选择当前需要调用的工具；
把自然语言修改翻译为候选原子操作；
根据工具 Observation 解释当前进展。
代码必须承担：
模板必填缺口审计；
任务状态迁移与工具权限；
字段坐标、下标和 Schema 校验；
用户确认值落盘；
工具结果写入和生产账本维护；
并发锁、CAS、fence 和异步恢复。
这条边界让模型保持灵活，也让真实副作用处于业务允许的范围内。这条边界让模型保持灵活，也让真实副作用处于业务允许的范围内。换句话说，ReAct 并不直接控制业务系统，而是运行在 Agent Harness 内：模型决定想做什么，Harness 决定当前能否做、可以操作哪里，以及结果能否成为业务事实。
Agent Harness：把模型
装进可生产运行的工程外壳
智能建场并没有被实现成一条只会调用模型和工具的业务链路。我们把模型视为可替换的推理内核，在它之外建设 Agent Harness：由 Harness 统一管理操作人身份、Session/Task 生命周期、状态与工具权限、真实副作用、流式交互、异步续跑以及运行证据。模型提供理解和决策能力，Harness 决定这些能力能否安全进入生产。
start  └─ app：Controller、Executor、HSF Provider、业务编排      └─ infrastructure：Spring AI、工具实现、MetaQ、Tair、外部 SDK          └─ domain：任务模型、状态机、Ability、Gateway 抽象              └─ common：AG-UI 协议、常量、异常与工具类infrastructure → client：对外 API 契约与 DTO
▐  4.1 请求、身份与流式生命周期
一次 Agent Run 不是匿名调用模型，而是在明确的操作人、业务场景、Session 和 Task 边界内运行。AbstractStreamingChatExecutor 统一完成“解析登录身份 → 创建或恢复 Session → 获取 Session Lock → 创建或加载 Task → 恢复消息与业务事实 → 执行 Agent → 持久化结果并释放资源”；BaseStreamingExecutor 负责 SSE 传输与生命周期。公共能力包括：
创建和管理 SseEmitter；
900 秒连接超时与 15 秒心跳；
客户端断连、超时和异常后的 Flux 取消；
并行事件发送锁； 身份解析、会话锁和资源释放；
Reactor 线程切换后的 Trace 上下文恢复。
生产请求从登录上下文解析 operatorId/operatorName，Session 与 Task 查询继续携带 operatorId 校验资源归属；这属于身份解析与数据归属隔离，而不是完整 RBAC。场景 Executor 只需实现“如何重建上下文、应用输入和调用场景 Agent”，AI 设计等新场景可以直接复用这套运行壳。
▐  4.2 AG-UI 事件基座
通用协议已经覆盖：
RUN_STARTED / RUN_FINISHED / RUN_ERRORTEXT_MESSAGE_START / CONTENT /ENDREASONING_MESSAGE_START / CONTENT /ENDTOOL_CALL_START /ENDCUSTOM
基础事件负责描述运行、文本和工具生命周期；场景只需定义自己的 CUSTOM 卡片。例如智能建场定义 clarification、modificationProposal 和 venueResult，AI 设计可以扩展设计方案卡、素材选择卡和画布结果卡，而无需重新设计整套流式协议。这样前端不会根据“我已经完成”之类的模型文本猜状态，而是根据工具事件、Task 结果和业务卡片驱动交互。
▐  4.3 Session、Task 与状态机：管理长流程业务生命周期
Harness 用四类持久化对象承接一次 Agent 的完整生命周期。对话上下文可以重新构造，但 Task 中的业务事实不能依赖模型记忆：
状态机在这套生命周期中不是流程展示，而是运行权限系统：TaskStatus 决定动态工具白名单，ProductionPlan 决定可操作字段，CAS 保证旧请求不能覆盖新阶段。当前实现提供 operatorId 归属隔离和环境隔离，不将其泛化为尚未建设的角色权限平台。
▐  4.4 Tool Runtime：让工具成为受治理的生产权限
AbstractStreamingAgentGateway 与 StreamingToolCallHook 共同构成 Tool Runtime：先按状态过滤工具并包装 ToolCallback，再完成坐标预检、Run 级原子防重、TOOLCALLSTART/END、工具计数、dependency.log 与 toolcalllog 留痕；执行完成后，在 Task 锁内委托 ToolResultPostProcessor 写入业务事实，最后进行模型表述与真实轨迹的一致性审计。Prompt 约束模型的行为倾向，Tool Runtime 约束真实执行权限。 失败且未产生副作用时，Runtime 可以撤销轮内坐标并允许有限重试；同一工具连续失败达到阈值后本轮熔断。只读或幂等工具可以在审计命中时安全重放，圈品、生图等生产型副作用工具不能因为模型声称“已完成”而自动补执行。 智能建场只需提供圈品、生图、生文和修改提案等场景工具，以及 VenueToolResultProcessor 和业务卡片映射；ToolContext 直接携带模板、当前结果、账本、圈品记录与 ProductionPlan，避免让 LLM 搬运大 JSON。AI 设计可以复用同一个 Runtime，把图片、图层或设计方案写入自己的结果模型。工具因此不是模型随意调用的函数列表，而是 Harness 管理的业务动作与生产权限。
▐  4.5 异步运行时、运行证据与场景复用
Harness 将“一次 Agent Run”与“完整业务任务”解耦。同步 Run 只登记外部任务已经受理，Tair 保存回调上下文，SSE 可以结束；MetaQ 到达后重新加载 Task，在 Task Lock 内修改事实，并通过 createBizId fence 判断结果是否仍代表当前用户意图。它不仅适用于 U+ 圈品，也可以承接异步生图、视频生成和批量设计。 运行证据同样属于 Harness：AgentRunLog 记录 Run、TTFT、Token、工具次数、熔断与审计；toolcalllog 记录真实工具输入输出；dependency.log 聚合 LLM、TOOL、HTTP、HSF、TAIR、METAQ 等依赖耗时和错误；Trace 串联 HTTP、Reactor、工具线程与回调线程。一个新场景主要需要扩展：

工具设计：把底层接口
转化为 Agent 可用的业务动作
▐  5.1 为什么不能直接暴露底层接口
底层服务通常围绕系统能力设计：创建圈品任务、查询预览商品、调用生图接口。模型需要的却是围绕业务目标设计的动作，例如“为指定模块坑位圈选商品”。因此场景工具不会直接暴露底层接口，而是以业务语义接入 Harness 的 Tool Runtime；Runtime 再统一处理状态权限、坐标校验、调用留痕、副作用和结果后处理。 因此，工具设计遵循三个原则：
一个工具表达一个模型可理解的业务意图；
参数只保留完成该意图所需的最小信息；
外部调用编排、协议转换和结果校验封装在工具内部。
▐  5.2 五个核心工具如何协作
analyzeRequirements  识别模板缺口并生成澄清卡selectProducts  将用户确认的条件提交给 U+，返回异步受理结果generateImage  结合生成指令、x-format 和 x-reference 生成图片generateCopy  结合用户意图与 ai_description 生成文案proposeModification  将自然语言修改翻译为待确认的原子操作
这些工具并不直接组成固定流水线，而是由 ReAct 根据 Task 状态、ProductionPlan 和上一轮 Observation 动态选择。
▐  5.3 工具参数如何收敛到业务坐标
所有生产型工具都需要携带统一坐标：
moduleUuid + moduleName + slot + key + index
moduleName 定位模块类型；
moduleUuid 区分同名模块实例；
slot 定位 Schema 资源位；
key 定位字段；
index 定位数组中的具体一组。
模型不是自由编造坐标，而是从 ProductionPlan 中选择。工具侧再次校验该坐标是否属于模板和本轮计划，工具后处理也按相同坐标写入结果。
▐  5.4 工具结果同时服务三类消费者
工具结果不是只给模型读的一段文本，它同时服务：
ReAct：作为 Observation 判断下一步；
Task：由后处理器写入终值或过程状态；
前端：通过工具事件和 venueResult 展示真实进度。
例如 selectProducts 返回 createBizId 后：模型观察到“已受理”，Task 把坐标置为 GENERATING，前端显示“正在圈品”。三者共享同一个事实，但呈现方式不同。
▐  5.5 按副作用设计错误和重试
工具被分为三类：
只读/提案工具：如 analyzeRequirements、proposeModification，可在安全条件下重放；
同步生产工具：如生图、生文，失败且未产生副作用时可有限重试；
异步副作用工具：如圈品，受理后不能因等待或本地异常机械重提。
错误协议需要表达：发生了什么、是否已经产生副作用、能否重试、需要用户修改什么。统一返回“调用失败”会诱发模型盲目重试。
需求进入系统：
从一句话到字段级生产计划
▐  6.1 先审计模板，再询问用户
前端首次请求携带 templateId、templateSchema 和类型化 content：
{  "sessionId": null,  "taskId": null,  "templateId": "template-id",  "templateSchema": "{...}",  "content": [    {      "type": "text",      "text": "帮我搭一个七夕轻奢箱包会场"    }  ]}
系统不会把整个模板交给模型后让它自由判断缺失项，而是先根据模板必填模块、need_clarify 字段和当前 renderResult 做确定性裁剪。LLM 只负责理解用户表达、生成摘要和提供预填建议。 这解决了两个问题：一是必填字段不会因为模型漏判而消失；二是模型服务失败时仍可退化为一张空白澄清卡，不让完整链路中断。
▐  6.2 澄清卡是输入协议，不只是交互组件
澄清卡下发内容包含需求摘要、缺失字段、已识别字段和预填值。其中 missingFields 与模板 Schema 同构，前端无需再次回查模板即可渲染表单。 用户提交时使用 value + fillMode 双树：
{  "type": "clarification",  "values": [    {      "moduleName": "alimod-tmg-act-feeds-v1",      "value": {        "tabFeedsList": [          {            "tabName": "轻奢箱包",            "displayId": "选择轻奢箱包类目商品"          }        ]      },      "fillMode": {        "tabFeedsList": [          {"displayId": "ai"}        ]      }    }  ]}
manual 或缺省：同坐标值是终值，直接写入 renderResult；
ai：同坐标值是生成指令，登记到 pendingGenerations。
用户确认值不再交给外层 LLM 二次解释。对圈品尤其重要：tabName 只负责展示，用户没有填写的价格、爆品、商品分层不能被静默加入真实条件。卡片所见即工具所执行。
▐  6.3 从确认结果生成 ProductionPlan
确认完成后，系统审计还缺哪些可自动生产的字段，并生成 ProductionPlan。每一项计划包含：
字段坐标operationType       image / text / productimageSize           从 x-format 解析referenceImageUrls  从 x-reference 获取description         用户确认的生成指令aiDescription       模板固有生产约束optional            是否允许自动生成
description 和 aiDescription 刻意分离：前者代表用户这一轮想要什么，后者代表模板长期要求的尺寸、字数和风格边界。用户填写新指令不能覆盖模板约束。当账本中存在待生产项时，只为 PENDING 项生成计划；账本整体为空时才允许根据 Schema 构造全量计划。若账本中只有 GENERATING 或 FAILED，不能回退到全量扫描，否则会再次生成正在执行或已经失败的字段。
素材生产：
ReAct 如何协调圈品、生图与生文
任务进入 RUNNING 后，模型获得 ProductionPlan、当前 renderResult、账本状态和允许使用的工具。ReAct 根据字段类型选择工具，可以串行执行存在依赖的动作，也可以并行执行互不依赖的素材。
▐  7.1 生图：用户意图与模板约束共同生效
generateImage 使用用户确认的生成指令作为内容目标，从 Schema 的 x-format 获取图片尺寸，从 x-reference 获取参考图。工具把这些信息转换成下游设计服务需要的参数，并在结果中带回图片 URL 和完整字段坐标。 结果后处理不依赖模型复述，而是直接：
校验坐标  → 定位 renderResult 中的模块和字段  → 写入图片 URL  → 从 pendingGenerations 销账  → 保存最新 Task
因此，即使多个生图工具并行结束，结果也能写入各自位置。
▐  7.2 生文：内容要求与生产约束正交
generateCopy 将用户生成指令和 Schema ai_description 分开传给 Prompt。例如用户要求“写一条轻奢感七夕文案”，模板仍可要求“8～12 字、不得换行”。两类信息共同约束结果，而不是相互覆盖。 成功文案按坐标写入 renderResult，并移除相应待生成项。工具结果中的纯文本不会再次 JSON 序列化，避免页面出现额外引号。
▐  7.3 选品：同步阶段只接受任务，不伪造终值
selectProducts 校验目标坐标后，将用户可见的条件提交给 U+。同步阶段只返回受理状态、createBizId 和选品上下文，并不向 renderResult 写入 displayId。
后处理器把账本项置为：
{"status":"GENERATING","createBizId":"biz-xxx","errorMsg":null,"datasetId":null}
这一设计明确区分：
工具调用成功 ≠ 圈品业务完成 ≠ 页面终值已写入
ReAct 得到的 Observation 是“任务已经受理”，不应在同一轮重新提交；前端看到的状态是“正在圈品”，而不是“圈品成功”。
▐  7.4 结果汇聚为唯一页面事实
Task.resultJson 中三类数据各司其职：
“正在生成”这类中间态不会写进页面终值。后端从账本聚合 moduleStates：模块内任一字段在途则为 GENERATING；无在途但存在失败项则为 FAILED。前端因此无需理解字段级编排，也能正确显示模块状态。
异步圈品：如何跨越一次
ReAct 和 SSE 生命周期
▐  8.1 为什么不能让 Agent 原地等待
U+ 圈品耗时可能达到分钟级。让 ReAct 在线程内轮询，会长期占用连接，并在超时后留下“不知道外部是否已经执行”的不确定状态；若模型因此自动重试，还可能创建多个真实圈品任务。 因此，异步圈品采用两段式执行。
▐  8.2 第一段：同步受理
Agent 调用 selectProducts  → 标准化用户确认的圈品条件  → U+ 返回 createBizId  → 回填上下文写入 Tair  → 账本坐标置 GENERATING  → 本轮 SSE 可以正常结束
Tair 中保存回调继续执行所需的 Task、字段坐标和选品上下文。回调不依赖原来的模型上下文或 SSE 连接。
▐  8.3 第二段：MetaQ 回调续跑
U+ MetaQ 回调  → 根据 createBizId 读取上下文  → 获取 Task 级锁  → 在 pendingGenerations 中查找受理号  → 回填业务终值  → 移除对应账本项  → 写入 selectionRecords  → 保存 Task 并释放锁
生产回调先校验 sessionId 与 datasetId：缺失时把账本和 selectionRecords 标为 FAILED；成功时直接使用回调 datasetId 清账并写入 COMPLETED 记录。回调侧只更新业务事实，不直接驱动任务状态机，任务阶段仍由正常对话编排推进。
▐  8.4 fence 如何处理迟到回调
用户可能在圈品等待期间修改同一字段。此时新操作调用 resetToPending，清空旧 createBizId 并登记新的生成指令。旧回调到达后无法在账本中命中受理号，被判定为已被新操作取代并丢弃。
这是一种面向业务坐标的 fence：不要求外部回调严格有序，只要求结果写入前仍然代表当前用户意图。
▐  8.5 前端轮询与刷新恢复
前端收到 moduleStates=GENERATING 后，整模块显示“正在圈品”占位，并按 10～30 秒查询：
GET/venueast/json/result?sessionId=123&operatorId=xxx
moduleStates 清空后停止轮询。即使用户刷新页面，也可以从 Task 恢复 renderResult、在途状态和圈品明细；连接不再是任务的事实来源。
结果交付：前端如何
看到真实生产进度
▐  9.1 一次 SSE 运行
主入口为：
POST /venueast/chat/streamContent-Type: application/jsonAccept: text/event-stream
SSE 连接超时 900 秒，每 15 秒发送心跳。客户端断连、超时、异常和正常完成都会取消上游 Flux、停止心跳并释放会话锁。
一次运行以 RUN_STARTED 开始，以 RUN_FINISHED 或 RUN_ERROR 结束。文本和 Reasoning 使用独立 messageId 聚合，工具事件按 toolCallId 配对。
RUN_STARTED  → TEXT / REASONING 增量  → TOOL_CALL_START ... TOOL_CALL_END  → CUSTOM 业务卡片  → TEXT_MESSAGE_END  → RUN_FINISHED
同名工具可以并行执行，前端不能按 toolName 配对，否则两个 generateImage 的开始与结束可能错位。
▐  9.2 三类信息必须分开
前端需要区分：
模型说明：自然语言解释，帮助用户理解；
工具事件：表示工具函数开始和结束；
业务卡片：表示用户可操作或页面可消费的结构化事实。
三个核心 Custom Event 为：
clarification：澄清卡；
modificationProposal：修改确认卡；
venueResult：会场结果。
venueResult 示例：
{  "type":"CUSTOM",  "name":"venueResult",  "value":{    "taskId":456,    "taskStatus":"WAITING_CONFIRM",    "renderResult":[],    "pendingGenerations":[],    "moduleStates":[],    "selectionRecords":[]  }}
前端以 renderResult 渲染终值，以 moduleStates 决定模块占位和轮询，以 selectionRecords 展示标准化条件、tab 名称、圈品链接、datasetId、后续创建的 displayId 和失败原因。
▐  9.3 运行结束不等于异步任务结束
RUN_FINISHED 表示本轮 Agent 调用结束，前端需要保存最新的 sessionId/taskId/currentStep，但不能因此停止仍在执行的圈品轮询。是否继续轮询由 moduleStates 决定。
这个语义拆分让同步对话和异步生产能够共享一个界面，同时避免用模型文本猜测真实状态。
人机协同：局部修改，
而不是重新生成整页
用户看到预览后，常见诉求不是“全部重做”，而是“把第二个模块的主图换成更轻奢的风格”或“删除第三个商品分组”。这要求系统理解自然语言，同时保护已经确认的其他结果。
▐  10.1 ReAct 先生成提案，不直接修改
在 WAITING_CONFIRM 状态，模型通过 proposeModification 将自然语言翻译为三类原子操作：
APPEND_ITEM   向数组资源位追加若干组UPDATE_FIELD  更新字段终值或登记新的生成指令REMOVE_ITEM   删除指定数组项
修改提案同时携带 moduleUuid、字段坐标、当前值、建议值、字段标题和 Schema 定义。后端先校验模块实例、数组下标和操作冲突，再通过 modificationProposal 卡片交给用户确认。
▐  10.2 确认后的操作不再由模型解释
前端把用户确认或微调后的 operations 以 modification 内容部件回传。应用层按确定性顺序执行：
APPEND_ITEM → UPDATE_FIELD → REMOVE_ITEM
manual 修改直接写入 renderResult；ai 修改重置对应账本项为 PENDING。系统只为受影响坐标生成新的 ProductionPlan，已经确认的其他商品、图片和文案保持不变。
▐  10.3 不确定时不猜测
当用户说“换一下那张图”但无法唯一定位模块，或者操作存在下标越界、同一资源位互斥修改时，服务端把原因放入 rejected，要求用户确认目标。生产系统宁可多一次确认，也不让模型猜测修改真实页面。
Harness 可靠性治理：
约束 ReAct 的不确定性
ReAct 提供动态决策能力，也会带来重复规划、参数漂移和语言结果与真实执行不一致等风险。可靠性治理的目标不是限制模型思考，而是防止一次模型抖动演变成业务事故。
▐  11.1 重复调用需要识别业务坐标
同一轮可能合法地为多个模块调用 generateImage，因此防重不能只看工具名。真正的业务键是：
toolName + moduleUuid + moduleName + slot + key + index
以 Run 级 Concurrent Set 对生产坐标做原子 check-and-add，并由 StreamingToolCallHook 在执行前统一预检。治理分为三层：
执行层：同坐标在途或已成功时，不再次产生副作用；
观测层：重复决策仍写入 tool_call_log，记录参数与拦截原因；
交互层：没有真实执行的拦截，不显示成一张“已执行工具”卡。
首次执行在未产生有效结果时会撤销 Run 内坐标登记，允许有限重试；同一工具连续失败 2 次后在本轮熔断，防止模型换措辞无限调用。跨轮则由 pendingGenerations 的 GENERATING 状态将已受理坐标排除出 ProductionPlan。异步圈品已经受理后不释放坐标，避免在 U+ 重复创建任务。
▐  11.2 三类并发使用不同机制
系统同时面对：同一会话的多轮请求、同一轮的并行工具、工具线程与 MetaQ 回调。对应机制为：
Session 分布式锁：同一 sessionId 只允许一轮对话；冲突时返回 SESSION_BUSY；
Task 级锁：串行化工具后处理与异步回调对同一 resultJson 的读改写；
CAS 状态迁移：只有旧状态符合预期才推进，避免旧请求覆盖新阶段；
SSE 发送锁：防止并行工具事件破坏帧顺序；
createBizId fence：阻止过期回调覆盖用户新操作。
锁解决并发执行，CAS 解决状态迁移，fence 解决跨时间结果有效性，它们不能互相替代。
