## 摘要

文章反驳了一个直觉做法：上下文满了就让模型写摘要。摘要的代价被低估——有损（文件路径、报错原文、用户随口提的约束最容易丢）、不可逆、昂贵（写摘要本身要读完整段历史），而且是“摘要的摘要”，多次压缩误差层层累积。更关键的是 Prompt Cache：主流服务支持前缀缓存，命中部分价格约为正常输入的十分之一，但一旦改写历史中某条消息，从这条往后的缓存全部失效。所以不是剪得越早越勤越好，而是攒够了一次性剪。文章给出五种手段，前四种纯工程、不调用模型，按顺序逐级使用：剪除无用片段；控制工具返回大小（超限只回“完整内容已存至 xxx，可分段读取”）；替换无用的工具结果；上下文折叠；最后才是写摘要兜底。原则是能保留原文就保留、能剪除就不改写、能折叠就不摘要。

一提到 Agent 的上下文压缩，很多人第一反应是"让模型写个摘要"。但从 Claude Code、Manus 等产品的工程实践来看，摘要恰恰是最后不得已才用的手段：它有损、不可逆、昂贵，还会让 Prompt Cache 失效。本文从"上下文由什么组成"讲起，给出一套评价压缩手段的标准，再按从无损到有损的顺序梳理五层工程化治理手段。

## 01

常见误解：压缩 = 写摘要

Agent 跑长任务时，上下文窗口迟早会被撑满。最直觉的做法是：快满了，就让模型把前面的对话总结一下，用摘要替换原文。

这个做法能用，但代价不小：

- **有损** ：文件路径、报错原文、用户随口提的约束，最容易在摘要里丢失；
- **不可逆** ：原文被替换后，模型再也看不到细节；
- **昂贵** ：写摘要本身就是一次"读完整段历史"的大请求；
- **会累积失真** ：多次压缩后，后面的摘要是"摘要的摘要"，误差层层叠加。

所以成熟的 Agent 框架遵循的思路是： **能保留原文就保留，能剪除就不改写，能折叠就不摘要** 。摘要不是主力，而是兜底。

## 03

如何评价一种压缩手段？

在讲具体手段之前，先明确评价维度。每一种手段，都可以从这四个角度衡量：

![](https://mmbiz.qpic.cn/sz_mmbiz_png/ZRhjO8xAWr6hsY6BKdD5wEicO1AZtmibEoUHhENnqkH0PcuC8d0zPtaDUIyG4Gc7rb6xicP0Vr3VXHbOcslQXA5usnMjHEkL4NvFJlbMfrvd7I/640?wx_fmt=png&from=appmsg)

其中最容易被忽视的，是 **Prompt Cache** 。

Agent 每一轮请求都会把完整历史重新发送给模型。主流模型服务都支持前缀缓存：只要请求的前缀和上一次完全一致，这部分就能命中缓存，价格通常只有正常输入的约 1/10，延迟也更低。

这意味着： **一旦你改写了历史中的某条消息，从这条消息往后的缓存全部失效** ，需要重新写入缓存。

由此得出一个结论： **不是剪得越早、越勤越好，而是要攒够了一次性剪** 。这也是为什么所有改写历史的手段都应该在"接近阈值"时批量触发，而不是每轮都做。

## 04

五种压缩手段

下面五种手段，前四种都是工程手段：不需要额外调用模型，只是决定"哪些内容发给模型、发多少"。第五种才是让模型写摘要。实际执行时按顺序来：前面的手段处理完，上下文还是太长，才用下一种。

先看一个例子。下图是让 AI "规划北京 3 日游"时的上下文，左边是处理前，右边是处理后，方块越高代表占的 token 越多：

![](https://mmbiz.qpic.cn/mmbiz_png/ZRhjO8xAWr54RImiahI38ICPU10NdNvHRwvLC2RHJCnWR7FeWiar5oBL1Y6lE2zmwJvdUHU3G2FLMBYxjYGicUu9OONnVicDfUXDiaGr3L0dc0Xg/640?wx_fmt=png&from=appmsg)

**4.1 剪除无用片段**

删除与当前任务无关的对话。比如让 AI 做旅行攻略做到一半，顺口问了一句"番茄炒蛋怎么做"，这一问一答对后续做行程没有任何影响，删掉不影响执行，但能省下不少上下文。 需要注意的是，判断"有没有用"并不容易。用户随口一句"我爸妈腿脚不好"，看起来像闲聊，其实是后面安排行程必须遵守的约束（不能排太多步行），删了就会出问题。拿 Claude Code 举例子，他们把一部分判断权交给了用户：

- `/btw` ：临时问个问题，这次问答不写入历史；
- `/clear` ：换一个不相关的任务时，直接清空上下文重新开始。

**4.2 控制工具返回大小**

限制工具输出的 token 数，超出部分不直接返回，而是提示"完整内容已保存在 xxx，如需查看可分段读取"，模型真需要时再去读。

另一种做法是把工具设计得更细：与其只提供一个"读整个文件"的工具，不如拆成"读标题""读正文""读首段""读指定行"。模型先看个大概，再决定读哪部分，而不是一上来就把几万 token 全拉进上下文。 同样的思路也适用于 System 部分：工具说明、技能说明一开始只放一句话简介，模型确定要用时再加载完整说明。

**4.3 替换无用的工具结果**

中间探索产生的大段结果，比如读过的文件、搜索结果、命令输出，模型看完用完之后，往往对后续任务就没影响了，可以直接去掉，换成一句简短提示，例如"这里原来是 30 家酒店的搜索结果，已清理"。后面真需要，再进行一次读取。 两个小技巧：

- 提示里写清楚原来读的是哪个文件、搜的是什么，这样模型知道去哪重新读；
- 结合上一节说的缓存问题，不要每轮都清，攒到一定量再一次性清。

Anthropic 认为这是最安全、最轻量的压缩方式，并且在 API 里直接提供了这个能力（ `clear_tool_uses` ）：上下文超过设定阈值时，自动清理最早的工具结果，只保留最近几次。

**4.4 上下文折叠**

对中间梳理过、后续可能还会用到的内容，比如 AI 对比过的 5 条游览路线，不再全文保留，只留关键片段和位置指引，例如：

> 选定路线 B（故宫→景山→北海），步行最少；5 条路线的详细对比见攻略第 12 页。

后续需要细节时，按位置重新读取原文即可。 它和第 3 点的区别在于：第 3 点处理的是 **已经没用** 的内容，直接去掉；折叠处理的是 **可能还有用** 的内容，留一个缩略版。

**4.5 写摘要（兜底触发）**

上面四种手段都用过了，上下文还是快满，才让模型把前面的对话总结成一段摘要，替换掉原始内容。Claude Code 里的自动压缩（autocompact）就是这一步。 摘要一定会丢细节，所以要尽量保留重要信息：

- **窗口满前压缩** ：不要等窗口完全满了才压，要给写摘要这次请求本身留出空间；
- **按固定格式写** ：要求摘要包含用户的原始需求（尽量保留原话）、已完成的工作、正在做的事、涉及的文件、待办事项，不要让模型随便总结一下；
- **压完补回关键内容** ：把最近改过的文件、项目规范文件重新读一遍放回上下文，不依赖摘要转述；

实际使用中，第 5 种调用模型写摘要往往是触发最多的。前四种只能让上下文涨得慢一点，任务足够长，最后总会走到写摘要这一步。

## 05

小结

**上下文压缩不是"怎么写摘要"的问题，而是"哪些内容该发给模型"的问题。** 无关的对话，删掉；工具返回的内容，从源头控制大小；用完没用的工具结果，去掉；以后可能用到的，留个缩略版；实在放不下了，再让模型写摘要。越往后，丢的信息越多、花的钱越多，所以能在前面解决的，就不要留到后面。
