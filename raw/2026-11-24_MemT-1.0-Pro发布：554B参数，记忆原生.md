# MemT-1.0-Pro 发布：554B 参数，记忆原生

**作者**: winkrun

## 摘要

MemTensor与NVIDIA发布MemT-1.0-Pro，总参数554B、激活59B，基于Nemotron 3 Ultra训练，核心是将记忆做成模型计算的一部分，用原生状态保存历史而非依赖上下文重贴，128K历史下持久状态较full context KV cache减少约66倍存储，Pro在BEAM-1M和MemoryAgentBench上分别提升4.76分和6.51分，但官方承认在需细节证据检索的长历史任务上仍落后于强文本记忆系统。

MemTensor 和 NVIDIA 发布了 MemT-1.0-Pro。模型总参数 554B，激活 59B，基于 NVIDIA Nemotron 3 Ultra，分布式训练使用 Megatron-Core 和 Megatron Bridge。

它想解决的问题不新：让 AI 记住历史。做法有变化。现在的“记忆”大多发生在上下文层，改 prompt，检索片段，把历史重新贴进去，模型权重不动。MemT-1.0 的方向是把记忆做成模型计算的一部分，用原生状态保存历史，后续交互不必把原文历史重新塞回 query context。

![MemT-1.0 概览](https://mmbiz.qpic.cn/sz_mmbiz_png/rY5icXvTTrJ8Ictiaia3FfpLtBgcC86rOhhfe16tj5EWYwaY2vgGL6m6PDOibNRX9VKTJSzYG3ZDGO30sLXlawic8wq4Nn6EHm72qNDsXOicyb8kc/640?wx_fmt=png&from=appmsg)

从 Flash 到 Pro，官方给出的提升是：BEAM-1M 增加 4.76 分，MemoryAgentBench 增加 6.51 分。模型家族里，Pro 是 554B 总参数、59B 激活参数，可训练记忆参数 4.23B，动态记忆状态 13M。Flash 是 288B 总参数、17B 激活参数。Nano 更小，36B 总参数、3B 激活参数。

技术报告给出的一个关键数字是存储。128K 历史长度下，持久状态相对 full context KV cache 约减少 66 倍。Nano 在这个长度下约有 1.86 倍端到端推理加速。对长任务来说，这比“能不能记住”更接近账单。

![MemT-1.0 原生记忆架构](https://mmbiz.qpic.cn/mmbiz_jpg/rY5icXvTTrJ8SHZLZAqKKWCfyQMK4OGuLFbbPWMiaR9mZbpViacJfZxXqQGib5eyia3bON9aVrMYp2z8I63VQG9REGK0z84fkfOxSydJo61p3lwQ/640?wx_fmt=jpeg&from=appmsg)

架构上，MemT-1.0 在 backbone attention 旁边放了 Native Memory Block。Local Memory Block 维护动态多通道记忆矩阵，跨交互步骤演化。Hyper Memory Block 包含可训练的记忆 query、key、value 投影，以及 erase、write、forget、output 门控。生成时，memory attention 读取当前记忆状态，归一化、门控，再加到 backbone attention 输出上。每轮或每段结束，用稳定的 GDN-2 做 token 级记忆更新。

评测结果要看清限定词。MemT 官方说，在 11 个记忆基准上，Pro、Flash、Nano 在“参数记忆方法”里排前三。强文本记忆系统整体仍然领先，尤其是长历史里需要细节证据检索的任务。这句话很重要。原生记忆不是全面碾压检索增强，至少现在不是。

![记忆基准结果](https://mmbiz.qpic.cn/mmbiz_png/rY5icXvTTrJibZjMoK6wMCQqySHwVsj2QSNT8nsQ2KfbXVnk28kqohoibH0hVZp25TrH4aTKa2icLKkuzbo7Nco4oE9boGJTvr98d2JETOtLuoE/640?wx_fmt=png&from=appmsg)

HuggingFace 模型卡里给了一个很直观的例子。开启 enable\_memory=True 后，用户说自家三个月大的小猫叫 memmy，爱吃小虾，记性很好。后续提问时，不用把这段原文重新贴进上下文，模型仍能回答名字、年龄、食物和特点。保存 state 后重新加载，restored.messages 长度是 0，再问小猫年龄，回答仍是 3 个月。这个演示把“记忆存在模型状态里”讲得很清楚。

![经验引导的编码代理](https://mmbiz.qpic.cn/sz_mmbiz_png/rY5icXvTTrJib2WIsiaubDAhZL2SPb0WvEID9hvzuZQozTVM4fQ48ORiaVD3MFj9icht5AS5PrXowSHyD4mlhu1cs1yiaN7s46Hiah0HuTaApbaa4M/640?wx_fmt=png&from=appmsg)

问题也在这里开始。

过去我们说的记忆几乎都只碰上下文，改 prompt、检索 chunk、重贴历史。权重保持冻结，推理引擎默认模型是静态的。可一旦记忆变成原生能力，状态要在 serving 期间写入，模型就不再静态。推理时更新参数，结构上类似 RL 系统每次 rollout 都要处理的 refit：重新拟合模型，把新权重推进正在运行的 runtime。

RL 框架对这套流程相对熟。推理引擎不熟，因为它以前不需要。难的不是更新本身，是更新周围的东西。

旧权重下生成的请求要不要跑完。跑完的话，它们的 KV entries 已经和接下来产出下一个 token 的模型不一致。refit 时正在生成中的请求，是修补状态，还是丢弃重生成。前者便宜，但可能悄悄错；后者正确，但贵。一个 batch 里不同序列期待不同参数版本时，scheduler 就多了一个它以前没有的 version 维度。

评论区有人盯着 554B 的推理成本，有人问在途 KV 状态怎么办，还有人直接说 scheduler 的 version 维度听着像噩梦。这些问题都指向同一处：benchmark 回答“记得住吗”，serving 回答“敢上线吗”。

SGLang for RL 文档里，refit 是一等操作。它支持从 disk、tensor、distributed group 更新权重，也提供 begin\_weight\_update、end\_weight\_update、pause\_generation、continue\_generation，以及 per-token weight version attribution。文档里写得很直白：一个请求可能跨过版本变更，暂停、refit、继续生成之后，meta\_info 能报告哪些 token 来自哪个权重版本

这套机制原来服务 RL rollout，现在被拿来问原生记忆模型。合理。只要模型在推理期间写状态、换权重，线上系统就得回答在途请求怎么处理。

模型已经放在 HuggingFace，技术报告在 arXiv。接下来值得看的，不只是记忆分数，还有各大推理引擎在生产环境里权重热更新和在途请求的解法。
