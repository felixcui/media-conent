大家好，我是创意猎人。

今天的主题是：Video as Code。

最近，Claude Opus 5.5 生成的各种视频案例火爆全网，我也各种收集了250+精彩案例，先来看看这个案例合集：

详请见飞书文档：https://aigcreative.feishu.cn/wiki/FNLNwGAwhip2SYkwdJucGb1in0W

随着 Claude Opus 5.5 的发布，它把视频制作当成了一份可以运行、修改和重新渲染的工程。

相较于Seedance这类视频生成模型，Opus 5.5 可谓是另辟蹊径，没有音图视频模型的 Claude，凭借其 LLM 语言模型的强大编码能力，硬是把自己变成了视频模型的对手！

Video as Code 这个概念，感觉也越来越适合解释最近一批 Claude Opus 5.5 的案例作品。

一支已经做好的产品片：第八秒把价格改掉，图表的比例必须和数据一致，片尾多停留半秒。

如果手里保留着文字对象、数据、时间轴和镜头参数，这些要求都有明确的落点。创作者可以改变工程中的对应部分，再把它渲染出来。

这种修改能力，很容易被忽略。

社交平台上的案例全是光影、运镜和视觉冲击，实际制作却经常卡在第二版、第五版，以及最后一轮看似简单的修改。视频的价值既包括画面，也包括它能否准确表达一件事，并在需求变化之后继续成立。

Opus 5.5 发布后，X 上出现了世界各地网友从代码绘画 MV、知识解说到三维动画、专业软件动效的多种作品。

Anthropic 在发布时，说明强调了 Opus 5.5 在编程、长任务与计算机操作的能力，但并没有提供它与视频模型的成片质量对照实验。

近期的这些案例值得研究的，是通用模型能否把创意转成可执行的制作流程，以及这种流程适合哪些视频任务。

我的判断是：

Video as Code 对“信息必须准确呈现、元素必须能改、版本必须能复用”的视频，具有很强的吸引力，而文生视频在自然影像与人物表演上的优势仍然明显。

两者的竞争会因任务而异，也会在同一支片子里合作。

## 01.

## Video as Code 到底把什么变成了代码？

这里的 Video as Code 是一种生产方式：用程序或结构化工程描述内容、对象、运动、时间和合成规则，再由渲染工具输出画面。

代码既可以直接绘图，也可以安排现有图片和视频，还可以指挥三维软件或后期软件。最终得到的 MP4，只是工程的一次输出。

看看这个我称之为最强的 Claude Opus 5.5 生成的视频案例：

它的核心可以用一句话理解：画面 = 渲染（内容、对象、时间、参数）。

例如，一条曲线由数据决定，一个标题由文本与字体决定，一个镜头由相机位置和时间决定。把这些因素显式保存下来，创作者就能找到“为什么这里是这个样子”，也能提出针对它的修改。

代码也由概率模型生成，也可能出错。

差别在于，得到工程后，可以检查其中的规则、修正它们，再让渲染器执行已经确认的结构。生成阶段的不确定性，能够被更多检查和明确参数约束；它不会因为用了代码而消失。这个中间工程，是理解两条路线控制差异的关键。

在这套流程里，Opus 通常负责理解要求、组织分镜、写代码、调用工具和修订项目；真正计算图形的，是浏览器、图形库、三维引擎或专业软件。音频和图像也可能来自别的模型。说明各自的分工，才能理解作品的能力来源。

编程动画并非新发明。

网页动效、程序化三维、自动剪辑和 After Effects 脚本都已经存在多年。

近期通用模型带来的机会，是降低把意图翻译成这些工具操作的门槛，并持续处理预览、报错、修改和交付。能写出第一段程序，与能完成整支视频之间，还有一段很长的工作链。

一套有用的 Agent 流程，还需要把需求变成内容清单和分镜，选择工具，建立项目，渲染关键画面，检查文字、布局与节奏，再修订和输出。

近期作品都给出了这种跨步骤工作能力的迹象：它们还不能证明“智能涌现”是一个已经测量出的原因，也不能证明模型能够稳定地无人完成所有制作任务。

## 02.

## 四条视频“生成”主要路线，分别把控制权放在哪里？

为了把事情讲清楚，可以按工程保存的核心对象来分类：直接保存绘图规则，保存视频时间轴，保存三维场景，或保存专业软件工程，它们也可以组合使用。

例如 Remotion 管理总时间轴，Three.js 绘制其中的三维镜头，AE 再完成合成。

## 2.1 直接用编程语言绘图：每一帧都有生成规则

最直接的一条路，是让模型用 JavaScript 配合 SVG、Canvas、WebGL 或 p5.js 画出动画；Python 也能通过 Manim 等工具表达数学图形和运动，再输出视频。

SVG 适合文字、图标与矢量图，Canvas 适合逐帧绘制，WebGL 适合大量粒子、着色器和更复杂的图形计算；Manim 官方入门展示的就是用场景和动画指令生成影片的方式。

这条路线要求把运动写成明确的规则：位置如何随时间变化，笔触如何扰动，颜色如何过渡。得到的不一定是规整的图表，也可以是有手绘感的视觉作品。算法规定的是画面如何产生，风格仍然取决于设计。

代表案例是《Functional Emotions》。

这支约 6 分 13 秒的 MV 有流动笔触、人物和火焰。公开项目用 Canvas2D 绘制底图，再以自写的 WebGL2 渲染器生成绘画质感；渲染脚本按歌曲时间取帧，最后合成音视频。它展示了程序绘图如何成为完整的视觉叙事，而非只做一个循环特效。

作者留下了被否决的首版、修改意见和分镜，最终剪辑包含 168 个镜头；音乐由更早的 Claude 4.6 与 Suno 工作流参与制作。这是有人指导、经过迭代的制作过程。公开源码提高了可检查性，但本文没有重新运行整个工程。

## 2.2 用 Remotion 管理时间轴：把影片拆成可复用的组件

第二条路更接近一套视频制作系统。

Remotion 用 React 组件描述画面，以帧号决定当前状态，再安排字幕、图表、图片、视频和声音的出现时间。它的价值不只在画图，还在于组织整支片子的结构。

创作者可以把标题卡、数据图表、产品界面和片尾做成组件，用内容参数填充它们。同一套设计因此能够服务不同产品、语言或数据。React、TypeScript 属于实现语言与技术；Remotion 属于组织和渲染视频的框架；SVG、Canvas 则可以继续负责组件内部的画面。

代表案例是 @kimmonismus 发布的三分钟 AI 发展史。

成片用模型名称、年份、发光网络与解释性图形推进叙事。

作者明确称它在 Claude Code 中以 React、TypeScript 和 Remotion 制作，图形使用 SVG、Canvas，声音包含开源 TTS 和 Python 合成配乐，没有调用图片或视频生成器。它体现的是把信息、版式和声音编排为一支固定时长影片的能力。

作者自报约 7,400 行代码、制作约一小时。源码未公开，这些数字与制作方法仍属于作者陈述；影片里的历史事实及对未来的推演，也需要另行核验。能够准确显示一个年份，与那个年份本身是否正确，是两个问题。

## 2.3 用 Three.js 建三维片场：对象和相机留在同一个空间里

第三条路把画面背后的世界保存下来。

Three.js 是 JavaScript 三维图形库，可以管理几何体、材质、灯光、相机和场景层级，并通过动画系统改变对象状态。把相机轨迹和动作绑定到时间，再逐帧输出或录制，就能形成三维动画影片。

这种方式特别适合需要明确空间关系的镜头。一个装置可以从正面转到侧面，再拆开外壳；同一个角色可以出现在不同机位下。工程中的对象提供连续性基础，镜头的变化由相机和动画来完成。空间稳定也需要正确的资产、代码和调度，单有一个场景并不会自动得到一部好影片。

代表案例是 @scheemunai 的九十年代卡通风格短片。

约 3 分 50 秒的视频围绕卧室、玩具机器人和发光小角色展开，有场景推进和镜头切换。作者给出的任务是先想故事，再用 Three.js 制作动画。这里选它，是因为它展示了有叙事目标的动画作品；普通游戏操作录像、可交互网页和场景漫游不作为本文的主要案例。

作者明确标注 Opus 5.5 与 Three.js，自报制作接近八小时、成本 173.23 美元，但未公开工程。提示词中的“Pixar 级”只是目标，不能当作品质量认证。这条案例也提醒人：有角色、镜头和声音的长叙事，仍可能需要不少计算与调试时间。

## 2.4 用脚本或 MCP 调用专业软件：交付可以继续工作的工程

第四条路让模型进入现有制作专业软件工具。

Opus 5.5 可以写 Blender Python 脚本组织模型与动画，也可以使用 After Effects 的脚本能力处理合成和图层，或通过支持相应操作的 MCP 服务调用软件。专业软件负责自己擅长的渲染、合成与工程管理。

MCP 是连接协议，让代理发现并调用外部工具。它提供的具体控制能力取决于服务器暴露了哪些操作，不会天然获得软件全部功能。直接执行脚本、使用软件 API 或控制界面，也可以完成自动化；谈到一个案例时，仍应核实它实际用了哪种方式。

代表案例是 Higgsfield × Claude Opus 5.5 的 Motion Design 演示。

官方原帖明确描述：通过 Higgsfield MCP 生成图像、标志与图形，搭建并动画化合成，渲染视频，最后交付可继续编辑的 After Effects 工程。对应页面还强调保留图层、关键帧与控制项，并要求连接桌面软件。这比只拿到一段成片，多了一次人工接手与后续修改的机会。

这是专业工具与生成素材结合的路线。Opus 承担编排和调用，素材与软件各有贡献；不能将它称为所有像素都由代码绘制。演示来自产品方，本文未获得实际导出的 AE 工程或完整调用日志，交付能力按官方展示记录。

## 03.

## Video as Code ，编码做视频的六大优势

四条路线的共同价值，是保留成片背后的结构：对象承载什么信息，变化何时发生，哪些部分可以独立处理。这让编码在以下六类制作问题上更有优势。

## 3.1 信息可以精确表达，逻辑可以接受检查

文字、数字、日期和公式可以作为明确的数据交给排版与图形工具。标题由文本决定，柱状图高度由数值计算，流程箭头由节点关系指定。创作者能够检查输入和关系，在渲染前纠错。

这对知识讲解、操作说明和数据报告尤其重要。算法可以按输入、状态变化、结果展开，产品功能可以按真实界面和操作顺序呈现。同一份数据同时决定图形、标签和动画，减少分别制作造成的错位。

工程还允许自动检查文字是否存在、数值与标签是否一致、元素是否越界、素材是否缺失。明确条件可以在每次修改后重新验收，视觉与声音仍需要观看和聆听。

这种优势是表达的可控性和逻辑的可检查性。模型仍可能查错资料、算错数字、讲反因果；程序也能把错误显示得十分清晰。字体缺失、文字溢出和过小字号也会损害显示效果。事实、叙事和画面必须分别把关。视频模型的文字能力会进步，编码的额外价值在于让文字、数据和逻辑从制作开始就进入同一工程，在多个版本里保持关联。

## 3.2 修改有具体对象，返工范围可以被约束

标题、相机、动作和背景成为独立对象后，改字号可以定位文本参数，放慢镜头可以调整时间曲线，改变产品颜色可以修改材质。自然语言帮助人找到并修改这些对象。

这改变了“抽卡”体验：明确细节可以定点修改，满意的背景不必因改字卡而重做；同一价格字段能同步进入片头、图表和片尾，减少改漏。

前提是结构被保留下来。只有 MP4，或源码难以维护，局部修改依然困难。模型若把全部画面写进一团代码，定点修改也可能变成困难的调试。共享组件的修改可能影响其他镜头，重渲染仍需时间，缓存也要由工程支持。可编辑性必须在交付时验证。

## 3.3 特定效果可以被规定，运动与空间有了约束

粒子沿指定轨迹移动、峰值在某一拍出现、零件按顺序拆开、标注持续指向同一部件，都要求多个具体条件同时成立。代码能将它们写成坐标、曲线和约束。

Three.js、Blender 保存空间关系，时间轴规定动作与声音的对应，着色器定义波纹和光效的演变。自然语言由此可以通向具体效果的实现。

与 Seedance 等模型相比，工程路线更适合要求效果稳定、准确、可重复地满足规则的任务。好看的爆炸可以生成，零件每次沿相同轨迹分离则需要对象控制。程序化也不保证物理正确：可信模拟仍取决于方程、参数与计算，必须与视觉示意区分。

## 3.4 长视频的连续性，可以由共享状态和时间轴承接

工程让不同镜头引用同一份角色资产、品牌样式和数据，进入统一时间轴。观众看到的镜头切换依然由导演设计，底层对象却可以重复使用。多个章节可以复用片尾、转场和标题；配音变长时，也能重新计算段落停留，减少每个镜头从头解释的工作。

这有利于几分钟的知识视频、产品解说和系列内容，但共享资产不会自动带来好的故事、表演与节奏。长片仍需要分镜、章节检查和全片观看，不能用代码行数代替完成度。

## 3.5 一支影片可以产生多个版本，资产可以持续积累

内容与表现适当分离后，确认过的模板可以接受新的产品信息、语言和数据，复用配色、图表、界面动画与声音规则。Remotion 的参数化能力支持用输入数据影响内容、尺寸和时长。

首支影片需要投入模板与组件制作，后续版本才可能摊薄成本。每周更新的数据解说、几十个产品版本，与只做一次的创意短片，有不同的账。

复用收益也需要预先设计：横转竖要调整构图，翻译影响版式与时长，换品牌可能改变视觉规则。不能把所有适配都理解为“改两个参数”。

## 3.6 生产过程可以留痕，交付物可以被接手

工程文件支持版本比较、问题追踪和多人协作：审核者查数字来源，修改者定位素材，后期人员继续调整图层。交付可以包含影片、源码或原生工程、素材、字体、依赖版本与渲染说明。

可复现性需要固定资产、字体、依赖、随机种子和渲染环境。实时状态不能随意漂移，也要记录每次渲染所用的输入，才能追踪版本差异。Remotion 提供有种子的伪随机函数，处理多线程渲染结果不一致的问题，这些维护工作也是成本。

交接前必须确认对方能打开、渲染和修改，并核查素材使用权。缺少字体、插件或外部文件的工程，仍可能无法接手。

## 04.

## 文生视频的优势，依然建立在另一类困难上

编码可以规定一滴水怎样移动，却未必能用较低成本做出真实水体、细微反射和复杂环境。要表现一个人紧张地看向镜头，困难又落在面部、身体、目光、皮肤和情绪上。自然世界里的大量细节很难逐项描述，更难手工建成资产。

视频模型的价值，是从训练中获得大量关于外观、运动和视觉风格的先验，让创作者能够用比较简短的要求得到复杂影像。人物、服装、风景、生活质感、电影化光影和自然动作，都是它们更容易发挥优势的区域。

具体效果仍取决于模型和任务，但将这些能力全部换成程序建模，通常会带来另一套制作负担。

画面美也不只有一种形式。

代码适合精确排版、几何秩序、数据运动与程序化风格；视频模型适合处理自然质感、复杂视觉联想和连续影像。用同一把“像不像电影”的尺子评价所有作品，会漏掉知识视频和产品视频最重要的要求。

视频模型也在获得更多控制能力。字节跳动的 Seedance 2.5 官方介绍已经包括多模态参考、时间点编辑和片段延长。因此，比较对象应该是正在进步的完整工作流，不能停留在早期文生视频只能多次重生成的印象。

两条路线的控制方式仍有差别。

视频模型可以接受局部编辑要求，但这不自动意味着创作者得到了可单独打开的文字层、角色骨骼或相机轨道。工程路线保存这些对象，也不自动意味着它能低成本获得高质量资产和表演。制作时需要同时考虑想控制什么，以及想生成什么。

## 05.

## 对文生视频的冲击有多大，要分任务、流程和入口看

现有案例缺少统一需求、完整成本和对照实验，无法量化行业份额转移。下面的高、中、低，是依据任务要求和制作机制做出的竞争判断。

## 5.1 任务层：信息越密、修改越多，编码路线的压力越大

结构化信息视频的潜在冲击较高。数据解说、软件操作、技术发布和图表动效，要求明确内容与对应关系，主要成本常在组织、排版和修改。工程路线能直接处理这些问题；若代理制作与维护工程更可靠，部分需求就可能减少对逐段生成画面的依赖。

产品广告和品牌片的潜在冲击中等，混合制作空间更大。标题、价格、界面、标志与转场适合代码或 AE；人物、环境和材质镜头可由视频模型提供。编码接走准确表达与合成，视频模型继续供应视觉素材。

人物表演与复杂自然影像的直接替代压力较低。对白、情绪和真实质地难以廉价地写成规则。编码可以参与剪辑和包装；纯代码做写实短剧，仍要承担角色资产、绑定、动画和表演的成本。

判断边界可以看：失败更多来自信息与对象不受控，还是画面、动作和情绪不够好？前者更需要工程控制，后者更依赖高质量素材或专业动画。

## 5.2 流程层：视频模型可能更多地承担镜头供应

代理可以按需求分配工具：视频模型生成写实人物，程序绘制图表，三维软件处理产品拆解，最后进入同一时间轴。整部影片的组织与单个镜头的生成，由此形成分工。

通过 API 或 MCP 调用 Seedance、Runway，仍然在使用视频模型。MCP 是连接方法，编码描述工程与操作，都不能单独说明画面来源。混合流程让确定内容与自然影像各取所长。

若流程成熟，视频模型可能更多承担镜头供应，需要稳定 API、参考控制、局部编辑和任务反馈，供制作系统可靠调用。画面质量仍重要，接入与修改能力的价值也会提高。这是产品方向的推演，尚不能认定平台地位已经转移。

## 5.3 入口层：谁管理项目，谁更接近持续的制作需求

掌握分镜、品牌资料、素材和修改历史的代理，更容易承接后续需求，并决定哪些步骤用代码、哪些镜头调用哪个模型。单次生成工具可能只收到一项素材任务。

视频平台可以增强工程、编辑和协作能力，或改善模型接入；专业软件也能通过脚本和连接器，把图层、时间轴与渲染接入自然语言工作流。

更强的模型也可能带来新增制作需求。能否抵消任务迁移，需要观察真实使用量：特定领域的替代压力可以上升，行业总需求仍可能增长。

## 06.

## 实际选路线，看三个变量：信息、影像和版本

选择制作方式时，可以先看信息精度要求，再看自然影像复杂度，最后看后续修改与版本数量。

下面这张表给的是起步方向：“编码优先”包括程序绘图、三维工程和专业软件自动化，不等于所有素材都必须由代码产生。

以一支假设的 60 秒产品片为例：开头需要人物使用产品的生活镜头，中间需要准确展示三项功能，结尾需要价格和行动指引。

人物镜头可以交给视频模型；功能界面、文字与价格使用可编辑对象；若产品结构需要解释，再加入三维镜头。配音、停留时间和音乐落点由统一时间轴管理。

这样安排，客户修改价格时就能定位文本；功能顺序变化时可以重排段落；人物表演不满意时可以替换对应素材。自然影像和确定信息分别接受适合自己的处理，再在同一个项目里合成。效果好不好，仍然要通过完整观看来判断。

成本也要按整条链来计算：策划与资料、模型调用、资产、首版制作、修改、渲染、多版本输出，以及人的审核时间。工程路线可能在后续版本中获得收益；视频模型可能在一次性复杂影像上节省建模负担。比较“每秒生成价格”或“用了多少 token”，都不足以决定整支片子的经济性。

## 07.

## 下一轮比较，应该把修改和交付也考虑进来

想判断 Video as Code 是否真正有优势，可以给两条路线同一份需求：一支包含指定中文、数据图表、人物镜头和固定配音的 60 秒视频。

首版完成后，再要求修改一个数字、延长一个镜头、换一种语言，最终交付可继续工作的项目。这比让双方各自生成一段最漂亮的镜头，更接近真实制作。

需要观察的不只是首版美感，还包括内容是否正确、修改有没有影响其他部分、全部轮次花了多少时间、总成本是多少，以及另一位制作人员能否继续修改。编码路线要证明自己的工程可靠，视频模型路线要证明控制与编辑可用。不同任务的答案可以不同。

Opus 5.5 这批作品提供的启发，是通用模型的编程能力开始能够被转换为视频制作能力。转换发生在理解要求、选择工具、保存结构和持续修订的过程中。它拓宽了自然语言能够调动的制作方法，也让那些原本需要较多软件操作经验的工作，有机会被更多创作者尝试。

Video as Code，最值得关注的地方，是影片背后的工程也成为了交付物。

一次输出可以结束，项目却能继续接受修改、产生版本、积累资产。

对需要长期生产内容的团队，这种能力可能比首版快了几分钟更重要。

我更期待的制作方式，是创作者能够保留准确的信息与可控对象，也能够自由使用自然影像、专业动画和真实素材。作品最后仍然要靠画面、节奏和表达打动人；工程让这些判断有了更明确的实施与修改路径。
