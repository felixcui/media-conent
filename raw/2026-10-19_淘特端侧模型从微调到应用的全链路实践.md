## 摘要

淘特App在2025年3月至8月间完成了端侧模型从微调到应用的全链路实践，选用QWen3-0.6B基础模型，通过两代数据集迭代将真机准确率提升至80%以上，并采用LoRA微调、ShortGPT深度剪枝、AWQ量化及Prompt精简、Prefix Cache、增量推理等工程优化显著降低模型体积与端到端延迟，最终落地于信息流重排序和流失前权益挽留场景，实现GMV正向增长，同时针对CDN下载等隐形成本提出按需下载等优化策略。

## 本文总结了淘特 App 从 3 月到 8 月在端侧模型建设上的全链路实践。为解决用户实时意图识别及云端大模型延迟与成本问题，团队选用 QWen3-0.6B 作为基础模型，通过两代数据集迭代将真机准确率提升至 80% 以上。在工程实现上，采用 LoRA 微调、基于 ShortGPT 的深度剪枝以及 AWQ 量化技术，大幅优化了模型体积与推理性能；同时结合 Prompt 精简、Prefix Cache 和增量推理等手段显著降低了端到端延迟。最终该端模型成功落地于信息流重排序与流失前权益挽留场景，实现了 GMV 的正向增长，并针对 CDN 下载等隐形成本提出了按需下载等优化策略。

背景: 为什么探索端侧模型

原因一 - 用户实时意图的探索从未停止：

翻开 ATA 搜索"用户实时意图"，会发现从 2013 开始到现在这个方向一直没有停止过，从纯工程实现到神经网络再到 LLM 大模型，我们一直在持续探索更优更准的用户实时意图获取方式。

原因二 - 端模型探索时机成熟：

AI 的浪潮推进到端侧。22 年 11 月 ChatGPT 证明其商业价值后 AI 浪潮以惊人的速度向前推进，到 26 年 4 月，集团内几乎所有技术团队都在拥抱 AI，集团内信息流 & 直播等团队基于 QWen 均已开始端模型的探索和应用。4 月 Gemma E2B 的推出带给端模型更多可能。

端模型基建成熟。AI 浪潮的推进让集团内公共训练环境、基础模型微调、量化等基建日渐成熟，加上 Claude Code / Cursor 等工具可以快速理解/改造 微调用的 LLaMaFactory、量化用的 AliNNPrivate等工程，原先站在大模型领域外围的同学已可以快速切入。

原因三 - 业务诉求：

怎么识别这个用户在 App 有较强的购物诉求还是随意浏览？用户有意图但快离开 App 时我们是否可以更精准感知并用权益挽留？目前有很多云端基于 LLM 的方案，速度和 Token 成本结合端侧模型是否有办法有更优的解法？

基于以上核心因素，淘特在今年 3 月底开始端模型的探索、应用和落地。

做什么：探测什么意图

结合信息流和权益方法的场景，反复权衡和实验后，最终针对进端购物的用户确定让端模型识别 3 种用户意图：

- 闲逛：用户无目的随意浏览。
- 比价犹豫：用户围绕某一单品反复浏览对比。
- 场景购物：围绕某一场景选购，例如露营(帐篷、天幕、GTI 桌)、钓鱼(鱼钩、鱼线、鱼竿、鱼饵)。

场景应用：

- 场景1 - 用户有购物意图但未下单准备离开时发券，用权益钩子提升用户下单意愿。
- 场景2 - 针对用户意图将未曝光 Feeds 基于意图重排序，感兴趣卡片靠前展示，提升点击率。

▐端侧模型整体架构

![](https://mmbiz.qpic.cn/mmbiz_png/DthwRd8vvp2RMUXHlbpTvtbltia7ciastghRpZxfNSWUyj9R8vhlAE17UwpickhNYQniaCOpchBZ8MdEfcKla1llWtC1N6hJ460nWYos1O9fVvs/640?wx_fmt=png&from=appmsg)

整体架构主要分成 4 层，各层主要职责如下：

- 模型层：通过训练数据集的清洗/优化、微调参数调整、量化参数调整等方式优化模型准确率；
- 推理引擎层：引擎原理的熟悉 & 推理性能优化，核心指标是端到端延迟优化；
- 端侧 AI Lab：模型管理和下载、用户UT获取和组装、引擎调用和意图结果分发；
- 业务层：意图结果监听 & 使用；

下面就各层中重点内容展开。

▐ **4**.1 微调数据集建设和迭代

模型输出(意图 + 关键词)确认后，最开始也最重要的一步是如何创建高质量数据集，数据集质量越高，LoRA 微调的效果越好，质量优于数量。从淘特经验看，第一个数据集我们的准确率只有43%，后续建设和迭代是一个持续调优的过程，N 版本之后建设到 91.8%。

数据集建设整体分成两个部分展开，一是基于 UT 链路埋点 从 0 到 1 建设的过程，二是灰度后利用上线数据优化的过程。

- 4.1.1 第一代数据集：从原始埋点合成训练数据

端模型冷启动阶段无线上推理数据可用，从埋点日志出发：规则引擎做硬过滤与预标注，云端大模型蒸馏出标签，有疑问项人工校对并标注，生成第一个版本的训练数据。

流程如下：

![](https://mmbiz.qpic.cn/sz_mmbiz_jpg/DthwRd8vvp35T1ZibRtrRtqlySHoibH9Ug65cbPSq0ibzJYMbDWGYUoAhBzQOdhykhy8uiaIffDwN0QGXQVj4eticwpMZVeWljrfibaCLy6lzqGME/640?wx_fmt=jpeg&from=appmsg)

第一代建设中几个要点：

- 废弃 CoT: 第一代在这个版本之前还有一个带 CoT (思维链)的版本，原想法是蒸馏云端模型思考方式喂给端模型增加输出准确性。CoT 被废弃原因：
	1、幻觉：给小模型增加 CoT 后，返回出现幻觉的概率大增，整体准确率不到 60%；
	2、耗时：在给出最终结果之前 CoT 的输出非常耗时，影响链路响应时间。用户行为输入到意图生成往往 1 分钟过去了；
- 云端标注从单模型优化成双模型：起初只有 Qwen3-Max，为增加数据有效性防止单模型偏好，引入交叉验证模型。50 条分层 benchmark 中 Kimi K2.5 与其一致率最高（72%，优于 GLM-5 70%、DeepSeek V3.2 68%）且延迟可接受，引入作为第二标注源做全量交叉标注：一致自动采纳，分歧转人工。以 0420 批次 10300 条为例，自动采纳 69.3%。

第一代方案的缺陷：

- 天花板等于教师模型规则。标签来自云端教师模型与规则引擎硬过滤，训练本质是蒸馏教师模型判断，学不到教师模型以外的判别力；
- 数据集分布和线上不一定一致。意图分布人为设定（场景购物 7% / 比价犹豫 15% / 闲逛 78%），边界场景的补充也不足，该数据集具体线上真实用例推理的数据、分布比例会有差异，这种差异可能导致离线测评数据和线上真是准确率数据的差异；

第一代数据集经过多轮迭代， DSW 环境准确率 84%, 量化后真机准确率 76%，7月上旬开始第一批少量灰度。

- 4.1.2 第二代：从线上真机推理日志回流重建

当第一个版本的模型灰度放量后，线上用户真实的数据逐渐积累，在放量到 10W 级别用户后，收集线上真实数据，清洗并按线上意图的分布比例重建数据集。流程如下：

![](https://mmbiz.qpic.cn/sz_mmbiz_jpg/DthwRd8vvp0PoO4fzCz0JggmIibnBnWTsJmPA5fiaTD6vMIa78qjrM09icvzWfeKQWic9uhBDG2PSYNo6Gadn8sg9DG4kcYibGQK1NQauLiaIJB9M/640?wx_fmt=jpeg&from=appmsg)

线上数据集清洗过程中的部分要点：

- 三方一致性 - 端侧输出与两个云端模型标注做三方比对：
	\- 三者一致为高置信正样本，直接入集；
	\- 两个云端一致而端侧不同单列为困难样本——这正是模型当前的错误边界，定向补入收益最高；

Tips：QWen3-Max 与 Kimi 2.5 两模型自身偏好也不一致，不能完全依赖云端双模的共识，需要抽样一定样本人工检测；

- 关键词质量保障 - 非闲逛样本由 qwen-max 按 0~3 分评估「候选关键词是否准确概括行为序列中的核心商品或场景」，≤1 丢弃。防止 LLM 的幻觉关键词进入训练数据；
- 人工标注 - 三个模型都不一致的样本由人工标注。人工标注文件不展示任何模型预测，只给行为序列，避免锚定效应。将人工标注后的部分数据集补充到训练数据集。目前人工校验耗时较大，每次只标注 50 条数据；

第二代数据集经过迭代 DSW 环境准确率 91%, 量化后真机准确率 80%。

▐ **4**.2 模型训练平台的选择

完成数据集建设后，下一步是挑选一个后训练平台，端侧除了微调还涉及微调后的模型合并、剪枝、下载、转换、量化，对平台的选择有更多诉求。有 2 个重点因素需要考虑：

1、是否支持微调后的转换、量化、下载。如不支持无法进行后续转换等操作，无法部署到端侧；

2、GPU 型号和性能。从目前经验看到老卡和新卡微调后结果 DSW 环境差异不大但量化后准确率差异明显。尽可能选择更高端 GPU；

尝试了 ideaLab、ModelScope 等诸多平台后，最终我们选择 ModelScope 平台 + LLaMaFactory 搭建微调环境。部分平台记录的坑：

- 不⽀持 QWen3-0.6B ⼩模型，只⽀持 2B 及以上参数模型；
- 不支持微调后下载，导致无法使用 MNN 转换和量化；
- 部分平台如果⽤公共资源排队时间超⻓；
- 部分平台显卡较⽼导致量化后效果较差；

不同 GPU 硬件量化后真机同⼀套 val 数据集 benchmark 准确率差异(最好和最坏准确率差异超过 21%)：

![](https://mmbiz.qpic.cn/mmbiz_png/DthwRd8vvp1xEZ2qWGEdSLIKeQeH8gcdxIJibKgeaGYuw5QArCVIaTDIovPqrePzfTOnqnyUjSRuAXqs46bXosgvoVZkEZrDWdw21hkEPrCE/640?wx_fmt=png&from=appmsg)

建议：资源紧张型的团队可以选择免费或低成本环境先搭建和走通整个流程，之后如果有条件切换到高阶 GPU 做微调等操作，之后对比同一数据集下测评结果。

▐ **4**.3 模型的选择

目前业界在移动端部署最广泛的模型主要集中在 0.5B 到 3B 参数规模。业界专为移动端和边缘计算优化的小模型家族包括 Google 的 Gemma 系列、微软的 Phi 系列、阿里巴巴的 Qwen 系列（及其衍生）、以及由社区驱动的 MiniCPM、SmolLM、TinyLlama 等多个分支，横向对比如下：

![](https://mmbiz.qpic.cn/mmbiz_png/DthwRd8vvp31icndLp0aibSzKmJEtRtwav3vQWiayS3XEDRiaMpngaZE4tsVw5FTCXrD8ruS5hT1EUsdS1iaPdGeIrktvbDFAfqqyO4B3JMhzU1A/640?wx_fmt=png&from=appmsg)

因微调后需要经过 AliNNPrivate 转换量化，并在 MNN 引擎中推理，Qwen 系列适配成熟度最高，并且集团内已有相关走通的案例，本着选新不选旧的原则最终在 QWen2.5-0.5B和QWen3-0.6B之间选择了后者作为基础模型。

▐ **4**.4 Prompt 优化 & 消融实验

我们提供给模型的 Prompt 大致分成 System Prompt + Content Prompt，目前版本使用的 System Prompt：

```swift
"根据用户行为序列判断购买意图并提取核心关键信息意图分类:闲逛:无主动购物信号,或跨多个无关品类随意浏览无场景主线比价犹豫:同品类内商品对比场景购物:同一大类下跨子品类围绕统一场景选购(如厨房/露营)类目说明:序列中 cat:大类.子类.孙类 为商品类目层级,首段为顶级大类。判定参考:多个无关大类→闲逛;同一大类跨子类→场景购物;同一完整类目重复→比价犹豫输出格式:- 闲逛: 仅输出\"闲逛\"- 比价犹豫: 输出\"比价犹豫|关键词1;关键词2;...\"- 场景购物: 输出\"场景购物|关键词1;关键词2;...\"关键词规则:- 3-6个,首位为主品类(比价犹豫)或主场景(场景购物)- 简短名词或形容词,2-6字\n- 按重要性降序排列"
```

Content Prompt 包含用户行为序列，包含搜索、详情、购物车等页面信息。

在端侧核心考虑的点： 保证准确率的情况下尽可能减少 Prompt 长度。

System Prompt 对已有规则细则描述越丰富，模型判断出的意图准确率越高，但System Prompt 长度的增加在端侧会导致推理时间呈线性增加，例如 Vivo S20 上端模型在不同 Prompt 长度下端到端延迟(横坐标是 Prompt 长度)：

▐ **4**.6 模型剪枝

- 为什么做剪枝

核心诉求是为了减少模型大小和增加推理速度。

- 剪枝前提约束:

剪枝方案的选择的几个约束：

- 改动小 - 产物必须能衔接现有 LLaMA-Factory 和 AliNNPrivate 链路，不改量化和部署逻辑，实现和维护成本要低；
- 指标不动 - 体积、延迟、内存同时降，同时准确率要求保持同样水位；

- 主流方法对照

![](https://mmbiz.qpic.cn/sz_mmbiz_png/DthwRd8vvp3cgAbjPCGSLRjA7f29InBwNc1zQqZ597LCoaLEOpCJhSZo4xibr9zaG7RJTTf0wHgvu4Iypr5YAKicEvmvvxVgibPkHrcVZtXWF4/640?wx_fmt=png&from=appmsg)

- 淘特剪枝方案

整体采用 ShortGPT 的方案。选层用 Block Influence，定义是 `BI = 1 − E[cos(h_in, h_out)]` ，出自 ShortGPT（Men et al., 2024，arXiv:2403.03853）论文的公式 (1)。公式解释：

```apache
h_in、h_out 是一层的输入输出隐藏态，余弦相似度越接近 1 越接近透传，1 − E[cos] 即平均改动量，期望对校准集所有样本、所有 token 位置求平均。实现上一次前向拿 output_hidden_states=True，对相邻 hidden 求 F.cosine_similarity 再取 1 − mean。选层去掉强制保护的首末层，取 BI 最小的 K 层。
```

QWen3-0.6B 一共有 28 层 Transformer Block，基于以上公式计算后 BI 的分布整体符合两头高，中间低的规律(Python 版本剪枝代码 100% 由 AI 实现)，淘特微调后 28 层模型 BI 值分布如下：

云端裁决是 K=8 最优：掉点最少，比 K=6 多砍两层，场景购物 Recall 与原始持平，端侧速度更快，但真机（量化后）评测数据不及预期：删 8 层在 iOS 上 73.7%，删 6 层 79.8%，差 6.1pp；Android 上删 8 层 76.8%，删 6 层 79.8%，差 3.0pp，速度收益不足以抵消精度损失。生产采用删 6 层，删 8 层不采用。

删层带来结构扰动，之后必须做恢复微调（healing），对比第一次微调修改两处：

- `model_name_or_path` 指向剪枝后的模型而不是原始 base，merge 时的 base 同样换成剪枝后模型；
- `num_train_epochs` 从 5 降到 3（收敛更快，训 5 轮会过拟合到剪枝残留噪声）；其他参数如数据、template、cutoff、LoRA 超参、学习率、验证集选优全部一致。

- 备份方案：Logit 蒸馏

除了剪枝后的 Healing 微调，尝试过的备选方案是 Minitron 式的 Logit 蒸馏，使用过该方案但结果不及 Healing 微调，遂暂时放弃该方案。

Logit 蒸馏大致原理：原始 28 层模型当老师，剪枝后的学生模仿它的概率分布，损失是 `loss = (1−α)·CE + α·KL·T²` ，默认参数 α=0.9、T=1.0。通俗点解释：以前教师模型告诉学生模型的是答案，这里告诉的是结果的概率分布。

官方 LLaMA-Factory 不原生支持 logit 蒸馏，用 AI 对 LLaMa-Factory 源码做了修改后实现。这里如果没有 AI Coding，估计直接就放弃了。

- 推理链路架构和核心流程概述

端侧意图推理链路采用“配置驱动、可观测、可灰度”的分层架构。

- 配置中心 - 配置中包括：模型地址、总开关、用户画像、疲劳度以及触发规则；
- 流程管线 - 负责下载管理和推理前检测；
- 推理链路 - 负责调用 MNN SDK 进行意图推理及意图分发；
- 监控系统 - 监控系统把每个关键节点的状态与性能指标上报到远程看板，同时在 Debug 包内保留一份本地环形缓冲日志；

一次完整的端侧意图推理核心流程包括：

1、配置拉取：应用启动或账户切换后，配置中心先读本地缓存让链路尽快具备可用状态，再异步请求服务端刷新，只有配置 MD5 变化才会更新本地数据；

2、下载管理：随后模型资源管理器根据配置中的模型地址判断是否需要下载，满足存储空间(Orange 配置，>=1 G 剩余空间)等条件才会在后台启动下载与解压；

3、用户行为记录：App 启动后用户行为事件经过白名单过滤后进入规则引擎，引擎会按照序列、统计、组合等条件持续匹配，当行为累计满足某条规则时(例如序列中>=3个详情 PV)，便根据用户路径生成一段标准 prompt 并触发推理请求；

4、推理准入：请求先经过五道闸，总开关是否打开、当前设备是否在允许范围、是否超过疲劳度限制、模型是否就绪、以及剩余内存/发热等运行时状态是否正常；只要任一条件不满足，本次推理立即终止并记录跳过原因。

5、意图推理 & 分发：全部通过5道闸判断后调用端侧推理接口执行推理，推理结束后剥离模型输出中的思考片段，通过关键词命中得到“比价犹豫”“场景购物”“闲逛”或“未知”四种意图；

6、意图分发：其中只有前两类会分别分发为 shopping\_hesitate\_trigger(比价犹豫) 和 shopping\_scene\_trigger(场景购物) 事件，交由业务方监听消费；

7、数据上报：整条链路的配置、下载、触发、推理、意图解析和分发结果都会作为监控数据上报，用于构建漏斗看板和后续优化。

端模型性能优化

完成端模型量化及上传 CDN ，客户端下载成功后，随着⽤户使⽤便进⼊了推理环节。

端侧推理耗时可以简化成 Prefill 阶段 & Decode 阶段，以 QWen3-0.6B 模型为例⼦简单介绍两个核⼼环节：

- Prefill(预填充)：

- 当你输入一段 prompt（比如 500 个 token）时，模型需要"阅读"这整段文字。Prefill 阶段会将所有 token 一次性 送入模型，计算出每个 token 在 28 层 Transformer 中的表示。

```makefile
输入: [token_1, token_2, ..., token_500]          ↓ 一次性送入     ┌──────────────────┐     │  Transformer     │  × 28 层     │  (并行处理)       │     └──────────────────┘          ↓输出: 第一个生成 token
```

- 核心计算特征：大矩阵乘法。每层包含 7 个矩阵乘（Linear：q/k/v/o\_proj + gate/up/down\_proj），例子中输入矩阵形状为 `[500, 1024]` （500 个 token，每个 1024 维），与权重矩阵相乘。这是一个计算密集型操作。

- Decode：

- Prefill 完成后，模型开始逐个生成输出 token。每生成一个 token，都要运行一遍完整的 28 层 Transformer，但此时输入只有 1 个 token；

```diff
┌─────────────┐已有的 KV Cache ──→  │ Transformer │ ──→ 生成 token_1+ 当前 token_0       │ (28 层)     │                    └─────────────┘                          ↓ 把 token_1 作为新输入                    ┌─────────────┐已有的 KV Cache ──→  │ Transformer │ ──→ 生成 token_2+ 当前 token_1       │ (28 层)     │                    └─────────────┘                          ↓ 如此反复...
```

- 核心计算特征：矩阵-向量乘法。输入变成 `[1, 1024]` ，权重不变。计算量骤降，但每次都要从显存加载全部权重。这是一个访存密集型操作。

▐ **5**.1 指标体系定义

要做优化先建基线。Prefill 与 Decode 的瓶颈在不同阶段，Prefill 是大矩阵乘，算力受限；Decode 是矩阵向量乘，每生成一个 token 都要把全部权重完整读一遍，带宽受限。指标因此拆成四类共十五项，按 P0/P1/P2 排优先级排列，包括 TTFT、Decode 吞吐、峰值 RSS、模型加载耗时为 P0，分别对应等待时长、出字连续性、被杀风险与首次打开耗时。具体指标如下：

业务落地的场景建设

淘特目前落地了基于用户意图对首猜未曝光卡片做重排序，以及判断用户有购物意图但未购物快流失时给用户发权益挽留。

这里针对端模型 + 权益的场景详细展开，架构和流程如下：

![](https://mmbiz.qpic.cn/mmbiz_png/DthwRd8vvp0Niasa3nvPQ0OmcVic1XN9XqLBaZFsbUlticwsMqIJU9nl3J6ibWPUBUee9HQY6OqlUX6xgLVQqyu1Muar1NSibYILnMUm99KGLcXc/640?wx_fmt=png&from=appmsg)

落地场景中端侧模型识别、权益模块触发、服务端统一管控，各模块分工概述：

- 端侧模型在用户浏览商品过程中基于本地行为序列识别意图，一旦输出有效意图，立即发送携带 sceneCode、modelId、modelVersion 和 eventId 的标准广播 ACTION\_CLIENT\_MODEL\_INTENT\_HIT；
- 端侧权益模块不参与权益决策、实验分组、命中计数或延迟处理。权益模块监听该广播后，读取 llm\_benefit\_dispatch\_runtime 配置完成 sceneCode → triggerGroup 映射，按会话累计同组命中次数；当达到第 N 次时启动延迟 X 秒，延迟结束时调用端侧 hasOrderedSince 接口确认用户是否已下单；若未下单则调用 BXPEIEngine.triggerPeiDecision 进入 PEI directTrigger 链路；
- 服务端负责从全人群中切出 40% 端模型验证人群，并在此人群中按实现组/对照组稳定分桶，端侧不感知，最终是否发放权益由后端根据上传的用户行为记录交由云端大模型判断并决定。如判断需要发券，则通过 UBA 动线系统给用户弹出权益 Pop 通知用户有新权益到达。

目前该场景还在实验和持续放量中，从阶段性数据可以看到对比对照组数据，实验组通过端模型意图识别并发券增量 GMV 持续正向(同样投资1元实验组增加的 GMV)，近一周数据：

后续规划和思考

到目前为止，我们验证了端模型在 App 侧业务中应用的可行性，以及对部分业务指标的正向作用。后续端侧模型规划包括：

- 模型能力拓展 - 目前的意图分类仅针对进端购物的群体，端侧有大量互动型的用户只玩/逛但是不买，后续将结合端侧模型能力更好理解这部分用户，增加购买率的转化；
- 模型准确率提升 - 探索并走通 剪枝 + AWQ + quant\_block=32 链路，实现真机准确率从目前80%水位提升到 90%；
- 推理性能优化 - 增量推理能力扩大放量并最终全量部署，将推理速度压缩到 1s 以内；
- 端侧 Agent 建设 - 在现有单次会话推理的基础上增加记忆，从基于用户行为序列推理升级为基于用户购物习惯的推理，更精准贴近用户意图；
