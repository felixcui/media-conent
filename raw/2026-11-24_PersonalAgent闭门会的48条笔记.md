## 摘要

Personal Agent 闭门会整理的 48 条笔记，信号很硬：Similarweb 11 月 13 日数据显示 Muse 上线两个多月，移动端 DAU 破 1000 万；Instinct 估值从 8 月的 25 亿美元升到 300 亿美元。团队抓取 6 款产品、1500 多条用户评论，得到 2737 次任务提及，结论是没有收敛出统一的 killer use case，任务横跨家庭、个人与工作。用户愿意长期交出去的是日程、日历、邮件整理、例行跟进；购物、电话沟通和高质量创作会交回原工具。评价一个 Agent 只看两点：交付质量，以及用户自己补做了多少。多 Agent 分工的坑也写了：两个 Agent 会互相改掉对方的修改；Notion 正把自己从协作 workspace 转成所有 Agent 共用的 context layer。主动性被拆成“推进”和“及时停止”，且要随场景调整。数据需求从单事件变成“人 × 时间”，已有头部公司把单用户月度轨迹组织成训练数据。

Insight *01*

Personal Agent 在解决什么

　⁠

今天对于 Personal Agent 到底是什么其实并没有一个统一的定义，从产品类型来看，有知识工作者群体普遍在使用的 Grok Bot、Duet（Anthropic）以及 Dots（OpenAI），也有 day 1 直接面向大众人群和生活类任务的 Instinct、Muse 等。

　⁠

为了更好地理解 Personal Agent 产品的用户画像和典型用例，海外独角兽围绕当下讨论度比较高的 6 款 Personal Agent 产品，从不同渠道对 1500+ 条产品的用户评论做了抓取分析。以下是核心发现：

　⁠

1.用户使用 Personal Agent 产品的具体任务并没有收敛到一个统一的 killer use case 上，对产品的使用横跨家庭、个人和工作场景，包括日程管理、生产力场景、邮件管理、预约购物、理财退税等等。

　⁠

这些任务的普遍共性是，过去用户得自己完成各种琐碎的操作，而 Personal Agent 可以自己把散落在邮件、日历、网站、IM 等零散的信息串联起来，把任务推进下去。从结果上来看这些场景首先节省了用户的时间，同时也解放了用户的 attention，不必一直惦记和跟进任务进度。

　⁠

![](https://mmbiz.qpic.cn/sz_mmbiz_png/QUs3kaltEh0wQxXW7yDCzARP4hXbycWeU31ZicJcps0YtpLkNvibF0hvZhFrFEo47CufGgQMfsW1MfGibLJFunZ2IicSKZqlKdKQ4uMXN6vL0hI/640?wx_fmt=png&from=appmsg)

　⁠

2.不同产品已经形成使用侧重，但工作与生活并不是互斥的用户分类。

　⁠

•这种分化更适合用来理解产品从哪里进入用户的日常：“偏生活”或“偏工作”描述的是当前用途侧重，还不足以划定产品的能力边界；

　⁠

•家庭用户也会处理业务邮件，小企业经营者也有旅行、账单和家庭安排，同一个人可能把两类任务交给同一助手，也可能主动分开。

　⁠

　⁠

3.用过一段时间后，用户会逐渐确定哪些任务长期交给 Personal Agent，相对应的也会把一些任务不再交由 Agent 处理。 比如日程提醒、日历、邮件整理、看板和例行跟进等都会继续交给 personal agent 来完成，但购物、电话沟通或高质量的创作则可能交回到原有工具或工作流。

Insight *02*

产品边界

　⁠

5.Personal Agent 和 Coworker Agent 的产品定位虽然各有侧重，但随着使用加深，部分用户会把工作和生活事务交给同一个产品。

　⁠

•比如有和 Instinct 用户交流过的人分享：Instinct 一开始的定位很偏生活场景，甚至没做独立 App，只能通过 iMessage / WhatsApp 交互，但用户渐渐会开始让它帮忙处理工作。

　⁠

•反过来也成立：有用户一开始借助 Claude、Codex、Grok Bot 来提高工作效率，但随着使用产品的时间和深度的增加，也会逐渐跟它分享生活相关 context、完成个人事务。

　⁠

6.至于工作和生活的 Agent 是否最终会相互渗透、甚至合并，还受企业数据管理要求的限制，“企业是否希望拥有员工的工作分身”：今天企业统一配置办公设备和内部账号，其中一个目的是让工作数据和管理权限留在公司，如果 AI Coworker 是确定性趋势，那么从公司视角出发肯定也会希望保留员工“工作分身”所积累的数据。

　⁠

7.所以更可能的格局是，工作上的 AI 分身可能由公司派发，生活分身则由个人选择，两者能共享哪些信息，要看各自的权限和用户意愿。对于小团队、OPC 这类 Power user，一个人的工作和生活 agent 更可能会融合，因为终局视角下，agent 能力不会拉开显著差异，此时 context 打通，只跟一个 agent 对接会更方便。

　⁠

8.如果把 Personal Agent 作为通用“入口”来理解，To Consumer 和 To Enterprise 未必还是最有效的产品分类：工作和生活场景可以共用底层能力，产品差异可能更多来自团队基因、用户基础和切入策略。2C／2B 的区别可能会影响采购、部署和数据管理，但未必对应两套截然不同的 Agent 产品形态。

　⁠

9.如果用户只面对一个入口，背后仍可以有多个 Agent 分工。考虑到不同 Agent 产品的 context access 和能力特征并不相同，有些重度用户会尝试让它们分工协作，比如下面两种方式：

　⁠

•一种由 master agent 掌握总体目标，其他 agent 完成各自的任务，比如以 Anthropic Duet 做主要入口，把 Notion 作为 Agents 共用的 context layer，抓取 X 信息的任务就交给 Grok Bot，并每天更新个人背景，减少切换产品时的重复交代。

　⁠

•让几个较强的 agent 直接通信，彼此了解分工，需要时再调用 subagent。但在实践中，这种分工也遇到过两个 agent 把彼此的修改来回改掉的情况。

　⁠

10.多 Agent 使用习惯下，Agent 之间共享多少 context、如何解决冲突、哪些事情需要交还给人，仍需要协调。无论由主 agent 统筹，还是 agent 之间直接沟通，关键都在于减少用户逐一协调的负担；如果这些工作仍落在人身上，多 Agent 分工带来的效率收益就可能被抵消。

　⁠

11.如果用户同时使用多个 Personal Agent，也有可能会出现独立的个人记忆层，所有 agent 都在这个 context layer 获取与任务相关的个人背景和进度，从而减少人类用户反复交代的负担，比如 Notion 最近就明确提出，要从供人协作的 workspace 转型为所有 Agent 共用的 context layer，让 Notion 成为一个底层的记忆库，其它家 agent 可以在上面共同协作。

　⁠

Insight *03*

Universal Interface: IM or Agent

　⁠

12.IM 可能会成为 Agent 的入口。协作类以 Slack、飞书为代表，生活类则以 iMessage、WhatsApp 和微信等作为代表。原因在于这些 IM 产品积累了大量的 context、组织和社会关系链。working agent 的日常入口，可能会长在飞书、Slack 这类协作软件里。

　⁠

13.今天主流的 AI 用户还是基于 Claude Code、WorkBuddy 这类 AI 办公产品完成，且 Agent 产品也在通过强化自己的 access 向 universal interface 的方向发展，但 IM 的优势是人际协作已经沉淀在这里，只要人与人的高频协作继续留在 Slack 或飞书，那么让 agent 参与同一个入口要更方便，而 agent 也在 IM 里实时响应是最高效的。

　⁠

14.理想状态下是用户可以留在聊天里， Agent 在后台继续工作。直接在对话里给 Agent 提任务需求，Agent 接手需求之后直接在沙箱调用工具来完成任务，并在群里完成交付、进一步沟通迭代。

　⁠

15.类似于 Anthropic 内部很多 researcher 会直接 @ Claude Tag 工作，国内有不止一个 AI lab 团队日常工作中，也已经开始大量调用 bot 来干活。模型训练里的数据、评测、训练、infra 等多个环节都可以由这个 bot 来完成，因为实际效果很好，researcher 已经相当依赖这类驻扎在 IM 中的 AI coworker。

　⁠

16.这个变化会像开发者、程序员一度觉得，写代码当然要在 VS Code 里写，这是天经地义、亘古不变的事。但仅仅一年时间过去，已经再也没有人用 VS Code 了。

　⁠

17.一个终局设想可能是 everywhere 都有 access point：需要时，在不同地方都能找到同一个助手。它未必要求用户选定唯一入口，但任务和 context 要能跟着用户走，也要知道当前是什么场景。

　⁠

18.Agent 入口是否足够方便触达会显著影响 Agent 的使用频率。比如因为 Instinct 可以直接通过 iMessage 或 WhatsApp 交互，和独立 App 比，用户使用 Instinct 的频率明显更高。这点对于本就常用 WhatsApp/iMessage 的海外用户来说感受会更明显。

　⁠

Insight *04*

如何做好主动性和个性化？

　⁠

19.用户在使用中提及的 bad case 最后都回到“如何做好 agent 的主动性”这个问题，主动性既包含 Agent 继续推进、提出问题的能力，也要求它可以主动识别情景、给出准确内容，甚至主动停止某个任务的跟进。否则对于用户来说要不断给 Agent 说明任务现状，要求 Agent 停止或者更快交付，对用户来说，更直接的感受是 attention 并没有得到解放。

　⁠

20.主动推进和及时停止，都需要持续更新任务状态。 Agent 要跟进的除了最初的交代，还有事情是否完成、安排是否变化、原信息是否仍适用。产品讨论中转述过这样的 bad case：用户已经解决问题，几天后 agent 又来追问，用户只好再说明一次；也有任务交代后迟迟不交付，让人觉得像没交代过。前者需要停止过时的跟进，后者需要继续推进或交代阻碍。

　⁠

21.主动性不是一个固定、单一的尺度，要随着当前任务和用户状态变化。 同一个用户，在不同场景中也会希望得到不同程度的介入。要不要追问、给选项还是开放问题、先解释还是先给结论，都要结合当下任务判断。收到负面反馈后，也要分清用户介意的是时机不对、信息无关，还是事情没有办好，避免把一次不满记成适用于所有场景的偏好。

　⁠

22.主动性也考验 Agent 的“读空气”能力。除了个人偏好，团队的工作方式和沟通习惯也会影响什么时候该介入、怎样回应，Agent 需要在具体 context 中适应。

　⁠

23.有人提到 Claude 的“Ask User Question 设计”是一个让 agent 往主动提问的方向更近一步的尝试，但这个设计也有短板，即如果模型只喜欢机械的选项式提问，一定会出现用户面临哪个选项都不想选的情况，对于用户而言还得打字解释，又带来了新的负担。

　⁠

24.把某个单场景任务的可靠性做好，是用户愿意提供更多个人 context 的起点。Personal Agent 把某一类任务完成得非常好之后，用户开始信任它，自然也更愿意分享原本没有主动交代的需求，从前面提到的用户使用习惯上我们也能看到这一趋势。

　⁠

25.模型怎样学会不同人的偏好，是另一个需要解决的问题。 一条思路是在训练数据中保留不同用户的背景和评价，让模型学习不同情况下应该怎样做；另一条思路是通过个人 context 和 memory，让同一个模型根据用户信息调整回答。但哪些差异适合在训练里学习，哪些通过个人 context 和 memory 处理，还没有明确答案。

　⁠

26.专门的用户 onboarding 流程可以帮助快速收集用户偏好、建立初始 profile，比如 Tolan 会和新用户先聊 6-7 分钟了解偏好（这也和它上一阶段做 AI 陪伴相关）。但用户说得出的偏好和真实的使用习惯之间未必一致，并且大量前置问题会提高开始使用的成本。

　⁠

27.做好 Memory 角度不仅要筛出值得记住的信息，还需要在合适的时候用上。 考虑到用户的对话和工作记录很多，Agent 需要判断哪些值得留下、哪些已经过期，以及当前任务该调用什么，不能把整理和核对的工作都交回用户。

　⁠

•先筛出真正值得确认的内容。 有使用者把 AI 对话轨迹和飞书信息交给 Agent，希望它逐渐整理出什么事该找谁、在哪个群里解决、相关文件在哪里。他原本只想每天或每周确认三五条有价值的信息，但系统总是提取无关紧要的小事，还给出很长的核对清单，最后检查了三天就放弃了。

　⁠

•记下来的信息，也要判断这次该不该用。 另一位使用者关闭 GPT Memory，是因为它经常在回答当前问题时，调用过去聊过但与这次任务无关的内容。信息即使记对了，也要区分适用的任务和场景，并随着事情的变化更新，避免旧信息反复干扰新的判断。

　⁠

28.除了在模型侧学习个人偏好，也可以考虑结合传统推荐算法的逻辑，因为在个人偏好的识别和优化上，推荐算法已经做得相当到位。比如 Muse 背靠 Meta，个性化部分有可能可以结合 Meta 的推荐算法积累、根据用户 profile 推送内容，这也引出一个问题：Personal Agent 对个人偏好的适配，哪些由推荐机制完成，哪些通过 context、memory 或模型训练实现？这几层如何分工，讨论还没有形成一致答案。但接下来既然 Personal Agent 有互联网大厂的参与，那么一定会把传统推荐和 LLM 做更综合、更深入地结合。

　⁠

Insight *05*

新的数据需求：“人 × 时间”

　⁠

29.Personal Agent 可能带来一类新的数据 workload：围绕一个人的连续事务，构造训练数据和 benchmark。当 agent 持续承担一个角色，数据需要交代它此前知道什么、当前负责哪些事情、期间发生了什么变化。相应的 benchmark 也需要包含连续的任务情境和评价标准，用来检查它能否在这些条件下持续作出合适的判断。

　⁠

30.Case 的组织单位从单个事件扩展到“人 × 时间”。过去是围绕单个事件设计 case，比如对于差旅场景，评测通常会围绕订机酒、整理会议资料这些单点任务展开。但真实生活中的个人助理还会考虑同期其他安排、日程平衡等，所以构造这类 case，需要把分散的背景和事件联系起来，再检查 agent 是否在相关时刻用上了这些信息。

　⁠

31.Personal Agent 的个性化需求催生了对长程用户数据的需求。目前已经有头部模型公司将单个用户的月度 trajectories 组织成一条训练数据给到模型，希望模型从中学习这个人的长期行为。

　⁠

32.考虑到 Personal Agent 用户的“千人千面”，有人提出数据评测可以尝试引入 simulated user 的思路，即把“同一 case 不同人有不同的答案”纳入考量。

　⁠

•把用户设定带进 case。 Simulated profile 可以包含角色、个人偏好和不同话题下的要求。例如在 MBTI 的分类体系下 N 型人的 reward 分布会跟 S 型人很不一样。甚至即便同一个 user 也需要区分情境：工作时愿意接受追问，休假时可能不希望过多打扰。

　⁠

•一个打分设想是，把回答在某个特征上的表现放到 0–5 的谱系上，再看它距离用户的理想位置有多远。有人想要 4，有人想要 2。但实际面临的一个问题是，模型在做 judge 的时候，只有做 yes or no 的分类才比较准，如果做 0-5 的渐进分类，准确度通常不高。所以可能要先拆成几个明确的 yes/no 问题，再组合出最终位置。

　⁠

33.两个人对同一个答案给出相反评价，可能是因为他们的偏好和任务要求不同。把这些背景补进训练数据，模型才有机会学到“对谁、在什么情况下，这个答案更合适”。

　⁠

•一条思路是在训练中覆盖不同用户的背景和评价，保留多种可能成立的答案；

　⁠

•另一条思路是先训练通用能力，再通过个人 context 和 memory 适配。补足背景是否足以让模型保留这些差异，训练和使用时的个人适配各自应该承担多少，还没有明确答案。

　⁠

34.评测也不能只看最后有没有做成。比如一段代码可能实现了功能、通过了测试，但上线后却可能浪费很多资源。成本是否合理、有没有理解用户的目标、沟通是否清楚，也需要纳入考量。

　⁠

35.数据量也是需要考虑的问题。用户和情境分得越细，每一类能收集到的样本就越少。数据应该按几类用户组织，还是细到每个人，需要同时考虑个性化程度和样本是否足够。

　⁠

　⁠

Insight *06*

用户数据能让 Agent 学到什么？

　⁠

36.头部 Labs 对回流数据的态度发生了反转。过去的训练重点是提升模型的 intelligence，大家普遍认为普通用户的回流数据用处有限。而 Personal Agent 类任务则要求模型要覆盖日常生活中的长尾任务，也要适应不同用户的个性化偏好，普通用户的真实使用记录因此变得更加重要。

　⁠

37.产品本身都是数据入口，产品形态决定了数据飞轮的强度。Cursor 的伟大之处在于，它区分了在 VS Code 里做专业开发的人和只会在网页端 copy 代码的人，本身就起到了一个筛选作用。这两类人回流数据的质量差别很大，Cursor 由此能拿到最高质量的 coding 数据。

　⁠

38.同一个产品，放到不同的工作环境里回流的数据也可能存在很大差异。和用户画像、使用习惯相关。比如如果今天想要更多获取 workflow 或者协作类任务数据，但实际使用的用户普遍只是用来完成整理纪要、做 PPT 这样的单点任务时，那这类回流数据对团队的价值并不高。

　⁠

39.用户数据能让 Personal Agent 产品更好用，但并不一定提升通用 intelligence：

　⁠

•Personal Agent 要处理大量日常、长尾任务，这类任务中的用户轨迹和反馈数据更多是改善用户体验，还是能够泛化到其他任务上提升模型智能还没有办法衡量；

　⁠

•判断 Personal Agent 用户数据的价值，需要看它具体改善了什么，而不只是看产品收集到了多少数据。

　⁠

40.具体怎样整理，还要看数据的用途。如果用于 SFT，需要挑出值得学习的工作过程；如果用来还原任务、让模型自己尝试完成，则可以保留真实环境里的杂乱信息，让模型学会找重点。但制定 rubrics 的人仍需要知道哪些信息与任务有关，才能判断模型有没有关注正确的事情。

　⁠

41.反馈有没有价值，要看它有没有说明具体哪里出了问题，不能只看对话轮数。 如果用户只是说“不对，重做”，模型仍然不知道错在哪里。如果用户指出哪一步不该做、为什么、应该怎样调整，才更容易把这次反馈整理成训练数据。除了记录交互过程，还需要留下用户作判断的理由。

　⁠

　⁠

Insight *07*

商业模式

　⁠

42.对于商业模式，Personal Agent 最主要的还是交易撮合、广告和订阅。

　⁠

•广告：Personal Agent 产品接入广告的难度比上一代互联网产品更高。用户用 agent，就是希望它先替自己筛一遍，直接找到需要的东西。如果用户的需求越具体，可推荐的范围就越窄，如果要实现推的东西需要既是用户恰好想要的、又有广告主愿意付钱。广告池得足够大、覆盖面足够广。

　⁠

•交易撮合：Muse、Instinct 现在都在考虑从未来交易类任务中收取 take rate 来实现商业化，这类模型已经在互联网时期被验证，只要确实能带来增量订单，商家就会愿意为此付佣金。

　⁠

•订阅：如果要成立只需要证明帮用户省下的钱远多于收取的钱即可。比如每月收 20 美元，但能帮用户省下 200 美元。比如有人在北美做过砍价 agent：拿着别家同款装备的低价，给不同商家发邮件争取 price match，产品计划按月收费，或者按实际省下的金额抽成。

　⁠

43.Personal Agent 能带来多大变化，一个重要变量是会不会出现新的交互体验。小程序刚兴起那几年，曾有人设想，微信会成为手机操作系统之上的又一层 OS，变成唯一的入口。结果这种情况并没有发生，真正改变互联网业态的反而是抖音，它通过推荐算法和上下滑把 “人找内容” 变成了 “内容找人”。

　⁠

44.Personal Agent 的交互方式也很可能会变：也许会出现新的硬件，也许语音会成为更常用的交互方式，也许大部分对话和任务会由 Agent 主动发起。这些变化都会影响人们什么时候想到 Agent，以及日常多少事情会用到它。

　⁠

45.Agent2Agent 也是很有想象力的部分：把本来没人有空逐一做的沟通、谈判和匹配做起来。5-10 年，A2A 网络成熟后，有可能大量长尾交易会在 agent 之间完成，创造新的增量。

　⁠

46.用久了的 agent 就像孙悟空的猴毛，可以代替你去做事、social。比如你没时间每天跟朋友聊天，你的 agent 可以每天和朋友的 agent catch up 一次，下班时用播客的形式告诉你今天有什么值得分享的信息。

　⁠

47.如果要让这些自动沟通成立，Agent 就需要能深入彻底地了解用户，同时把重要决定交回本人。AI 社交已经有过反例：账号自动发内容、彼此互动，真人反而不想看了。仅靠注册问卷建立画像，缺少持续 context，也没有和真人生活中的其他事情连起来，很难让交流持续产生本人关心的信息。

　⁠

48.一个授权设想是，两个 Agent 聊到有风险的话题、准备发邀请或作承诺时，把此前的聊天带给主人，请人决定可以怎么说、能不能继续。纠正和确认既保留本人的决定权，也可能帮助 Agent 后续更准确地代表本人。

　⁠
