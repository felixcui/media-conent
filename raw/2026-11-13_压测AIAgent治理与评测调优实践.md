## 摘要

压测智能分析 Agent 上线后的治理闭环。方法：用 **Langfuse** 记录每次执行链路、还原问题现场，结合用户反馈判断错在**证据采集、工具调用、规则校验还是模型推理**；把高频问题固化成**固定场景回测集**，用**五档评分**打分，再按低分案例定位改进点。效果（001→007 两轮迭代）：**解决率 61.67% → 96.15%**，**平均延迟 175 秒 → 113 秒**，**单 Trace 成本 $0.5868 → $0.1980**；中间并非单调，**006 比 005 更快更省，但评分从 92.31% 回落到 83.33%**，说明质量与开销要一起看。Dubbo 专项评测由约 **50% 提升到 90%**，是整体改善的主要来源。

压测智能分析Agent接入真实业务后，分析结果跑偏可能是证据采集、工具调用、规则校验或模型推理中任意一环出了问题。只看最终结论，很难定位根因，也没法验证改动是否有效。

上线后的日常迭代主要得解决两个问题：

- 收到“分析不准”的反馈时，如何通过Trace还原Agent的执行链路，并定位具体出错环节。
- 完成Agent修复后，如何在相同的上下文和证据下开展回测，既确认原有问题已修复，也避免引入新的问题。

本文以Dubbo调试为例，还原从用户反馈、Trace排障、沉淀经验到固定场景回测的完整过程，介绍如何结合Langfuse与CLI Mock持续打磨 Agent。

**一**

**建设背景：让Agent进入调试流程**

压测调试是用户反馈问题最集中的环节。平台支持10种常用协议和30多个脚本组件，新手在接触陌生协议、编排脚本或配置参数时，经常遇到调试报错。过去排查此类问题，往往需要逐一核对场景配置、JMX 脚本、请求响应、JMeter日志和Trace，排查链路长且耗时费力。

针对这类调试问题，我们将智能分析Agent接入现有业务流程，由它自动收集场景配置、脚本、请求响应、日志和Trace等信息，完成初步排查并给出处理建议。涉及脚本修改时，Agent会先展示具体的修改内容，经用户确认后再写回平台。

**二**

**目标：从上线反馈到治理闭环**

Agent推广到真实业务后，我们遇到的治理问题主要集中在三个方面：

**反馈难采集：** 用户通常在分析结束后反馈问题，依赖事后描述和人工沟通，容易缺少当时的输入、场景配置和执行记录，难以完整还原问题现场。 **评价不统一：** 不同场景、版本和用户关注点不同，缺少统一的评测标准，单凭主观反馈难以客观比较Agent的实际效果。 **过程不透明：** 如果看不到Agent的工具调用、证据来源和判断过程，就很难确认问题出在证据采集、规则处理还是模型分析。

针对这些问题，我们希望将用户反馈、Trace排查、问题修复和回归评测串联起来，形成一套持续治理流程： **用户反馈→关联Trace→还原并定位问题→修复Skill、规则或证据采集逻辑→固化回归Case→评测通过后上线** 。

每个确认的问题，都应留下可复用的排查经验和可重复执行的回归样本。这样，后续版本可以在相同的问题现场中验证改动效果，避免仅凭一次经验或主观感受判断Agent是否真正得到改进。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/FMFU1P6sHHuDMZZ6DoRicuQsGibQUCbfpdXKb60J9aRZwEPOMjmWKECGWGZ3v8DgrBt4tudmGmhywDJghHlNHgFCmZH2sEdHJMptEpJvKLlQA/640?wx_fmt=png&from=appmsg)

**三**

**Langfuse治理基础：从过程记录到问题排查**

上一节定义了从用户反馈到回归评测的治理闭环。要让这套流程运转起来，首先需要完整记录Agent的分析过程，并将用户反馈、调用证据和评测结果关联到同一次执行。

Langfuse不直接参与业务诊断。它负责保留Agent的输入输出、工具调用、执行耗时和模型成本，让一次分析可以被还原、检查和比较。当用户反馈方案未解决问题时，我们可以通过对应的Trace回到当时的分析现场，判断偏差发生在哪个环节。

**Langfuse在治理闭环中的作用**

压测平台负责运行Agent和执行工具，Langfuse负责记录过程并关联治理数据。线上Trace用于排查具体问题，离线实验用于验证修改后的方案质量。相关能力见Langfuse官方说明。

**四**

**评测体系：用固定证据验证Agent质量**

上一节介绍了如何通过Trace还原一次分析过程。本节进一步说明，Agent完成修改后，如何验证改动是否真正有效。

评测的基本原则是让不同版本的Agent面对相同的问题、业务上下文和诊断证据，只改变需要验证的因素，再比较最终方案的质量、耗时和成本。Langfuse负责管理评测数据集、实验和评分结果，CLI Mock负责在回测时还原固定的业务证据。

**固定问题现场，回测Agent方案**

平台将用户问题、场景配置、JMX脚本、日志和请求响应等信息固化为评测Case，并为每个 Case配置人工校对后的参考答案。回测时，CLI Mock返回与原始问题一致的证据，避免线上数据变化影响前后版本的比较。

评测过程中运行的仍是真实Agent。Agent会按照正常业务流程调用工具、读取Mock证据、分析问题并生成方案，评测器再对实际输出进行评分。因此，固定的是问题输入和工具证据Agent 的分析过程和最终答案仍会重新执行。

验证Agent调优效果时，固定数据集、Mock证据、模型、评测器和执行预算，只修改对应的 Skill、规则或分析流程。比较候选模型时，则固定Agent实现和评测配置，只切换模型。对于结果波动较大的Case，需要重复运行并观察多轮结果，不能只根据单次最高分判断效果。

**评测流程：固定问题与证据 → Agent 重新分析 → 自动评分 → 结果对比与回归。**

**评测指标：方案质量、延迟与成本**

评测结果从方案质量、响应延迟和使用成本三个方面观察Agent的表现：

![](https://mmbiz.qpic.cn/mmbiz_png/FMFU1P6sHHuKlpTUPalItOCRQsOriaGVRtw8n2SZPjZIkmvc9bGty2cFyUdeqNU6VcyTjXfox7nkjMKCjHnibbyaX2rdUExqeqGctL8GibDPIw/640?wx_fmt=png&from=appmsg)

质量是首要判断标准。在质量接近时，再结合延迟和成本进行取舍。正式比较时，除平均值外，还应关注P95延迟、成本波动和重复运行结果，避免平均值掩盖极端情况。

**评测器：以人工期望答案为基准的五档评分**

评测器采用模型评审（LLM-as-a-Judge）： **以人工校对的期望答案为主要依据** ，判断 Agent 输出的语义一致性与关键内容覆盖程度。它接收三类输入：input是用户问题，用于理解背景、目标和约束；expectOutput是人工期望答案，提供评分基准；actualOutput是Agent实际生成的方案，作为评测对象。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/FMFU1P6sHHvCI6D5J3icLhwzGVF7vIh3haCIaeMiaSR9uudjcr9sNiayzXdfIMECU1xlYngaTJT1WaAk9uoULgSTia0GCl8bpMxw39ibfQ4vbKQw/640?wx_fmt=png&from=appmsg)

**评分边界：参考答案不是唯一的标准答案，也不要求实际输出复现参考答案的推理过程、措辞、结构、证据顺序或输出风格。**

评测器只返回一个合法分数，不输出理由或其他文字。人工期望答案提供统一标准，也决定了评测边界；需要抽样复核高低分和争议案例，修订遗漏的有效解决路径后，再用统一版本重新评测。线上修复效果由用户再次调试确认。

**① 定义评测器：** 在Langfuse中编辑需要的评测器定义，定义清楚需要传递的变量信息。

