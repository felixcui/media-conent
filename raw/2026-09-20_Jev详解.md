## 摘要

TypeSafe AI 于2026年9月发布了一款名为 Jev 的“系统一模型”，定位为语义决策引擎，专为软件中大量毫秒级的小判断设计，如工单紧急度评估、请求路由、危险命令检测等。它接收文本或JSON格式的状态信息与问题，支持Choice、Score和Noul三种输出类型，返回预设答案及其概率。

我们一直在用大语言模型（LLM）处理各种 AI 问题，连简单判断也交给它。Jev 专门处理这类判断，耗时以毫秒计，成本也低得多。下面看看它如何工作，以及适合用在哪里。

TypeSafe AI 于 2026 年 9 月 15 日发布了 Jev。这个模型不会对话、不会写代码，甚至无法生成一段有用的文字，却引起了相当大的关注。

这种限制恰好是它的设计意图。

多数软件需要完成成千上万个小判断：这张工单紧急吗？这个请求该交给哪个模型？这条 shell 命令危险吗？检索到的段落回答了问题吗？再加一个聊天机器人，并不能直接解决这些需求。

团队常把每个判断都发给通用 LLM。模型逐个生成 token，应用再解析、校验答案，格式不对时还要重试。这种方式能用，但如果答案总共只有五种，付出的时间和成本就偏高了。

Jev 专为这类决策设计。TypeSafe 将它称为“系统一模型”（System One model）：输入非结构化的状态信息，输出符合预设类型的答案及其概率。

接下来拆开看它的含义、适用位置，以及哪些宣传说法需要更谨慎地理解。

## 1\. Jev 要解决什么问题

工具调用和结构化输出出现后，把 LLM 接入软件容易了许多。

工具调用让模型以预先约定的格式请求执行函数；结构化输出让它返回符合结构定义（schema）的 JSON。两者都减少了大量脆弱的解析逻辑。

但底层模型仍然是生成式的。即使答案只有一个词 `billing` ，它也要按顺序生成 token。你需要为输入付费，等待生成，通常还要为输出支付更高的单价。

再把这个过程放进智能体执行循环：

```python
while not done:
    action = llm(context)
    result = run_tool(action)
    context += result
```

模型可能反复被调用，用来选择工具、判断结果、检测风险、决定任务是否完成，以及选择下一个模型。一次智能体运行中，可能有许多调用只需要作出判断，无须生成文字。

Jev 面向的就是这些调用。

> 它的出发点很简单：当代码已经知道所有可能的答案时，语言生成就不是合适的接口。

## 2\. Jev 是什么

最简洁、准确的描述是：语义决策引擎。

你向 Jev 提供两类信息：

- **状态（State）：** 描述当前情况的文本或 JSON。
- **问题（Questions）：** 希望它针对当前状态作出的判断。

每个问题都要预先声明答案的形式。Jev 支持三种基本类型：

- **Choice：** 从你定义的列表中选择一个选项，并返回每个选项的概率。
- **Score：** 按照你定义的有序等级对输入作出评定，例如低、中、高。
- **Noul：** 处理是非问题，返回该判断为真的概率。

Noul 是 TypeSafe 为这种布尔判断类型起的名字。名字不常见，但使用时更需要关注输出：一个介于 0 和 1 之间、可供代码使用的数值。

```json
{
  "model": "jev-latest",
  "state": "The deploy failed twice and customers are seeing 500s.",
  "questions": {
    "urgent": {
      "type": "noul",
      "instructions": "Does this need attention right now?"
    },
    "owner": {
      "type": "choice",
      "instructions": "Which team should handle this?",
      "criteria": {
        "engineering": "Product failures and outages",
        "billing": "Charges, invoices, and refunds",
        "sales": "Pricing and new accounts"
      }
    }
  }
}
```

响应会包含“是否紧急”的概率，以及三个团队选项的概率分布。你无须解读一段文字，模型也无法凭空添加第四个团队。

控制权仍在程序手中：

```python
if urgent > 0.9 and owner == "engineering":
    page_on_call()
elif confidence < 0.6:
    send_to_human_review()
else:
    add_to_queue(owner)
```

所以，大家常把 Jev 称为“智能 switch 语句”。这个说法听起来有些轻描淡写，却说中了设计中实用的部分：普通代码负责分支，模型负责那些普通代码难以可靠计算的模糊判断。

## 3\. Jev 与 LLM 的主要区别

传统 LLM 和 Jev 都能对客服工单分类，但得出答案的方式不同，也适合放在系统的不同位置。

![](https://mmbiz.qpic.cn/sz_mmbiz_jpg/IUJGIjicknic1FyiaicP0qx1kNYtWictjWvOJ3Y7xE7SzO5LKDHynZicHgUZLzT2goE9ZUDQgUicUucN6ekYXjrfXiasicWtU2N7DaVuyuxLKtLNeTRg/640?wx_fmt=jpeg&from=appmsg)

TypeSafe 表示，Jev 会并行评估同一个请求中的所有问题。这会影响工作流设计：对于同一份状态，可以在一次请求中提出所有相互独立的问题，再让代码按需使用答案，省去逐个提问、等待、再决定下一问的过程。

据该公司公布的数据，Jev 的端到端延迟为 **70 至 500 毫秒，** 每百万输入 token 的价格为 **0.042 美元，** 输出免费。其主要宣传数据是：相较于可比的 LLM 工作流，速度最高约快 200 倍，成本最高约降低至 1/400。

这些较大的倍数来自 TypeSafe 自己的工作流评测，取的是对它有利的比较结果，应视为评测中达到的上限，不能当作对所有应用的承诺。其背后的优势仍有合理依据：Jev 专门处理答案范围明确的决策，因此省去了冗长的推理过程和生成式输出。

## 4\. 概率为什么重要

符合预设类型的答案，只解决了一半问题。

假设 Jev 将一张工单分给账务团队。选中的标签告诉你哪个选项胜出，概率分布则告诉你它领先了多少。

```json
{
  "choice": "billing",
  "probabilities": {
    "billing": 0.52,
    "technical": 0.46,
    "sales": 0.02
  },
  "confidence": 0.18
}
```

直接自动分派这张工单会很冒进。账务选项虽然胜出，但优势很小。低置信度的答案应该触发另一条处理分支。

开发者可以据此采用一套实用的处理方式：

- **高置信度：** 操作影响较小时，自动执行。
- **中等置信度：** 请求确认，或调用能力更强的模型。
- **低置信度：** 交给人工处理，或补充收集信息。

阈值应该写在代码中，便于审查和调整。仪表盘上的一个标签，可以容忍把握不大的预测；删除数据的命令，则应设置高得多的门槛。

TypeSafe 使用“面向校准决策的强化学习”（Reinforcement Learning for Calibrated Decisions，RLCD）训练 Jev，目标是让置信度在大量预测中反映实际准确率。如果模型为一组答案都给出 90% 的概率，那么这组答案中应当有大约 90% 是正确的。

## 5\. “不会产生幻觉”需要限定范围

TypeSafe 声称 Jev 不会产生幻觉。这个说法只有在较窄的定义下才成立。

Jev 无法返回结构定义之外的选项。如果你定义了 `billing` 、 `technical` 和 `sales` ，响应就不能凭空添加 `legal` 。当代码期待一个标签时，它也不会返回一段格式不符的文字。

但它仍可能很有把握地选中一个合法却错误的选项。

类型安全能阻止不符合结构的输出，却不能保证判断正确。这个区别很重要：即使输出符合结构定义，错误判断仍可能导致向错误的客户退款、将事故分派到错误的处理方，或批准一条危险命令。

更严谨的表述是：“Jev 不会违反声明的输出结构，但仍可能判断错误。”

## 6\. Jev 在智能体中的位置

Jev 更适合与 LLM 配合使用。

LLM 负责需要语言能力或更深推理的工作，例如规划、写作、解释和使用工具。Jev 则负责围绕这些工作频繁出现的小判断。

有三个位置尤其适合接入。

### 6.1 模型路由

简单查询和架构评审，对模型的要求不同。Jev 可以评估请求，选择可能完成任务的模型中成本最低的一个。

```python
route = jev.choice(
    state=user_request,
    options={
        "fast": "Lookups, extraction, and small local edits",
        "powerful": "Architecture, ambiguity, and high-stakes work",
    },
)

model = fast_model if route == "fast" else powerful_model
```

路由器只负责选择由哪个模型处理，请求本身交给选中的模型回答。

### 6.2 工具风险检查

在智能体执行 shell 命令前，Jev 可以把命令分为只读、可逆或破坏性操作。还可以分别询问：它是否删除文件、改写 Git 历史、操作生产环境，或访问仓库范围之外的内容。

高置信度的只读操作可以继续执行；具有破坏性或判断不确定的操作，则可以暂停并等待人工批准。LangChain 的 Jev 集成通过在执行前检查工具调用的中间件，应用了这一模式。

### 6.3 验证与监督

测试还没通过，智能体也可能声称任务已经完成。Jev 可以查看当前状态，回答范围明确的问题：测试通过了吗？智能体是否在重复同一个动作？输出符合规则吗？这个结果需要复核吗？

已有明确程序测试的地方，仍应使用测试。Jev 补充的是那些需要理解含义才能判断的语义检查。

## 7\. Jev 目前能解决哪些问题

最适合的场景有三个共同点：可以列出可能的答案；认真阅读的人能快速作出判断；判断发生得足够频繁，延迟或成本已经值得关注。

### 7.1 客服与运维

- 判断意图、紧急程度、归属部门、是否为垃圾信息，以及客户的不满程度。
- 通过几项小检查，确定退款和政策例外的处理路径。
- 在人工阅读前，根据语义所反映的严重程度，对日志和事故排序。

一次请求就可以针对同一张工单提出这些问题，再由代码组合答案，执行公司具体的分派规则。

### 7.2 搜索与检索

- 根据检索段落能否回答查询，对结果重新排序。
- 检查引用是否支持某项论断。
- 在把上下文发送给成本较高的 LLM 前，过滤无关片段。

基于向量表示的检索擅长查找语义相关的文本。Jev 则可以进一步判断：某个段落对当前这个问题是否有用。

### 7.3 质量与安全

- 检查提示词中是否存在越狱或提示词注入。
- 按照规则或评判标准，检查生成的内容。
- 在代码变更生效或工具调用执行前，标记风险。

这些检查应与确定性控制配合使用。语义分类器适合处理模糊风险；权限、沙箱和测试则负责执行软件能够精确验证的规则。

### 7.4 大规模分类

- 为文档、研究论文、商品条目或客户消息打标签。
- 将自由文本转换为传统机器学习模型的特征。
- 按同一套评判标准，为大型语料库中的每条内容打分。

在这些场景中，较低的单次调用成本会产生实际影响。过去因为太贵而无法覆盖每一行数据的判断，可以成为常规数据流水线的一部分。

### 7.5 实时界面

- 从已知页面元素中，选择下一步浏览器操作。
- 在用户写作时，评估语气或表达是否清晰。
- 根据结构化的游戏或模拟器状态，选择下一步动作。

Jev 目前只支持文本，因此这些系统必须先把环境转换成文本或 JSON。它无法直接看屏幕，也不能直接根据像素画面玩游戏。

## 8\. 哪些场景不适合 Jev

一旦无法事先确定答案范围，Jev 的作用就会减小。

- 它无法撰写回复、总结文档、生成代码或解释推理过程。
- 它在算术、计数、日期比较和精确字符串处理上不够可靠。这些操作应交给代码。
- 如果判断需要经过多个隐含的推理步骤，它就比较吃力。可以把判断拆成更小的问题，或使用推理模型。
- 它无法直接提取未知值。需要先找出候选值，再让 Jev 从中选择。
- 无关上下文可能降低准确率。只发送当前判断需要的状态信息。
- 模型权重未开放，产品仍处于早期开放阶段，只支持文本输入，独立的校准数据也有限。现在还不适合不加验证地信任它。

还有一条更简单的规则：如果确定性代码已经能正确解决问题，就继续用代码。普通的 `if` 语句比任何模型都更快、更便宜，也更容易测试。

## 9\. 怎样接入 Jev，避免引入新的故障

模型本身便宜，出错后的重试、人工复核或生产事故仍可能让总成本很高。应该衡量整个工作流的成本和效果，不能只看 token 单价。

一个合理的接入过程如下：

1. 选择一个范围明确、风险较低、可列出所有可能答案的判断。
2. 调用模型前先写好评判标准，明确每个选项包含哪些情况。
3. 收集有代表性的样例并标注预期答案，也要纳入模糊情况和对抗性样例。
4. 让 Jev 以影子模式与现有工作流并行运行，记录结果，但不让它改变现有行为。
5. 绘制准确率与置信度的关系图，根据自己的数据设定阈值。
6. 先自动处理最安全的分支，不确定的情况仍交给人工或能力更强的模型。
7. 固定或记录模型版本、问题、判定标准和阈值，确保发生变化后，可以在同一套评估数据上重新运行并比较结果。

问题本身就是程序的一部分。像对待代码一样管理它们：纳入版本控制、进行审查，并在模型或评判标准改变时重新测试。

### 9.1 这种设计带来了什么变化

Jev 值得关注的地方，在于它主动放弃了生成文字的能力。

它提供了一种更贴近软件的模型接口：固定的答案类型、明确表达的不确定性、并行提问，以及由代码控制的分支。

这让它适合与生成式模型配合。LLM 生成计划、解释或代码；Jev 为请求选择处理路径、检查高风险操作、核验结果，并判断不确定性是否高到需要交给人工或更强的模型。

即使以后有其他模型取代 Jev，这个思路仍然有价值。过去几年，我们一直让生成式模型通过文本完成各种智能任务。许多生产系统需要的，只是一个小而快、能被普通软件安全使用的判断。

Jev 正在尝试建立这样一类模型。

### 9.2 从哪里开始

不必一开始就围绕 Jev 重建智能体。先找出一个判断：它目前依赖缓慢的 LLM 调用，或一条总是出问题的正则表达式。

给 Jev 最少的必要状态，定义可能的答案，把它返回的概率与当前结果一起记录。先验证它能否胜任一个分支，再考虑交给它更多工作。

可以这样理解 Jev：普通 `if` 语句能检查数据值，却不能理解含义；Jev 为这类地方补上语义判断。
