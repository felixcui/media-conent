## 摘要

一篇讲 Agent 评测方法论的实践总结。核心判断是 Agent 评测有两重不确定性：一是模型输出不可预期，二是 Agent 内部强耦合——改第一句 Prompt，可能让另一句 Prompt 要求的行为也变，所以改一处要重测全局。由此带来两个坑：其一，评测和迭代常由同一批人做，手段和目标同源，等于裁判兼选手；其二，指标可被“作弊”，比如把“搜索要全面”定成指标，工程侧在 Prompt 里写“没搜到二十个结果就重试直到搜够”，分数立刻上去，真实体验未必更好。方法论上作者强调顺序：先确定评分指标，再设计题目，反过来做会让题目和产品目标之间留缺口；极端做法是先不定指标，只把结果（截图、录屏）铺出来看。有时效性的信息要存快照做回归，可以用网络存档加搜索搭基础能力评测，也可以把环境动态性写进题目、每天跑，以暴露问题。公共 benchmark 只能作参考：正规的有指标论证和社区反馈，社媒上的效果展示往往分不清是不是 one-shot。

**Agent 评测的定义**

评测也是测，评测就是一个测试工作。

传统的软件工程中的测试工作是服务于迭代后验证系统行为是否符合预期的，这一点上没有区别。

那为什么单独拎了个词出来叫评测，而不是直接叫模型测试/Agent测试？

跟软件测试工作相比，模型及 Agent 迭代的时候，改动的不确定性非常强，以本文主要讨论的 Agent 举例，具体有两方面的不确定性：

1\. Agent 依赖模型的输出，模型的输出是有不可预期性的，人类操控 Agent 的工具「语言」，本身也存在大量歧义。

所以我们对模型的输出的控制能力是有限的，可以说是远低于对一个传统软件代码系统的控制。

2\. Agent 是一个内部耦合性很强的系统，并且它的内部复杂程度跟模型的随机性之间是在做一个乘法。

你改了第一句 Prompt，可能会令另一句 Prompt 所要求的行为也产生影响。

比如：我的 Agent 本来有一个计划机制，Prompt 写的是「在开始任务之前进行计划」，后面迭代中要加一个对简单问答直接回答的机制。

如果通过改 Prompt 的方式来迭代，就要考虑到和「在开始任务之前进行计划」这句Prompt不打架。

Prompt 写的比较多的人应该有类似感受：

你在 Comfy UI里面用生图的时候，想搞出一个效果，很多时候要求你对每一个关键词及他们之间的关联有很精细的了解，加一个不合适的风格描述词可能把原本定好的角色发色和光影效果全部带偏。

Agent 在迭代中，想要的效果和实现方式之间有一定程度关联，相比模型训练也有一定可控性，但整体还是比较黑盒的。

把它的逻辑完全梳理清楚是一件太困难的事情，对人的要求非常高。

所以评测就从正常软件开发里的测试分化了出来。并且相比传统软件测试，工作的重要性也被提了上来。

不过，Agent 评测和模型评测到底有什么区别？

**Agent 评测和模型评测的区别**

在 Agent 或者模型工作内部，评测工作往往跟迭代深度绑定，两者放在一起，改进手段和评测目标往往是同源的，会形成同时做裁判和选手的局面。

对模型公司来说，很多能力的迭代上采用跟评测集设计灵感同源的训练集并不算一个致命问题。

因为现有训练范式是在确保在某些能力方向上考虑到这个问题在内也能做出效果，放到用户手里也能Work。

相比之下，大部分 Agent Harness 迭代是工程工作，并没有哪种工程范式可以做这样的保证。

有句古话叫压缩即智能，为了刷榜/满足评测维度定义服务的训练虽然是数据的压缩，但多少也有智能。

可Harness 工作是 Decompression（解压缩） 或者 Steer（引导），Decompression 还谈得上对智能的释放，但很多评测是通过 Steer 完全可以满足的，Steer 在一些程度上就相当于作弊了。

举个例子，我定一个评测指标是要求 Agent 搜索的时候要尽可能全面，工程老师在Prompt ⾥写⼀句「没搜到⼆⼗个结果就重试直到搜够」，分数⽴刻上升很多，但实际使用体验未必好。

再到实际的团队协作方式去看，Agent 评测和迭代就没法像模型团队那样分工。

很多模型训练任务可以从评测出发，评测在整个流程里是灵感的起源，但Agent 完全无法复刻这条路径。

总结一下上述观点：模型评测只定义问题，Agent 评测同时要定义解决⽅案，难度更高，难以跟现有模型迭代一样分工。

评测的设计有两部分：

1\. 第一部分是比较产品角度的，非技术人士和用户关心的非常多的：怎么样设计题目以及打分机制

2\. 第二部分是工程角度的事情：围绕评测的 Infra 应该怎么设计。

工程角度的部分，Anthropic 的文章以及互联网上的各种文章都有很充分的实践经验介绍。

我们接下来分享下做第一部分工作时遇到的难点以及积累的解决经验。

3.1 围绕 Agent System 迭代的评测设计

Anthropic 对于评测基建的定义中有以下两个部分：

题目（Task）：A task is a single test with defined inputs and success criteria.（一项包含明确定义的输入和成功标准的单一测试）

评分器（Garder）：A grader is logic that scores some aspect of the agent’s performance. A task can have multiple graders, each containing multiple assertions.

题目和评测是一个 Bench 设计时候最核心的部分，它一般的组织形式就是：有若干个题目（Task）；每个题目里面有若干个评测维度。

这些评分器也有公用的，比如同样是设计 PPT 和设计网页，可能都会用到视觉相关的评分器去给出意见；

也有专用的，比如设计一道题，题目是计算 6 个宝可梦在进化前和进化后尾巴数量会有多少区别，那么会给这套题写一个专用脚本来判断 Agent 最后回答的那个数字是否正确。（本题出自 Gaia Benchmark）

其中，题目和评分的设计是一个产品问题。你的产品要表现成什么样子，题目和评分就要设计成什么样子。

对于怎么设计评分维度和题目，这里我想分享四条主要经验：

1）先确定产品的评分指标再确定题目

我观察到很多人在做评测集的时候，习惯性做的事情是一上来就直接开始想题目，接着就陷入一种这个题目是不是不太合适、这个题目能不能体现出我要表现的产品能力之类的纠结情况。

这个事情的原因是，设计Agent产品的时候，我们就知道要处理的用户任务是不可枚举的。

它里面的任务有低频、也有高频，不同任务之间也会有组合，组合的时候会有先后顺序，并且用户完全是自然语言输入。

所以，我们是不可能把用户所有处理任务都枚举出来，用这些任务去代表我们的产品。

如果跨过评分指标设计去设计题目，这题目其实跟你的产品设计目标之间总会存在一些 GAP。

所以应该从我们的产品想呈现出什么样的东西，也就是我们对好坏判断的角度出发，先设计好打分机制，再去设计题目。

我们可以捞一堆用户的反馈起来看，这里面有哪些共性。比如对设计类的任务，用户往往都反馈希望设计出来的东西符合某些标准，那就根据这个标准写个评测维度。

我们也可以从你生活中见到的各种理论里面提取，比如 [Manus 就从语言学中理解出的「隐喻率」](https://mp.weixin.qq.com/s?__biz=Mzk4ODYxNDE2OQ==&mid=2247488938&idx=1&sn=b9d8a04891e9ae0db477d39d269ecdf0&scene=21#wechat_redirect) 。

或者直接定义好需要的产品特性。比如我要设计一个做设计Agent，那我对产品的定义一定是：

要设计比较好看的动效；

有相应的流程；

动效在里面要做到特别强，还是不喧宾夺主。

确定好了，再根据这些前提做Agent。

2）可观测性是评测工作里最重要的部分

围绕大语言模型的工作很多时候像一门实践学科，而可观测性是实践学科中最重要的实验设计原则之一。

尤其对于那些依赖反复试验、反馈和迭代来积累知识的学科，可观测性几乎是实验能够产生有效知识的前提。

我们设想一个最极端的评测设计，先不确认任何指标，只把结果拿出来铺出来，比如最后产出的结果、结果的截图、录屏视频。

我的所有设计目标都服务于把产出的结果尽可能方便地展示给受众，可能包括：

1\. 它做了一个前端，有截图预览和完整的交互预览

2\. 它做了一个视频，有一个录屏预览

3\. 它的路径，每一步行动 Summary（摘要）

4\. 它用了多少时间，它用了多少 Token，用的什么 Effort（推理强度），加载了哪些 Skill

5\. 它基于哪个 Harness

那观测者不需要我给他指导，依靠自己的主观喜好直接去看，也可以给出对结果好坏的判断。

所以观测者把自己的主观喜好梳理清楚，就能设计出一个更可靠的评分维度。

3）做主观判断的实验并且为之负责

有两类问题，我们在建立评价维度时非常困难的：

1\. 大量用户的用法中，对于 Agent 给的结果的评价是非常主观的。

比如一篇文章好不好看或者说一个游戏好不好玩，这类问题的评测对于模型和 Agent 迭代都是难题。

2\. Agent 作为一个刚诞生的技术产品，大家都还搞不清楚该提供何种服务，都还围着用户问你们怎么用 Agent 以及都用 Agent 做什么。

另外，Agent 评测还需要评测轨迹，评测针对任务的某个中间步骤中 Agent 的运作方式等等，大量不直接跟用户需求相关的东西，更难以寻找确切的标准。

我们前一节提到了我们的工作很像一门实践学科，实践学科的重要工作 Mindset 之一是：敢下主观判断，不用特别纠结于推理演绎，直接下判断然后再去做实验观测。

任何道理、任何规律刚刚诞生后都是「主观定义」，「客观标准」是经历了长久时间形成的「主观定义」。

Agent 这个技术和产品形态都刚诞生没多久，很多定义没有被大量的使用检验过，难以形成共识，在推演一个设计是否合理的时候也难以寻找完全可信的论据。

所以我们要接受自己去做一些主观的判断，并为之负责。

一个开发者认为自己的 Agent 应该表现出某种产品特性，但他无法通过已有证据证明这个特性到用户手里是否真的好。

那他没有必要继续寻找证据，完全可以发上线直接做 AB Test。

同时，在摸索的过程中，评测完全可以作为描述自己对产品和整体架构认知的核心手段。

作为 Harness 的核心维护者，脑子里要尽可能了解自己的系统是怎么运行的，在什么样的条件下会有什么样的行为——评测就是这些行为的具象化。

4) 跟真实世界关联性比较强的 Task

对于跟真实世界关联性很强的任务，要有两套评测机制：

1\. 给有时效性的信息搞一套快照，来对一个很明确的我们要实现的 Capability（能力）进行 Regression（回归测试） 。

2\. 直接基于真实世界的运行任务，从里面提取迭代灵感以及建立评测维度。

举个例子，我让Agent帮我检索每天国际政治新闻，他每天搜出来的东西是不一样的，所以我无法把搜索的环境固定下来。

这类Task 评测有两个问题，一个是无法常规意义上进行完成与否的校验；另一个是不稳定，每天的搜索结果可能都不一样。

有两种手段可以进行这类问题的评测，第一种是构建一个 Internet Archive + Search（ 网络存档 + 搜索）的基建来进行基本搜索能力的评测；

第二种是在设计题目的时候将环境的动态性考虑进来，然后以暴露问题为目的来每天运行，方便寻找评测维度。

举个例子，我们让 Agent 去搜集 50 个国际大事新闻，再通过脚本或者 API 的形式去抓 100 个新闻网站当天的新闻列表。

再结合这两份数据进行评测维度定义：

1\. 判断一下这 50 个国际大事，有多少在多少个新闻网站里出现过，可以展现它抓的准确性或者权威性。

2\. 有多少个没有在新闻网站里出现过，代表它挖小道消息的能力；

这类评测是可以考虑用来每天日常运行，方便观测、暴露问题和寻找迭代灵感的。事实上，现在实际上存在大量用户实际发起的任务，都依赖真实世界中有时效性的信息。

**关于Agent System 评测和 Harness 迭代**

**4.1 Harness 会不会被模型能力吃掉**

模型能力不够强的时候，要不要靠工程问题先来兜一部分？

这是一个被很多Agent 开发者讨论很久的问题。

我个人观点是：

1\. 技术上大家的理解不会差太多，但一方面是产品总是要解决最后一公里问题，提供确定性的价值；

另一方面很多商业决策都有个时不我待的问题，如果依赖模型的迭代来让 Agent 变得更好，不论是等待前沿模型更新还是自己根据需求做后训练，迭代周期都太长。

工程（Harness）改动最快几个小时，就能完成一轮从定义好问题到改动完成到上限验证全流程。模型真发展好了，删了也不心疼，甚至还可以把这个东西卖给模型。

2\. Harness 工作的一大部分内容是理解模型能力并且把它激发出来。

「智力」「审美」这种抽象的词其实误导了很多人对模型的理解，模型的很多行为都是针对性训练后表现出来的，并非完全不可预期。

比如 Claude 的模型训练了大量的设计风格数据，开发者的 Harness Engineer 工作就应该是看如何 Prompting，好让模型也表现出这些行为。

即使模型进步了，Harness 也绝对不可能变成冲着模型吼一句「不完成就不要停下来」或者「把这个页面做的好看」，然后模型就能稳定地满足一个模糊的预期。

3\. 很多 Harness 工作是跟模型训练共同进步共同演化的。现在 Harness Engineering 工作中的很多特征，比如看轨迹，纠错，验证，交付等等流程，都是在对齐或者延伸 Agentic RL 阶段的训练数据分布。

Harness 的工作也促进了模型继续使用 Harness 下积累的数据进行训练。

4.2 那直接抄一个Harness可行吗？

最狭义的 Harness 就是让 Agent Loop 能正确跑起来和终止，再加上一些加载 Skill，扩展 Tool 等能力。

这部分的工作量并不大，搭一个并没有多大难度。

直接基于 Pi 或者 Claude 或者 OpenAI 的 Agent SDK 封装，甚至把一个已经跑的还不错的 Agent 拷贝下来去魔改，都不是困难的事情。

但实际业务跑起来的时候，你会收到用户各种各样的反馈，每个人都对 Agent 有各种效果上的要求。抄了后你得懂里面有什么，还得懂怎么改，又得有评测。不可能抄过来就完全不变了。

所以抄一个 Agent 框架解决不了问题。

这个工作和做产品是一样的，都是先跑起来再说，很多效果优化拍脑袋拍不出来。

**5.1 模型大造词**

我们前面把评测当成一个独立概念讲了很多，现在社媒上不断冒出来各种独立概念：Prompt Engineer、Context Engineer、Harness Engineering 等各种新奇的词语...

我觉得这些词确实在独立代表一些思想，但它们之间的交叉也极多。

创造概念就是在创造抽象层级。好的抽象可以降低协作成本，所以造词也不是个坏事，是提升生产力必须要有的流程，不然程序员们估计还在写汇编语言。

但坏的地方在于，市场太热的时候从业者们会急着造词争夺话语权，大家创造出来的大部分概念完全不具备一层好的抽象应该符合的基本要素。

像 Skill、Agent、Harness 这些东西到底是个啥也说不清楚，较真的用户和从业者们遇上了也一头雾水。

本来是一个造福大家的事情，但最后实际产生的作用只有 FOMO 老板，然后老板们折腾下面的人。

评测也好，Harness Engineering 等词也好，所有围绕模型的工作，还是要记住核心目的——让AI表现出符合自己设计目标的效果。

5.2 用户视角的评测

除了专业的评测设计，还有一个话题我认为尤为重要，就是用户视角的评测。

这里有两个问题，一个是用户怎样理解一个模型，或者理解Harness的能力及表现出某种倾向性的原因，另一个是用户怎么看待各种评测分数。

现有广泛传播的评测是有明显问题的。

大部分人，不只是用户，甚至包括专业从业者，也没有时间专门测试一个模型的表现，所以人们能看到的模型效果展示非常参差不齐。

日常大伙现在能接触到的 Bench主要分两部分。

第一部分是专业的 Benchmark。每个模型发布的时候都会跑，也有配套论文。

他们在设立的时候定了很多指标，再通过论证去证明它合理，并且同时有社区不断反馈，在一些角度证明是相对公允的。

但也给受众带来了很大的理解难度。像 Terminal-Bench、SWE 很火，大家都在这个上面评测，受众会觉得它用的人多公允。

但对里面有什么题目、有什么东西，大家没有特别多的认知。

很多人对专业 Bench，最后只看个分数或者少数参数，比如只看通过率和耗时，但这样就会忽略 Token Efficiency，

更重要的是忽略了评测维度。

本身一个从多角度理解可以保障公允的东西，经过了一次断章取义后就失真了。

甚至如果忽略了评测维度，对模型的理解也仅仅停留在一个抽象的好与不好，那这个 Benchmark 就没有特别大的意义了。

一个相对公允的 Benchmark 如果受众无法充分理解，那它的价值也会缩减很多，甚至存在误导。

第二部分就是社媒上各种效果展示，你也搞不清楚是不是 One-Shot。

很多较真一点的受众都会质疑，比如很多社媒上 Opus 5.5 做的视频，自己做一下就会发现也就那么回事。

同时，社媒上也有针对专业 Benchmark 进行包装的二次传播，比如非常容易带歪人们对模型能力理解的斩杀线截图：

如果一个模型只针对一个评测集里面部分容易完成且步骤少的任务方向进行了训练和优化，那它理所应当的会在斩杀线之上。

但这只能代表它针对少部分任务效果是好的，并非很多斩杀线理论传播者说的性价比高。
