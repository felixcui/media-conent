## 摘要

腾讯云 Venus 算法团队与 QQ 音乐合作，解决智能应用“第一公里”的判断问题：请求该走哪条链路、属于哪类需求。常见两条路线都不理想——用生成式大模型顺手做分类，慢且格式不稳；用规则，覆盖不住长尾。他们改用 JEV 决策模型：不做自回归解码，一次前向同时回答多道题，输出被约束在选项集合上。业务方给真实场景与判定规范，技术方负责数据治理、后训练、统一评测和量化部署；数据用“教师初标、异构复核、人工仲裁”三步走，期间发现一批高置信“错误”其实是标注错了，反过来修正了标签。交付尺寸选 9B：单卡可承载、延迟达标、效果与 27B 相当，冻结骨干只训练低秩适配层和决策读出头，双卡 H20 数小时一轮，支撑周级迭代。效果：路由 + 意图两道判断一次完成，p50 25 毫秒；题级准确率提升 24.9 个百分点，record 级全对率从 0.38 翻倍到 0.78，选项置换翻转率从 6.5% 降到 1.0%；比最好的公共 API 高 18 到 32 个百分点，作者说这差距本质是“懂业务”与“不懂业务”。FP8 量化后准确率与 BF16 完全一致（0.926），逐样本 top-1 一致率 98.8%，显存减半、效果零损失。

在智能应用里，用户query抵达系统后，系统要做的第一件事往往不是生成答案，而是"做一次判断"：这个请求该走哪条处理链路？它属于哪一类需求？这个判断是整个系统的"第一公里"。判断慢了，用户感到卡顿；判断错了，请求被错误路由。长期以来，这类判断有两条常见路线：用生成式大模型"顺手"做分类，或者维护一套规则/传统小模型。前者延迟以秒计、输出格式不稳定、调用成本高；后者泛化能力有限，面对口语化、上下文依赖的真实用户表达时力不从心。

这次 **Venus算法团队** 与QQ音乐业务团队的合作， **Venus算法团队** 给出了第三条路线：用专门为"判断"而生的JEV决策模型，配上一整套从数据到训练到部署的完整解决方案，实现JEV决策模型取得切实业务收益。

## 01

JEV：为"判断"而生的模型范式

JEV决策模型与LLM类生成模型有着本质的设计差异。生成模型根据用户输入文本，生成用户所需答案，让它做分类，本质是让它把答案逐个token生成出来，处理速度慢，并且难以保证格式稳定。而JEV决策模型从一开始就是为结构化判断设计的：

- 输入：一段结构化的上下文【state】，加上一组带类型的问题【选择题choice、是非题noul、打分题score】。每个选项都附带业务方书写的判定规范【criteria】。
- 输出：非文本形式，而是每个选项上的概率分布。

这个设计带来三个直接的业务价值：1） **足够快** ，不做自回归解码，一次前向计算即可同时回答多道题。在 QQ 音乐的场景里，"路由+意图"两道判断一次完成，p50延迟低至25毫秒；2） **非常稳** ，输出空间被严格约束在选项集合上，不存在"模型不按格式回答"的问题。选项顺序置换后的答案翻转率低至1%，决策行为高度确定；3） **可度量** ，输出是校准过的概率，业务可以基于置信度做阈值拦截、灰度发布和线上监控。

然而，JEV模型并非"开箱即用"，当前不管是官方的JEV模型、Gemini-Decisions，均在业务实际场景表现不佳，同时，我们发现基于LLM主干结合JEV范式与后训练，可以把特定业务的判定规范深度内化，取得更佳业务指标。这正是本次合作的技术主线。

## 02

共创：业务出场景与规范，技术出范式与服务

基于上述共识，Venus算法团队与QQ音乐业务团队，开启了一次基于“数据共创”的JEV决策模型业务落地探索。

**QQ音乐业务团队** ：可以提供真实业务场景与特定领域知识。训练与评测所需的全部数据都来自真实线上会话，业务特定的State包括用户偏好标签Slots、当前播放曲目、多轮对话历史、本轮Query等真实业务上下文；问题包括router与intent 两种意图分类，每种分类的判定边界等信息。

**Venus算法团队** ：可以提供一套围绕JEV范式的完整解决方案，包括数据治理（数据过滤与教师模型Relabel）、后训练流水线（多尺寸梯度产出）、统一口径的评测体系（公开评测与业务评测）、量化与部署支持（Venus Infra同事支持）。

## 03

数据治理：三步走的 Relabel 流水线

目前，用生成式模型批量构造标注数据已是行业常态，其中的核心挑战是如何获得高质量数据。真实业务数据尤其如此：历史标注口径随版本漂移、边界 case 各执一词、机器生成的标签里混着系统性的错标。在这样的数据上直接训练，模型学到的是噪声而非规范。因此，我们没有急于训练，而是先建立了一条 **教师初标 → 异构复核 → 人工仲裁** 的三步走数据治理流水线。

**第一步：27B教师全量初标** 。 我们首先在27B的Qwen3.5系列决策模型上完成JEV范式的后训练，得到一个深刻理解业务判定规范的高质量教师模型。随后用它对业务训练集与验证集做全量筛选，教师输出所有选项上的完整概率分布，我们取最高概率选项作为候选新标签；其中两类样本会被自动标记进入重点复核队列，一类是 **高置信分歧样本** ，也就是教师以极高置信度给出与原始标签不同的答案，这往往是原标签有误的强烈信号，另一类是 **分布平坦、置信度不足的疑难样本** 。相比人工逐条标注，教师模型全量初标既保证了口径的统一，也把人力从逐条标注解放到只处理疑难Case。

**第二步：GPT-6-Astra异构二次校验** 。单一教师无论多强，都存在自己的盲区与系统性偏差，往往它在错误样本上表现的很有自信。因此业务同学引入GPT-6-Astra模型对初标结果做独立的二次校验，两个异构模型判定一致的样本直接通过；判定分歧的样本，自动降级进入人工队列。这道双保险过滤掉的，正是单一模型无法自知的错误。

**第三步：人工校验与规范沉淀** 。进入人工队列的分歧样本与疑难样本，由业务同学依据判定规范逐条仲裁。这一步的价值不止于改对标签，更多的，每一次仲裁都在回答规范为什么这样定，仲裁结论会反哺判定规范的措辞，让规范本身在迭代中变得愈发清晰、无歧义，而清晰的规范，又会让下一轮教师 relabel 更加准确。数据、规范、模型三者由此形成正向循环。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/ZRhjO8xAWr4EnCvcl2NmUCVWf5ZWcnACYYU6ExJYAHag1m3yZVadRjH1HGOSqpjwibKJZHicDRz6Zyz3PfpH5UNL8aibFgCZpyWiaPWMXl5VpfY/640?wx_fmt=png&from=appmsg)

经过三步治理，最终产出 **近万条** 高质量训练样本投入训练。两份独立测试集（含线上 真实case 集）也按同一标准完成 Relabel，保证评测口径与训练口径严格一致，这是后续所有效果数字可信度的前提。

这套流水线还天然支持持续迭代：线上暴露的 badcase 回流后，走同样的三步流程进入训练集，形成" **线上回流 → 三步治理 → 周级迭代** "的自迭代完整闭环。本次合作期间，我们完成了一轮线上 case 的回流验证，模型整体表现保持稳定。

## 04

后训练路线：从 27B 验证，到 9B 交付

**4.1 摸底：通用基座"水土不服"**

我们首先评测现有决策模型在QQ音乐业务原始评测集上的效果，既包括27B JEV基座模型，也包括通过官方API调用的Typesafe-Jev。结果让双方对模型的业务适配程度形成了清晰、统一的认识：

![](https://mmbiz.qpic.cn/mmbiz_png/ZRhjO8xAWr5MiccFHfzWqpM5bicKo4oGTcJCv3y9Hh9uicX73PIDE6ticFa9Riau7JuNQdRrib2jbxhs3mRu6Tg9Auh3KwTHbepQ3qOtcJZiaqsQbA/640?wx_fmt=png&from=appmsg)

即便是27B的JEV模型，joint\_acc也只有0.43，即： **超过一半的请求会在路由或意图上判错** 。不仅零样本的27B JEV基座存在明显差距，Typesafe-Jev官方API的效果也不足以支持直接上线。换言之，当前JEV类模型业务适配偏低，不足以满足QQ音乐场景要求的可交付能力。这个结果也明确告诉我们， **后训练不是优化项，而是必选项** 。

**4.2 27B 后训练：验证了范式，也"验证"出了数据问题**

在 27B 模型上完成 JEV 范式后训练后，效果立竿见影：

![](https://mmbiz.qpic.cn/mmbiz_png/ZRhjO8xAWr7aYDibfFkZqV1q9coFqPaLZSWPlzaPqLZs2ibB422SCQvSibYCrc0IKWgk3emL7cNFBGicvsNLoOJkFNOhaqm7PlUIWvdB7n67NDk/640?wx_fmt=png&from=appmsg)

分题型来看，如下所示：路由题准确率86.5%，意图分类题准确率76.3%。范式的可行性得到充分验证。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/ZRhjO8xAWr4y7MI8FsBrLljibRmGVUdwBLJv4RBgDULjWPdVdYqL9lRlOKghrtCFCu1fCbnJkKICuQriajywneoGwKkgQ7nscDpvpMsaILsQE/640?wx_fmt=png&from=appmsg)

但这轮训练还带来一个 **意料之外的收获** 。在分析模型的高置信错误（high-confidence error）时，我们注意到数十条样本的"错误"非常可疑，模型以极高置信度给出了与标注不同的答案，而对照判定规范逐条复核，模型的判断反而更合理。我们将这批样本同步给 QQ 音乐的同事人工核查， **确认其中约 35%~40% 确实是脏数据（标注错误）** 。测试集如此，那训练集大概率也存在类似的问题。

这个发现改变了项目的走向：也就是模型已经"好到能发现数据的问题"，那么数据问题不解决，训练与评测都会触及天花板，这正是第三章"三步走"数据治理流水线的由来。

**4.3 9B 后训练：交付尺寸的确定与上线**

数据治理完成后，我们在清洗后的数据上对 9B 模型直接进行后训练。选择 9B 作为交付尺寸，是效果与工程成本的平衡点，业务需要单卡即可承载、延迟满足线上要求、效果与27B模型相当的模型，随后完成FP8量化、测试无损并部署上线。

训练方案本身采用参数高效路线：冻结模型骨干，仅训练低秩适配层与决策读出头——既完整保留基座在预训练阶段获得的通用决策能力，让业务数据只负责"教它懂规范"，又把单轮训练成本压到双卡H20数小时，支撑"周级迭代"的节奏。从拿到新数据到产出新模型，整体周期以"天"计。

## 05

效果：后训练的收益，以及与公共 API 的公平对比

**5.1 评测口径**

所有数字都建立在统一口径之上：同一份测试集、同一套指标。指标包括题级准确率（acc）、 **record 级全对率（joint acc，路由与意图同时判对的比例，最接近线上真实体验）** 、分题准确率、校准误差（ECE，衡量置信度的可信程度）、选项置换翻转率（flip，衡量决策稳定性）。

**5.2 交付模型 vs 基座 vs 公共 API：全面领先**

在清洗后的同一测试集（数百条真实业务样本）上，最终交付的9B模型与自身基座、两个有代表性的公共决策API的完整对比：

![](https://mmbiz.qpic.cn/mmbiz_png/ZRhjO8xAWr74g3hXXW143sXE1O4iam6YxK3qbgjSkcIqjTOxzyE79UqjicN8NjDnCj4W39JibjrwHozTTaPiaTuGrUhIF1n29YkfMUATMzdcq90/640?wx_fmt=png&from=appmsg)

交付模型在 **所有指标上全面显著领先** ：相比自身基座，题级 acc 提升 24.9 个百分点，joint acc 从 0.38 翻倍至 0.78，选项置换翻转率从 6.5% 降至 1.0%，这个指标代表后训练不只是"答对更多"，更让决策行为变得 **稳定、可预期** ；相比最好的公共 API（jev-1.14.0），题级 acc 高出 18.4 个百分点，joint acc 高出 32.2 个百分点。

需要说明的是，公共 API 是 **通用** 决策模型，从未见过 QQ 音乐的判定规范；这个对比的意义不在于分出高下，而在于说明： **业务判定规范无法被通用模型"猜"出来，必须通过数据与后训练注入** 。18~32 个百分点的差距，本质上就是"懂业务"与"不懂业务"的差距。此外，自托管还带来了数据不出域、无按量调用成本、延迟可控的附加价值。

## 06

量化与部署：从模型训练到推理上线的Co-Design

模型训练完成只是半程，技术团队的服务一直延续到上线前的最后一公里。我们和Venus Infra团队一起Co-Design，对模型做推理加速，为业务方提供高效高质的模型服务。

**量化** ：我们验证了 FP8 量化方案——在专项测试集上，FP8 与 BF16 的准确率完全一致（0.926），逐样本 top-1 一致率 98.8%，平均 KL 散度仅 0.0027，延迟持平。 **显存占用减半、效果零损失** ，量化从"需要权衡的取舍"变成了"默认就该做的事"。

**部署** ：9B 模型单卡即可承载（BF16 峰值显存约 29GiB，一张 L20 绰绰有余）；需要更高吞吐时，需要更高吞吐时，采用每卡一个完整实例的多副本横向扩展，前置负载均衡即可，无需复杂的模型并行改造。

## 07

延伸探索：数据质量到位之后，小模型也能打

9B 模型交付上线后，我们的服务故事已经讲完了。但还有一个技术问题没有答案： **在 JEV 范式下，决策任务的效果瓶颈，到底在模型容量，还是在数据质量？** 带着这个疑问，我们又做了一组探索性实验——在同一条训练流水线、同一份清洗后且添加了部分线上bad case的数据上，额外训练了 4B 与 2B 两档更小的模型。

结果超出了我们的预期：

![](https://mmbiz.qpic.cn/mmbiz_png/ZRhjO8xAWr7X2qFicv5ppibx06PcN4buaF638PNpGVFrqX2HMyPnjPnVG4cjicCjhf5ZKa3Tp0f4sTDSg9YCO4m1kXicFsL9kn6XjdUR5Cp1zOo/640?wx_fmt=png&from=appmsg)

三档模型的效果差距在 **0.5 个百分点以内** ——连 2B 这样的小模型，也没有出现明显的效果折损。这组实验回答了我们最初的问题： **在 JEV 范式下，当判定规范被高质量数据充分注入后，任务的瓶颈不再是模型容量，而是数据质量。** 前三章在数据治理上的投入，不仅抬高了 9B 交付模型的上限，也让小尺寸模型"站在同一片肩膀上"。

这个结论的价值不止于一个数字：一方面，它为未来更低成本、更低延迟的部署形态提供了数据支撑——2B 档 p50 延迟仅 25ms，意味着在延迟敏感或算力受限的链路上，业务有了"几乎不掉点"的备选方案；另一方面，它验证了这套方法论的可复制性—— **"高质量数据 + 小模型后训练"是性价比最高的落地形态** ，这对把 JEV 范式推广到更多业务场景是一个强有力的论据。

此外值得一提的是，9B 交付模型在两个独立测试集上表现一致（差距 <1pt），说明模型没有过拟合，效果可复现、可预期。

## 08

结语：不止一个模型，更是一套可复用的服务

![](https://mmbiz.qpic.cn/mmbiz_png/ZRhjO8xAWr49Uy8qNibO32OxL1SOibhxqrNWCSSkUXHscpjKjLMicgQR429XWB9XiaDWMcmIOttVChlgA4v6U7QzvuYkWKGWUr1EcJ0FV4wbbHc/640?wx_fmt=png&from=appmsg)

回顾这次合作，算法团队交付的远不止一个模型文件，而是一整套可以复用的服务：

1. **JEV落地** ：把JEV决策模型这一更轻量的算法路线更稳定的引入业务，替代生成式大模型做判别的重方案；
2. **数据方案** ：提出一整套业务+算法标注规范共建、教师模型relabel、人工审计、badcase自动回流的机制；
3. **训练经验** ：搭建参数高效的后训练流水线，适配多尺寸模型（27B、9B交付，4B、2B给出探索结论）、适配周级迭代需求；
4. **评测服务** ：统一口径的指标体系、与公共API的横向基准、逐case的预测明细分析；
