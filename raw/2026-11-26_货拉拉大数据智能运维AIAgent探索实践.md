## 摘要

货拉拉大数据运维的演进分四段：人肉、工具、平台、智能。早期大数据 SRE 近 70% 的工作时间花在事务性任务上，扩容要照 SOP 和脚本一步步来，手工干预还容易出稳定性事故；于是自研自动化运维平台 TSL，做资产管理、工作流编排、服务管控 Agent，支撑超千项运维资源和故障应急扩容、大促保障、发布变更、云迁移。但告警仍然难缠：治理后周均还有 50 多个电话告警，平均定位耗时 20 到 30 分钟，还要在多个系统间切换。智能阶段的做法是 Workflow 加 Agent 协同：Workflow 给标准化、可审计的流程骨架，Agent 处理信息不完备、需要动态判断的部分。文章把取舍讲透了——只用 Workflow 会规则爆炸、长尾异常覆盖不了，最终只自动化了最简单那部分；只用 Agent 则决策路径不固定、结果难复现，高风险操作要的安全边界、审批、回滚预案和可追溯审计都保证不了。具体场景上，告警自愈走“告警→路由分析→读资产信息→workflow+Agent→生成自愈计划→人工兜底判断”，根因分析因涉及指标、日志、健康度、血缘、变更多维证据，改用多 Agent 分工；另建了覆盖基础设施、监控、日志、故障、操作五类的运维知识库。

**摘要：随着大数据集群规模的持续扩大，传统依赖人工经验的运维模式已无法满足稳定性和效率要求。本文分享了从自动化运维平台 TSL 到智能运维 AI Agent 的完整建设路径：涵盖流程编排、根因分析、告警自愈、多Agent 架构与运维知识库等核心能力。最终，推动运维从人工经验驱动向智能化演进。**

## 背景

伴随公司全球化布局加速，我们在多云、多地域部署了10余个数据中心，支撑实时、离线与分析等多类型大数据场景，形成 **场景多元、规模庞大、架构复杂** 的分布式体系，对交付效率与稳定性保障提出更高要求。主要挑战包括：

1. 1\. **运维流程多，难以复用** ： SOP 数量多，大量环节依赖脚本和人工操作（集群部署/扩容/升级/配置发布等）；同类操作在不同组件上步骤差异大，经验难以沉淀为可复用的自动化能力。
2. 2\. **多集群、多组件导致标准化困难** ： 集群与组件规模大，发布、维护、变更的入口和步骤不统一。
3. 3\. **跨地域变更与回滚协同成本高** ： 一次变更常同时涉及多地域、多集群、多服务及第三方组件，需要分批灰度；组件多为有状态服务，回滚往往伴随数据一致性处理，风险控制难。
4. 4\. **多场景并存，SLA 分层明显** ： 批处理、实时计算、在线服务与 OLAP 对时效和可用性的要求不同，资源调度与稳定性策略需要按场景分层。
5. 5\. **故障定位链路长** ： 问题可能同时跨采集、传输、计算、存储，指标、日志和任务状态分散在多个系统，关联分析依赖人工，定位和恢复时间容易被拉长。

为应这些挑战，急需在以下两个核心维度持续强化：

1. 1\. **运维效率提升** ：当前支撑100+集群、5万+CPU核数、40+组件的日常运维，亟需通过自动化与智能化手段替代传统人工操作；
2. 2\. **系统稳定性保障** ：鉴于全球化架构下任一单点故障均可能波及多条业务线，需构建覆盖全链路的端到端稳定性保障体系。

针对上述挑战，我们通过四个阶段逐步完善运维能力：

1. 1\. **人肉时期** ：从规范化入手，构建并完善运维SOP、变更管控以及服务组件的监控部署。
2. 2\. **工具时代** ：对关键流程进行脚本化改造，完善全球化架构，初步提升运维人效。
3. 3\. **平台时期** ：建设自动化运维平台，推动能力落地。
4. 4\. **智能时期** ：自动化已覆盖大部分运维场景，开始探索智能化运维。

## 智能运维建设

### 1\. 问题与痛点

通过以上能力建设，自动化平台达到相对成熟阶段后，我们开始探索大数据智能运维方向。  
当前告警治理后周均仍产生50+电话告警，平均定位耗时达20～30分钟，且需在大数据内的多个系统间切换分析操作，人工投入成本高、效率低。一旦告警未及时响应，可能直接带来作业失败/延迟、数据产出不准或中断、报表与看板不可用、下游业务决策与线上服务受影响，并进一步引发SLA违约与影响面扩大。同时，告警场景复杂度持续上升，对准确率要求高。基于上述挑战，已正式启动根因分析与告警自愈能力的构建工作。

### 5\. Workflow与Agent

在大数据告警场景中，系统复杂度高、异常类型多且链路长，既存在大量可标准化的操作，也充满信息不完备与动态变化的决策问题。

| **维度** | **Workflow** | **Agent** |
| --- | --- | --- |
| **核心理念** | 规则+流程 | 自主决策+行动 |
| **输入要求** | 需求相对明确、边界清晰 | 可处理模糊需求/不完备信息 |
| **稳定性** | 极高（结果可预测） | 相对较低（可能存在决策差异） |
| **扩展性** | 弱（新增功能需调整工作流） | 强（新增对应工具即可） |
| **维护性** | 弱（项目大、节点多、维护难度高） | 相对较好（集中于提示词&模型） |

- 只用 Workflow 的代价：规则爆炸与覆盖率不足
- 大数据异常组合多、变更频繁，IF-ELSE 很快膨胀，维护成本指数级上升；
	- 一旦遇到长尾异常或信息缺失，流程要么失败，要么必须人工介入；
	- 最终“自动化”只覆盖最简单的那部分，真正耗时的排障仍靠人。
- 只用 Agent 的代价：生产不可控与执行边界
- 决策路径不固定，结果一致性与可复现性较弱；
	- 高风险操作需要安全边界、审批策略、执行窗口、回滚预案；这些必须工程化；
	- 对外/对内合规要求（可追溯、可审计、可回放）很难靠纯 Agent 保证。

因此我们采用 **Workflow + Agent 的协同模式** ：以 Workflow 提供标准化、可审计的流程骨架，以 Agent 提供面向不确定性的智能分析与动态调度工具，实现效率与可控性的统一。

### 6\. 多Agent

在大数据根因分析场景中，故障通常涉及多维信号与跨系统证据（指标、日志、健康度、依赖/血缘、变更等）， **分析链路长、分支多且信息不完备** 。在 **单Agent架构** 中，难以在保证时效的同时稳定覆盖多域方法与复杂工具链，且推理链条过长易带来误判与不可复现。为提升分析的系统化能力与结果可信度，我们采用 **多Agent架构** ：将端到端归因分析拆解为多个可并行的专项分析任务，由不同 Agent 结合各自的工具与策略完成证据采集与推断；最终通过汇总/仲裁机制对多路证据进行对齐、交叉验证与置信度评估，输出结构化、可解释、可复盘的根因判断与处置建议。

### 7\. 运维知识库

我们建设了智能运维知识库，作为“知识中枢”支撑问题理解、经验复用与精准决策。知识库涵盖基础设施、监控、日志、故障、操作五类，并通过七个标准化步骤完成与应用场景绑定，形成可用、可扩展的运维知识体系。后续将随场景深化持续更新，进一步提升分析与决策准确性。

### 8\. 评测体系

在模型应用服务场景中，评测体系的引入至关重要，大数据智能运维场景亦不例外。实现评测时主要有三类难点

1. 1\. **维度多、门槛高** ：一次告警要同时看日志/指标是否有效、分析是否正确、建议是否可执行。
2. 2\. **维护成本大** ：口径、知识库和 BadCase 都要持续更新；不迭代就会过期，难长期坚持。
3. 3\. **线上数据不稳定** ：告警上下文每次不同，同类问题结论也会波动，单次对错不足以代表整体服务水平。

这些难点可收敛为一条闭环：现场只做分档评分+备注，知识库/BadCase 按周期更新，效果用真实告警的长期数据衡量。平台跑通“ **告警分析—用户评测—数据录入—迭代优化** ”，形成数据飞轮，让分析越用越准，知识库越用越丰富。

1. 1\. **告警分析** ：用专家知识辅助归因 / 自愈判断，结论经飞书输出
2. 2\. **用户评测** ：值班同学对分析质量打分（不及格 / 合格 / 优秀）并备注
3. 3\. **数据录入** ：数据分析并将优秀案例（GoodCase）录入知识库，知识库定期更新

4\. **迭代优化** ：BadCase分析及针对性优化，提升归因诊断的准确性

## 未来与展望

### 1\. 服务化体系架构

统一整个智能运维体系架构，自下而上分为四层及稳定性保障能力：

- • **数据层** ：主要负责数据采集和上报，包括日志、指标、事件、资产等数据
- • **工具层** ：由各类 Skill、MCP、模型及外部 API 等组成
- • **平台层** ：包含网关、记忆系统、调度及安全鉴权管理
- • **业务层** ：面向智能运维场景，围绕稳定、成本、效率三大要素
- • **稳定性能力** ：高可用架构、容灾能力、监控告警、可观测能力、服务降级等等
