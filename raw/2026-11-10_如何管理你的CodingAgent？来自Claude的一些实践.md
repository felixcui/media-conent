## 摘要

使用编程智能体本质上是在做管理，最能发挥其价值的工程师往往已掌握管理能力。文章借鉴优秀工程管理者实践，提出与智能体协作的核心习惯：提供测试、构建等验证机制让其自行确认结果，交代目标、约束与成功标准等背景，让纠正积累为持久规则，默认交由智能体判断只强制不可妥协项，先明确计划再实现，尽早纠偏及时重启，委派任务但保留判断，设计好无人值守流程，扩大验证能力减少注意力依赖，并决定哪些事不做。不必先有管理头衔，但需学会通过支持他人取得成果的方式管理智能体。

**管理智能体所需的能力，与管理团队所需的能力相当接近。你不必先成为管理者，才能学习这些能力。**

如果你整天都在使用编程智能体，你就在做管理。你反复挑选任务、编写指令、分派工作、跟进进度、评估结果，并决定哪些改动可以交付。最能发挥智能体价值的工程师，未必最擅长提示词工程；他们往往已经有意无意地学会了管理。

你可能不太愿意接受这个说法。我欣赏的许多工程师选择走个人贡献者（IC）路线，是因为他们希望继续亲手做技术工作。他们见过朋友转做管理后，日程被会议填满。我并不想让你成为那样的管理者。这里的“管理”有一个具体含义：通过支持他人开展工作，取得好的结果。当然，我也没有说智能体可以替代管理者或同事。

你对糟糕管理者的每一条抱怨，都能成为检查自己如何与智能体协作的问题清单。想想任务交接。如果你经历过一次糟糕的交接，收到的要求可能很模糊，缺少背景，或者预期总在变。对走技术路线的工程师来说，好消息是：多年接收任务的经历，可能已经让你知道一次好的交接应该是什么样。

我之前写过，你的编程智能体需要一位管理者 <sup>[2]</sup> 。也写过委派工作时一个不易察觉的风险：认知让渡 <sup>[3]</sup> 。这篇文章将优秀工程管理者的实践，与我们使用和开发 Claude Code 的经验放在一起比较。各节大致按影响大小排列，最能带来改善的习惯放在前面。

## 1 给它验证工作的办法

**最佳实践：** 给智能体提供验证工作的机制，例如测试套件、构建或截图，并要求它拿出验证结果作为证据。

**反面做法：** 把“看起来做完了”当作完成确认。这会迫使你承担所有验证工作，自己成了智能体的测试套件。

问一位有经验的管理者，如何在不逐项检查所有工作的情况下，仍然确信团队产出质量可靠，他们会谈到护栏：持续集成（CI）、代码审查、监控看板、值班机制等。缺少经验的管理者如果不建立这些护栏，最后就得亲自验证一切，不出一个季度就会成为瓶颈。智能体也是如此。Claude Code 最佳实践指南 <sup>[4]</sup> 解释过，智能体会在工作看起来完成时停下来。如果没有验证机制，“看起来完成了”就是它唯一的判断依据。提供验证机制后，智能体就可以完成工作、运行验证、发现失败，再自行修正。对于界面改动，这可能意味着实际用浏览器打开页面，反复调整，直到功能和视觉表现都符合要求。

验证机制可以有很多种，只要能给出明确的通过或失败结果。测试、构建退出码、代码检查工具、差异比较脚本和截图，都可以用来验证。指南指出，在 `CLAUDE.md` 里，最有用的一行内容就是运行这些验证的命令。这个指令文件会在每次会话开始时提供给智能体。有了验证机制，你可以用下面几种方式把它接入工作流：

- **直接要求。**
	“完成后运行身份认证测试，持续修正，直到测试通过。”
- **设定目标。**
	使用 `/goal` ，由另一个模型在每轮结束后检查目标条件。它尤其适合长时间在后台运行的工作。
- **强制执行。**
	通过 Stop 钩子，在类型检查通过前阻止当前轮次结束。
- **安排审查。** `/code-review`
	会把代码差异交给一个未看过当前对话的新子智能体审查，就像代码作者不能批准自己的 PR 一样。

你甚至可以控制审查范围。让它找问题，它总能找出一些；让它只找正确性问题、忽略代码风格，它也会照做。优秀管理者在征求反馈时，也会学习如何明确范围。Claude Code 工具集中的大部分功能，都在帮助缩短这个验证循环。技能、钩子、子智能体和 MCP 将执行工作与验证结果衔接起来，让你只需关注智能体无法自行验证的部分。有经验的工程管理者也在做同样的事。

## 2 把背景交代清楚

**最佳实践：** 简明说明智能体无法通过查看仓库获知的信息，包括任务目标及其重要性、约束、不在本次范围内的事项，以及成功标准。

**反面做法：** 只给一句任务描述，把实际预期留在自己脑中；或者用智能体读代码就能发现的信息填满任务说明。

有效的管理者会清楚说明预期结果、约束和目标。他们讲明工作要达成什么，同时给执行者留下决定具体做法的空间。军队把这称为“指挥官意图”，Netflix 则强调提供背景、减少控制。

与智能体协作的一个难点，是你很难知道它缺少哪些背景。编程智能体接到任务后，首先就会读代码。现在的模型很擅长从仓库中了解目录结构、约定和测试配置，速度远比你逐一介绍更快。

动笔之前，先想想哪些内容智能体能自行弄清楚。如果某项信息写在代码里，而且智能体确实会去读，就不必再说。把篇幅留给仓库里没有的内容，例如一次会议决定、某个人使用的内部部署流程、这项任务为什么重要，以及这次怎样才算完成。

以“让看板更快一点”这个模糊任务为例，把它改写成一段提示词。这里的数字仅作示例。

```text
对成员达到 1 万人及以上的组织，将 /team 看板的 p95 加载时间降到 2 秒以下。

原因：企业管理员每天都会打开这个页面，加载缓慢是他们提交最多的支持工单问题。

约束：不改动数据库结构；保持 API 响应结构不变。

不在范围内：界面改动；整页缓存。
验证：运行 scripts/perf/team.sh，展示优化前后的数据。
```

不必每个任务都这样写。如果还处于探索阶段，用一个宽泛的提示词完全可以，后续逐步细化即可。如果暂时写不出提示词，可以让智能体向你提问，直到它能据此写出规格说明，再把说明保存为文件。之后新开一个会话，让智能体依据这份说明实施。后续审查时，也可以用它来核对结果。

你可能还需要让智能体访问其他工具，例如问题跟踪系统、错误监控看板或团队聊天工具。可以像对待刚加入团队的同事一样对待它。如果是它已经熟悉的命令行工具，例如 `gh` ，通常不需要额外解释。

## 3 让每次纠正都能积累下来

**最佳实践：** 同一个问题纠正不止一次后，就把经验写进团队的 CLAUDE.md <sup>[5]</sup> ，或做成共享技能。随着时间推移，也要检查新模型是否已经不再需要这些纠正。

**反面做法：** 每次会话都手动纠正同一个问题，或者依赖只保存在自己机器上的隐性知识。

能充分发挥 `CLAUDE.md` 价值的团队，会不时更新它，记下那些值得避免再次发生的错误。有些团队甚至会在代码审查中提及 @claude <sup>[6]</sup> ，把反馈转成长期规则。 `CLAUDE.md` 要保持简短，适合写入的内容包括：

- 如何验证某项工作，包括具体命令。
- 代码中容易引起误解的地方。
- 仓库中没有记录的决定。
- 你已经纠正过两次的问题。

这些例子体现了文字记录的积累效应。人员换团队、模型换版本，记录仍然可以继续发挥作用。

## 4 默认让它判断，只强制执行不可妥协的要求

**最佳实践：** 默认让智能体自行判断。只有少数必须始终执行或绝不能发生的事项，才通过钩子、拒绝规则等机制强制约束。

**反面做法：** 用全大写强调指令，为可选偏好设置钩子，或者在新模型已不再需要时，继续沿用旧模型时期的习惯。

安迪·格鲁夫在《高产出管理》（High Output Management）中，将这称为“任务相关成熟度”：监督程度应取决于一个人在这项具体任务中的过往表现，而不能只看其总体能力。

给新管理者的一条老建议也表达了同样的意思：给人比自己觉得安心的程度稍多一点的自主空间，同时提供支持，并要求他们对结果负责。

Claude Code 明确区分了这两类约束：提示词、 `CLAUDE.md` 和技能是请求，模型会结合情况判断是否执行；钩子、拒绝规则和托管设置则是始终强制执行的要求。大多数时候，你应该让智能体自行判断。模型看到了实际代码，往往比你事先设定的规则更有条件判断某条指南是否适用。强制机制应留给硬性要求，例如“绝不编辑自动生成的客户端”或“始终运行许可证头部脚本”。具体来说，新的终端和 VS Code 会话会以自动模式启动，由分类器过滤部署到生产环境、强制推送并覆盖他人工作等不安全行为。

指南的建议有两面。如果你不断强调 `CLAUDE.md` 中的某一条要求，智能体仍然执行不到位，就应该把它做成钩子。如果某个钩子表达的只是偏好，就应该移除，让智能体自行判断。这与团队废除已经无用的流程一样。模型更新后，也要相应调整。指南列出了一些可以停止使用的习惯：全大写指令、“再努力想一想”（如今推理力度已经可以通过设置调整），以及“别偷懒”。对当前模型而言，这些表达往往会导致规则执行过度和不必要的工作。与智能体协作时，流程过多也会成为事无巨细的控制。

## 5 先把计划说清楚，再开始实现

**最佳实践：** 在智能体开始写代码前，就计划达成一致。审阅其中隐含的假设，把任务拆成互不重叠、可以并行推进的工作。

**反面做法：** 让多个智能体同时处理范围重叠的任务，然后花一下午解决合并冲突，以及各自重复作出的决策。

一种有效的工作方式是先进入计划模式，反复讨论，直到计划合适，再把编码交给智能体。计划清楚时，模型往往一次就能完成实现。较大的任务可以再开一个会话，让它像资深工程师一样审阅计划。这相当于一次设计评审，也是以最低成本发现方向错误的阶段。审阅时要留意计划背后的假设，就像在一对一沟通中问：“哪些地方你还不确定？”

任务拆解也越来越多地交给智能体。Claude Code 的 `/batch` 可以接收一项大规模机械性改动，将其拆成 5 到 30 个任务，展示计划，再分别放到独立的工作树中执行，并为每个任务创建一个 PR。工作树是同一仓库的独立检出副本。你不必再亲自拆分全部工作，只需检查各部分是否重叠，并确保共享接口先完成。否则，并行可能只是表象。五个智能体处理互相重叠的任务，未必带来五倍产出，却可能留下一个由五位“作者”共同造成的合并冲突。

## 6 尽早纠偏，及时重新开始

**最佳实践：** 观察最初一分钟的执行过程，及时引导智能体。一旦发现偏离方向，就立即纠正。如果已经两次纠正失败，就用更好的提示词开启新会话。

**反面做法：** 继续尝试第三次、第四次纠正，却不修改最初的任务要求。

有经验的管理者知道，如果一个有能力的人反复做错，问题可能出在上游的指令、背景或任务范围上。对智能体，相应做法很明确：一旦发现跑偏，就按 Esc。如果两次纠正都没成功，就清空会话，把已经学到的经验写进一段更好的提示词。继续第三次纠正，通常只会增加模型需要反复读取和处理的信息，其中还包含之前失败的尝试。

低成本回退也改变了尝试的方式。 `/rewind` 可以把代码和对话恢复到之前的某个时间点，让你先尝试更有挑战性的方案，而不必承担太大风险。优秀管理者对待同事时也会这样做：如果错误容易撤销，就允许他们先尝试更有挑战性的方案。之后再复盘，适用时把修正经验整理成通用规则，写入 `CLAUDE.md` 。

## 7 委派任务，保留判断

**最佳实践：** 智能体负责执行，你负责重要决定：产品取舍、安全边界，以及哪些改动可以交付。审阅每一份代码差异时，都把自己当作故障发生后会被叫醒处理的人。

**反面做法：** 看到测试通过、命名合理，就批准一大批改动。这只是给代码放行，谈不上审查。

管理者不能用“那是下属交付的，跟我无关”来推卸责任。你运行的每一个智能体也是如此。我自己也犯过这样的错误。我让智能体研究产品与竞品之间的差距，并在本地准备 PR 来补齐。我读了调研结果，粗略看了代码，差点就推送了一批收益不大、却给用户增加复杂度的改动。我已经委派了工作，也险些把决策一起交了出去。这个陷阱很容易踩中：600 行代码差异，命名看着合理，测试全绿，于是点了批准。

一种合理的分工是：把代码风格、静态检查、审查意见跟进、常见缺陷修复和单元测试交给智能体，把安全边界、合规与产品决策留给人。

协调工作也是如此。智能体可以跟踪交接进度，但在互相竞争的需求之间作出取舍，以及让相关人员明确承诺，仍然需要人来完成。

你不必参与每次改动的内部执行循环。需要由你掌握的是外层循环：约束是什么，你实际阅读多少产出，需要保留哪些证据，以及哪些事项必须由人批准。同时，要控制每次改动的规模，因为每次审查覆盖的范围，也就是你需要理解的范围。

## 8 设计好无人值守的运行过程

**最佳实践：** 启动自主执行的任务前，明确完成条件、自我验证方式、操作边界、护栏，以及人工批准环节。

**反面做法：** 睡前启动一个长时间运行的任务，却没有定义何时完成、何时停止，第二天早晨才发现模型基于一个错误前提忙了一整夜。

负责跨层级管理的人，不会直接管理每位工程师的具体工作；他们管理的是目标、护栏、检查点和负责人。AI 智能体也在沿着类似方向发展。它们已经会把部分任务交给子智能体，也能按计划、在 CI 失败后，或在新 PR 创建后自主运行。更进一步的发展方向，是能够自主启动、自行验证，并且只在需要决策时请求人工介入的系统。

你的职责也随之从控制单次会话，转向设计整个工作循环。设计无人值守任务时，需要问自己五个问题。这与一位优秀管理者把项目交给资深工程师、随后准备休假时要问的问题相同：

- **它知道怎样才算完成吗？**
	可以是目标条件、规格说明文件，或一个需要修复到通过的失败测试。
- **它有自行验证的机制吗？**
	可以是测试套件、Stop 钩子或审查步骤。
- **它的操作边界是什么？**
	可以通过权限控制、沙箱、工作树，或只允许推送到某一个分支来界定。
- **有哪些限制运行的护栏？**
	例如轮次上限或费用上限。
- **结果交到哪里，由谁批准？**
	例如输出 PR 或摘要，并要求任何不可逆操作都经过人工批准。

指南还提出了两个管理者会熟悉的习惯：先小范围试运行，例如先让批处理任务处理三个文件，改进提示词后再处理剩余文件；新任务最初几次运行时，要先观察，再决定是否让它无人值守。可以把这看作一个试用阶段。

## 9 扩大验证能力，减少对注意力的依赖

**最佳实践：** 只有当自动检查、目标检查和独立审查者能够接手监控时，才相应增加智能体的使用规模；衡量吞吐量的同时，也要衡量质量。

**反面做法：** 开启的会话数超过自己能够认真审查的范围，再用 AI 写了多少代码来衡量成效。

管理者通常很快就会发现自己的管理幅度有上限。直接下属超过一定数量后，每个人能得到的关注都会减少，质量也随之下降。智能体也是如此。我把这称为“编排税”：超过最初几个智能体后，每增加一个，需要额外投入的注意力都会比前一个更多。大多数时候，我会运行四五个后台智能体，再开几个本地会话；有些日子，这样的数量也已经太多。

管理大量会话，靠的是把大部分监控交给自我评估、目标检查，以及使用独立上下文的审查者，把注意力留给决策。用通知代替反复轮询，以及集中查看后台任务的状态，也会有帮助。增加智能体数量的前提，是让它们更少依赖你的盯守。随后应衡量整个系统的成效，避免只统计活动量。有用的指标包括 PR 周期、新员工上手时间，以及回退或返工频率。AI 编写代码的占比并不是一个有用的目标，因为你希望得到的是质量和可靠性。格鲁夫关于配对衡量指标的原则在这里同样适用：统计合并 PR 数量时，也要同时统计回退和返工。

## 10 决定哪些事情不做

**最佳实践：** 问清楚谁需要它、如何判断做成了、什么情况下应该停止，并限制同时进行的工作量（WIP）。

**反面做法：** 觉得实现成本低，就把每个看似合理的想法都做成 PR。结果留下大量零散改动，等着团队审查、检查安全性并长期维护。

管理者说出的最重要的一个字，往往是“不”。有了智能体，说“不”却更难了。启动一项工作几乎没有成本，任何看似合理的想法，都可能在午饭前变成 PR。但接下来，团队就要审查这些 PR、确保安全、提供支持并持续维护。如今稀缺的是审查和验证能力。

那些传统的管理问题因此比以前更重要：谁提出的需求？怎样衡量成功？如何判断何时该停？当实现变得便宜，“该不该做”就比“能不能做”更难回答。

## 11 这个类比有哪些局限

**最佳实践：** 借鉴优秀的管理实践，同时考虑智能体的特殊之处：返工便宜、容易赞同要求，以及每次模型更新后都可能变化的能力优势。

**反面做法：** 把智能体完全当作初级开发者，或者因为能同时运行五个智能体，就认为自己已经能管理五个人。

这个类比有用，但不完美。做得好的人知道，它的局限在哪里：

- **管理人更难，这些能力也不能直接反向迁移。**
	运行过五个智能体，并不代表你已经准备好管理五个人。激励、冲突处理、职业发展，以及持续数月建立信任，在智能体管理中都找不到对应的工作。
- **返工几乎没有成本。**
	有些事你不会要求同事做，却可以交给智能体。例如白板前出现技术争论时，可以让智能体实现两三种方案，再实际比较。
- **智能体没有经验，只有笔记。**
	自动记忆只会在一台机器上记录笔记，不会传到同事的会话里。这些笔记也不同于你在职业生涯中积累的经验和判断力。需要把经验写下来，让整个团队都能使用。
- **智能体积极配合，而且充满信心。**
	让一位优秀工程师做错误的事，他会提出异议。智能体更可能照做，而你也更容易过度信任它。在沃顿商学院关于认知让渡的研究中，参与者大多数时候都接受了 AI 的错误答案，而且变得更有信心。让智能体反驳自己的答案，可以帮助你抵消这种过度自信。
- **你手里只有一种智能体类型，而且每隔几个月就会变化。**
	人类团队有不同的技能和长处；你使用的智能体却有相同的优势和弱点，而且这些特点会随着模型版本更新而改变。
- **初级开发者仍然需要培养。**
	当智能体接手了初级开发者用来学习基本功的入门任务，管理者就需要有意识地为他们安排这样的练习机会。
- **人与人组成的团队仍然重要。**
	有时你忙了一整天管理智能体，却没察觉到，原本用于建立团队凝聚力的时间已经被挤掉了。要避免这种情况。

## 12 不必先有管理头衔

**最佳实践：** 把精力放在促成好软件上：交代背景、定义完成条件、认真审查。

**反面做法：** 用代码行数评价自己，同时让缺少充分任务说明、也没有检查机制的智能体继续运行。

优秀的资深工程师一直在这样工作。他们写设计文档，交代背景，认真审查，帮助身边的人做得更好。智能体让每位工程师从第一天起就有机会练习这些能力，相当于一门管理速成课。几分钟就能收到反馈，无须等上一个季度；自己的错误，也有机会撤销。工作的重心正逐渐从亲手写代码，转向为好代码的产生创造条件。

没有人生来就是优秀的管理者或工程师。能力仍然要靠练习一点点积累。只是有了智能体，练习的成本降低了。

可以试试这些做法：

- 每项任务都要有它能运行的检查，并要求提供证据。
- 告诉智能体它看不到的背景，省去它能够自行获取的信息。
- 写代码之前，先把计划讨论清楚。
- 同一个问题纠正过两次，就记进 `CLAUDE.md` ；反复执行的工作流，就做成技能。
- 连续两次纠正失败，就重新开始，换一种方式写提示词。
- 审阅代码差异时，把自己当作故障发生后需要响应的人。

你不必立志成为管理者。但那些能把智能体用好的工程师，会在这个过程中逐渐学会管理。
