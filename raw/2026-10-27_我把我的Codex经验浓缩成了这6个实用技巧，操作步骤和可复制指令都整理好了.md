## 01 频繁重连，先检查代理配置

有时候，任务还没开始做，界面就已经在反复重连了。重连5次才正常，很浪费时间。遇到这种情况，其实是正常的，因为我们大部分人都是用的系统代理在操作，codex其实是试着重连5次，之后才走代理。

所以，我们的方法就是直接让codex走代理，不要直连，具体怎么做呢？

### 第一步：让它先检查

把下面这段话发过去：

●●●  
帮我检查当前安装版本是否支持 respect\_system\_proxy。然后检查 Codex 的 config.toml，在 \[features\] 下面有没有 respect\_system\_proxy = true。先检查并告诉我结果，不要修改。

codex回复我了

![操作截图01](https://mmbiz.qpic.cn/mmbiz_png/bh9XUZB5jhpeickiaNTAeT113e5YuPSjcuiaANcuRGlOcGY3Cy4BM6QMJFBKSYQxa5ySWmCj6fuhZRgCtyUAMLZqTkFHFzMMh2KQmniauayzlYE/640?from=appmsg)

注意它属于 **\[features\] 这一节** 。不要只看到这句英文，就随便粘到配置文件的某个位置。

### 第二步：确认后再修改

如果检查结果是当前版本支持、配置里还没有，再让它处理：

●●●  
请先备份 config.toml，再在已有的 \[features\] 节下加入 respect\_system\_proxy = true；如果已有这一项就修改它，不要重复创建配置节。完成后告诉我文件路径和修改内容。

这里不需要自己去翻一大堆文件，让它检查、备份、修改，再告诉你改了哪里就可以。

### 第三步：重新打开，再试一句话

保存配置后，关闭并重新打开 Codex，再发送一句简单的问题，例如：

> 这是什么项目？

看它能不能正常开始处理、正常回复。 **配置里有这一行和连接已经恢复，是两件事，最后要用一次实际对话确认。**

## 02 换对话之前，先写接力文件

这是我很建议大家养成的一个习惯。

一个任务聊久了，里面往往有很多信息：你想做什么、哪些方案已经排除、哪些内容已经完成、下一步应该做什么。直接换一个新对话，这些事情就容易交代不全。

我的做法是： **离开旧对话之前，先让它写一份接力文件。**

### 第一步：在旧对话里交代清楚

直接发这段话：

●●●  
我要切到其他任务了。你按照项目说明、关键决定、当前进度、下一步任务，帮我写一个接力文件。没有的写无。

这几个点分别解决什么问题？

| 内容 | 要留下什么 |
| --- | --- |
| 项目说明 | 这个项目是干什么的，文件放在哪里 |
| 关键决定 | 已经确定的方向、要求和取舍 |
| 当前进度 | 哪些做完了，哪些还没做，卡在哪里 |
| 下一步任务 | 接下来具体要做哪件事 |

### 第二步：打开文件，看一下是否写全

它生成文件后，点开 **接力文件.md** 。

![操作截图02](https://mmbiz.qpic.cn/sz_mmbiz_png/bh9XUZB5jhoiaaQsFFCoicDPZ1Ubt7DsK8qeMAicgzA0ZQdxxLqpSAicv7ZyichMUzg9ZkxDVXPmGN9X2SUgBh9dkyy1t90cicd5obKPWcOwr8rmU/640?from=appmsg)

向下翻，还可以看到当前进度和下一步任务。

![操作截图03](https://mmbiz.qpic.cn/sz_mmbiz_png/bh9XUZB5jhptAIz8zf3WrkXhIicD13qcQ2dpibRJr9sUfYTsWoTbHnQu8h34ahA9rb31uHjibgjBBWnS4zHficaoZm9EhbwdcQk6BNzXsqdzYQU/640?from=appmsg)

### 第三步：把接力文件交给新对话

在新对话里提供这份文件，或者告诉它文件的完整路径，再发：

●●●  
先读取这份接力文件，告诉我你理解的当前进度和下一步任务。确认理解后，我们继续。

## 03 新任务开新对话，并用接力文件继续

接力文件准备好了，接下来就是选对聊天的位置。

我一般会分这几种情况：

- **还在修改同一个任务**
	，例如同一份 PPT 调整标题、换配图，就继续在原对话里聊。
- **开始一件新的事情**
	，例如刚做完 PPT，又想处理 Excel，就新建对话。
- **同一件事已经聊了很久**
	，前面堆了很多讨论和修改，就先写接力文件，再开新对话继续。

### 第一步：找到新聊天入口

左侧上方有 **新聊天** ，项目里的聊天则集中在对应项目下面。

![操作截图04](https://mmbiz.qpic.cn/sz_mmbiz_png/bh9XUZB5jhpeMGDLe0BHIMq4mYBGYEe0zv4L73nASnkkYFUNz35kKlaWOaoUiaV8Ud2FFdsJ2ML8cxrPXIibu0XicT9cRedDZTx049G3iadyUow/640?from=appmsg)

如果接下来仍然处理同一个项目的文件，就在对应项目里新建聊天，开始前看一下选中的项目位置。

### 第二步：给新对话一个明确的起点

新任务可以直接说目标和资料；接着旧任务做，就先交接力文件。

比如：

> 我们继续制作教学 PPT。先读取接力文件，沿用已经确认的受众、页数和风格，从下一步任务开始。

**新建聊天只是换了一个对话，真正让工作接得上的，是你交过去的资料和说明。** 所以，写接力文件和开新对话最好搭配着用。

## 04 大任务先写任务卡

做 PPT、做网站、整理一整套资料，这些任务往往不是一句“帮我做一下”就能说清楚的。

拿 PPT 来说，同样是介绍 Codex，讲给完全没用过的新手，和讲给有开发经验的人，内容就不一样。做一场短分享，和做一套完整课程，篇幅也不一样。

这些信息不先对齐，后面就容易反复改。

我的做法是： **让 Codex 先帮我写任务卡，把要做的事情摆在一张表里。**

### 第一步：给它一个任务，让它帮你补齐问题

例如做一份介绍 Codex 的 PPT，可以这样说：

●●●  
我要做一个关于如何使用 Codex 的 PPT。你帮我写一个任务卡，分别包括目标、背景、输入、受众、输出、步骤、验收。有不明白的你问我。

最后这句“有不明白的你问我”，就是把那些你一开始没想到、但会影响成品的问题找出来。

比如它问：给谁看？讲多久？有没有现成资料？你就把实际情况补上。

### 第二步：看懂任务卡里的七项内容

| 项目 | 用大白话解释 |
| --- | --- |
| 目标 | 这件事做完，要解决什么问题 |
| 背景 | 为什么要做，现在是什么情况 |
| 输入 | 你能提供哪些文档、数据、图片或参考 |
| 受众 | 最后给谁看，对方懂多少 |
| 输出 | 需要交一份什么文件，什么形式 |
| 步骤 | 准备按什么顺序完成 |
| 验收 | 做到什么程度，才算完成 |

这是codex回复的任务卡。你看，一份任务卡会把“做个 PPT”拆得很清楚。目标、资料和交付形式摆在一起，你就能判断它有没有理解你的意思。

![操作截图05](https://mmbiz.qpic.cn/sz_mmbiz_png/bh9XUZB5jhoM5iaB6lNriaDQRUdMQM6eGIWibGZtdiaekWa21Oicd1xicXDLIzFdzLBebB19KsPLL3VZuR6xAkNbbXCKOYK9e8kKMUEjvA6FWJUWs/640?from=appmsg)

### 第三步：先改任务卡，再开始制作

如果受众写错了、输出不完整、步骤不符合你的安排，直接改这里。

比如：

> 受众改成完全没用过 Codex 的非技术人员，先用容易理解的话解释。输出需要可编辑的 PPT，操作部分要有真实截图。先更新任务卡给我看。

等任务卡对齐，再说：

> 任务卡确认，按这个开始做。

==任务卡适合在开始前对齐要求，接力文件适合在中途留下进度。== 两份文件各有用处，用起来以后，你会少重复很多话。

## 05 初始化 Git，进行项目版本管理

接下来这个技巧，相当于给项目准备一个“存档”的办法。

你可能有过这种经历：原来已经改得差不多了，想再优化一点，结果越改越不对；这时候又记不清之前的内容到底是什么。

**Git 就是用来记录文件版本的工具。** 我在创建项目时，会先让 Codex 检查并初始化 Git 仓库。

### 第一步：检查项目有没有 Git

在当前项目里发：

●●●  
检查当前项目有没有 Git 仓库。如果没有，请初始化；如果已经有，就告诉我当前状态。先不要提交文件。

这是codex的回复

![操作截图06](https://mmbiz.qpic.cn/sz_mmbiz_png/bh9XUZB5jhoxnGa0Ro8ibCsQ3qTBuHnywUFSQGOYwRo3EDYq7ibQtr8OKwNqsYmMyHFfWya4J0jboMa6vRs6ic5ckzSkGUlaaumTLDWxKkanoI/640?from=appmsg)

这里有一个很关键的细节：回复里写着 **“尚无提交”** ，说明仓库虽然建立了，但还没有存下一个版本。

### 第二步：把当前确认的版本提交一次

初始化可以理解成准备好存档的位置， **提交才是真正保存一个版本** 。

所以，确认当前文件没问题以后，再跟它说：

> 请检查这次准备提交的文件，排除密钥、账号配置和临时文件，列出清单给我确认。

看过清单，再让它提交：

> 按确认的清单提交为一个版本，提交说明写“初始可用版本”。完成后告诉我提交结果。

后面每完成一个你满意的阶段，也可以让它再保存一个版本，例如“完成首页排版”“完成教学内容初稿”。这样之后找起来就清楚了。

### 第三步：改坏了，先比较再恢复

需要找回之前的内容时，可以直接描述：

> 我想找回上一个确认过的版本。先列出相关版本和文件差异，告诉我哪些文件会受影响，等我确认后再恢复。

你不需要一开始就记住很多 Git 命令。先把“初始化、提交存档、比较差异”这几个动作交代清楚，Codex 就能帮你处理。

## 06 设好全局规则和项目规则

最后一个技巧，是把你经常重复交代的话写成规则。

比如“用中文”“先讲人话”“完成后告诉我文件在哪里”，每次都输入一遍很麻烦。这些稳定的偏好，就适合放到全局规则里。

而只针对某个项目的要求，就放到项目规则里。

### 全局规则：放你长期的使用习惯

先点左下角头像，进入 **设置** 。

![操作截图07](https://mmbiz.qpic.cn/mmbiz_png/bh9XUZB5jhoN9h5ia6DHwMvz4ofN1gqibLySN5pUC0ls4KoeW0oP2icOqwOFKU2fvN9XCsVDso9Q6Hf57k2FFpKPEI5yp05ibb8wrhxUKVNDbr4/640?from=appmsg)

进入 **个性化** ，找到“自定义指令”下面的 **Codex 指令** 。

![操作截图08](https://mmbiz.qpic.cn/mmbiz_png/bh9XUZB5jhpUwHNYDk1XDia62xMjRqXcG5nBicllHhRtpsGWpOYiaK7YNRz0gPicfkXiaXKA0EHxCxgQ3icaLfUlQY2gx9tX61uia4WmpEOGgDgZR0/640?from=appmsg)

点进去，就可以编辑这台机器上的全局指令。

我这里用的是这样一段：

●●●  
默认用中文；先用容易理解的语言解释；不要自行批量删除；不确定的内容明确标注；完成后报告文件路径和检查结果。

你可以直接参考，再按自己的习惯调整。写好之后点右上角 **保存** 。

这里适合放反复使用的要求，比如回复语言、解释方式和交付时需要告诉你的内容。

### 项目规则：放当前项目的具体要求

项目规则可以直接让 Codex 帮你写入项目的 **AGENTS.md** 文件。

为了方便观察效果，我用了一个很简单的例子：

> 设置一个项目规则：每次开始回复前都说“老板”。

你看，codex每次都叫我老板，这个感觉太爽了。

![操作截图09](https://mmbiz.qpic.cn/mmbiz_png/bh9XUZB5jhqDiaS0wa62z5dwsruyEEQaKf1bdeFHmyDBqLR6JV3iaJTzU909A3yGRshViciaCcXAbK17xEHuiaX8JnXLo1tOGAYGfp8Pc2Zv4m8I/640?from=appmsg)

实际工作里，你可以把这句称呼换成更有用的要求，例如：文章采用什么口吻、文件统一放哪个目录、品牌名称怎么写、交付要用什么格式。

已有规则时，让它先读取，再补充你这次的要求：

> 先读取当前项目已有的 AGENTS.md，把这条要求补充进去，保留已有规则。完成后告诉我修改位置。

全局规则里放长期偏好，项目规则里放当前项目的约定。以后做事，就不用每次从“请用中文”开始交代了。

## 07 从下一次任务开始用起来

这六个技巧，你可以顺着一次真实任务练下来：先确认连接正常，把长期偏好设好；开始大任务时先写任务卡；文件做到满意的阶段就提交存档；聊天太长或需要换对话时，先写接力文件，再开新对话继续。
