## 摘要

Lauren Tan（前 Meta React 团队、pstack 作者）被追问一个月的约 2500 个 PR 到底怎么来的。她的路径是先让单个 Agent 能观察、验证并改进自己的工作，再把它放进多人协作环境。验证是关键：不是让 Agent 读完代码说“看起来没问题”，而是给它能观察结果的眼睛和能操作应用的工具——启动程序、像用户一样交互、必要时调试、采集运行记录和快照；真正让循环转起来的是“看得见改动带来的结果”，光有循环命令只能让任务继续跑，验证才提供改进所需的反馈。团队后来为各个应用建立并自动维护专门的验证技能，当成公共基础设施，因为这类能力必须按应用建，一条“认真验证”的通用要求替代不了。她的组织比喻是米其林厨房：一个人在家做饭什么都自己来，多几个人进厨房若不知分工只会更乱，主厨的工作是安排材料、工具、工序和出餐质量。另外，确定性的重复步骤应该固化成脚本和 CLI，减少上下文消耗。需要说明：那 2500 个 PR 多数是维护和重构，且有持续人工抽查，不等于独立完成 2500 项新功能。

答案逐渐落到同一件事上：先让一个 Agent 能观察、验证并改进自己的工作，再把这套能力放进多人协作的环境。那些 PR 中有大量维护和重构，背后也有持续的人工抽查，并不等于一个月独立完成了 2500 项新功能。

## 从盯着一个Agent，走到组织一间厨房

离开 Meta 后，Lauren 因为疲惫休息了一个月，却又开始做个人项目。起初，AI 已经在帮忙写代码，但 Lauren 仍要花很多时间微观管理一个 Agent，也很难判断自己编写的 Skills 究竟改善了多少结果。

后来加入 Cursor，参与 Agents 窗口的性能优化，问题再次出现：需要查看火焰图、堆内存快照，弄清应用为什么卡顿。Lauren 成了 Agent 与 Chrome DevTools 之间的信息中转站，工具产生了信息，仍要由人读完，再告诉 Agent 怎么做。

Lauren 更喜欢用“米其林厨房”形容工作，因为这个比喻同时保留了分工、品质和手艺。一个人在家做饭，会自己备菜、烹饪、清理；突然多几个人走进厨房，如果大家不知道工具在哪、如何分工，通常只会更混乱。主厨的工作因此不只是亲自做菜，还包括安排材料、工具、工序和出餐质量。

"最终结果仍然要由你负责，你的名字、声誉，仍然和你做的工作联系在一起。"

Agent 的数量增加以后，工程师更需要安排它们怎样工作，以及凭什么相信交付结果。

Lauren 因而不认为领域经验正在失去价值。模型越强，瓶颈越可能转向人能否清楚表达目标、判断什么是好结果。Matt 用测试驱动开发（TDD）举例：准确的术语能让模型把注意力放到测试和验证上；Lauren 则提到，应明确排除那些只是重复实现逻辑、无法提供独立证据的测试。词语本身可以浓缩很多专业判断，但前提是使用者知道自己要约束什么。

## 验证让Agent真正进入闭环

对 Lauren 而言，验证不是让 Agent 读完代码后说“看起来没问题”，而是给它一双能观察结果的眼睛、一套能操作应用的工具：启动程序、像用户一样交互，必要时调试，采集运行记录和快照。

这是加入 Cursor 后，最早帮助 Lauren 建立信任的一项技能。此前，即使写代码的方法、解释原因的方式、清理低质量代码的规则都在改善，只要最终结果仍要靠人查看，迭代就离不开人的逐次介入。

性能优化是一个很具体的例子：先给出衡量表现的标准，让 Agent 运行、测量，尝试修改，再根据结果继续改进。Lauren 把它称作“爬山式改进”——知道怎样评价一次尝试，才有可能反复朝更好的方向走。

真正支撑循环运行的，是Agent能否看见修改产生的结果，并据此决定下一步。 循环命令只是让任务继续运行，验证才提供了改进所需的反馈。

按 Lauren 的描述，团队后来为各个应用建立并自动维护专门的验证技能，逐渐把它们当作大家都使用的基础设施。这些能力需要针对具体应用建设，不能靠一条“认真验证”的通用要求代替。

## 确定的步骤，交给脚本和CLI

Matt 注意到，Lauren 甚至为验证做了专用命令行工具。它的价值在哪里？

Lauren 最初关注的是上下文：早期 Agent 在总结、压缩聊天内容后容易丢失信息，因此希望尽量少占用上下文。后来，模型运行框架处理总结的能力改善了，但专用工具还有另一项好处——把不需要反复判断的工作固定下来。

例如，调用浏览器自动化工具、通过 Chrome DevTools Protocol 获取信息，或者把一种代码模式机械地改成另一种模式，都有相当一部分可以写成脚本。每次都让 Agent 临时编写工具，就会重复经历“写脚本、发现不好用、调试”的过程，而上一次已经可用的办法可能早被丢掉。

![Lauren 解释验证工具的做法：封装 Playwright 和浏览器调试接口，让多个 Agent 复用同一套可靠工具。](https://mmbiz.qpic.cn/sz_mmbiz_jpg/UNwPtic6UWKYCib9SickZnKwt6y9p7k9Rtmb2amibNophPLbGO6G3y7ZT0B6YiciaM1h7tuZ5YIgDlTyYePpDeFRBjhvDEOxeWN51AqPSKRt5r00c/640?from=appmsg)

Lauren 解释验证工具的做法：封装 Playwright 和浏览器调试接口，让多个 Agent 复用同一套可靠工具。

把这些步骤封装起来，后来执行同一任务的 Agent 就能复用。Skills 只需要说明什么时候使用、怎样调用，以及结果该如何判断。对于代码迁移，还可以利用抽象语法树等结构化工具完成机械转换，减少逐处生成新写法的必要。

把确定的部分变成可靠工具，才能把Agent的判断能力留给真正需要判断的部分。 Lauren 也强调，这个 CLI 并不神秘，主要是把现有接口和工具连接起来；可复用和一致性，才是它的价值。

## 把常见错误，变成代码库里的约束

工具之外，代码库本身也会影响 Agent 走向哪里。Lauren 用 TypeScript 的类型收窄作类比：把“什么都有可能”的范围，逐步缩小到明确允许的选项，很多错误便不必等人最后发现。

Lauren 介绍的内部框架 Dune，类似为 Electron 应用准备的一套内部 Next.js，尚非开源项目。它结合严格的 lint 规则和固定目录约定，例如让每个功能有自己的目录，再由注册机制发现它们。Agent 新增功能时，已有一条明确的路径可以走。

这个设计来自实际遇到的问题：早期 Grok Bot 有大约八个庞大的文件，单个文件达到上万行，功能不断往里面追加。拆分目录、固定组织方式，既改善了结构，也减少了后来 Agent 继续照着旧模式扩写的机会。

反复出现的错误，值得转化为结构和自动检查，而不是每次都靠人重新提醒。 Lauren 会观察 Agent 怎样失败，再判断是否应该增加 lint 规则、调整类型约束或修改代码组织。

这项投入也解释了为什么不能只催着 Agent 交付功能：如果人始终困在逐条纠错中，就很难腾出时间改善工具，下一次任务又会重复相同的过程。把环境修好，受益的不只是某一个 Agent，也包括其他工程师和刚加入团队的人。

## 把外部反馈，接进内部开发流程

验证和环境做好以后，还有一个瓶颈：工作从哪里来？Lauren 并不是每月手动创建 2500 个聊天窗口，而是区分了“内层循环”和“外层循环”。

内层循环负责理解任务、修改代码、验证和推进交付。外层循环则接触 Slack、Linear、X、邮件等外部信息，获取用户报告、功能请求和新的限制条件。如果两者没有连接，内层 Agent 拿到的只是一份可能过时的目标快照，人仍要不断来回搬运新信息。

在 Lauren 使用的配置里，Grok Bot 的例行任务会持续关注这些信息，再把上下文送给 Cursor Projects。按访谈中的描述，Projects 里的协调 Agent 在云端有自己的计算机环境，像负责统筹的主厨，维护任务列表、分配工作、向子 Agent 传递信息，推动它们完成任务。

这里的协调不只是把任务平均分出去。如果同时出现多份性能问题报告，一条报告派一个 Agent，可能会产生重复修复，也可能看不出共同根因。把相关问题放进同一个项目，让协调者先观察它们之间的联系，反而有机会发现更上层的问题。

"我总会想：为什么Agent需要我来回答这个问题？怎样让它自己找到答案？不是靠编造、靠猜，而是靠真实数据。"

例如，收到 bug 报告后，Agent 可以先复现，再确认问题在当前主分支上是否仍然存在，区分代码缺陷、用户配置和数据差异。此前建设的验证能力，在这里成为处理外部反馈的基础。

并行工作的前提，是让Agent取得完成任务所需的信息，并有人或机制识别任务之间的关联。 Lauren 把这种管理方式与在 Netflix 学到的“提供上下文，而不是控制每个动作”联系起来。

## 高产出里，有大量整理和维护

谈到 PR 数量，Lauren 特意澄清：2500 个 PR 并不是 2500 项功能，其中相当多是“园艺式维护”——清理代码、调整结构，改善后来的人和 Agent 工作时面对的环境。

这些维护任务也并非都需要一发现就立即执行。Lauren 举了一个 React 代码巡查的例子：让 Agent 持续寻找不好的模式，先把发现追加到文档，而不是马上逐项修复。过几天再回看，可能发现很多条目其实是同一类问题。

![巡查 React 代码时，Lauren 先让 Agent 将发现追加到文档，积累几天后再识别和处理共性问题。](https://mmbiz.qpic.cn/sz_mmbiz_jpg/UNwPtic6UWKZ9dcJlvX61shSJONSH8gWIicoT99pCfmh6gibAcYBMz923iaD6JAZNTXHd1M9I9oB58yYg2GPM7gNiahfURIkicvW4oQpHI1uU5StM/640?from=appmsg)

巡查 React 代码时，Lauren 先让 Agent 将发现追加到文档，积累几天后再识别和处理共性问题。

这份缓冲清单，让人和协调 Agent 有机会看见整体，再决定怎样统一处理。如果每个发现都立刻触发一次修复，系统可能忙着执行许多小任务，却错过了修改一处规则或抽象就能解决的共性问题。

有时，先积累问题、识别模式，再组织修复，比不断增加执行中的Agent更有效。 PR 数量只是这套工作流产生的一个结果，真正有用的改善，还包括代码是否越来越容易理解和修改。

## 从逐条审批，转向严格验证后的抽查

最直接的质疑是：这么多 PR，Lauren 全部审查了吗？答案不是逐条在合并前审批，也不是从此不看代码，而是每天抽查，认真检查输出质量，再改进造成重复问题的环境。

Lauren 描述，启用完全自动运行的流程时，每个 PR 会经过一组验证 Agent：实际运行应用、进行探索性交互，寻找回归和实现中的缺陷，修复后重新验证，直到达到可以合并的状态。这里仍然需要前面那些针对应用建设的工具和检查标准。

这会消耗相当多的 token。验证 Agent 的数量和强度可以调整，Lauren 举过十个与一个验证者的不同配置，而不是要求所有项目照搬同样的并行规模。

在这套特定环境中，Lauren 已经让 Agent 夜间自行合并，第二天查看提交历史；发现问题就回退、修改，或者补上新的规则。与此同时，Lauren 还维持着十多个负责不同方向的协调 Agent，分别处理性能、用户问题或探索性项目。

"我不想把它说成只要用了pstack，就能轻松做到的事。你需要花很多时间和精力，观察代码、观察Agent在哪里失败，再认真设置约束。"

抽查的价值，在于发现系统性问题并修正整套流程，而不是用少看几次代码来替代质量保障。 一次孤立失误可能只需局部修复；多个 Agent 反复采用同一种捷径，则应回到技能、规则、类型或代码结构上找原因。

Matt 也追问了无法轻易撤销的改动，例如造成数据损失的操作，以及医疗、法律、金融等难以验证的场景。Lauren 承认，没有一个通用答案：能否放手，很大程度取决于结果能否被可靠验证，软件工程也并非每个方面都能完全验证。

Lauren 因此期待程序与证明更紧密结合，提到形式化验证，以及 Lean、TLA+ 等工具。这个方向表达了对更强验证能力的期待，却没有消除当前难以验证、难以回退的工作所需的额外判断。

## 从自己的聊天记录里，长出Skills

最后，Matt 问两套技能库应该怎样搭配。两人的理解很接近：Skill 是用语言表达出来的流程，可以阅读、修改和组合，不必把不同作者的工具当成互相排斥的整套框架。

Lauren 更建议回头查看真实聊天记录：哪些地方自己总要介入？反复纠正过什么？Agent 在什么情景下走错路？这些记录保存着实际发生过的决策和修改，比脑海里设想的一套完美流程更具体。

Recall 技能就来自这样的需要。处理 Cursor 应用中的虚拟化问题时，Lauren 发现不同聊天之间有大量相关上下文，每次开启新对话都舍不得丢掉，于是把查找、提取过去讨论的过程整理成可复用技能，减少重复解释。

随着模型能力提高，Lauren 也开始重新看待技能里的细节：有些早期逐条指定命令和实现方法的内容可以精简，让技能更集中地表达步骤、判断和工作流程。已经适合固定为工具的机械步骤，仍可由工具承担。

最值得沉淀的技能，往往来自你已经做过、纠正过、知道怎样验收的真实工作。 可以借用别人的验证、规划或执行技能，再根据自己的项目组合和调整，最终建立一套自己理解、也信得过的工具。

## 写在最后

不必把“同时运行多少个Agent”当作第一步。可以先选一个经常需要你反复检查的任务，让Agent能够运行它、观察结果，并拿出你认可的验证证据。当一次交付逐渐变得可靠，再扩大任务范围和并行数量。 过程中最有价值的记录，往往就是你仍然必须介入的地方；它们会指出下一项该补的工具、规则或判断标准。
