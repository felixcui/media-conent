## 摘要

Anthropic《Building always-on agents》的中译。核心框架先说清一个误解：**持续在线的 agent 不是一直跑着的进程**，而是**大部分时间休眠、被事件叫醒后跑一次**——这段叫一次 **run**，休眠期间**不消耗 token**。一次 run 分四步：**事件到达 → 会话启动 → 执行 Agent 循环 → 状态写回存储**，供下次沿用。能力来自**外围的五个部件**：①**事件收件箱**（所有事件源先投递，再由工作进程领取，避免并发乱套）；②**定时器**（给自己定的跟进、给你的周期任务，到点只加事件）；③**记忆**（跨 run 保留，只存别处查不到的）；④**权限**（风险最大：凭据隔离、危险动作分类器拦截、需批准的先挂起）；⑤**发件箱**（发消息／不发／反问，默认安静）。门槛下降的两个前提：**模型判断更准**（知道何时该主动找你）、**推理成本下降**（长程任务受益）。

过去几个月，我们看到持续在线的智能体（always-on agent）再次兴起。

这类智能体能够保留状态并主动行动。它们可以跨会话管理上下文，也可以在无人直接监督时执行操作。它们采用与其他智能体相同的核心循环 <sup>[2]</sup> 。持续在线的能力来自外围架构。架构中的各个组件共同决定何时唤醒智能体、哪些信息会从一次运行保留到下一次，以及工作结果如何送达用户。

这波复兴主要得益于近期的模型进步，这些进步使运行持续在线的智能体更可行。一方面，新模型判断得更准，更善于理解用户意图，也更善于判断什么时候该主动联系用户。另一方面，模型推理的成本在下降，长程任务尤其受益。例如，在一项长程编程基准测试 <sup>[3]</sup> 中，Opus 5.5 每成功解决一项任务的成本比 Opus 5 低 78%，而在典型工作负载中，成本降幅为 40%。

一些客户开始问我们，如何把这种体验集成到自己的产品中。有的公司希望现有智能体能更主动，有的则准备从头构建。

下面逐一介绍这类智能体的架构组件，再看它们如何协作。

## 一、持续在线的运行循环

「持续在线」说的是用户体验。实际执行呈间歇性。

实际上，智能体大部分时间都处于休眠状态，每隔一段时间醒来处理工作。智能体每次醒来后处理工作的这段过程称为一次运行（run）。它接收事件，完成任务，再保存这次运行的相关信息。一次运行在会话（session）内进行，会话是消息和工具调用的完整记录。运行一结束，智能体便回到休眠状态。等到下一次唤醒时，同样的过程会再次发生，整个循环可以持续下去。

## 二、五个核心组件

持续在线智能体的外围架构由五个核心组件组成，分别是事件收件箱、定时器、记忆、权限和发件箱。下面依次看每个组件。

### 2.1 事件收件箱

大多数 AI 智能体只在用户发消息时运行。持续在线的智能体还可以由 Webhook、定时任务或后台作业等多种事件触发。

让每个事件源直接调用智能体，乍看是个简单的做法，但两个事件同时到达时，可能启动彼此竞争的运行。系统一旦崩溃，事件也可能彻底丢失。

有了事件收件箱（event inbox），所有事件源都先把事件交给收件箱，再由工作进程（worker）领取。

最简单的实现有三个部分。

- 一份持久化的事件列表，通常是一张数据库表。
- 一个将事件写入列表的处理器，通常是 HTTP 端点。
- 一个从列表读取事件的工作进程，通常是后台服务。

收件箱应记录每个事件的处理状态，并可依据事件源提供的唯一标识去重。关系型数据库适合用于实现收件箱，每个事件追加为一条新记录。建议初期为每位用户分配一个收件箱，之后有更高的并行需求时可以进一步拆分。

![事件收件箱示意图。处理器是一个 HTTP 端点，它把每个事件写入收件箱，并唤醒工作进程。收件箱是一张数据库表，用于跟踪事件状态和去除重复事件。工作进程读取待处理事件，开始一次运行，等运行结束后再将这些事件标记为已完成。](https://mmbiz.qpic.cn/mmbiz_png/IUJGIjicknic1iaJ9rnnA3EdkzbT2Eqpg2aQWqO9ics4CY8bRlk2G0H942RrR1kquahAMES7SSyYJhUxA7KECXu1uicLh2FibcUr3F7Q31u6KgUIA/640?wx_fmt=png&from=appmsg)

*事件收件箱示意图。处理器是一个 HTTP 端点，它把每个事件写入收件箱，并唤醒工作进程。收件箱是一张数据库表，用于跟踪事件状态和去除重复事件。工作进程读取待处理事件，开始一次运行，等运行结束后再将这些事件标记为已完成。*

新事件到达后，处理器将它写入收件箱并唤醒工作进程。工作进程从收件箱读取当前待处理的事件，启动一次运行。如果事件需要接着上一次的工作处理，例如用户回复了此前的消息，这次运行就恢复原有会话。其他事件会开启新会话。

随后，工作进程把事件传给智能体循环，等待运行结束，并将相应事件标记为已完成。这个流程的实现细节容易变得复杂。下面是几条实践建议。

- **尽快确认收到事件。**
	有些事件源会把响应过慢视为投递失败，Webhook 服务提供方就是一例。处理器可以执行轻量检查，更深入的校验应放到运行期间，比如检查是否存在提示注入。
- **以收件箱中的记录为准。**
	工作进程被唤醒后，先从收件箱拉取最新事件。这样，即使工作进程在运行途中崩溃，新的工作进程也可以重新领取同一事件并重试。
- **每个收件箱同一时间只允许一个工作进程处理事件。**
	这样可以避免两次运行重复工作或互相覆盖状态。运行期间到达的事件可以留到下一次处理、并入当前运行，或者中断后重新运行。
- **合并待处理事件。**
	例如，用户连续发送几条消息时，工作进程可以把它们合并到同一次运行中，让智能体只回复一次。

### 2.2 定时器

定时器与事件收件箱配合，让智能体可以主动开展工作。定时器通常分为两类，一次性跟进（follow-up）和周期任务（schedule）。一次性跟进是智能体为自己设定的期限，例如到时检查是否收到回复。周期任务则按已知的节奏重复执行，例如每天发送一份简报。

定时器应有独立的持久化存储，通常是收件箱之外的另一张数据库表。收件箱只保存已经可以处理的事件。一次性跟进和周期任务可以使用相近的表结构。周期任务还需要额外记录它如何重复。

![定时器示意图。一次运行将定时器写入数据库表，定时器可以是智能体设置的一次性跟进，也可以是用户设置的周期任务。调度器找出已到期的定时器，将事件写入事件收件箱，由此启动下一次运行。](https://mmbiz.qpic.cn/mmbiz_png/IUJGIjicknic0OWlghW0TYyXricIiaHPaB4ia575C7MXibIogGcHIv3mOLztu032K4ZqOxVkpCzKflwMKD6iaC1kHSLc6fyicKTeHF06ibkhg7QxAIicU/640?wx_fmt=png&from=appmsg)

*定时器示意图。一次运行将定时器写入数据库表，定时器可以是智能体设置的一次性跟进，也可以是用户设置的周期任务。调度器找出已到期的定时器，将事件写入事件收件箱，由此启动下一次运行。*

一次运行要经过调度器和事件收件箱才能由定时器触发。调度器通常是一个后台服务，按固定间隔轮询定时器存储，触发所有已经到期的定时器。每轮轮询按以下顺序处理。

1. 扫描存储，找出已到期的定时器。
2. 按类型更新每个已到期的定时器。
1. 将一次性跟进标记为已完成。
	2. 将周期任务的到期时间更新为下一次执行的时间。
4. 将事件写入收件箱并唤醒工作进程。

调度器可以自行实现，也可以交给持久化执行引擎。

### 2.3 记忆

持续在线的智能体会经历许多彼此分开的运行。记忆让它在这些运行之间保持连续性。

与事件收件箱和定时器一样，记忆也应有独立存储。我们的产品采用文件目录来组织记忆，例如 Claude Code 的自动记忆 <sup>[4]</sup> 和 Messages API 的记忆工具 <sup>[5]</sup> 。对持续在线的智能体来说，这些目录应映射到持久化存储，通常是数据库或对象存储。这样，工作进程退出后，记忆仍然可用。

通常只需保存智能体无法重新查到的信息。已经存在于其他系统里的信息，例如工单系统中的记录，保存引用即可。持续在线的智能体应保存以下几类记忆。

- **用户指令。**
	把用户对智能体行为的要求单独写入一个文件，每次运行开始时加载。用户并非每次运行都在场，无法随时指导智能体，因此这些指令需要保留下来，供后续运行使用。
- **用户笔记。**
	保存智能体了解到的用户信息，例如用户的角色、偏好，以及用户曾向智能体作出的纠正。起步时可以用一个文件，内容增多后拆成多个小文件。拆分后，每次运行开始时只加载索引，需要细节时再把对应文件读入上下文。
- **历史消息。**
	记录已经告诉用户的内容，避免重复通知。可以把这些内容存入单独文件，每次运行开始时加载，也可以由工作进程加载智能体与用户最近的几条消息。
- **任务进度。**
	每项进行中的任务都维护一份进度文件，记录已完成的工作和剩余事项。后续运行可以读取文件，从上次中断的位置继续。和用户笔记一样，启动时只加载索引，需要细节时再读取单独文件。

#### 2.3.1 上下文窗口里有什么

开始工作前，智能体会加载系统提示词、工具定义和记忆文件。这些初始内容构成了每次运行都要承担的上下文开销，因此建议只加载必要的内容，并使用提示词缓存 <sup>[7]</sup> 降低成本。

新会话启动时，只有这些初始内容和触发本次运行的事件。恢复已有会话时，还会把这个会话先前各次运行留下的消息和工具调用重新带入上下文。

会话过长时，可以压缩早期消息 <sup>[8]</sup> ，也可以另开会话。两种做法都会丢失细节，因此需要长期保留的信息应在运行过程中及时写入记忆。

*上下文用量随时间变化的动图。系统提示词、工具和记忆在每次运行中都占据一段固定的上下文。恢复已有会话时，会载入该会话的完整记录。随着记录变长，上下文用量继续增长，直到压缩将较早的记录变成摘要。*

### 2.4 权限

权限是持续在线智能体风险最集中的地方。智能体可以使用用户授予的访问权限，并且会在无人值守时运行。对于每次工具调用，智能体都必须判断是自行执行、阻止这次调用，还是等待用户审批。

持续在线的智能体使用的权限组件与其他智能体相同。

- **凭据存储。**
	持续在线的智能体经常需要借助密码或访问令牌等敏感凭据才能完成工作。推荐做法 <sup>[9]</sup> 是在智能体运行环境之外部署一个代理。智能体发出不含凭据的请求，代理在转发前注入真实凭据。
- **自动模式。**
	持续在线的智能体应能在无须用户持续输入的情况下工作。我们已经在 Claude Code 的自动模式 <sup>[10]</sup> 中处理过一个类似的问题。它用分类器审查风险较高的操作，拦截被判定为危险的操作，让 Claude 寻找更安全的做法。最重要的决定仍需用户审核。
- **延后工具调用。**
	在 Claude Code 中，可以通过钩子延后一次工具调用 <sup>[11]</sup> ，等待用户补充输入。持续在线的智能体也可以用同样的机制，在执行某些操作前请求澄清或审批。工具调用被延后时，本次运行结束，会话保存到工具调用尚未完成的位置。系统向用户展示请求，例如通过用 MCP Apps <sup>[12]</sup> 构建的交互卡片。随后，用户的答复会作为事件进入收件箱。这条事件会启动一次新的运行，智能体带着用户刚提供的信息，恢复此前保存的会话。工具调用等待答复期间，工作进程可以继续领取其他事件，智能体仍能处理其他工作。

### 2.5 发件箱

大多数 AI 智能体会将回答实时流式传给用户，方便用户跟进 Claude 如何分析问题、调用工具和撰写回答。

持续在线的智能体大部分工作都在后台进行。用户最终收到的是工作结果和少量相关细节，整个逐步处理的过程留在后台。

![发件箱示意图。一次运行结束时，智能体可能没有消息要发，也可能调用发送工具，或者延后工具调用以向用户提问。消息进入发件箱，由分发进程送达用户。发件箱是一张数据库表。延后调用产生的请求可以经由发件箱发送，也可以直接显示在产品自己的界面上。](https://mmbiz.qpic.cn/sz_mmbiz_png/IUJGIjicknic1tpAK2UgoicFkAgNUAnHpYxDDehb6bmbD29A16icAajeLHJAcPPiaLplT74LAhXOVdlLjRTbGib1Sh4xdsz6kyGRcjRlWcAlibUPIk/640?wx_fmt=png&from=appmsg)

*发件箱示意图。一次运行结束时，智能体可能没有消息要发，也可能调用发送工具，或者延后工具调用以向用户提问。消息进入发件箱，由分发进程送达用户。发件箱是一张数据库表。延后调用产生的请求可以经由发件箱发送，也可以直接显示在产品自己的界面上。*

一次运行有三种结束方式。

- 智能体发一条消息到发件箱。
- 智能体判断没有消息需要发送。
- 智能体延后工具调用，请求用户授权或补充输入。

对大多数持续在线的智能体来说，一个可以直接向用户投递消息的发送工具就够了。需要控制发送节奏或让智能体能在遇到错误后恢复工作时，再引入独立的发件箱（outbox）。

发件箱与事件收件箱类似，有一张独立的表保存待发送的消息。分发进程通常是一个后台服务，角色类似于收件箱的工作进程。它读取待发送消息，决定要投递哪些，再发送给用户。延后工具调用产生的请求可以通过发件箱投递，也可以直接展示在界面中。

消息发多少也需要调校。发得太多会打扰用户，发得太少又可能让用户错过有必要知道的事情。我们建议为通知建立评测，找出合适的平衡。实践中，智能体可以从少发消息做起，随着它持续证明自己能提供有用的信息，再逐渐赢得用户更多的关注。

*五个核心组件协作的动图。定时器和事件收件箱启动一次运行。智能体在会话内使用记忆，并按权限执行操作。发件箱将消息送达用户，用户的答复随后作为事件回到收件箱。*

每次运行都从收件箱里的一条事件开始。它可以是用户消息、Webhook，也可以由定时器产生。工作进程领取事件后，会启动一次运行，在新的或已有的会话中唤醒智能体。智能体先读取记忆，了解当前情况，再在获准的权限范围内行动，并把新获得的信息写回记忆。运行结束后，智能体向发件箱写入一条记录，由分发进程把消息送达用户。

这些组件由此连成一个循环。当前运行可以设置定时器，让智能体稍后再次被唤醒。用户回复消息时，答复也会作为新事件回到收件箱。每次运行都很短，但这个循环可以一直持续，所以用户会觉得智能体一直在线。
