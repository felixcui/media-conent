## 摘要

作者因 Claude 账号被封转用 Gemini 和 Google Antigravity，发现后者虽一度被吐槽，但迭代很快，部分功能已经超过 Claude。文章重点对比多 Agent 协作：Claude Code 的子进程彼此看不见，靠主进程传话，既耗算力又容易互相覆盖文件；Codex 的私聊式协作难以追踪，还常忘了关助手。Antigravity 的 /swarm 模式把后台黑盒搬到界面右侧，每个 worker 有独立草稿间和分支，质检通过后统一合并；主策划发完任务卡片就休眠，不烧算力，成员在白板上直接交棒，看板实时可见。另外新上的 run-workflow 能把重复流程固化成可复用的工作流。整体更透明，也更省。

因为 Claude 被封，再加上谷歌最近的模型有点给力，我现在日常干活基本上也跟着全切到了 Gemini 和 Google Antigravity 上。

老实说，之前 Antigravity 我没怎么用过，就有限的使用来说，体感巨差。

圈里不少人也有类似感觉，老觉得跟 Codex、Claude Code 比起来，这玩意儿简直是垃圾。

但说实话，我这半个月用下来，觉得好多别扭的地方其实全卡在习惯上。

Antigravity 并没有想象中的那么差，而且最近版本迭代还非常快。

它也已经不再是完全对着 Claude 抄了，而是推出了几个我觉得比后者还牛逼的工具，这篇文章就来具体聊一聊。

我们先从两个最常用到的主力说起：拉群协作的 /swarm，和同一个窗口里自动换脑的调度器 Orchestrator。

## /swarm：看得见的公开工作群

为了加快 Agent 干活的进度，我们经常需要多个任务并行跑，这时候就得开一些子进程。现在几乎所有的 Agent 都支持子进程（subagent）的模式。

但主进程和子进程、子进程和子进程之间怎么通信，各家的差异非常大。

我拿同一款底座模型在我的 Mac mini 上跑了一组四角色测试：1 个主策划带 2 个开发加 1 个质检，账单一拉出来差距就很明显。

![▲ 图：同样带多 AI 干活，三个应用架构差在哪](https://mmbiz.qpic.cn/mmbiz_gif/8TRTn7cvcJJcib5NY49lJVYyQpcEbNAqyyq92IltHzN1lu9d6EvibD5h4zWpYog0eXtRzlgBkHuyQyzN6deek7upwX8tfVYhLD8LAiaaiclja2w/640?from=appmsg)

▲ 图：同样带多 AI 干活，三个应用架构差在哪

Claude Code 默认的分工模式里，底下几个子进程（助手）彼此看不见，大小事都得回头找主进程（主策划）传话。

我跑了一轮 4 分 46 秒、烧掉 209 万 Token 的小任务，主策划光当传话筒就吃掉 50.2% 算力，有时还自己改文件把旧版覆盖掉。

没想到我们以为最强大的 Claude Code 也这么离谱。

后来它补了直连团队模式，成员既要在群里通知队友，回头还得单开小窗再跟总管汇报一遍。

一轮压到了 4 分 10 秒左右，结果额度反倒多烧出去将近 40%。

所以，Claude 也不是完美的……

换成 Codex 点对点发消息只用 2 分 11 秒，可我去翻后台那 21 条私聊全加密成乱码，根本看不出聊顺没有。

更尴尬的是领队收工还忘关助手，干坐在原地等了 26 秒直到超时报错才退出来。

![▲ 图：Mac mini 同模型三方实测耗时与额外花费](https://mmbiz.qpic.cn/mmbiz_gif/8TRTn7cvcJKpmrmhibNjdmV0cCwmlBHFeibGIew0yR6EBkBsHiaxocer7Y9hTEO6JfY3Ny4z5nS5CXagtv3Q1s1iaGr0U175iaIyUeibwxexxHytQ/640?from=appmsg)

▲ 图：Mac mini 同模型三方实测耗时与额外花费

还有个吓人的问题，两个并行助手共用同一文件夹，1 号刚测完顺手删掉临时旧文件，0.3 秒后 2 号去读就当场报错。

Antigravity 里面用的是另外一种模式，它叫 Swarm。

在 Antigravity 里用 /swarm 拉群，可以把后台黑盒直接搬到界面右边。

每个子进程（界面里是一只只像工蜂一样的 worker）会分到一间独立草稿间，自己分支自己改，最后质检过关再统一往正式目录合，谁也覆写不着谁。

主策划这边软件写死规矩不准下场改文件抢活，在右边 Swarm Board 发完卡片它自己就休眠挂起了。

干等别人干活那会儿真的一点算力都不烧。

执行员写完自己那块，直接在白板上 @二号成员 和 @质检员 往下交棒，留言板、成员和连线图都摆在右边。

▲ 图：Antigravity 右侧 Swarm Board 实时看板

如果是在 CLI 终端里，直接敲一句 /swarm board，同样能拉出实时看板，一眼看清哪只小蜜蜂在干活、哪只在休眠待命。

▲ 图：终端命令行里的 /swarm board 实时看板

平时三五个角色需要边写边对口径，像前后端联调或者几路人分头查资料交叉核实，开 /swarm 就特别顺手。

所以目前来看，Antigravity 的 Swarm 用了一种更合理、也更接近人类团队配合的模式，来解决多进程之间的协作和通信问题，整体确实更强大高效。

## Orchestrator：单聊自动切换大小脑

现在每一家公司基本上都有多款模型，有旗舰的，有主打性价比的，还有介于两者之间的。

但这往往给使用者造成了很大的困扰，到底什么时候要用最强的？什么时候要用最佳性价比的？

对于很多不是那么懂的人来说（比如我），就会一直使用最强的，这样就非常浪费。

对于我来说呢，我以前经常是在 CLAUDE.md 或 AGENTS.md 里面写一些规则，让 Claude 提醒我什么任务应该切换到什么模型。

但这很麻烦，因为它没法做到自动。

Antigravity 第一次解决了这个用户痛点，它自己来帮你协调。

在 Antigravity 的模型选择菜单里，多了两个选项：一个是 Orchestrator (Carbon)，一个是 Orchestrator (Argon)。

![▲ 图：Antigravity 终端模型选择菜单里的两个 Orchestrator 选项](https://mmbiz.qpic.cn/sz_mmbiz_png/8TRTn7cvcJIy4GbeLlUjeRP0x5Ib3QAmg4oJOOypMVyOPex0vyrwhgEh15xZiacV1MN5hm4JU56kIxs8b40Z8rGXC7jaNRs2hCd90ibnicHgxE/640?from=appmsg)

▲ 图：Antigravity 终端模型选择菜单里的两个 Orchestrator 选项

如果你选择其中一个，那么它就会把 Carbon/Argon 作为思考策划的模型，作为大脑。而它的便宜的模型 Hydrogen 就会作为一个执行模型。

在工作的时候，它是自动的，不需要人工去做切换。这样就大大提高了整个工作的效率和性价比。

![▲ 图：Orchestrator 大小脑接力与 /boost 流程级重武器示意](https://mmbiz.qpic.cn/mmbiz_gif/8TRTn7cvcJJGWVAVtqNUVRFlaufXY1U4wTM5IhIJHj2o2VClPGibf43XNbJMibWMo5rHRaVcbTfRnMEGbQM7aXx3KqJ0IJ2rBGibNN6XLDv06M/640?from=appmsg)

▲ 图：Orchestrator 大小脑接力与 /boost 流程级重武器示意

为了测测它到底能省多少算力，我试了一个吃几何计算的网页活：做一个 85㎡ 两居室摆家具工具。

家具得能随便拖和转，撞进 90° 开门扇区就变红，过道窄于 60cm 也要报警，还得跑通 15 项自动检查。

▲ 视频：85㎡ 户型拖动防挡门实测录屏

一开始只用纯强脑从头写到尾，光对齐布局它就截了三轮图反复改。

跑完花了 24 分钟多，烧掉 37.7 万 Token。

换成 Orchestrator 来跑，前 6 分钟强脑先把墙体和碰撞规则定死。

后面自动切给便宜的快脑 Hydrogen，只用 3 分钟写完 4 份文件，15 项检查一次全过。

整单花了 568 秒、22.0 万 Token，比纯强脑快 61%，额度省出 41.6%。

## run-workflow：批量派活的 AI 流水线

前面说了，如果是想加快任务，我们可以用 Swarm 来开启多个子进程，它们可以互相通信。

但是子进程一多的话，也会出现麻烦，它们相互通讯也会耗费大量的资源。

比如要一次性处理几十份同类文件这种事情，拉 /swarm 开群互发消息太浪费额度。

Claude Code 或 Codex 干这种活很折腾，主 AI 挨个派助手很快撑爆上下文，不然得退出去写脚本跑命令行。

Antigravity 这几天新上了一个功能叫 run-workflow。

它不像 /swarm 要开群聊，没有留言板和临场讨论，是一条用 Python 脚本跑起来的流水线。

普通人平时根本不用写代码，框里说一句“用 run-workflow 帮我把这 30 个文件排查一遍”就行。

![▲ 图：自然语言触发 run-workflow 并发盘点多目录的终端实测](https://mmbiz.qpic.cn/mmbiz_png/8TRTn7cvcJKXZUd0loXfPriaAaGSpUr3ibgagicSjlTjgRvZicRsk6060V0ywQQGpxwHBOxJaicD40B8pzoGicjscrMrEAlwazib7ZLSwys5Gibq9FU/640?from=appmsg)

▲ 图：自然语言触发 run-workflow 并发盘点多目录的终端实测

主 Agent 会在后台自己写好脚本，并发拉起几十个彼此看不见的子进程去干。

打个比方，全仓库要统一改个老接口名，搜出 30 个受影响文件。

主 Agent 先拆成搜集、过滤、交叉核对三阶段，并发派便宜的 Flash 模型分头核查。

需要直接改代码时，系统会给每路自动分出隔离的临时分支互不覆盖，最后统一合并。

我实测下来，这个速度快到飞起。

![▲ 图：批量派活不拉群：run-workflow 编排流水线](https://mmbiz.qpic.cn/sz_mmbiz_gif/8TRTn7cvcJL53iaytfV5ekpxibB420QkJMetSFiahK19B9hVVEHq0Y9cGffQmg99XOsX0u8uZhHvpzSXjIOia3jGaJT4OBVbdU2lRy684B8ld04/640?from=appmsg)

▲ 图：批量派活不拉群：run-workflow 编排流水线

用起来最省心的是，每路都按定死的格式交卷，合起来正好是一份整齐的汇总表。

半路哪一路报错挂了，其余任务会立刻停掉止损。

想抽查哪一步，点开面板对应阶段的卡片就能翻记录。

## /boost 与 /grill-me：单轮加力和动手前对齐

有了自动调度和流水线，平时八成常规活已经很省心。

但碰上算错就亏几千块的硬题，比如跨文件疑难 Bug、深度评测防硬伤或核对复杂条款，默认档位还是没底。

以前在 Claude Code 要用 /plan 配 ultrathink 拉预算，Codex 得用 /model 切高推理档搭 PLANS.md。

但这么干不但步骤烦，操作完这些难题还经常忘了切回来，额度容易白烧。

Antigravity 针对这事做了单轮重武器 /boost，它不是简单调高思考档，而是把深想、规划、多视角挑刺反驳和严格验证串成一键流程。

只要在问题前加上 /boost，当前这轮核验拉满，下句话自动退回省油档。

模型经常会在没有理解清楚我们意图的情况下就开始干活，吭哧吭哧干了半天发现全错了。不仅浪费时间，而且浪费 Token。

特别是 Carbon 这样的模型，一声不吭就开始干活，一跑通常就是半小时甚至几小时，干完发现完全跑偏了，真的让人吐血。

以前在 Claude Code 或 Codex 防跑偏，得进 /plan 或手敲“先别改代码先提问”，结果甩一屏文字还得逐条打字回。

Antigravity 为此做了 /grill-me，需求前带上它，AI 会先刹住不改文件，在框里弹出带推荐项的原生选择题卡片逼你拍板。

## 最后

对于很多经常使用 Claude Code、Codex 的朋友来说，心里或多或少有些偏见，认为它们是最好的。

现在我们可以看到，Antigravity 已经进步很多，它没有完全抄袭其他产品，而且逐渐走出了自己的特色。

它真正在解决一些我们日常遇到的痛点，不仅帮我们提高效率，还能节省成本。
