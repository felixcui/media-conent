## 摘要

文章剖析了DeepSeek Harness实现99%缓存命中率的原理与价值。DeepSeek对缓存命中与未命中的输入定价相差30倍，而Agent场景需多轮累加发送系统提示、工具说明和聊天记录，重复内容极易推高成本。其缓存机制是将推理prefill阶段生成的KV状态存入硬盘，当下一个请求开头与缓存完全一致时直接加载复用，跳过绝大部分重复计算。

当缓存的命中率提高以后，实际输入的单价可以这样算。

```
实际输入单价 = 命中率 × 命中价 + 未命中比例 × 未命中价
```

我们任然按照 v4-flash 高峰价计算。

| 命中率 | 100 万输入 tokens 的实际价格 | 相当于全未命中价格的 |
| --- | --- | --- |
| 0% | 3.000 元 | 100% |
| 90% | 0.390 元 | 13% |
| 99% | **0.129 元** | **4.3%** |

从 90% 提到 99%，看起来只多了 9 个百分点，实际输入费用从 0.390 元降到 0.129 元，又少了约三分之二的成本。Agent 一天跑几万次请求时，这个差距会非常明显，而且会直接落到账单上。

上面只算输入。模型生成答案的输出 tokens 仍按输出价收费，不受输入缓存命中率影响。

## 缓存到底存了什么

我们先来看下缓存到底存了什么，首先要理解它在缓存什么，我们需要先知道 LLM 推理的两个阶段。模型收到用户需求后，第一件事是对所有输入 token 做一遍前向计算，生成每一层的 KV 状态（这个在技术上通常称之为 prefill），然后才能逐个计算出输出 token（decode）。 **长的上下文内容的成本大部分就在 prefill 的 GPU 计算上面** 。

缓存要做的事情就是把请求输入部分的 KV 状态 **存到硬盘上** ，当下一个请求的开头和它完全一致时，服务端直接加载这份 KV 状态，跳过绝大部分 prefill 计算。

可以把它当成模型读完上下文之后，留下了一份计算结果保存到硬盘上，下一次又看到完全相同的开头时，DeepSeek 可以从硬盘取回这份结果，省掉重复计算。

![](https://mmbiz.qpic.cn/mmbiz_jpg/6Uzn2S5AAyQ6rtKtF0icE5RjiaprcBicicssGo31OU03D14aZpQWTAia1ypyUnlnYxRmyntPWicjkdWSzou16h5afG2LcPXdnHs1KBYFGhqiaMYaQ8/640?wx_fmt=webp&from=appmsg)

DeepSeek 的缓存有下面的几条规则

第一，缓存默认开启，在服务器计算保存，调用接口时不用加开关来控制是否开启缓存

第二，它从请求的第一个 token 开始对比，中间有一段相同，前面有不同的内容，中间这段相同内容也使用不了旧缓存。

第三，缓存按完整的前缀单元命中，DeepSeek 会在用户输入结束、模型输出结束和长文本中的固定间隔处保存前缀，后来的请求完整匹配其中一个单元，才能复用。

第四，公共开头可能需要到下一轮才用得上，第一次发 `A+B` ，第二次发 `A+C` ，第二次无法直接复用 `A+B` 。系统这时会发现公共部分 `A` 并把它单独保存。第三次发 `A+D` ， `A` 就能命中。

![](https://mmbiz.qpic.cn/sz_mmbiz_jpg/6Uzn2S5AAyS13cKarPLtqvUibvmKSC6tGmM1Eb5DzMQ612GRQ9chqmIfmrVNdsVyAYqu5HI9c5a6iczQQ2sRhFNpBO0Iyfo79icMTwKib7nRia1c/640?wx_fmt=webp&from=appmsg)

第五，缓存会过期。官方文档写的是几小时到几天，具体时间不固定。缓存构建也要几秒钟，而且服务按尽力而为的方式运行，不承诺每次都命中。

接口响应里的这两个字段可以直接查看结果。

```
{
  "prompt_cache_hit_tokens": 15232,
  "prompt_cache_miss_tokens": 154
}
```

这两个加起来就是本次输入的 token 总数，这里有 15232 个 token 复用了旧结果，154 个 token 重新计算。

从这里来看，我们可以看到缓存其实挺简单的，只要前缀不变就可以很好的命中缓存。

## Agent 很容易把缓存弄丢

按前面的缓存规则来看，多轮 Agent 其实非常适合做前缀缓存。

比如一个 Agent 连续运行了三轮：

```
第一轮：
系统提示 + 工具列表 + 用户消息 A

第二轮：
系统提示 + 工具列表 + 用户消息 A + 模型回复 A + 用户消息 B

第三轮：
系统提示 + 工具列表 + 用户消息 A + 模型回复 A + 用户消息 B + 模型回复 B + 用户消息 C
```

可以看到，第二轮基本是在第一轮后面继续追加内容，第三轮又是在第二轮后面追加。

如果前面的内容完全不变，那么第二轮请求时， `系统提示 + 工具列表 + 第一轮消息` 都有机会直接命中缓存，到了第三轮，可以复用的上下文还会变得更多。

理论上，一个会话运行得越久，可以复用的旧内容应该越多，缓存的命中率就会一直在提高。

但实际开发 Agent 时，缓存命中率经常没有这么理想。

原因在于，Agent 每一轮请求并不一定只是往后追加。

很多框架会在调用模型之前，重新组装一次完整请求，系统提示、工具列表、运行环境、历史消息，都可能在这个过程中发生变化。

比如系统提示里放了当前时间：

```
第一轮：

You are a coding agent.
Current time: 10:31:05

第二轮：

You are a coding agent.
Current time: 10:31:18
```

看起来只改了一个时间，但对前缀缓存来说，这个变化发生的地方如果太靠前了，基本无法命中缓存

缓存匹配是从请求开头开始的。

前面是：

```
A + B + C + D + E
```

下一轮变成：

```
A + B + X + D + E
```

那么真正能够继续复用的主要是 `A + B` 。

从 `X` 开始，后面的 `D + E` 即使内容和上一轮完全一样，也不能直接接着原来的前缀缓存继续使用。

所以缓存优化里有一个很重要的点，我们需要把变化的内容放到消息的尾部

```
系统提示 + 工具 + 历史消息 + 新内容
```

这样的话历史内容基本都还能复用缓存。

但如果变成：

```
系统提示 + 动态内容 + 工具 + 历史消息 + 新内容
```

后面本来已经计算过的大量内容，也会跟着失去这次前缀命中的机会。

这也是为什么 Agent 里一些看起来很小的实现细节，会对缓存命中率产生很大的影响。

比较常见的有下面这几种

**第一种，系统提示每轮都在变化。**

最典型的就是把当前时间、当前目录、权限状态、随机 ID 之类的动态信息直接拼进系统提示词里面。

这些内容每轮都可能不同，而且系统提示又在整个请求最前面，很容易提前截断缓存。

**第二种，工具列表顺序不稳定。**

假设 Agent 有三个工具：

```
read
bash
edit
```

下一轮变成：

```
bash
edit
read
```

工具个数没有发生变化，Schema 也完全相同，但是序列化之后的 token 顺序已经变了。

如果工具说明位于大量历史消息之前，这个变化同样会让后面的缓存无法继续沿用。

**第三种，每轮重新整理历史消息。**

有些Agent会在发送请求之前重新格式化历史记录，比如调整消息顺序、重新生成 XML、JSON，或者改写之前的消息，从程序角度看，这些信息表达的意思可能没有变化,但是可能多了一个空格，字段顺序变了、文本重新序列化都会产生新的token序列，都可能产生不同的前缀导致缓存命中失败

**第四种，请求参数在后台发生变化。**

Agent因为额度限制，超时等原因自动切换模型或者服务商，某个插件在运行的时候动态修改一些运行参数或者动态注入一段系统提示词。

如果这些变化最终影响了请求头、系统提示或者是工具定义，同样会形成一条新的请求前缀。这样也没法再次命中缓存

我们想要的理想状态其实非常的简单：

前面的已经发送给模型内容尽量保持不动，新的、容易变化的内容不断往尾部追加。

这样会话越长，可以复用的前缀也越长。

## DeepSeek Harness 怎样为缓存保住请求前缀

DeepSeek Harness 是一个插件化 Agent 框架。系统提示、工具和运行环境都可以由插件提供。插件多起来之后，它是怎么保证前缀的稳定性呢。

具体缓存的数据保存在 DeepSeek 的服务端，DeepSeek Harness 不负责保存或读取这份缓存，Harness 只管自己发出去的请求，它尽量让相邻两轮请求拥有相同的开头，好让服务端已经计算保存好的缓存可以被命中。

它采用的办法其实也很简单，系统提示和工具定义这类稳定内容按固定规则组装，沙箱模式和审批策略这类会变化的内容追加到消息末尾，已经写进历史的消息尽量不去修改变动。

可以把连续两轮请求想成这样。

```
第一轮  system + tools + 历史消息 + 用户消息 A
第二轮  system + tools + 历史消息 + 用户消息 A + 模型回答 B + 用户消息 C
```

DeepSeek Harness 的具体实现可以分成五步，前三步负责把稳定内容固定下来、把变化内容放到消息体的后面。后面两步记录请求历史，并检查模型看到的内容有没有在发送前被改动，如果缓存命中率突然下降时，也能查看历史记录，找到变化来源。

### 第 1 步 先把稳定内容和可变内容分开

![](https://mmbiz.qpic.cn/mmbiz_jpg/6Uzn2S5AAySHbILocEExnLRJAOAQUngkdHEZVFhdYZ2J40bJpdIzxwsR6TmcK4LRLMQDfuh586FM5x3qejZ0cKO8mtL0QvwYib9Rf3VWchN8/640?wx_fmt=webp&from=appmsg)

DeepSeek Harness 允许插件提供系统提示词、工具和运行环境。每个插件先把自己的内容交给同一个登记处，等 Agent 调用模型时，Harness 再把它们组装起来。这样可以统一决定哪些内容放在前面，以及它们按照什么顺序出现。

系统提示词和工具说明通常在一段会话里面是保持不变的，适合放在请求开头。沙箱模式、审批策略和子 Agent 权限可能会在中途发生变化，Harness 就需要把它们当成可变内容处理。

源码里面给这几类内容用了不同的登记入口，系统提示使用 `section()` ，工具使用 `tools()` ，可变状态使用 `context()` ，模型名和工作目录等填充值的时候使用 `variable()` 。我们不必关心这几个函数名，DeepSeek Harness 在组装消息前就已经知道每份内容属于哪一类。

当前工作目录虽然也属于环境信息，但同一个会话里的工作目录一般都不会变换，所以可以把它留在系统提示词里面，判断一项内容该放在哪里，主要看它在会话运行期间会不会发生变化。

### 第 2 步 每一轮都按同样的规则排序

![](https://mmbiz.qpic.cn/mmbiz_jpg/6Uzn2S5AAyQxY7wdtqpJR8VExV2cibVyCSMeQsZT3MWFd410m9WPfianBrR4JE4ic0cyIICenWYkm5n5l4x4ibSB8DAqalg2icfsic8MJdMP7n7tE/640?wx_fmt=webp&from=appmsg)

每一轮开始时，Harness 都会重新取出当前 Agent 能看到的内容，再按同一套规则组装。系统提示按照登记时给出的编号排列，工具没有指定位置时就按名称排列。

顺序稳定很重要。两轮请求包含同样的工具，如果工具排列顺序变了，转换成 token 以后仍然是两个不同的开头，缓存只能命中到发生变化的位置，Harness 统一排序，就是为了避开这种没有必要的变化。

模型名、工作目录等需要动态注入的值也会在这一步写入到系统提示里面，参数名称错误或者本轮没有取到值，Harness 会在请求发出前报错。

### 第 3 步 可变状态追加到历史末尾

![](https://mmbiz.qpic.cn/sz_mmbiz_jpg/6Uzn2S5AAySkSqmMMTBKzElySTn67tL4QaRMZRovSdGR38pMiccFO2XKAZGGFxedpdRPaQ9uGpyatRgxbEyHH65WTs14jFJ2FsngxXlg50Sw/640?wx_fmt=webp&from=appmsg)

沙箱模式、审批策略和子 Agent 权限会影响模型当前能做什么，也可能在会话中途改变。Harness 会把这些内容整理成一份运行状态快照，源码里叫 runtime context。

每一轮开始时，Harness 会把当前快照和上一轮比较。内容相同，这一轮不用重复发送。内容变了，它就生成一条新的消息，追加到会话末尾。上一轮的运行状态、这一轮如果已经清空时，也会追加一条清空消息，告诉模型之前的状态已经失效。

默认情况下，本轮用户消息在前，新的环境快照跟在后面，然后一起写进会话日志。插件可以调整这个顺序，但普通请求都会遵守追加规则。

这一步对缓存最关键。运行状态变了，变化只追加到请求末尾。前面的 system、tools 和历史消息继续保持原样，下一轮请求便有机会复用这段长前缀。

### 第 4 步 把这次请求的固定部分记下来

![](https://mmbiz.qpic.cn/sz_mmbiz_jpg/6Uzn2S5AAyS77k1IjtuFhmVvduaXkca5SiaDmxdkMb8LibR4ibTEmXYChXO3oTkQQrbAicZGYhdrBHQibuibtenwepkvvTuIw5vGqpedxSfB1uECs/640?wx_fmt=webp&from=appmsg)

一次模型请求除了聊天内容，还要确定使用哪个模型，以及模型里面温度、最大输出长度等调用参数。Harness 会把这些参数连同系统提示和工具列表一起记进会话日志。

第一次调用会写入完整记录，后面只有内容真的变了才新增一条变化记录。

这个历史会话内容记录下来后，如果那天缓存命中率突然下降时，就可以查看日志，先看哪一轮对话中出现了新记录，再检查模型、系统提示、工具或调用参数改了什么。

### 第 5 步 每次都从同一份日志还原请求

![](https://mmbiz.qpic.cn/sz_mmbiz_jpg/6Uzn2S5AAyTnqlRjTu1sGVL2I5xjUGhicjHDchIVEuDL5sHLnuxzICwGvpVTN3uevmWozoEIEpGywxoicdAsGXjzF8bxd3Iic6DUWzSWsuAcoQ/640?wx_fmt=webp&from=appmsg)

每次调用模型时，Harness都会按照上面记录的日志顺序取回用户消息、模型回答和工具结果。系统提示、工具定义与模型参数记录在 request header 里。两部分合起来，就是这一轮的完整请求。

请求组装好以后，就会被冻结，不允许改变。后面负责发送消息的插件可以查看，但是不能临时改一句系统提示，也不能变更工具，日志里面记了什么内容，模型就只能收到什么内容。

消息发出去之前，Harness 还会核对一遍内容。它从日志取回消息和 request header，和当前这份请求逐项比较。只要对不上就报错，不让这次请求继续发送。

模型返回消息后，也会把模型的回复追加到同一份日志里。下一轮照旧从这里还原历史，再把新消息接到末尾。中间没有改动模型输入，上一轮的完整请求自然会成为下一轮的开头。

到了这一步，Harness 能做的都做完了。剩下的事情归 DeepSeek 服务端管。

## 自己做 Agent 时可以照着检查

先抓住核心 **旧内容不改，新内容后加** ，再逐项看实现。

1. 系统提示的各段内容要有固定名字和固定顺序。
2. 当前时间、随机编号和环境状态放到消息尾部。
3. 工具按名字或明确配置排序，工具参数的字段顺序也要稳定。
4. 历史消息只追加，少做每轮重排和改写。
5. 模型、服务商和参数发生变化时，留下明确记录。
6. 上下文压缩时，尽量保留前面仍可复用的内容。
